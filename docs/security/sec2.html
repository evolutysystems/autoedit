1. 総評と指摘一覧

配布物そのものから開発者の秘密が漏れる状態ではない。 sec1 で指摘した開発機パスの混入（S7）は解消しており、秘密鍵・API シークレットの類も入っていない （§6）。

問題は 2 種類に分かれる。

1. 何を盗めばよいかが分かった

Twitch トークンが平文で置かれており（S4）、解析者は保存先と形式を知ったうえで それを直接持ち出せた。Stretheus の JWT は DPAPI で守られているのに、 同じ仕組みが同じコードベースにありながら Twitch 側だけ使っていなかった。 同日の是正で DPAPI 化し、既存の平文からの移行も入れた。

2. 差し替えを止める手立てが乏しい

漏洩そのものではないが、漏洩を仕込む側の経路として本書で最も重い。 同日の是正で自動更新の検証を入れた（S1）ため、取得経路の改ざんは検知できるようになった。 残るのはインストール済みのファイルを後から差し替える経路で、 これはコード署名でしか塞げない（S2。証明書の調達が要る）。

初版（2026-11-07 午前）の訂正。 本書は当初、配布 setting.json の接続先が dev を指していることを 「リリース前の戻し忘れ」として最上位の指摘（N1・高）に挙げていた。 これは誤りで、HowToRelease.md §6 と StretheusPlan/plan.md §7.8.4 のとおり prod が未デプロイのため dev が実運用を担うという意図的な運用である。 同日の是正で接続先の決まり方だけを直し、N1 は深刻度を下げて §4 に訂正の経緯を残した。

2.5 再現手順

本点検に使った解析スクリプトはセッション限りの一時領域に置いたため残していない。 再現する場合は以下で足りる（いずれも標準ライブラリのみ）。

  1. Stretheus.exe を末尾から b'MEI\014\013\012\013\016' で検索し、 struct.unpack('!8sIIII', …) でクッキー（pkglen / toc_off / toc_len / pyvers）を読む
  2. pkg_start = cookie_pos + 88 - pkglen を起点に TOC を走査し、各エントリを切り出す （エントリ構造: !i 長さ, !IIIB 位置・圧縮後・圧縮前・圧縮フラグ, 1 バイトの種別, 残りが名前）
  3. 取り出した PYZ.pyz の先頭 PYZ\0 を確認し、 オフセット 8 の !i が指す位置から marshal.load で TOC（dict）を読む
  4. 各値 (typ, pos, length) について zlib.decompress → marshal.loads で code object を得る
  5. co_consts を再帰的に辿れば入れ子の code object・文字列定数がすべて得られる

この手順を妨げる手立ては、Python で配布する限り存在しない。 難読化は時間稼ぎにしかならないため、「クライアントに秘密を置かない」設計を守ることで対処する。 現状その設計自体は守られている（§6）ので、崩さないことが要点である。

3. 高

S1 高 sec1 から継続 自動更新が取得した実行ファイルを無検証で起動する

現況

src/utils/updater.py は sec1 の指摘当時のままである。

def download_installer(url, on_progress=None):
    dest = os.path.join(tempfile.gettempdir(), _INSTALLER_ASSET)   # 固定パス
    urllib.request.urlretrieve(url, dest, reporthook=on_progress)  # タイムアウト無し
    return dest

def launch_installer(installer_path):
    subprocess.Popen([installer_path], close_fds=True)             # 無検証で実行

ハッシュ検証・署名確認・URL の検証（スキーム / ホスト）・ダウンロードのタイムアウトのいずれも無い。 インストーラ本体（AutoEdit.iss の PrepareToInstall）は payload を SHA-256 で検証しているのに、その検証をする側の exe が無検証で降ってくるという 連鎖の切れ方も変わっていない。

v1.4.6 から v1.8.2 まで 9 回のリリースがこの経路を通って配布された。 既存利用者は全員この無検証の経路で更新している。

是正（2026-11-07・実施済み）

sec1 §2.1 の案に沿って src/utils/updater.py を書き換えた。

穴対応
a 完全性検証が無い 取得しながら SHA-256 を計算し、期待値と一致しなければ実行経路へ残さない（一時フォルダごと削除）
b 保存先が固定・予測可能 tempfile.mkdtemp(prefix="stretheus_update_") で毎回作る専用フォルダへ置く
c URL を検証しない https + _ALLOWED_HOSTS（github.com / objects.githubusercontent.com / release-assets.githubusercontent.com）に限定。 リダイレクト先も同じ関数で確かめる
d タイムアウトが無い _DOWNLOAD_TIMEOUT_SEC = 300 を設定

期待ハッシュは次の順で解決する（sec1 の案 A）。

  1. GitHub API が返すアセットの digest（sha256:<hex>）。あれば追加の通信をしない
  2. 併置した StretheusSetup.exe.sha256 アセット

どちらも得られないリリースへは更新しない（fail closed）。 検証できないものを実行しないためで、利用者には何も出さず、ログに WARNING を残す。 この運用が崩れると利用者が更新に気づけないため、HowToRelease.md §8.1 と installer/README.md §3.1 に手順とチェック項目を足した。

tests/test_updater_verify.py に 16 件を追加（URL 許可判定、ハッシュ形式の正規化、 不一致時に取得物が残らないこと、ハッシュが無いときに見送ること）。

残る限界。ハッシュも GitHub 経由で取るため、 配布元アカウントの侵害には無力である。守れるのは経路上の改ざん・取り違え・TOCTOU までで、 配布元の侵害まで塞げるのは S2 のコード署名を前提とした署名検証（sec1 の案 B）だけである。
移行: v1.8.2 以前のアプリは古い updater で動いているため、検証が効くのは 「この仕組みを載せた版から、さらに次の版へ」の更新からである。

S2 高 sec1 から継続 インストール先がユーザー書込可能で、実行ファイルが未署名

現況（実測）

Get-AuthenticodeSignature Stretheus.exe  →  Status: NotSigned   Signer: (なし)
AutoEdit.iss  →  DefaultDirName={localappdata}\Programs\Stretheus
                 PrivilegesRequired=lowest

同一ユーザー権限で動くプロセスが _internal/ の DLL や Stretheus.exe を 差し替えられる。署名が無いため、利用者にも差し替えを検知する手段が無い。

インストール先の setting.json を書き換えるだけで 接続先 API を攻撃者のサーバーへ向けられる点にも注意する （JWT はそのサーバーへ送られる）。N1 の是正で配布 setting.json の api.base_url は空になったが、利用者が後から書き足せば効いてしまうことは変わらない。

対策と現況（2026-11-07 時点）

本丸のコード署名は未実施のままである。証明書の調達が要るため、 実装だけでは解消できない。今回入れたのは「証明書が手に入った日に、手順どおり実行すれば 署名できる」状態までである。

#対策状況
1Authenticode コード署名 未実施（証明書が無い）。土台のみ整備: AutoEdit.iss に #ifdef SIGN で SignTool / SignedUninstaller を追加し、ISCC /DSIGN で有効になるようにした。 証明書が無い間は従来どおりビルドできる。手順は HowToRelease.md §7.2 に具体化
2管理者インストールを選べるようにする 未実施。PrivilegesRequired=dialog にするだけでは setting.json の書き込み先が書けなくなるため、対策 3 とセットでなければ壊れる
3設定・トークン・ログをインストール先から出す 部分的。作業フォルダ・Twitch トークン・ポイントは %LOCALAPPDATA%\Stretheus\ へ移っている。残るのは setting.json 本体とログ（S8）

S1 のハッシュ検証が入ったことで、未署名のままでも更新経路の改ざんは検知できる ようになった。ただし「インストール済みのファイルを後から差し替える」経路は署名でしか塞げない。

初版の指摘の訂正

本書は当初、配布 setting.json が dev を指すことを「リリース前の戻し忘れ」とみなし、 最上位の指摘（高）に挙げていた。これは誤りである。

  • HowToRelease.md §6: 「本番 API をデプロイするまでは dev のままで配る（prod は未デプロイ）」
  • StretheusPlan/plan.md §7.8.4: 「④ 配布クライアントの接続先（prod を立てる場合のみ）」 「dev は live キーで動いている」

dev を指しているのは意図的な運用であり、stretheusapi-dev が 実運用を担っている。また接続先のホスト名は通信を観察すれば分かるため、 配布物から読めること自体を情報漏洩の指摘とするのは筋が悪い。 この 2 点で初版の判断は成り立たない。

残っていた実質的な問題

それでも次の 2 点は実際の事故リスクだった。

#問題
a接続先が 3 か所で決まる。 setting.json（新規インストール）/ DEFAULT_SETTINGS（設定が欠けたとき）/ _normalize_legacy_values（既存の利用者）。1 か所だけ直しても向き先が変わらず、 plan.md §7.8.4 自身が「最も見落としやすい」と書いていた
bsetting.json は git 管理下かつ開発端末で日常的に書き換わる。 そのときの接続先がリポジトリと配布物の両方へ焼き付く（sec1 S7 と同じ構図）

是正（2026-11-07・実施済み）

接続先を services/config.py の _DEFAULT_BASE_URL 1 箇所へ集約した。

箇所変更
services/config.py _DEFAULT_BASE_URL を現運用（dev）に。優先順位を 環境変数 > setting.json > 既定 とし、環境変数 STRETHEUS_API_BASE_URL を追加。凍結配布では環境変数を無視する （配布物の向き先を外から変えさせない / S2 の緩和）
settings/settings_window.py DEFAULT_SETTINGS の api.base_url を空に。 _MANAGED_API_BASE_URLS を追加し、既定として配ったことのある URL が 保存されていたら空へ寄せて既定に追従させる
settings/setting.json api.base_url を空に（リポジトリから接続先が消えた）
main_window.spec 同梱時に api.base_url を必ず空へ落とす （general の 4 キーと同じ安全柵）
tests/test_api_base_url.py 15 件を追加。「どの環境が現運用か」は固定せず、 _DEFAULT_BASE_URL へ倒れることだけを見る

これにより 接続先の切り替えは 2 か所で済む（_DEFAULT_BASE_URL を変え、 _MANAGED_API_BASE_URLS へ切り替え前の URL を足す）。開発端末で別環境を試すときは 環境変数を使うため、setting.json を汚さない。

plan.md §7.8.4 の「3 か所セット」手順は autoedit 側のこの変更に 追従していない。別リポジトリのため本書では直していない。更新が要る。

残る論点（本書の範囲外）

dev という名前の環境が、live 決済を含む実運用を担っている （plan.md §7.8.7）。技術的な欠陥ではないが、命名と環境の役割が食い違っている状態は 事故のもとになる。prod を立てるのか、dev を正式な環境として扱い直すのかは、運用側で決める話である。

同じコードベースに DPAPI の実装が既にある。 src/services/auth_store.py の protect() / unprotect() を src/services/device_id.py は使っており、Stretheus の JWT（auth.dat）も 同様に守られている（§6 で実測）。Twitch 側だけが取り残されている。

何が問題か

配布物を解析すれば保存先も形式も分かる（§2.2 で archive_work / twitch_token.json の文字列がそのまま得られる）。利用者の端末で動く任意のプロセスが、 このファイルを読むだけで Twitch のユーザーアクセストークンを持ち出せる。 scope に user:read:broadcast が付くため、 配信者のアカウントに対する読み取りが成立する。

是正（2026-11-07・実施済み）

sec1 §3.2 の案どおり、src/services/auth_store.py の protect / unprotect（DPAPI / CurrentUser）を twitch_auth.py から借りる形にした。同じ仕組みを 2 つ持たないため、 新しい依存も新しい鍵管理も増えていない。

何が問題か

是正（2026-11-07・実施済み）

5. 低・情報

N3 低 新規 端末 ID の導出が決定論的で、ソルトが配布物から読める

# src/services/device_id.py （PYZ から復元した文字列定数にそのまま出る）
_DERIVATION_SALT = "stretheus-device-v1"
digest = hashlib.sha256(f"{_DERIVATION_SALT}:{seed}".encode("utf-8")).digest()

seed は Windows の MachineGuid。ソルトが配布物から読めるため、 ある端末の MachineGuid を知る立場なら、その端末の匿名セッション ID を計算できる。

個人を直接特定する値ではなく（MachineGuid 自体は外部へ出さずハッシュだけを送る設計で、 プライバシー配慮としては妥当）、悪用には MachineGuid の入手が別途要る。 影響は「匿名セッションのなりすまし（未ログイン利用者のポイント消費）」に限られるため 低とする。

対策を入れるならサーバー側で、匿名セッションの発行時に サーバーが生成した乱数を混ぜてクライアントへ返し、以後はそれを使う （クライアントだけでは ID を決められないようにする）。クライアント側の難読化では解決しない。

N4 情報 内部 API のエンドポイント一覧が配布物から完全に読める

PYZ の復元で、以下がそのまま一覧できる。

/api/auth/twitch/authorize-params   /api/auth/google/authorize-params
/api/auth/twitch/login              /api/auth/google/login
/api/auth/device   /api/auth/refresh   /api/auth/logout
/api/billing/config  /api/billing/checkout-session  /api/billing/portal-session
/api/billing/subscription            /api/points
/api/analytics/{sessions,projects,events,export-logs,processing-logs}   /api/errors

これ自体は設計上避けられない（クライアントが叩く以上、通信を見れば同じことが分かる）。 記録として残す趣旨であり、クライアント側の対応は不要である。

ただし前提として、サーバー側がクライアントを信用していないことが要る。 本書ではサーバー側を点検していないため、StretheusAPI 側で 「全エンドポイントが JWT の検証と所有者チェックを持つか」「/api/points が クライアントの申告額をそのまま信じていないか」を別途確認すること（§8）。
