1. 総評と指摘一覧

sec2 の是正はすべて配布物に効いている（§2）。 配布サイズは 1.5GB → 837MB、exe 内のモジュール数は 8,259 → 1,802 まで落ち、 解析して得られる情報も減った。 開発機の痕跡・秘密情報が配布物に無いという状態も保たれている。

そのうえで、本書では新たに 6 件を挙げる。性質が 2 つに分かれる。

1. アプリを消しても情報が残る

アンインストールは archive_work しか消さないため、 Stretheus の JWT（auth.dat）と編集したファイルのパス一覧 （project_ids.json）が端末に残り続ける（T1）。 本書で最も実害に近い。

2. 防御の「効く範囲」が狭い

S4・N2 で入れた DPAPI は、同じ Windows ユーザーで動くプロセスなら 鍵を知らなくても復号できる（実際に復号して確かめた / T2）。 S1 の検証も、検証から起動までの隙間は塞げていない（T5）。 どちらも「平文よりはるかにまし」だが、万能ではない。

3. 新規の指摘

T1 中 新規 アンインストールで JWT と利用者データが残る

該当

; installer/AutoEdit.iss の [UninstallDelete]
Type: filesandordirs; Name: "{app}"
Type: filesandordirs; Name: "{localappdata}\{#MyAppName}\archive_work"
Type: dirifempty;     Name: "{localappdata}\{#MyAppName}"

消えるのは {app} と archive_work だけである。 %LOCALAPPDATA%\Stretheus\ の直下に残るものを実測した。

残るファイル中身消えるべきか
auth.dat（984 bytes） Stretheus の JWT（access_token / セッション期限 / ユーザー情報） 消すべき
points.json（344 bytes）サブスク判定のキャッシュ消すべき
pending_commits.jsonポイントの送信待ちキュー消すべき
project_ids.json（3,613 bytes） 編集したファイルの絶対パスと projectId の対応表消すべき
device.dat（環境により）端末 ID の控え消すべき

dirifempty は「空なら消す」ため、これらが残る限り %LOCALAPPDATA%\Stretheus ごと残る。

何が問題か

  • アンインストールしたのに認証情報が端末に残る。JWT はセッション期限まで有効で、 auth.dat を持ち出せば（T2 のとおり同一ユーザーなら復号できる） そのアカウントとして API を叩ける
  • project_ids.json は「何を編集したか」の履歴である。 中身は絶対パスで、先頭を見ると {"d:\\develop\\… のように 利用者のファイル構成がそのまま入る
  • 中古 PC の譲渡・共用 PC・退職時の端末返却で、利用者は「消したつもり」になっている

sec1 は「アンインストールでトークン・設定ごと {app} を削除する」を 守れている点に挙げていた。これはデータが {app} にあった頃の話で、 docs/error/fromUser/resolve.md §6-6-6 で %LOCALAPPDATA% へ移したときに この前提が崩れた。archive_work だけは追従させたが、認証情報は取り残されている。

対策

[UninstallDelete] へ明示する。archive_work を足したときと同じ形で済む。

; 認証情報と利用者データもインストール先の外にあるため明示削除する (sec3 T1)。
Type: files;          Name: "{localappdata}\{#MyAppName}\auth.dat"
Type: files;          Name: "{localappdata}\{#MyAppName}\device.dat"
Type: files;          Name: "{localappdata}\{#MyAppName}\points.json"
Type: files;          Name: "{localappdata}\{#MyAppName}\pending_commits.json"
Type: files;          Name: "{localappdata}\{#MyAppName}\project_ids.json"
Type: filesandordirs; Name: "{localappdata}\{#MyAppName}\project_thumbs"
Type: dirifempty;     Name: "{localappdata}\{#MyAppName}"

サーバー側のログアウトまでは行わない点に注意する。 ローカルの JWT を消すだけで、サーバーのセッションは期限まで残る。 そこまで求めるなら POST /api/auth/logout を叩く必要があるが、 オフラインのときに失敗するため「消せるものはローカルで消す」で十分と考える。

T2 中 新規 DPAPI にエントロピーを与えていない（S4・N2 の限界）

該当

# src/services/auth_store.py
ok = ctypes.windll.crypt32.CryptProtectData(
    ctypes.byref(source), _DESCRIPTION, None, None, None,
    #                                   ^^^^ pOptionalEntropy = None
    _CRYPTPROTECT_UI_FORBIDDEN, ctypes.byref(result))

実証

アプリのコードを一切使わず、素の ctypes で CryptUnprotectData を 呼ぶだけの「第三者のツール」を書いて試した（対象は本点検で作ったダミーのみ）。

アプリと同じ方法で保護して保存した: 344 bytes
  平文が残っていないか: True
エントロピー無しで復号を試みた結果:
  **復号できた** -> {"access_token": "DUMMY-NOT-A-REAL-TOKEN", "scope": "user:read:broadcast"}

何が問題か

CRYPTPROTECT_LOCAL_MACHINE を使っていない（＝ CurrentUser スコープ）ので 他ユーザー・他端末では読めない。ここは正しい。 しかし pOptionalEntropy が無いため、同じ Windows ユーザーで動くプロセスなら、 アプリの鍵も知識も持たずに復号できる。

是正前是正後
ファイルを開いて読むトークンが読める暗号文で読めない
DPAPI を呼ぶツールで読む（不要）読める
別ユーザー・別端末へコピー読める読めない

ブラウザの Cookie 窃取ツールが DPAPI blob を無差別に復号して回るのと同じ手口が通る。 「平文よりはるかにまし」だが、同一ユーザーのマルウェアは防げない。

対策

# アプリ固有のエントロピー (sec3 T2)。
# DPAPI blob を無差別に復号して回る汎用のツールは、このバイト列を知らないため通らない。
# **このアプリを狙った攻撃には効かない** (配布物から読めるため / sec2 §2)。
# 用途ごとに変えると、auth.dat の暗号文を points.json へ置いても復号できなくなる。
_ENTROPY_AUTH = b"Stretheus/auth/v1"

既存ファイルの移行が要る。エントロピーを変えると今の暗号文は 復号できなくなるため、「エントロピー付きで試す → 失敗したら無しで試す → 読めたら付きで書き直す」 の順にすること。S4 で平文から移行したときと同じ形である。
効果は限定的で、T1（そもそも消えない）のほうが先に手を付ける価値がある。

何が問題か

  • 使わないデコーダ・プロトコル・プラグイン読み込み経路の分だけ攻撃面が広い。 FFmpeg の脆弱性は「細工した入力ファイルを解析させる」形で成立するものが多く、 本アプリは利用者が持ち込んだ動画や Twitch から取得した VOD を解析するため、 入力が常に信頼できるとは限らない
  • ビルドが 2026-03-12 で、本書の時点から約 8 か月前。その間の修正が入っていない （本書では CVE の照合をしていない。版が古い事実のみを挙げる）
  • 容量面でも、essentials_build に替えれば 426MB の大半を削減できる見込みがある

2essentials_build への差し替えを検討する libass を含むことの確認が要る（字幕焼き込みに必須）。差し替え後は 無音カット・字幕焼き込み・結合・縦動画・ぼかしの実走行で確認する

T4 低 新規 音声認識モデルを実行時に外部から取得する

# src/modules/subtitle_generator.py:594,599
whisper_model_cls(model_name, device=device, compute_type=compute_type)

download_root も local_files_only も指定していないため、 faster-whisper はモデル名（配布既定は large-v3）を HuggingFace Hub から取得し、 %USERPROFILE%\.cache\huggingface\hub へ置く。 配布物に入っているのは VAD の silero_vad_v6.onnx だけで、認識モデル本体は入っていない （転送用の hf_xet 8MB が同梱されているのはこのため）。

  • 配布物に無いデータを、初回利用時に外部から取り込む経路がある。 完全性は huggingface_hub の検証任せで、アプリ側では確かめていない （S1 でインストーラのハッシュを検証するようにしたのと対照的である）
  • 取得先・取得量を利用者へ事前に説明していない（数 GB になる）
  • オフライン環境では音声認識が使えない

モデルは実行コードではなく ctranslate2 のデータであるため、差し替えられても コード実行に直結するわけではない。深刻度は低とする。

対策

  1. HowToRelease.md と README に「初回に HuggingFace からモデルを取得する （モデル名と概算サイズ）」を明記する
  2. 取得先を固定したいなら、モデルを配布物へ同梱して local_files_only=True で読む （large-v3 は数 GB のため配布サイズとの引き換えになる）

T5 低 新規 更新の検証後から起動までの差し替え余地（S1 の残存）

S1 の是正で、インストーラは専用の一時フォルダへ置き、SHA-256 が一致しなければ 実行経路へ残さないようにした。ただし検証を終えてから launch_installer が起動するまでの間は、 同一ユーザー権限のプロセスがファイルを差し替えられる。

path = updater.download_installer(url, sha256)   # ここで検証が通る
...                                              # ← この隙間
updater.launch_installer(path)                   # ここで起動する

是正前（%TEMP%\StretheusSetup.exe 固定）より狙いにくくなった（毎回名前が変わる）が、 %TEMP% を列挙すれば見つかるため、原理的には残っている。 実際には「更新ダイアログで利用者が OK を押してから数秒」という短い窓である。

対策

# 起動の直前にもう一度確かめる (sec3 T5)。
def launch_installer(installer_path, expected_sha256):
    if _file_sha256(installer_path) != _clean_sha256(expected_sha256):
        raise ValueError("更新プログラムが置き換わっています。更新を中止しました。")
    subprocess.Popen([installer_path], close_fds=True)

根本的には S2 のコード署名が入れば、OS 側が起動時に検証してくれる。

5更新の取得物を検証する（S1 の是正） URL 許可・SHA-256・専用一時フォルダ・タイムアウト
6検証できない更新は見送る（fail closed） 期待ハッシュを得られないリリースへは更新しない
7使っていないコードを配らない（S6 の是正） torch / transformers ほかを除外し 663MB 削減
8テレメトリ送信前にパス・ユーザー名・メール・トークン風文字列をマスク log_payloads._MASK_RULES
9ログにトークンを出さない実ログの検索で 0 件
10ビルド時の機械的な安全柵（開発機パス・client_secret・接続先） main_window.spec がビルドを止める／空へ落とす

7. 対応の順序（提案）

段対象内容目安

段 1 の 2 件はどちらも小さく、次のリリースに入れられる。 特に T1 は .iss へ数行足すだけで、「アンインストールしたのに認証情報が残る」という 利用者にとって分かりやすい問題が消える。

8. 本書の限界

  • サーバー側（StretheusAPI）を点検していない。 本書は「クライアントから何が見えるか」までである
  • 動的解析・侵入テスト・マルウェアスキャンは行っていない。 静的な読み取りと、ローカル保存データ・配布 exe の起動の実測のみである
  • 依存パッケージの CVE 照合をしていない。 T3 は同梱 FFmpeg の版が古い事実を挙げたもので、 特定の脆弱性の有無を示すものではない
  • zip 化・インストーラ生成・クリーン PC での挙動確認をしていない。 対象は src/dist/Stretheus/ である
  • T1 のアンインストール挙動は .iss の記述から判断した。 実際にインストール → アンインストールして残存を確かめたわけではない
  • 本書は 2026-11-07 時点のスナップショットである。 件数・サイズ・パスをそのまま後の版へ引用してはならない
  • 各対策のコード片は方針を示すためのもので、そのままの動作確認はしていない
