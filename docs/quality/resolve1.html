0. 結論

切り抜き経路の品質は「どの区間を選ぶか (採点)」で決まり、その採点が 音量だけで盛り上がりを判定しているため、要望の 3 点はいずれもここに帰着します。

#要望切り抜き経路での答え根本原因
1 発話を認識し、配信者が喋っているタイミングで切れているか できていない 採点の「感情点」は正規化した mean_db の平均 + 大声セル加点 − 無音セル減点のみ。声か否かを区別しない (A1)
2 ゲームや他の音声を含めていないか 区別していない。むしろゲーム音が高得点を取る 45 秒セルの max_db は単発の効果音で決まり、silence_ratio はゲーム音で常に 0 になるため減点が効かない (A2)
3 文字起こしの精度向上に必要なものは何か (a) 固有名詞辞書 (b) 信頼度の可視化 (c) 置換辞書 faster-whisper の精度系パラメータを既定のまま使っている (§3.2)
4 テロップの区切りがおかしい (結合・分割の手作業) 設定 1 つの二重用途で区切りが崩れている 切り抜きも recognize_for_timeline を共有するため、subtitle.min_line_length=5 がテロップ下限まで下げている (C1)
5 YouTube に合わせた最適な音量調節ができているか クリップ単位では合うが、出来上がった 1 本では合っていない 正規化がクリップごと個別。イントロカード・OP/ED は未正規化で、結合後は一度も測っていない (§4.2)

第2部 — 切り抜き区間の選定と自動カット

切り抜きにおける「自動カット」は 2 段階ある。① どの 3 分を切り抜くか (採点) と ② その中の無音をどう詰めるか (無音カット)。 要望①②は①に対する問いであり、②は本流と同じ仕組みを使っている。

2.1 ① 区間選定 (採点) の現状

scoring.score_window() が 1 窓 (180 秒 = 4 セル) を採点する式は以下だけです。

base    = (窓内セルの正規化 mean_db の平均) * 100.0              # 0..100
loud    = loud_points * (max_db >= 80 パーセンタイル のセル数)    # +10/セル
silent  = long_silence_points * (silence_ratio >= 0.6 のセル数)   # -8/セル
emotion = clamp(base + loud + silent, 0, 100)

comment = clamp(ｗ総数 * 1 + 急増ボーナス 10, 0, 100)

total   = emotion * 0.55 + comment * 0.45
つまり 感情点 = 音量そのものです。コードのコメントにも 「R1 は大声/無音のみ検出可能」と明記されています (scoring.py)。

2.2 問題点 (区間選定)

A1「声」を判定していない — 要望①の答え: できていない

mean_db / max_db は volume_analyzer.measure_region_volume() (= FFmpeg volumedetect) の出力で、音の大きさしか表しません。 配信者の声・ゲーム BGM・効果音・配信 BGM がすべて同じ 1 本のミックスに混ざったまま、 区別なく点になります。

状況現状の採点望ましい採点
配信者が静かに喋る + ゲームが静か低得点 (選ばれない)内容次第で選ぶ
配信者が黙っている + ゲームの戦闘 BGM が大きい高得点 (選ばれる)選ばない
配信者が叫ぶ + ゲーム音も大きい高得点 (正しいが偶然)選ぶ
現状の切り抜きは「音が大きい 3 分」を選んでおり、要望の 「配信者が盛り上がっている 3 分」を選んでいません。
訂正 (§12.3-1): この項目を当初「声かゲーム音かを区別していない」問題として 書きましたが、実際にはもう 1 つ別の区分がありました。 ゲーム内のボイスは音響的には人の声そのものなので、 F1 (VAD) を入れても「配信者の声」と「ゲーム内の声」は分かれません。 採点の歪み (A1) と、テロップがゲーム内ボイスを拾う問題 (A9) は 別の問題として扱います。

A2ゲーム音が「大声加点」と「無音減点」の両方を無効化する

(a) 大声加点 (loud) が常に入る

loud_threshold() は全セルの max_db の 80 パーセンタイルを しきい値にします。max_db は 45 秒セル内のピーク 1 点なので、 効果音・銃声・爆発音・通知音が 1 回鳴れば満たされます。 ゲーム実況ではほぼ全セルが「大声セル」になり、加点が区間の差を付けません。

(b) 無音減点 (long_silence) が一度も入らない

silence_ratio は volume_analysis.base_noise_db = -30 dB 固定の silencedetect 結果からの按分です。ゲーム音が鳴っていれば -30 dB を 下回らないため silence_ratio はほぼ 0、 >= 0.6 の条件は成立しません。 つまり「配信者が黙っている 45 秒」はゲーム音があるだけで減点されません。

結果、emotion は実質 base (= 音量平均) 1 本になります。

A3感情点の設定が死んでいる

setting.json には以下があります。

"emotion_points": {
  "big_laugh": 15, "loud": 10, "surprise": 8,
  "cry": 15, "anger": 12, "long_silence": -8
}

ところが scoring.score_window() が読むのは loud と long_silence の 2 つだけです。 

loud_points          = float(points.get("loud", 10))
long_silence_points  = float(points.get("long_silence", -8))
# big_laugh / surprise / cry / anger はどこからも参照されない
笑い・驚き・泣き・怒りは一切検出されていません。 設定画面や setting.json でこれらを変えても出力は 1 ビットも変わりません。 「設定があるのに効かない」状態は、利用者が調整を試みるほど混乱するため、 検出を実装するか、少なくとも未実装であることをコメント・UI で明示すべきです。

A4コメントの笑いエモートと「草」が未カウント

comment_source は Twitch のエモート ID を正規化して emotes に持っています。

return {"offset_sec": ..., "user": ..., "text": ..., "emotes": emotes}

しかし aggregate_into_cells() が集計するのは comment_count と count_w_chars(text) の 2 つだけで、emotes はどこでも使われません。 

cells[idx]["comment_count"] += 1
cells[idx]["w_count"]       += count_w_chars(c["text"], runs_only)
# emotes は捨てられる

count_w_chars() 自体はよくできており (全角ｗを常に笑い扱い / world のような英単語を除外)、ここは評価できます。足りないのは:

  • 笑いエモート (LUL / KEKW / Pog など) — emotes にあるのに未使用
  • 「草」「笑」「くさ」 — 日本語配信の笑い表現の主力なのに未カウント
  • 連続投稿の勢い — comment_count は急増ボーナス (一律 +10) にしか使われない

A5ローカル入力ではスコアが音量 100% になり、満点が 55 になる

チャットを取得できない入力 (ローカル mp4 / 取得失敗) では comments が空なので comment = 0 に固定されます。 

total = emotion * 0.55 + comment * 0.45   # comment=0 → total = emotion * 0.55
  • 順位付けは音量のみになる (A1 の問題がそのまま出る)
  • 表示スコアの上限が 55 点になる。v1.6.0 で出せるようにした採点グラフも 同じ値域になるため、「満点でも 55」という読み取りにくい目盛りになっている

A6cut_region が -c copy で、採点した区間とずれる

cmd = [ffmpeg, "-y", "-ss", f"{start:.3f}", "-i", input_path,
       "-t", f"{duration:.3f}", "-c", "copy",
       "-avoid_negative_ts", "make_zero", dest]

-c copy はキーフレームより細かく切れません。 -ss を -i の前に置いているため実際の開始は 要求時刻の直前のキーフレームになり、-t もそこから数えられます。 配信 VOD のキーフレーム間隔は概ね 2 秒なので、 切り抜きの頭と尻が最大 2 秒前へずれます。

ストリームマーカー由来の区間 (前後 120 秒) では相対的に無害ですが、 archive.section_add.min_length_sec = 1.0 で 1 秒のセクションを足せる仕様では 区間長と同じオーダーのずれになります。

なお -c copy は「同じ引数なら出力が決定的になる」ことを狙った意図的な選択で (プロジェクト再開時の素材復旧で同じ関数を使うため / ver3 resolve9 §3-1)、 単純に再エンコードへ変えると再開時の互換を壊します。F5 で両立案を示します。

A7特徴抽出がセルごとに FFmpeg プロセスを起こす

for i in range(n_cells):
    result = volume_analyzer.measure_region_volume(input_path, start, end, ffmpeg_cfg)

2.4 補足 — 音声感情認識は発話区間のみで実行できるか (質問への回答)

質問

2.3 F3 の音声感情認識 (案 B) は、発話区間のみ実行できるか？

2.4.1 結論

できます。むしろ発話区間のみに限定するのが実装の前提条件です。
ただしそれだけではゲーム音の混入は解決しません (§2.4.3)。

2.4.2 発話区間のみに限定すべき 3 つの理由

(1) SER モデルの入力粒度がそもそも発話単位

音声感情認識のモデルは 1〜4 秒程度の発話単位で学習されています。 45 秒のセルを丸ごと入力するのは設計上の誤りで、

  • 1 つのセルに複数の感情が混ざり、出力が平均化されて意味を失う
  • セルの大半が無音・ゲーム音のみなら、そちらに引きずられる

F1 (Silero VAD) が返す発話区間は、 ちょうどモデルが期待する入力粒度になります。 つまり F1 を入れることが案 B の前提であり、F1 を入れたなら発話区間は既に手元にあります。

(2) 計算量が実用域に落ちる

2 時間 VOD の全長 7200 秒を推論するのは非現実的です。 発話区間のみ + セルごとの代表サンプルに絞れば、推論量は桁で落ちます。

方式推論対象の音声長 (2 時間 VOD)
全長を推論7,200 秒
発話区間のみ (発話率 50% と仮定)約 3,600 秒
発話区間のみ + セルごとに最長 3 本 × 各 4 秒 約 1,920 秒 (160 セル × 12 秒)

採点はセル単位の代表値しか要らないため、セル内の全発話を推論する必要はありません。 「そのセルで最も長い発話 N 本」を採れば、セルの性格は十分に表せます。

  • 新設定 archive.scoring.emotion.max_samples_per_cell (既定 3)
  • 新設定 archive.scoring.emotion.sample_max_sec (既定 4.0)
  • 新設定 archive.scoring.emotion.min_sample_sec (既定 1.0) — これ未満の発話は推論しない (SER モデルが短すぎる入力で不安定になるのを避ける)

(3) 無音への誤検出が構造的に消える

無音・ゲーム音のみの区間に感情ラベルが付くことがなくなります。 これは A2 (ゲーム音が大声加点を常に入れてしまう) と同じ構造の問題を、 最初から作らないという意味を持ちます。

2.4.3 ただし — 発話区間に限定しても解決しない問題

VAD は「いつ声があるか」しか教えません。「声だけが鳴っているか」は教えません。

発話区間として切り出した音声も、ゲーム音・BGM・効果音と混ざったままです。 SER は背景音・特に音楽に非常に弱く、混入した音声では学習時の分布から外れて 精度が落ちます。つまり:

問題発話区間のみに限定すると
計算量が非現実的解決する (§2.4.2-2)
無音に感情ラベルが付く解決する (§2.4.2-3)
入力粒度がモデルと合わない解決する (§2.4.2-1)
ゲーム音・BGM が声に混ざる解決しない

そして切り抜き経路では、この最後の 1 行を解く手段がほぼありません。

入力音声の構成マイク分離
Twitch VOD (twitch-dl 取得) HLS の ミックス 1 本 (AAC ステレオ) 原理的に不可能
ローカル mp4 (OBS 複数トラック録画) Track1=ミックス / Track2=マイク / … 可能だが現状コードが 0:a:0 固定
  • VOD を入力する運用では、配信時点で既にミックスされているため マイクだけを取り出す道がありません。残るのは音源分離 (新規依存・数百 MB・実行時間大 / 本書では採用を提案していません) だけです。
  • ローカルの複数トラック録画を入力する運用なら分離は不要ですが、 silence_cutter / features / waveform / audio_source がすべて 0:a:0 決め打ちなので トラック選択の実装が先に必要です (F14)。
したがって、VOD を入力する運用では案 B (SER) に着手すべきではありません。 精度が出ない前提で重みファイルを足すことになります。 この判断は Q9 (どの入力を使う運用か) の回答に依存します。

B2信頼度を捨てている → 直す場所が分からない

faster-whisper は各セグメントに avg_logprob / no_speech_prob / compression_ratio、各単語に probability を返しますが、 _recognize() は text / start / end / words だけを拾い、すべて捨てています。

切り抜きは 1 回の出力で 10 クリップ分の字幕をまとめてレビューする作りなので、 「どこが怪しいか」が分からないと確認の手間が本流の 10 倍になります。
  • entry["confidence"] = avg_logprob、entry["no_speech_prob"]、 単語ごとの probability を保持する
  • regroup_items_by_length() で束ねた単語の確率の最小値・平均を引き継ぐ
  • SubtitleClip.origin["confidence"] へ保存 (origin は dict で そのまま JSON へ入るため project_io は無改修)
  • ArchiveResultWindow / Timeline 編集画面で低信頼度のテロップを色分けし、 「要確認だけ表示」フィルタと「次の要確認へジャンプ」を付ける
  • 閾値 subtitle.low_confidence_logprob (既定 -0.6) / subtitle.low_confidence_word_prob (0.4)

B3置換辞書が無い → 同じ誤りを毎回直している

  • 新設定 subtitle.replacements: [{"from": "...", "to": "...", "regex": false}, ...]
  • 適用箇所: _item_from_words() / WhisperTextSource._recognize() の 本文整形 (strip_fillers と同じ層 = _refine())。 改行より前に適用すること
  • B1 の hotwords が「認識前の予防」、これが「認識後の治療」

B4計算精度が int8 固定

  • 既定は int8 のまま (互換)。GUI に「認識精度 (速度優先 / 標準 / 精度優先)」の 3 択
  • 切り抜きは 1 クリップ 180 秒 × 10 本 = 30 分相当なので、 全長 2 時間を認識する本流より精度優先モードが現実的です

B5文脈を切っているため同音異義・漢字選択が弱い

# 1 本のテロップに使える幅 = 1 行の幅 × 最大行数

  • 新設定 subtitle.min_line_ratio (既定 0.5) — 1 行の下限を「使える幅のこの割合」で決める (短すぎる行を避ける。 現 min_line_length の px 版)
  • wrap_by_budoux() の len(line) <= max_line_length 判定を metrics.text_width(line, size) <= usable へ差し替える (文節境界で折る規則は変えない)
  • regroup_items_by_length() の over 判定も同じく px へ移す (= G3 の文節境界で切る規則と自然に噛み合う)
  • metrics が None (フォントが読めない) のときは G1 の文字数経路へ落ちる

  • 縦動画の上書きが不要になります。 _VERTICAL_OVERRIDE_KEYS は現在 min_line_length / max_line_length を縦用の値で差し替えていますが、px 基準なら キャンバス幅から自動で決まるため、 この 2 キーを上書き対象から外せます (request14 の設定が 2 つ減る)。

4.2 問題点

E1クリップごとに個別正規化され、切り抜きの山場が潰れる

normalize_file() はクリップ 1 本ずつに対して走ります (clip_writer.py:528)。各クリップが独立に -14 LUFS へ揃えられるため:

クリップ元の性格正規化後
静かな会話 (元 -20 LUFS)落ち着いた場面+6 dB されて -14
絶叫・盛り上がり (元 -8 LUFS)山場-6 dB されて -14
「盛り上がって切り抜いた」という編集意図が音量から消えます。 切り抜き集では、1 本の中での相対的な起伏が残っている方が自然です。

本流 (1 本編集) は素材 1 本に 1 回しか掛けないため、この問題は切り抜き固有です。

E2イントロカードが正規化を通らず、本編より約 5 dB 大きい

_build_intro_card() は元 VOD (または保存した控え) から直接 切り出します。 

if source and os.path.exists(source):
    input_args = ["-ss", f"{start_buf:.3f}", "-i", source, "-t", f"{length:.3f}"]
...
if card["mute_intro"]:
    cmd += ["-af", "volume=0"]      # mute_intro=false なら音声はそのまま

現在の設定は archive.intro_card.mute_intro = false なので、 イントロの 3 秒は元 VOD の生音量のまま流れます。 一方で本編は -14 LUFS へ下げられています。

実測例 (VOD I=-9.2 / 目標 -14) では、イントロが本編より約 4.8 dB 大きい。 テーマを付けた全クリップの頭で、毎回この段差が起きます。

これは聴感上はっきり分かる差で、テーマ演出を使うほど目立つ不具合です。

E3OP/ED も正規化を通らず、結合後は一度も測っていない

_build_combine_parts() は general.opening_video / ending_video をそのままパーツ列へ追加します。 OP/ED は固定素材なので一度合わせれば済みますが、現状は合わせる仕組みが無く、 本編 -14 LUFS との差が出たままになります。

さらに結合後の最終ファイルのラウドネスを測る工程がありません。

  • YouTube は「-14 LUFS より大きい動画を下げる」だけで、 小さい動画は上げません。最終値が -16 LUFS なら、 他の動画より小さく聞こえたまま公開されます。
  • 1 本の中で OP → 本編 → ED の段差があっても気付けません。

loudness.audio_bitrate = "192k" が効くのは 破棄される中間ファイルだけです (loudness_normalizer.py:213)。その音声は後で再デコードされ、 最終結合で改めて AAC へエンコードされますが、 concat_processor.concat() が使う build_encode_options() は -b:a を渡していません。

def build_encode_options(ffmpeg_settings):
    return ["-c:v", ..., "-preset", ..., "-crf", ..., "-c:a", "aac"]   # -b:a が無い

最終出力は FFmpeg の aac 既定ビットレート (ステレオで概ね 128kbps) になります。 切り抜き経路は結合で必ず全再エンコードが走るため、本流より確実に この経路を通ります。 loudness.audio_bitrate という設定が事実上死んでいるのも 設計の不整合です。

E5短いクリップでは loudnorm の測定が信頼できない

EBU R128 の Integrated は一定の長さを要します。 archive.section_add.min_length_sec = 1.0 で 1 秒のセクションを足せる仕様では、そのクリップの loudnorm 測定はほぼ無意味です (ゲート後に有効なブロックが残らず、極端なゲインが掛かる恐れがある)。

E6linear=true が実際に線形適用されたか記録していない

loudnorm は線形ゲインが True Peak 目標を破る場合に 黙ってダイナミックモードへ落ちます。2 パス目の出力を解析していないため、 ダイナミック処理が掛かったことに気付けません (= 意図せず音の質感が変わる)。

E7True Peak 目標 -1.0 dBTP は AAC には少し強気

AAC エンコード後は符号化誤差で True Peak が 0.5〜1 dB 程度上振れし得ます。 切り抜き経路は結合でもう一度 AAC を通るため、 本流より上振れの機会が多いです。

12.4 3 行になるテロップがある (H1 / 修正済み)

  • max_lines=0 を渡せば従来どおり幅だけで判断します (切り戻し経路)。

12.6 F15 を実測した結果 — MFCC 方式では分離できない

「まず試してみる」ご指示を受けて実装し、docs/quality/kensyou の VOD と 人が判別したラベル (配信者 14 件 / ゲーム 24 件) で測りました。

12.6-1 結果

方式配信者を残すゲームを除く
MFCC そのまま (L2 正規化のみ) 7/14 (50%)19/24 (79%)
MFCC + centering (全体平均を引く) 7/14 (50%)17/24 (71%)
MFCC + centering + 白色化 13/14 (93%)6/24 (25%)
(比較) 区間音量による判定 = F16 9/14 (64%) 22/24 (92%)
MFCC 方式は音量による判定より劣ります。 類似度の分布も重なっていました。 
配信者 14 件  類似度 中央値 +0.026 / 範囲 -0.660〜+0.476
ゲーム 24 件  類似度 中央値 -0.257 / 範囲 -0.745〜+0.639

ゲームなのに配信者に近い  +0.63「マイガー敵変態が侵入なんとかしのいてくれ」
配信者なのに遠い          -0.66「いや絶対完璧じゃなかった絶対フック引っかかってない」

12.6-2 原因

背景にゲーム音が常に乗っているため、MFCC の統計量が 「ミックス全体の音色」に支配されます。 正規化しただけではどのベクトルも同じ方向を向き (コサイン類似度が全件 0.97〜0.99)、話者の差が埋もれていました。

全体平均を引く (centering) と中央値の差は出ましたが (配信者 +0.026 / ゲーム -0.257)、分布の重なりは残りました。 MFCC の統計量 (supervector) はクリーンな単独話者音声向けの手法で、 常時 BGM が乗った素材には向きません。

12.6-3 実装でどう扱ったか

  • 既定の方式を "onnx" にしました。 モデルが無いときはMFCC へ勝手に落ちず、絞り込みを行いません (ログに 1 行出る)。実測で分離できなかった方式を黙って使うと、 「話者照合を入れたのに効かない」という分かりにくい状態になるためです。
  • "mfcc" を明示的に選んだときだけ使えます (選ぶと警告が 1 行出ます)。
  • centering は実装へ取り込みました (_center)。ONNX モデルでも 背景音の共通成分を除く効果があるため、方式に関わらず効かせます。
  • 既定は speaker_filter="off" です。 モデルを置いて "flag" にすると印が付き、 精度を確かめてから "drop" へ上げられます。

12.6-4 次に必要なもの

ONNX の話者照合モデル 1 つです。要件は 「入力 [1, T] の 16kHz モノラル波形 → 出力 [1, D] の埋め込み」 だけで、ECAPA-TDNN / x-vector / ReDimNet のいずれでも構いません。
  • 入手手順とライセンスの注意は src/models/README.md に書きました。
  • 配置すれば 設定を "flag" にするだけで動きます (コード変更は不要)。
  • ネットワーク取得と配布ライセンスの確認が必要なため、 モデルの入手はご判断のうえお願いします。
なお §12.3-3 の実測どおり、区間音量による判定 (F16) は MFCC 方式より精度が高く (ゲーム 92% 除去 / 配信者 64% 保持)、依存も増えません。 モデルを入れるまでの間、F16 を先に入れておく価値があります (段 1 / 小規模)。

12.7-5 切り出し区間が正しいことの裏取り

「そもそも違う音を測っていないか」を確かめました。 §12.3-3 の音量測定は、ここと同じ時刻計算 (clip.vod_start + origin.source_start) で切り出しています。 その測定で配信者とゲームが 17 dB 分離できていたので、 切り出し区間はラベルどおりの音を指しています。 つまり時刻の対応ではなく、音そのものが混ざっていることが原因です。

  • 既定は speaker_filter="off" のままです。 有効にすると「実測では分離できていない」旨の警告が 1 行出ます。
  • 検証中に blur/models.py のセッションキャッシュがパスだけを 鍵にしていたため、同じ名前でモデルを差し替えても古いセッションが 返る問題を見つけ、更新時刻とサイズを鍵へ加えて直しました (2 つのモデルで数値が完全に一致する、という形で現れて気付きにくい問題でした)。
