# quality resolve2 — アーカイブ切り抜き「書き出し」の所要時間 実機分解

- 対象: `docs/quality/qua2.md`
- 調査日: 2026-10-30
- 対象 VOD: <https://www.twitch.tv/videos/2913872726>
  「回線工事の予約が取れた」/ 6170.7 秒 (1 時間 42 分 51 秒) / Magic: The Gathering
- 調査方法: 本体コードを一切変更せず、モジュール属性を差し替える計装
  (`run_ffmpeg_progress` と各工程関数をラップ) で実機実行し、工程別の所要時間と
  FFmpeg プロセスの実行回数を記録した。再現手順は §8 に置く。

## 0. 結論

### 0.1 実測の要点

30 分ぶんの切り抜き (採点結果どおりの 6 セクション) を 1 本へ書き出すのに、
この実機では **約 88 分** かかる。テーマを指定すると **約 110 分**。
そのうち **73% (64 分) が「同じ映像を 3 回エンコードし直している」時間**で、
文字起こしは 18% (16 分) にすぎない。

| 区分 | 換算値 (6 セクション / 1800 秒) | 比率 |
| --- | --- | --- |
| エンコード 3 パス (ベース映像・字幕焼き込み・最終結合) | 3857 秒 | 73.3% |
| 文字起こし (Whisper デコード + モデル読込) | 994 秒 | 18.9% |
| VOD 全体の解析 (音量 + ラウドネス) | 266 秒 | 5.1% |
| その他 (正規化・編集点検出・プレビュー音声・切り出し) | 145 秒 | 2.8% |
| 合計 | **5262 秒 = 87.7 分** | 100% |

### 0.2 「中断・失敗」の正体

**止まっているように見えるから利用者が落としている**、が最有力である。
実測した進捗表示の動きは次のとおりで、**4 回も「数分間まったく動かない区間」がある**。

| 経過 | 表示 | この表示のまま止まる時間 (2 クリップ実測 → 6 セクション換算) |
| --- | --- | --- |
| 0 秒 | `0%` 音量解析 (VOD 全体) | 122 秒 → 122 秒 |
| 122 秒 | `0%` ラウドネス解析 (VOD 全体) | 145 秒 → 145 秒 |
| 502 秒 | `60%` クリップ 1/2 を書き出し中… | 264 秒 → **約 430 秒** |
| 1029 秒 | `92%` 結合中… | 243 秒 → **約 1220 秒 (20 分)** |

- 最後の **`92%` で 20 分間、進捗率もラベルも 1 文字も変わらない**。
  原因は 2 つあり、どちらもコードから特定済み (§3 P9)。
- そして**書き出しを中止する手段がない** (§3 P10)。
  待つしかない画面が 20 分動かなければ、強制終了は妥当な判断である。
- さらに、1 クリップのレンダリングが失敗しても例外を飲み込んでそのクリップを
  飛ばすため、**短い成果物が「成功」として出る** (§3 P11)。
  「失敗」の一部はこれを指している可能性がある。

### 0.3 最優先で入れるべき 3 件

| # | 内容 | 効果 (実測換算) | 変更規模 |
| --- | --- | --- | --- |
| R1 | 最終結合を再エンコードからストリームコピーへ | **−1205 秒 (−20 分)** | 数行 |
| R2 | 出力キャンバスを素材等倍 (720p30) にできるようにする | **−1847 秒 (−31 分)** | 設定 + 数十行 |
| R9 | 進捗を実際に流す + 中止ボタンを付ける | 0 秒 (体感と中断率) | 中 |

R1 + R2 だけで **88 分 → 35 分**。R1 は画質に一切影響しない (むしろ劣化を 1 回ぶん減らす)。

### 0.4 ディスク容量は今回の原因ではない

調査開始時の C: 空きは 42.7 GB、設定の下限は 20 GB。
2 クリップ (359 秒) の最終成果物が 144.5 MB = 0.40 MB/秒だったので、
30 分の成果物は約 725 MB、中間ファイルを含めた同時使用は数 GB の桁である。
**今回の VOD では容量が枯渇する水準に届かない。** 計測中に容量起因の失敗も出ていない。

### 1.3 計測の単位

- 採点 (`pipeline.analyze`) は **VOD 全長で実測**した。
- 書き出し (`clip_writer.write_clips`) は **上位 2 セクション (clip1 / clip2 = 各 180 秒)**
  を実測し、工程ごとに「尺あたりの率」を求めて 6 セクション / 1800 秒へ換算した。
  全 6 本をそのまま流すと 1 回で 1.5 時間を超えるため、率を取る方式にした。
  率の根拠と換算は §2.3 に全て載せてある。実測合計 1271.6 秒のうち
  **1271.1 秒を工程へ帰属できており (未帰属 0.5 秒)**、換算の土台としては十分である。
- 結果画面は注入していない (`result_callback=None`) ため、テーマなしで全件採用される。
  これは GUI の既定操作 (テーマ未入力) と同じ経路である。

### 1.4 採点が選んだセクション

```
clip1: 1395-1575s (180s)   score=50.1
clip2: 1755-1935s (180s)   score=44.1
clip3: 2025-2745s (720s)   score=59.5
clip4: 3015-3195s (180s)   score=46.7
clip5: 3330-3690s (360s)   score=57.3
clip6: 5580-5760s (180s)   score=47.3
```

`select_top_events` は重なりのない窓を `top_n` 件選んでから隣接を統合するため、
**書き出し対象の尺は常に `top_n × window_sec` = 10 × 180 = 1800 秒 (30 分) になる**。
セクション数が 6 本に見えても仕事量は 10 本ぶんである。
**VOD の長さには依存しない**ので、書き出し時間はこの 2 つの設定でほぼ決まる。

### 2.5 無音カットがほぼ効いていない (時間にも直接響く)

```

VOD 全体のカット閾値 -38 dB を全クリップで共有 (F7)
```

360 秒の素材から 359 秒が残っており、**カットできた量は 1% 未満**である。
品質面の話は resolve1.md の担当だが、**本書の観点でも重要**である。
再エンコードは 3 パスとも「残った尺」に比例するので、
**カットが本来の 2〜3 割効けば書き出し時間もそのぶん短くなる**。
現状はその短縮分をまるごと取り逃している。

## 3. 原因の分解

### P1. 出力キャンバスが常に 1920x1080@60fps 固定で、素材を毎パス拡大している

`output_profile.resolve_output_profile` は横動画と判定した場合、
素材の寸法を見ずに `ffmpeg.output_width/height` をそのまま返す。

```python
# src/modules/output_profile.py
def _landscape_profile(ffmpeg_cfg):
    return {
        "is_portrait": False,
        "orientation": "landscape",
        "width": int(ffmpeg_cfg.get("output_width", _DEFAULT_LANDSCAPE_WIDTH)),
        "height": int(ffmpeg_cfg.get("output_height", _DEFAULT_LANDSCAPE_HEIGHT)),
    }
```

`compositor.still_filters` はキャンバスと一致しなければ正規化チェーンを挟むため、
720p30 の素材には毎パス `scale=1920:1080` + `pad` + `fps=60` が付く。

- 画素スループットは **(1920×1080×60) / (1280×720×30) = 4.5 倍**。
- 拡大とフレーム複製で**情報は 1 ビットも増えない**。投稿先が YouTube なら再エンコードされる。
- 実測 (同一素材 60 秒を 1 本エンコード):

| 設定 | 所要 | 実時間比 | 出力サイズ |
| --- | --- | --- | --- |
| 1080p60 libx264 medium crf20 (現状) | **46.6 秒** | ×0.78 | 23.4 MB |
| 1080p60 libx264 veryfast crf20 | 19.4 秒 | ×0.32 | 16.1 MB |
| **720p30 libx264 medium crf20 (素材等倍)** | **14.0 秒** | **×0.23** | 12.8 MB |
| 720p30 libx264 veryfast crf20 | 6.3 秒 | ×0.11 | 10.0 MB |
| 1080p60 h264_qsv (GPU) | 15.2 秒 | ×0.25 | 21.6 MB |
| 720p30 h264_qsv (GPU) | 5.8 秒 | ×0.10 | 10.7 MB |

**素材等倍にするだけで 3.3 倍速くなる。** しかも画質は上がる (拡大による軟化が無くなる)。

### P2. 最終結合が concat フィルタで全体を再エンコードしている

`clip_writer._combine` → `concat_processor.concat` は、
入力ごとに `scale`/`pad`/`setsar`/`fps`/`format` を掛けて `concat` フィルタで繋ぎ、
`build_encode_options` でまるごとエンコードし直す。

```python
# src/modules/concat_processor.py
chains.append(
    f"[{i}:v:0]scale={width}:{height}:force_original_aspect_ratio=decrease,"
    f"pad={width}:{height}:(ow-iw)/2:(oh-ih)/2,"
    f"setsar=1,fps={fps},format=yuv420p[v{i}]"
)
```

**結合する部品はすべて直前の字幕焼き込みが作ったもので、
既に 1920x1080@60fps / yuv420p / aac 48kHz ステレオに揃っている。**
つまりこの `scale`/`pad`/`fps` は全て恒等変換で、再エンコードは丸ごと無駄である。

- 無駄な時間: **1217 秒 (20 分)**
- 無駄な劣化: 世代が 1 つ増える
- しかも、この 20 分がちょうど `92%` で固まる区間である (P9)

同じ役目の `silence_cutter.concat_files(..., reencode=False)` が既にあり、
レンダラはベース映像の連結でこれを使って 0.9 秒で済ませている。

### P3. ベース映像構築が「何もしないパス」になっている

Timeline 経路では残す区間 1 件が V1 クリップ 1 本になる
(`timeline_builder.build_archive_timeline`)。実測では clip2 が **区間 1 件**だった。

このとき `renderer._render_base` の仕事は
「`normalized.mp4` を `-ss`/`-t` で切って 1080p60 へ正規化してエンコード」だけで、
続く字幕焼き込みが**同じ映像をもう 1 回エンコードする**。
区間が 1 件なら、正規化チェーンを字幕焼き込み側へ寄せれば 1 パス省ける。

- 実測の構成 (359 秒のうち 181 秒 = 50.4% が区間 1 件のクリップ) で **−約 200 秒**
- カット閾値が -38 dB のままならほとんどのクリップが区間 1 件になる (= 上限の −390 秒に近づく)

### P4. 解析パスに `-vn` が無く、音声解析のために映像を復号している

`silence_cutter.detect_silence` と `volume_analyzer.measure_region_volume` は
`-f null -` 出力で、**映像ストリームも復号して捨てている**。
`loudness_normalizer.measure_loudness` だけは `-vn` を付けており、
「測定は音声のみで足りるため映像デコードを省いて高速化する」とコメントまで書かれている。

実測 (同一 VOD):

| 処理 | `-vn` なし (現状) | `-vn` あり | 倍率 |
| --- | --- | --- | --- |
| `silencedetect` 600 秒ぶん | 7.7 秒 | **0.7 秒** | **11.0 倍** |
| `volumedetect` 45 秒ぶん (5 本平均) | 0.76 秒 | **0.21 秒** | **3.6 倍** |

全長 6170 秒の `silencedetect` は 127 秒 → **約 12 秒**になる。
採点フェーズと書き出しフェーズの両方に効く。

### P5. 全長の `silencedetect` が採点と書き出しで二重に実行されている

同じ引数・同じ入力で 2 回走っている。

| 呼び出し元 | 引数 | 実測 |
| --- | --- | --- |
| `features.extract_cells` (採点) | `base_noise_db=-30`, `base_min_silence_sec=0.3` | 127.2 秒 |
| `volume_analyzer.analyze_min_speech_db` (書き出し / `cut_db_scope=vod`) | 同一 | 99.0 秒 |

resolve1.md §2.3 F7 は
「`"vod"` は採点フェーズで既に VOD 全長を解析しているため、
**F6 の 1 パスで得た分布から分位点を取るだけ**で追加コストがほぼゼロです」
と書いているが、**F6 が未実装のまま F7 だけを入れたため前提が崩れている**。
現状は「ほぼゼロ」ではなく 122 秒の追加コストになっている。

### P6. ラウドネス測定が独立した全長 1 パスになっている

`analyze_vod` は `loudnorm` の測定だけのために全長 (6170 秒) を 1 回流す (144.5 秒)。
`-vn` は付いており音声のみなので、1 パス自体の効率は悪くない。
問題は**全長を流すパスが採点・音量解析・ラウドネスで 3 本に分かれている**ことである。
`ebur128` と `astats`、`silencedetect` は 1 つのフィルタグラフへ同居できる。

### P7. Whisper がクリップごとにモデルを読み直す

```python
# src/modules/subtitle_generator.py
def _recognize(self, whisper_model_cls, input_path, language, device, compute_type):
    model = whisper_model_cls(self._model_name, device=device, compute_type=compute_type)
```

`extract()` のたびに `WhisperModel` を作るため、large-v3 (約 1.5 GB) の読み込みが
**クリップ数ぶん繰り返される**。実測 7.5 秒/本 → 6 本で 45 秒。
額は小さいが、インスタンスを使い回せば 1 回で済む純粋な無駄である。

### P8. 文字起こしの設定が最も重い組み合わせになっている

180 秒の実音声での実測 (本機 / CPU):

| 設定 | デコード | 実時間比 | セグメント | 文字数 |
| --- | --- | --- | --- | --- |
| **large-v3 / int8 / beam8 / word_ts=True (現状)** | **71.7 秒** | **×0.40** | 23 | 235 |
| large-v3 / int8 / beam1 / word_ts=True | 45.0 秒 | ×0.25 | 22 | 219 |
| large-v3 / int8 / beam8 / word_ts=False | 65.6 秒 | ×0.36 | 22 | 227 |
| medium / int8 / beam8 / word_ts=True | 38.6 秒 | ×0.21 | 21 | 235 |
| large-v3 / float32 / beam8 / word_ts=True | 142.0 秒 | ×0.79 | 23 | 238 |

- `beam_size` を 8 → 1 にすると **1.6 倍速い** (949 秒 → 595 秒)。
- `word_timestamps=False` の効果は 1.09 倍しかなく、
  一方でカット跨ぎの分割に単語区間を使っている (ver8 resolve6 §4-1) ため**切ってはいけない**。
- `float32` は `int8` の 2 倍重い。resolve1.md §3.2 **B4 が提案する「精度優先モード」は、
  本機で 30 分ぶんを認識させると文字起こしだけで 24 分になる**。
  B4 を入れるなら「精度優先は時間が倍になる」ことを画面に明示すべきである。
- 速度と精度は正面からぶつかるため、**本書は beam 値の変更を単独では推奨しない** (§9-2)。
  まず無損失で削れる 64 分 (エンコード 3 パス) を削るのが順序である。

### P9. 進捗が `0%` と `92%` で固まる (中断の直接原因)

原因は 3 箇所ある。いずれも**値を渡していないだけ**である。

**(a) レンダリング中の進捗が捨てられている**

`clip_writer._render_clips` が作る `PipelineContext` に `progress_callback` を渡していない。

```python
# src/archive/clip_writer.py
context = PipelineContext(input_path=prepared["normalized_path"],
                          settings=clip_settings, working_dir=clip_dir)
```

`PipelineContext.__init__` は `progress_callback or _noop_progress` で既定を埋めるため、
`renderer` が `context.progress_subcallback("ベース映像構築")` で取るコールバックは
**何もしない関数**になる。FFmpeg は毎秒進捗を返しているのに、全部捨てている。
結果、`クリップ n/N を書き出し中…` が 1 本ぶん (換算 430 秒) 固まる。

**(b) 最終結合に進捗コールバックを渡していない**

```python
# src/archive/clip_writer.py
def _combine(parts, final, ffmpeg_cfg):
    if len(parts) >= 2:
        ...
        concat_processor.concat(parts, final, ffmpeg_cfg, total_duration=total_dur)
```

`concat_processor.concat` は `on_progress` を受け取れるのに、`_combine` は渡していない。
`finish_clips` が直前に `progress_cb(0.92, "結合中…")` を出したあと、
**完了まで 20 分、画面は一切動かない**。

**(c) VOD 全体の解析が `0%` 固定**

`_prepare_clips` は `analyze_vod` の進捗を `progress_cb(0.0, label)` で渡すため、
最初の 266 秒は `0%` のままラベルだけが 1 回変わる。

### P10. 書き出しを中止できない

`ArchiveClipWorker` には中止の仕組みが無い (`cancelled` シグナルを持つのは
`ArchiveResumeWorker` だけ)。`write_clips` にも `cancel_cb` 相当の引数が無い。
**画面が 20 分動かないとき、利用者に残された手段はアプリの強制終了だけ**である。
「中断」の実体はこれだと考えるのが自然である。

### P11. 1 クリップの失敗が黙って飲み込まれ、短い成果物が「成功」になる

```python
# src/archive/clip_writer.py
try:
    renderer.render(sub_timeline, context)
except Exception:  # noqa: BLE001 (1 クリップの失敗で全体を止めない)
    _logger.exception("clip%s のレンダリングに失敗 → このクリップを飛ばします", clip_index)
    continue
```

意図 (全損を避ける) は妥当だが、**結果画面と完了通知に「何本落ちたか」が出ない**。
`_finish_label` はイントロカードの欠落だけを文言に出しており、クリップ脱落は扱っていない。
容量不足だけは `DiskSpaceError` で貫通するが、それ以外は静かに落ちる。

### P12. 書き出し対象の尺が設定だけで決まる

§1.4 のとおり `top_n × window_sec` = 1800 秒が固定で乗る。
`top_n=10` / `window_sec=180` は「10 本の切り抜き」を意図した値だが、
統合後は 6 セクションになり、**利用者の目には「6 本なのに 30 分ぶん」に見える**。
時間の見積もりが立たない原因でもある。

### P13. 出力設定が設定画面に無い

`ffmpeg.output_width` / `output_height` / `output_fps` / `preset` / `crf` / `video_codec` は
`settings_window.py` にウィジェットが無く、**`setting.json` を手で書くしか変更手段が無い**
(縦動画用 `vertical.output_width` だけは画面にある)。
利用者が「速度を取る」判断を下せない。

## 4. 改善案

### R1. 最終結合をストリームコピーへ (最優先 / 数行)

P2 への対処。部品は字幕焼き込みが出した同一規格の mp4 なので、
concat デマルチプレクサでそのまま繋げる。レンダラが既に使っている関数を流用する。

```python
# 変更前 (src/archive/clip_writer.py)
def _combine(parts, final, ffmpeg_cfg):
    if len(parts) >= 2:
        total_dur = ...
        concat_processor.concat(parts, final, ffmpeg_cfg, total_duration=total_dur)

# 変更後の方針
#   ・部品の規格が揃っている (= 本編のみ / OP・ED 無し) なら
#     silence_cutter.concat_files(parts, final, ffmpeg_cfg, reencode=False) で繋ぐ
#   ・OP/ED や外部素材が混ざるときだけ従来の concat_processor.concat へ落とす
#   ・切り戻し用に archive.combine.reencode (既定 false) を設ける
```

- 効果: **−1205 秒 (−20 分)**。世代劣化も 1 回減る。
- 判断が必要な点: OP/ED は利用者が用意した任意規格なので、
  **規格が一致するかを `ffprobe` で確かめてから copy を選ぶ**こと。
  一致しなければ従来経路へ落とす (安全側)。
- 併せて `on_progress` を渡す (R9 と同時に入れる)。

### R2. 出力キャンバスを素材等倍にできるようにする (最優先)

P1 への対処。ハードコードを増やさず設定で切り替える。

```
新設定 ffmpeg.output_scale_mode:
  "source" (推奨の新既定): 素材の表示寸法・fps をそのまま出力キャンバスにする
                            (上限は output_width/height/output_fps でクランプ)
  "fixed"  (従来)        : output_width/height/output_fps をそのまま使う
```

- 実装箇所は `output_profile._landscape_profile` の 1 箇所に寄せられる。
  以降の工程はすべて profile を見ているため、他は触らなくてよい。
- `compositor.needs_normalize` が偽になるので、**正規化チェーン自体が消える**
  (`scale`/`pad`/`fps` が付かない = コマンドが短くなる)。
- 効果: **−1847 秒 (−31 分)**。画質は上がる。
- 注意: 縦動画 (`vertical`) は 1080x1920 固定のままにする
  (切り抜き位置の計算が寸法に依存するため)。
- 注意: 素材の fps が 28.8 のような非整数のとき、そのまま使うと CFR 化の前提が崩れる。
  **`fps` は素材値を最も近い標準値 (24/25/30/50/60) へ丸める**こと。
  実測ログに `1280x720 28.8fps` が出ているので、この丸めは必須である。

### R3. 区間が 1 件のクリップでベース映像構築を省く

P3 への対処。`renderer.render` で
「V1 が 1 本・ギャップ無し・オーバーレイ無し」の場合に限り、
ベース映像を作らず、字幕焼き込みへ `-ss`/`-t` 付きの素材を直接渡す。

- 効果: 実測の構成で **−約 200 秒**、全クリップが該当すれば −390 秒 (720p30 換算)。
- 区間が 2 件以上のクリップには適用しない。
  部品を PCM 中間で作って demuxer で繋ぐ現行方式は、
  AAC のエンコーダ遅延とフレーム量子化の累積対策 (20260812 resolve3) として
  意図を持って入っているため、**崩してはいけない**。
- 条件分岐 1 つで済み、条件を満たさなければ従来経路のままになるので安全である。

### R4. 解析パスに `-vn` を付ける (数行)

P4 への対処。`silence_cutter.detect_silence` と
`volume_analyzer.measure_region_volume` のコマンドへ `-vn` を 1 つ足す。

- 効果: 採点 −約 190 秒、書き出し −約 100 秒。
- 出力は `-f null -` で音声フィルタの副作用 (stderr のログ) しか使っていないため、
  **検出結果は 1 件も変わらない**。
- `measure_loudness` が既に同じことをしており、前例としても整合する。

### R5. 全長の無音検出を 1 回に寄せる

P5 への対処。採点で得た無音区間と区間音量を書き出しフェーズへ引き継ぐ。

- `pipeline.analyze` の戻り値へ `silence_ranges` と `cells` を足し、
  `write_clips` / `analyze_vod` が渡されたらそれを使う (渡されなければ従来どおり測る)。
- 効果: −約 100 秒 (R4 適用後は −約 10 秒)。
- 併せて resolve1.md **F6 (`archive.scoring.feature_mode="single_pass"`)** を入れると、
  採点の 138 プロセスが 1〜2 プロセスになる (採点 259 秒 → 数十秒)。
  F7 が前提にしていた設計へ戻すことになる。

### R6. Whisper モデルをプロセス内で使い回す

P7 への対処。`WhisperTextSource` にモデルのキャッシュを持たせ、
`(model, device, compute_type)` が同じなら作り直さない。

- 効果: −37.5 秒 (6 本)。
- メモリは 1 インスタンスぶん (int8 で約 1.5 GB) を保持し続ける。
  本機の 31.5 GB なら問題ないが、**書き出し終了時に解放する**こと。

### R7. ラウドネス測定を採点パスへ相乗りさせる

P6 への対処。`ebur128` を `silencedetect` / `astats` と同じフィルタグラフへ入れ、
全長を流すパスを 1 本にまとめる。

- 効果: −144 秒。
- R5 / F6 と同じパスの話なので、まとめて設計するのが合理的である。

### R8. プレビュー音声の抽出を遅延させる

`recognize_for_timeline` は認識に使わない「プレビュー初回再生用の音声」を毎回作る
(区間ごとに 1 プロセス / 換算 41 秒)。再生されなければ捨てられる。

- 新設定 `subtitle.asr_audio_prefetch` (既定 `true` = 従来) を設け、
  `false` なら初回再生時に作る。
- 効果: −41 秒。小さいので優先度は低い。

### R9. 進捗を実際に流し、中止できるようにする (最優先 / 体感)

P9 / P10 への対処。**時間は 1 秒も縮まないが、中断を止めるのはこれである。**

1. `_render_clips` の `PipelineContext` へ `progress_callback` を渡す。
   クリップ内の比率を全体比率へ写す係数は `_render_clips` が既に持っている
   (`0.6 + (pos-1)/total*0.3`) ので、そこへ内側の比率を足し込むだけでよい。
2. `_combine` → `concat_processor.concat` へ `on_progress` を渡し、`0.92〜1.00` に割り当てる。
   R1 を入れれば所要自体が数秒になるが、**OP/ED 混在で再エンコードへ落ちた場合に要る**。
3. `analyze_vod` の進捗を `0.0` 固定ではなく `0.00〜0.05` の実比率にする
   (`measure_loudness` は `on_progress` を受け取れる)。
4. `write_clips` に `cancel_cb` を追加し、工程の境目と `run_ffmpeg_progress` の
   進捗コールバック内で確認して `PipelineCancelled` を投げる。
   GUI に中止ボタンを出す。`ArchiveResumeWorker` に前例がある。
5. 残り時間の目安を出す。本書の率 (×0.72 など) をそのまま使えば、
   「30 分の素材 → 約 N 分」は計算できる。

### R10. 脱落したクリップを完了時に明示する

P11 への対処。`_render_clips` が飛ばしたクリップ番号を集めて `_finish_label` の
文言へ加え、結果画面にも出す。イントロカード欠落と同じ扱いにする。

- 1 本も残らなかった場合は成功扱いにしない。

### R11. 出力設定を設定画面へ出す

P13 への対処。`ffmpeg` の `output_scale_mode` / `preset` / `crf` / `video_codec` を
設定画面へ出す。細かい値を並べるより、**3 択のプリセット**が実情に合う。

| 選択 | 中身 | 1800 秒の 3 パス合計 (実測換算) |
| --- | --- | --- |
| 速度優先 | 素材等倍 + `veryfast` | 521 秒 (8.7 分) |
| **標準 (推奨既定)** | **素材等倍 + `medium`** | **1159 秒 (19.3 分)** |
| 品質優先 | 1080p60 + `medium` (従来) | 3857 秒 (64.3 分) |

### R12. GPU エンコード (QSV) を選べるようにする — 要判断

`video_codec` は設定値なので `h264_qsv` を入れること自体は今でも可能だが、
`-crf` が渡されるため**そのままでは失敗する** (`h264_qsv` は `-global_quality`)。

- 実測: 1080p60 で ×0.25 (x264 medium の 3.1 倍)、720p30 で ×0.10。
- 対応するには `build_encode_options` をコーデック別の分岐にする必要がある。
- 同梱 FFmpeg は QSV 入りでビルドされているので、**追加ライブラリは不要**。
- ただし **GPU の有無・世代で使えない環境がある**。
  失敗時に libx264 へ自動で落とす仕組みが必須で、ここは実装判断が要る。
- **素材等倍 (R2) を入れれば x264 medium で 19 分**になるため、
  QSV は「それでも足りない場合の次の手」として扱うのが妥当である。

### R13. 書き出し対象の尺を利用者に見せる

P12 への対処。採点結果の画面に
「選択中: 6 セクション / 合計 30 分 / 想定書き出し時間 約 N 分」を出す。
`top_n` と `window_sec` が時間を決めていることが分かれば、利用者が自分で調整できる。

## 5. 積み上げ試算と優先順位

### 5.1 積み上げ (6 セクション / 1800 秒 / 本機)

| 段階 | 所要 | 削減 |
| --- | --- | --- |
| 現状 | **5262 秒 = 88 分** | — |
| + R1 (最終結合をストリームコピー) | 4058 秒 = 68 分 | −1205 秒 |
| + R4 / R5 (`-vn`・全長無音検出の再利用) | 3948 秒 = 66 分 | −110 秒 |
| + R2 (出力を素材等倍 720p30) | 2100 秒 = 35 分 | −1847 秒 |
| + R3 (区間 1 件のベース省略 / 実測構成) | 1903 秒 = 32 分 | −197 秒 |
| + R6 / R7 / R8 (モデル再利用・ラウドネス相乗り・プレビュー音声遅延) | 1681 秒 = 28 分 | −222 秒 |
| + R12 (QSV / 任意) | 約 1200 秒 = 20 分 | −480 秒 |
| + beam_size 8→1 (品質と引き換え / 単独では非推奨) | 1328 秒 = 22 分 | −353 秒 |

**R1 + R2 + R4 + R5 で 88 分 → 35 分。ここまでは品質を落とさない。**
R3 までで 32 分、R6〜R8 まで入れて 28 分。

### 5.2 推奨の実施順

| 順 | 項目 | 理由 |
| --- | --- | --- |
| 1 | **R1** 最終結合をストリームコピー | 数行で 20 分。劣化も減る。失うものが無い |
| 2 | **R9** 進捗を流す + 中止ボタン | 「中断」を止めるのはこれ。時間短縮と独立に効く |
| 3 | **R2** 出力を素材等倍 | 31 分。画質も上がる。影響範囲が 1 関数に収まる |
| 4 | **R4** 解析パスに `-vn` | 数行。採点の待ち時間にも効く |
| 5 | **R10** 脱落クリップの明示 | 「失敗」の見えない部分を見えるようにする |
| 6 | **R11** 出力設定を画面へ | 利用者が自分で速度を選べるようになる |
| 7 | **R5 + F6** 全長パスを 1 本に寄せる | 採点 259 秒 → 数十秒。F7 の前提を回復する |
| 8 | **R3** 区間 1 件のベース省略 | 条件分岐 1 つ。効果は中 |
| 9 | **R6 / R7 / R8** 細かい無駄取り | 合計 −222 秒 |
| 10 | **R13** 想定時間の表示 | 見積もりが立つ |
| — | **R12** QSV | R2 で足りるなら不要。失敗時フォールバックの設計が要る |

## 8. 計測の再現手順

計測スクリプトは本体を変更しない計装方式で書いた。要点だけ記す。

1. **計装**: `src.utils.progress.run_ffmpeg_progress` を時間記録付きの関数へ差し替え、
   `ffmpeg_runner.run_ffmpeg_progress` も同じものへ向ける。
   `silence_cutter` / `volume_analyzer` は `subprocess.run` を直接使うため、
   `ffmpeg` 実行だけを見分けて同様に記録する。
2. **工程の計測**: `pipeline.analyze` / `clip_writer.analyze_vod` /
   `clip_writer.cut_region` / `loudness_normalizer.normalize_file` /
   `silence_cutter.detect_edit_points` / `subtitle_generator.recognize_for_timeline` /
   `renderer.render` / `renderer._render_base` / `renderer._extract_clip` /
   `renderer._render_overlays_and_subtitles` / `clip_writer._combine` を
   モジュール属性ごとラップする (Python はグローバルを呼び出し時に解決するため、
   モジュール内部の呼び出しにも効く)。
3. **Whisper のモデル読込**: `faster_whisper.WhisperModel` を計時付きの派生クラスへ差し替える
   (`extract()` 内で `from faster_whisper import WhisperModel` しているため、
   モジュール属性の差し替えで届く)。
4. **実行**: 取得 → `pipeline.analyze` (全長) → `clip_writer.write_clips` (上位 2 本)。
   `result_callback=None` / `points=None` で GUI を介さずに流す。
5. **注意**: 標準出力が cp932 だと FFmpeg の出力で `UnicodeEncodeError` になるため、
   `PYTHONUTF8=1` を付けて実行する。

ベンチ (§3 P1 / P4 / P8) は同じ VOD の 1800 秒地点から 60 秒 (エンコード) /
600 秒 (`silencedetect`) / 180 秒 (Whisper) を切り出して測った。

### 8.1 計測値の信頼性について

- 書き出しの換算は 2 セクション (359 秒) の実測から率を取った外挿である。
  未帰属時間が 0.5 秒 / 1271.6 秒 (0.04%) まで追えているため、
  工程の取りこぼしは無い。ただし**実際の 6 セクションには 720 秒の長いクリップがあり**、
  1 クリップあたりの固定費 (モデル読込など) の比率は下がる = 換算値はやや保守的になる。
- 計測中は他の負荷をかけていないが、**ノート PC のため連続負荷で温度制限が入り得る**。
  1.5 時間の連続実行では実測より遅くなる可能性がある (= 換算値はここでも保守的)。
- **音声のみの長い単一スレッド処理はばらつきが大きい。**
  `loudnorm` の全長測定を 3 回測って 144.5 秒 / 218.4 秒 / 377.9 秒
  (実時間比 42.7 倍 / 28.3 倍 / 16.3 倍) だった。本書は最短の 144.5 秒 (パイプライン内の実測)
  を採用しているため、この工程の削減効果は**実際にはもっと大きい可能性がある**。
  一方でエンコードの率 (×0.72 / ×0.74 / ×0.68) は単独ベンチの ×0.78 と整合しており、
  本書の結論を支える値としては安定している。
- `medium` モデルのベンチで `load=273.9s` と出ているのは**初回のモデルダウンロード**で、
  読み込み時間ではない。比較には `decode` 列だけを使っている。

## 9. 判断が必要な点

推測で実装しないため、ここへ残す。

### 9-1. 出力解像度・fps の既定を「素材等倍」にしてよいか

今回の VOD は 720p30 なので出力も 720p30 になる。
「YouTube へは 1080p で上げたい」という要件があるなら、
`"fixed"` を既定に残し、設定画面の既定選択だけ変えるという案もある。
→ **本書は `"source"` を推奨**する。拡大で情報は増えず、時間だけ 4.5 倍かかるため。

### 9-2. beam_size / モデルの既定を下げるか

resolve1.md B4 は精度を上げる方向 (float32 / 精度優先モード) を提案しており、
本書の測定とは逆向きになる。
本書は**エンコード側だけで 88 分 → 35 分になるため、認識側は触らない**のを推奨する。
触る場合は A/B 評価 (resolve1 §6) を先に回すべきである。

### 9-3. QSV を入れるか (R12)

R2 を入れれば 3 パス合計 19 分なので、QSV の追加は必須ではない。
対応すると「GPU で失敗したときに静かに CPU へ落ちる」挙動が増える。

### 9-4. 無音カットが効いていない件の扱い (§2.5)

カット閾値が -38 dB で 1% も切れていない。これは resolve1.md の
A8 / F7 の範囲だが、**時間にも 3 パスぶん比例して響く**。
本書の範囲外として扱うか、性能課題として併せて直すか。

### 9-5. 想定時間の出し方 (R13)

本書の率 (×0.72 など) は機械によって変わる。
初回実行時に短い区間で実測して係数を持つか、固定係数で出すかは判断が要る。
