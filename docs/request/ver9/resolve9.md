## 0. 先に結論

### 0.1 3 行で

1. **テロップトラックの複数化は原因ではない。** 字幕トラックを 1 本から 8 本へ
   増やしても再描画は **+1.2〜1.5ms** しか増えない (1 行あたり約 0.2ms)。
   画面外のクリップはスキップするため、同じテロップを 1 本に積もうが
   8 本に散らそうが**描く個数は変わらない** (§2)。
2. **「余裕があるのに重い」は資源不足ではなく、処理が 1 本の列に並んでいるため。**
   Timeline の描画は GUI スレッド 1 本の CPU 描画で、しかも Python なので
   GIL があり分割できない。**1 コアを使い切っても全体 CPU は 1/14 ≒ 7%** に
   しか見えない (§4)。
3. **ただし「もっと食わせて速くする」余地は実際にある。** 今は資源が足りない
   のではなく、**使わない設定になっている** (`cache_frames=8` / `proxy.mode=off`
   / `proxy.workers=1` / 先読みなし)。ここは空き RAM と空きコアを
   そのまま速さへ変換できる (§5)。

### 0.2 追問への回答 (§6)

| 問い | 回答 |
| --- | --- |
| Timeline 画面の処理も CPU か | **そう。本アプリは入口から出口まで全部 CPU。** 文字起こし (whisper / int8)、書き出し (libx264)、Timeline の描画 (Qt `QPainter`) のいずれも GPU を使っていない |
| GPU を使うと GPU がない PC で動かなくなるか | **ならない。** 配布物に既にソフトウェア実装 (`opengl32sw.dll`) が同梱済みで、GPU が使えない環境では自動的に CPU 描画へ落ちる = **今と同じ速度で動く**。ただし設定で明示的に切り戻せるようにすることが条件 (§6.3) |

## 1. 計測の方法

| 対象 | 測り方 |
| --- | --- |
| Timeline の再描画 | 実プロジェクトを読み込み、`QImage` へ `render()` し、ズーム・字幕トラック数別に 10 回の平均 |
| オーバーレイの再構築 | `SubtitleOverlayItem` を同時テロップ数ぶん生成し 40 回の平均 |
| 要素の走査 | `timeline.overlay_elements()` + `contains()` を 200 回の平均 |

計測環境:

| 項目 | 値 |
| --- | --- |
| CPU | **Intel Core Ultra 7 155U** (12 コア / 14 スレッド / U 系の省電力品) |
| RAM | **31.5 GB** |
| プロジェクト | `output/vod_2884417212.archive.timeline.json` (要素 **774 件** / 字幕 **272 件** / トラック 5 本・字幕 2 本) |
| 画面 | 1600 x 700 |

### 1.1 この計測の限界 (先に明記する)

- `QT_QPA_PLATFORM=offscreen` で測っているため、実機の画面合成ぶんは含まない。
  ただし `QPainter` は CPU 描画なので描画時間そのものは実機と近い (resolve7 §1 と同じ条件)。
- 計測に使ったプロジェクトは**素材の実体が無い** (11 件が見つからず該当クリップは無効)。
  そのため**波形は描かれていない**。つまり §2 の数字は
  **「行とクリップを描くぶん」だけを切り出したもの**である。
  波形のコストは resolve7 §2.1 で別に測ってある (ズーム別に +6.4〜13.6ms)。
  トラック数の影響を見るという本題には、むしろ波形が混ざらないほうが都合がよい。

## 2. 字幕トラック数ごとの再描画時間 (本題)

同じ 272 件の字幕クリップを、1 本のトラックへ寄せた場合と 2・4・8 本へ
散らした場合で比べた。

| 字幕トラック数 | 表示行数 | zoom 20 px/秒 | zoom 50 px/秒 | zoom 200 px/秒 |
| --- | --- | --- | --- | --- |
| **1 本** | 4 | 6.34 ms (158fps) | 4.28 ms (234fps) | 3.57 ms (280fps) |
| **2 本** (実際の構成) | 5 | 6.80 ms (147fps) | 4.92 ms (203fps) | 3.72 ms (268fps) |
| **4 本** | 7 | 7.37 ms (136fps) | 4.87 ms (205fps) | 3.99 ms (251fps) |
| **8 本** | 11 | 7.72 ms (129fps) | 5.85 ms (171fps) | 4.74 ms (211fps) |

**1 行増えて約 0.2ms。** 1 本から 8 本へ増やしても +1.2〜1.5ms である。

### 2.1 なぜ増えないのか

クリップの描画は**画面外をスキップする**実装になっている。

```python
# src/gui/timeline/timeline_view.py  _paint_row
if x2 < -2 or x1 > self.width() + 2:
    continue  # 画面外はスキップ (長尺でも描画コストが増えない)
```

つまり**描く個数は「画面に映っている範囲の要素数」で決まる**。同じテロップを
1 本のトラックへ積もうが 8 本へ散らそうが、映っている個数は変わらない。
トラックを増やして増えるのは**行の下地 (`fillRect`) とグリッド線だけ**で、
これが 1 行あたり約 0.2ms にあたる。

`build_rows()` もトラック数ぶんの辞書を組むだけで、トラック数は多くても
十数本なので無視できる。

## 3. プレビュー側 (同時テロップ数の影響)

トラックが複数あると**同時に出るテロップが増える**ため、プレビューの
オーバーレイ再構築が増えるのではないか — ここも測った。

| 対象 | 時間 |
| --- | --- |
| 全要素の走査 (`overlay_elements()` + `contains()` / 292 件) | **0.047 ms** |
| `SubtitleOverlayItem` の生成 — 同時 1 件 | 0.04 ms |
| 同 — 同時 2 件 | 0.07 ms |
| 同 — 同時 4 件 | 0.14 ms |
| 同 — 同時 6 件 | 0.22 ms |

`metrics_mode` が `"libass"` でも `"em"` でも差は出なかった
(`font_metrics` 側で解決済みの値を使うため)。

**1 件あたり 0.04ms。** 同時に 6 件出しても 0.22ms で、体感には影響しない。

## 4. なぜ「タスクマネージャに余裕があるのに重い」のか

これは**資源不足ではなく、処理が 1 本の列に並んでいる**ことによる遅さである。

### 4.1 1 コアを使い切っても全体では 7%

| 事実 | 帰結 |
| --- | --- |
| Timeline の描画は Qt の `QPainter` = **CPU ラスタ描画** | GPU は使っていない (§6) |
| ウィジェットの描画は **GUI スレッド 1 本**でしか走れない (Qt の規約) | 別スレッドへ逃がせない |
| 描画ロジックは **Python** なので **GIL** がある | スレッドを増やしても分割できない |
| このマシンは **14 スレッド** | **1 コア 100% = 全体 7.1%** |

つまり「余裕がある」という観察は正しいが、**その余裕は使えない余裕**である。
メモリも同様で、アプリはメモリ待ちで止まっているわけではないため、
空き RAM が増えても速くならない。

### 4.2 U 系 CPU の事情

Core Ultra 7 155U は 2 P コア + 8 E コア + 2 LP-E コアの構成で、
**GUI スレッドが E / LP-E コアへ載ると単コア性能が目に見えて落ちる**。
Windows の電源モードを「最適なパフォーマンス」にすると P コアへ載りやすくなる。
効果は環境依存だがコストはゼロなので、確認する価値はある。

### 4.3 正しい見方 (ユーザー向け)

タスクマネージャ → パフォーマンス → CPU グラフを右クリック →
**「論理プロセッサ」**に切り替える。**1 本だけ天井に張り付いていれば**
この診断で合っている。全体の % では絶対に見えない。

## 5. 空いている資源を速さへ変える余地

「もっと食わせてよい」という見立ては正しい。今は資源が足りないのではなく、
**使わない設定になっている**。

| 設定 | 今の値 | 余地 | 効果 |
| --- | --- | --- | --- |
| `timeline.preview.cache_frames` | **8** 枚 (1920x1080 rgb24 ≒ 6.2MB × 8 = **約 50MB**) | 64〜128 枚 (0.4〜0.8GB / 31.5GB 中) | Undo・やり直し・再生ヘッドの行き戻りが **32〜44ms → 0ms** |
| `timeline.preview.proxy.mode` | **off** | 対策F (停止中だけタイルを使う) | デコードがタイル読み出しに置き換わる。**最も効く** |
| `timeline.preview.proxy.workers` | **1** | 4〜6 | 遊んでいるコアを裏の先読みへ回せる |
| フレームの先読み | **なし** (要求された 1 枚だけ取る) | 再生ヘッド周辺を裏で取っておく | 空きコア + 空き RAM をそのまま速さへ変換できる |

### 5.1 逆に、空きコアでは解決しないもの

**描画そのもの (resolve7 §2.1 の 14.6ms)** である。Qt のウィジェット描画は
GUI スレッド専有なので、ここは**仕事を減らすしかない**。

| # | 対策 | 位置づけ |
| --- | --- | --- |
| **B** | 波形を `QLine` の列から塗り (`QPainterPath`) へ / 列を間引く | 常時の 14.6ms を削る**唯一の手**。resolve7 §6 で見送り |
| **C** | 部分再描画 (`update(rect)`) | resolve7 §6 で見送り (描き残しの不具合を生みやすい) |
| **G** | `QOpenGLWidget` で GPU へ逃がす | §6。設計が大きく変わる |

## 6. CPU 描画と GPU 描画 (追問への回答)

### 6.1 本アプリは入口から出口まで全部 CPU

| 処理 | 実装 | GPU |
| --- | --- | --- |
| 文字起こし | whisper (`device="cpu"` / `compute_type="int8"` 固定) | 使わない |
| 書き出し | ffmpeg `libx264` / preset `medium` | 使わない |
| **Timeline の描画** | Qt `QPainter` (CPU ラスタ描画) | **使わない** |
| プレビューのデコード | PyAV / ffmpeg (`hwaccel` 指定なし) | 使わない |

ただし**この 2 つは理由が別である**。ここを混ぜると判断を誤る。

| | 文字起こし (whisper) | Timeline の描画 (Qt) |
| --- | --- | --- |
| CPU な理由 | **明示的な判断**。ver1 resolve8 の「CUDA 不使用方針」 | **判断の結果ではなく Qt Widgets の既定** |
| 経緯 | CUDA ランタイム同梱 (約 1.93GB) を廃止して配布を軽量化するため。`src/modules/subtitle_generator.py:313` に経緯のコメントがある | 何も指定していないため既定の CPU ラスタ描画になっている。`src/` に `QOpenGL` 系の呼び出しは **1 件も無い** (同梱 DLL のみ) |
| 言い換えると | 「CPU に決めた」 | **「何もしていないから CPU」** |

つまり文字起こしの CPU 固定は守るべき決定だが、Timeline の描画が CPU なのは
**まだ誰も選んでいない状態**にすぎない。GPU 化の是非を考えるときは、
前者の判断を後者へ持ち込まないこと。

### 6.2 「GPU がない PC だと動かなくなる」か → ならない

ここが追問の核心だが、**CUDA の話と画面描画の話はまったく別**である。

| | CUDA (文字起こし) | OpenGL / Direct3D (画面描画) |
| --- | --- | --- |
| 対応ハード | **NVIDIA 製 GPU のみ** | ほぼすべての PC (Intel UHD / Iris、AMD Radeon Graphics などの内蔵で足りる) |
| 同梱サイズ | 約 **1.93GB** | **0** (Qt に既に入っている) |
| 使えないとき | **動かない** (だから廃止した) | **自動で CPU 描画へ落ちる** |

配布物を確認したところ、フォールバックは**すでに同梱されている**。

```
src/dist/Stretheus/_internal/PySide6/
  Qt6OpenGL.dll
  Qt6OpenGLWidgets.dll
  opengl32sw.dll     ← OpenGL のソフトウェア実装 (GPU 不要)
  plugins/platforms/qdirect2d.dll
```

Qt は「ネイティブの OpenGL → Direct3D 経由 → `opengl32sw.dll` (ソフトウェア)」の
順に落ちていく。したがって GPU が使えない環境でも**今と同じ CPU 描画で動く**だけで、
動かなくなることはない。

実際に「GPU がない PC」にあたるのは、内蔵グラフィックスすら無い相当古い機種、
リモートデスクトップ / 仮想マシン、ドライバが壊れている環境である。
いずれも**遅くなるだけで、起動しなくなるわけではない**。

### 6.3 それでも GPU 化を最初にやるべきではない

| 理由 | |
| --- | --- |
| 効くのは描画 (14.6ms) だけ | 体感の主因であるデコード (32〜44ms) には効かない。そちらは §5 の対策F |
| 設計が大きく変わる | `QGraphicsView` / `QWidget` の描画経路を差し替えることになる |
| 環境差が増える | ドライバ依存の表示崩れは原因の切り分けが難しい |
| 代わりに B・C は全 PC に効く | GPU の有無に関係なく軽くなる |

**もし実装するなら必須の条件**: 既存の `timeline.waveform.hide_while_dragging` や
`timeline.preview.proxy.mode` と同じく、**設定で切り戻せること**。
GPU 描画を既定にするとしても、落ちたときに CPU 描画へ戻せる逃げ道を残す。
本プロジェクトは一貫してこの作りになっているので、踏襲すればよい。

## 7. 推奨する着手順

| 順 | 対策 | 規模 | 効果 |
| --- | --- | --- | --- |
| **1** | `cache_frames` を 8 → 64 | **設定値のみ** | 編集の行き戻りで 32〜44ms が消える。メモリ 50MB → 400MB (31.5GB 中) |
| **2** | 対策B — 波形の描き方を変える | 小〜中 | 常時の描画 14.6ms を削る。全 PC に効く |
| **3** | フレームの先読み (+ `proxy.workers` を上げる) | 小〜中 | 空きコアを使う |
| **4** | 対策F — プロキシ案b (停止中だけタイル) | 中〜大 | **根本的**。ただし ver8 resolve8 §24 の暗転と同じ機構に触るため設計から |
| — | 対策G — GPU 描画 | 大 | §6.3 のとおり後回し |

1 と 2 が費用対効果で優先。4 が本筋だが設計が必要である。

ゼロコストで試せるものとして、**Windows の電源モードを「最適なパフォーマンス」**に
する確認を §4.2 に挙げてある。

## 8. 再現方法

計測に使ったスクリプトは一時領域に置いたため残していない。再現する場合は以下。

```python
# 字幕トラック数ごとの再描画時間 (§2)
import os, json, time
os.environ.setdefault("QT_QPA_PLATFORM", "offscreen")
from PySide6.QtWidgets import QApplication
from PySide6.QtGui import QImage
from src.timeline import project_io
from src.gui.timeline.timeline_view import TimelineView, build_rows
from src.gui.timeline.timeline_controller import TimelineController

SETTINGS = json.load(open("src/settings/setting.json", encoding="utf-8"))
app = QApplication.instance() or QApplication([])
tl = project_io.load_project("output/vod_2884417212.archive.timeline.json")

# merge_subs() / split_subs(n) で字幕クリップを 1 本へ寄せる / n 本へ散らす
# (Track(..., TRACK_SUBTITLE, index) を足してクリップをラウンドロビンで配る)
ctrl = TimelineController(tl, SETTINGS)
ctrl.set_zoom(50)
view = TimelineView(ctrl); view.resize(1600, 700)
img = QImage(1600, 700, QImage.Format_ARGB32)
for _ in range(2):
    view.render(img)                       # ウォームアップ
t0 = time.perf_counter()
for _ in range(10):
    view.render(img)
print((time.perf_counter() - t0) / 10 * 1000, "ms", len(build_rows(tl, ctrl.cfg)), "rows")
view.shutdown()
```

注意: `view.render(painter)` ではなく **`view.render(img)`** (QPaintDevice を渡す)。
`QPainter` を渡す形は `targetOffset` が必須で `TypeError` になる。

## 10. チャットでの回答 (2026-10-27 / 記録)

本調査の結果をチャットで回答した内容を、あとから経緯を追えるようそのまま残す。
数字と根拠は §2〜§6 にある。

### 10.1 「テロップトラックの複数化が原因か」への回答

**原因ではない。** 実測した (§2)。

- 字幕クリップ 272 件を 1 本のトラックへ寄せた場合と 2・4・8 本へ散らした場合で、
  再描画は **1 行あたり約 0.2ms** しか変わらない。1 本→8 本でも +1.2〜1.5ms。
- クリップは画面外をスキップする実装 (`timeline_view.py:519`) なので、
  同じテロップを 1 本に積もうが 8 本に散らそうが**描く個数は変わらない**。
  増えるのは行の下地とグリッド線だけ。
- プレビュー側も同様。同時に出るテロップが増えてもオーバーレイ再構築は
  **1 件あたり 0.04ms**、全要素の走査は **0.047ms** (292 件)。
- 一方 resolve7 の実測では波形込みの再描画が **14.6〜27.4ms**、
  デコードが **32〜44ms**。重さの本体はこちらで、
  **トラック数の寄与は 1〜2 桁小さい**。

### 10.2 「PC に余裕があるのに重い」への回答

**資源不足ではなく、処理が 1 本の列に並んでいることによる遅さ** (§4)。

- Timeline の描画は Qt の `QPainter` (CPU ラスタ描画) で、**GUI スレッド 1 本**
  でしか走れない。しかも描画ロジックは Python なので **GIL** があり分割できない。
- **1 コアを 100% 使い切っても、全体 CPU は 1/14 ≒ 7%** にしか見えない。
  「余裕がある」のは正しいが、**その余裕は使えない余裕**である。
- メモリも同じで、アプリはメモリ待ちで止まっていないため空き RAM では速くならない。
- 155U は U 系の省電力品で、GUI スレッドが E / LP-E コアへ載ると
  単コア性能が目に見えて落ちる。
- 確認方法: タスクマネージャ → パフォーマンス → CPU グラフを右クリック →
  **「論理プロセッサ」**。1 本だけ天井に張り付いていればこの診断で合っている。

**ただし「もっと食わせて速くする」余地は実際にある** (§5)。今は資源が足りない
のではなく、`cache_frames=8` / `proxy.mode=off` / `proxy.workers=1` / 先読みなし
という**使わない設定になっている**。

### 10.3 「Timeline の処理も CPU か」への回答

**そう。入口から出口まで全部 CPU** (§6.1)。文字起こし (whisper / int8)、
書き出し (libx264)、Timeline の描画 (`QPainter`)、プレビューのデコード
(`hwaccel` 指定なし) のいずれも GPU を使っていない。

ただし**理由は 2 つで別**である。文字起こしの CPU 固定は ver1 resolve8 の
「CUDA 不使用方針」による**明示的な判断**だが、Timeline の描画が CPU なのは
**Qt Widgets の既定**にすぎない。前者は「CPU に決めた」、
後者は「何もしていないから CPU」である (§6.1 の表)。

### 10.4 「GPU を使うと GPU がない PC で動かなくなるか」への回答

**ならない** (§6.2)。**CUDA の話と画面描画の話はまったく別物**である。

| | CUDA (文字起こし) | OpenGL / Direct3D (画面描画) |
| --- | --- | --- |
| 対応ハード | **NVIDIA 製 GPU のみ** | ほぼ全 PC (内蔵グラフィックスで足りる) |
| 同梱サイズ | 約 **1.93GB** | **0** (Qt に既に入っている) |
| 使えないとき | **動かない** (だから廃止した) | **自動で CPU 描画へ落ちる** |

しかも配布物を確認したところ、**フォールバックはすでに同梱済み**だった
(`opengl32sw.dll` / `Qt6OpenGL.dll` / `Qt6OpenGLWidgets.dll` / `qdirect2d.dll`)。
Qt は「ネイティブ OpenGL → Direct3D 経由 → `opengl32sw.dll` (ソフトウェア)」の
順に落ちていくため、GPU が使えない環境では**今と同じ CPU 描画で動くだけ**で、
起動しなくなることはない。

実際に該当するのは内蔵グラフィックスすら無い相当古い機種、
リモートデスクトップ / 仮想マシン、ドライバが壊れている環境で、
いずれも**遅くなるだけ**である。

**それでも GPU 化を最初にやるべきではない** (§6.3)。効くのは描画 (14.6ms) だけで
体感の主因であるデコード (32〜44ms) には効かず、描画経路の差し替えは設計が大きく
変わり、ドライバ依存の表示崩れは切り分けが難しい。代わりに対策B・C は
**GPU の有無に関係なく全 PC に効く**。

将来実装するなら、`timeline.waveform.hide_while_dragging` や
`timeline.preview.proxy.mode` と同じく**設定で CPU 描画へ切り戻せること**が
必須条件である。本プロジェクトは一貫してこの作りなので、踏襲すれば安全に入れられる。

**② 対策B (波形の描き方)** が費用対効果で優先、と伝えた。

## 11. 解消した対策 (2026-10-28 / 実装済み)

本書の §7 の着手順とは**別の原因**で重さが解消した。経緯と原因は
**[resolve11.md](resolve11.md)** に詳述する。本節はその要点を本書へ残す。

### 11.1 実際に効いた対策

**プレビューの字幕の縁 (アウトライン) の描き方を、パス合併からペンのストロークへ
変えた。** 原因は `src/gui/timeline/preview_items.py` の `paint()` が
`QPainterPathStroker.createStroke(path).united(path)` を**描画のたびに**
計算していたことである。`united()` はパスのブール演算で、要素数に対して
非線形に重くなる。

| テロップ | パス要素数 | `createStroke` だけ | **`createStroke + united` (従来)** | ペンでストローク (修正後) |
| --- | --- | --- | --- | --- |
| 短い (12 文字) | 567 | 0.2 ms | **54.2 ms** | 0.2 ms |
| 普通 (26 文字) | 2571 | 0.8 ms | **733.3 ms** | 1.2 ms |
| 長い (46 文字) | 4435 | 1.5 ms | **1752.1 ms** | 2.1 ms |

縁の太さを 10px (利用者の設定) から 4px へ落としても 179ms / 431ms で、
オーダーは変わらない。**`createStroke()` は速く、`united()` だけが遅い。**

幅 2W の `QPen` (丸い継ぎ目・丸い端) で字のパスをストロークすれば、
「字の外側に W px」という太さの規約を保ったままパス演算を 0 にできる。
設定 `timeline.preview.subtitle_outline_mode` を追加し、既定 `"pen"` /
従来の描き方は `"union"` で選べる (`"union"` でも形を作り置きし、
paint のたびには計算しない)。

### 11.2 効果 (実画面・最大化 3440x1369 / 同一プロジェクト / 25 操作)

| | 中央 | 90%点 | 最大 | 字幕 paint 中央 | 字幕 paint 最大 |
| --- | --- | --- | --- | --- | --- |
| **修正前** | 44 ms | **539 ms** | **1088 ms** | 138〜291 ms | **916 ms** |
| **修正後** | 38 ms | **128 ms** | **219 ms** | 71 ms | 99 ms |

* **90%点 539 → 128ms (4.2 倍) / 最大 1088 → 160〜219ms (5〜7 倍)**
* 「クリックしてから 1 秒」は**出なくなった** (2026-10-28 に利用者が確認)
* 見た目は完全一致ではない。縁の輪郭の AA 1 画素ぶんが差分として出る
  (差 32 超の画素は全体の 0.006〜0.039% / 形・太さ・位置は同一)。
  厳密に見比べたいときは `"union"` へ切り戻す (resolve11 §3.3)

### 11.3 本書の測り方のどこが足りなかったか

| 本書の測り方 | 足りなかった点 |
| --- | --- |
| `SubtitleOverlayItem` の**生成**時間 (0.04ms/件) を測った | 重いのは生成ではなく **paint** だった |
| 再描画の**総量と中央値**で評価した | 体感は**裾**で決まる。中央 44ms に対し 90%点 539ms / 最大 1088ms |
| `QT_QPA_PLATFORM=offscreen` で測った | 実画面・最大化でないと拡大倍率が変わり、塗る面積が桁で変わる |
| Timeline の `_paint_row` を中心に測った | 主因はプレビュー側 (`preview_items.paint`) にあった |

**教訓**: 体感の調査では ① 実プラットフォームで最大化して測る
② 中央値ではなく 90%点・最大を見る ③ 生成ではなく paint を測る。
