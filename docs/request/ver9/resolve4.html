0. 先に結論

0.1 3 行で

  1. PDF の技術の正体は「TUSS」で、ソースコードと学習済みモデルが GitHub で公開済み (merlresearch/unified-source-separation)。プロンプトに speech / musicbg / sfxbg を指定して混合音から声だけを取り出す使い方は、 ゲーム実況アーカイブの音とまさに同じ問題設定。
  2. 技術的には動かせる。 torch 2.11.0+cpu と torchaudio は既に配布物へ同梱済みで、 新しい依存は要らない。重みも medium 44.9MB / large 153.2MB と現実的なサイズ。
  3. ただし「そのまま我々の配布物へ同梱」は 2 つの理由で不可。
    ① ライセンスが AGPL-3.0-or-later (配布物へ入れると当方のソース開示義務が及ぶ)

0.2 ご質問「文字起こしの精度が上がるとふんでいます」への回答

仮説の方向は妥当です。 ただし「音源分離を入れれば精度が上がる」とまでは、 今回読んだ資料では言い切れません。理由は 3 つ:

区分内容
根拠あり ゲーム音 (BGM・SE) と声が 1 本にミックスされた音は、分離すれば声の SNR が上がる。 論文の DnR (映画音響＝声/音楽/効果音の混合) では声の SI-SNR が 15.1dB 改善と報告 (§2.1)
根拠なし 論文はどれも音質指標 (SI-SNR / SNR) のみで、文字起こし精度 (CER/WER) は 1 つも測っていない
既知の逆効果 分離の副作用 (子音の欠け・ミュージカルノイズ) で音声認識が悪化することは 一般に知られている。Whisper は雑音混じりの音でも学習済みのため、 綺麗だが不自然な音より生音のほうが当たることがある

→ やるなら「まず測る」。 §7 に 1〜2 日で回せる A/B 計測の手順を書きました。効果が出た場合に初めて実装へ進むのが、投資として安全です。

0.3 我々としての推奨

TUSS 本体ではなく、MIT / Apache-2.0 の軽い分離モデルを「認識専用の前処理」として入れる案 (§5 案B)

  • 分離した音は Whisper へ渡すためだけに使い、 出力動画の音声には一切使わない → 視聴者に届く音は今と 1 バイトも変わらないので、音質面のリスクがゼロになる。
  • 入口は 1 か所。text_source.extract(input_path, …) に渡すパスを 「分離済み 16kHz モノラル WAV」へ差し替えるだけで済む (§6)。
  • 失敗・未導入・時間切れのときは元の動画パスへ落とせば、現行とまったく同じ動作に戻る。

2. 参考論文 4 本の要点 (ここが実現可能性の判断材料)

2.1 ※1 TR2025-032 — TUSS 本体 (ICASSP 2025)

  • 正式名 TUSS (Task-aware Unified Source Separation)。 著者は Kohei Saijo (早稲田大学からの MERL インターン)、Janek Ebbers、 François G. Germain、Gordon Wichern、Jonathan Le Roux。
  • 問題意識: 音源分離は「何を分離したいか」がタスク依存で、しかも 矛盾するタスクがある (音楽分離では楽器を分けたいが、映画音響では楽器をまとめたい)。 だから 1 つのタスク非依存モデルでは全部こなせない。
  • 解法: 可変個の学習可能なプロンプトで 「どの音を何個取り出すか」を指定する。プロンプトに応じてモデルの振る舞いが変わるので、 矛盾するタスクも 1 モデルで扱える。
  • 構成: エンコーダ (STFT + バンド分割) → 学習可能プロンプト → cross-prompt モジュール → 条件付き TSE (目的音抽出) モジュール → デコーダ。 土台は TF-Locoformer (畳み込みと注意機構を組み合わせた時間-周波数デュアルパスモデル)。
  • 規模: medium 11.1M / large 38.2M パラメータ。 48kHz、モノラル前提。
  • 対応プロンプト (実装の既定 8 種): speech / sfx / sfxbg (効果音の混合) / drums / bass / vocals / other / musicbg (楽器音の混合)。追加拡張も可能。

性能 (Table III / 統合モデル L5)

ベンチマークタスク指標

WHAM!話者分離 (SS)8.7 / 11.9 dB

→ 我々の用途に一番近いのは DnR (CASS)。「声 + 音楽 + 効果音」の混合から 声を取り出す設定で、Speech 15.1dB。 ゲーム実況 (声 + BGM + SE) とほぼ同じ構図です。

重要: 論文中に “code and trained models are available online” と明記、 リンク先は https://github.com/merlresearch/unified-source-separation。

2.2 ※2 TR2025-143 — FasTUSS (WASPAA 2025) = 計算量の実数が分かる論文

  • TUSS は「パラメータは少ないが演算が多い」モデル。その設計を見直して軽量版を作った研究。
  • TUSS オリジナルの演算量 = 音声 1 秒あたり 43.1 GMAC (6 秒チャンク / シフト 6 秒)。
  • 長尺を扱う CSS (チャンク分割処理) の実測値:
    • 60 秒を 6 秒チャンク・シフト 6 秒 → 2,800 GMAC (≒ 46.7 GMAC/秒)
    • 60 秒を 6 秒チャンク・シフト 3 秒 (50% 重ね) → 5,400 GMAC (≒ 90 GMAC/秒) ※ 重ねたほうが品質は上がる (DnR Speech 14.4 → 14.6dB)
  • FasTUSS-11.7G / FasTUSS-8.3G で演算を 73% / 81% 削減、 性能低下は全ベンチマーク平均 −0.4dB / −1.2dB。 因果 (ストリーミング) 版も検討。
  • ただし FasTUSS の学習済み重みは公開されていない (公開されているのは TUSS の medium / large)。

2.3 ※3 TR2026-034 (ICASSP 2026) / ※4 TR2026-032 (ICASSP 2026)

  • ※3 はマイク本数に依存しない単一モデル化 (1 本でも複数本でも同じモデルで分離)。 我々の入力は VOD の 1 本 (モノ/ステレオミックス) なので直接の恩恵は無い。
  • ※4 はプロンプトで指定した音源ごとに分離された圧縮表現 (コーデック) を推定する技術。 音をトークン化して LLM へ直接入れる布石。我々の文字起こしとは別方向 (将来 LLM で場面理解をやるなら関係してくる)。

4. 実現可能性の評価

4.1 ライセンス (最大の壁)

TUSS は AGPL-3.0-or-later。影響は配布形態で変わります。

使い方評価
配布物 (Stretheus.exe / _internal) へ同梱 不可 AGPL のコードを頒布すると、結合した作品に同じ条件 (ソース開示) が及ぶ。当方は課金・ポイント機構を持つクローズドな配布物なので、 事業判断として採れない
利用者が自分で導入した TUSS を別プロセスとして呼ぶ (あれば使う) グレー寄りだが現実的 当方は AGPL 物を頒布せず、CLI 越しの疎結合に留める形。 ただし「同梱していないのに実質セット」と見なされる余地は残るため、法務確認が必要
サーバ側で動かして結果を返す AGPL §13 発動 ネットワーク利用のため利用者へソース提供の申し出が必要。 改変しなければ上流リポジトリの提示で足りるという解釈はあるが、やはり法務確認が必要。 加えて音声アップロードの転送量・保管の問題が乗る
三菱電機から商用ライセンスを受ける 選択肢として実在 PDF に問い合わせ窓口 (axc-contact@rb.MitsubishiElectric.co.jp) があり、 2027 年度中の製品実装を目指す段階なので、商用提供の話は時期的に早い可能性が高い

4.2 計算量 (第 2 の壁)

論文の実数から、我々の CPU 専用配布でどうなるかを試算しました。

TUSS (medium / 11.1M) = 43.1 GMAC / 音声 1 秒   (1 MAC ≒ 2 FLOP → 86.2 GFLOP/秒)
50% オーバーラップで処理する場合は約 2 倍 (90 GMAC/秒 ≒ 180 GFLOP/秒)

本開発機 (12 スレッド) で torch の行列積スループットを実測すると 361.7 GFLOPS (fp32)。素直に割ると理論 RTF は 0.24 倍速 (音声より速い) ですが、注意機構・正規化・メモリ帯域の制約で 実効効率は行列積ピークの 10〜30% 程度に落ちるのが通例なので、

条件本開発機での粗い見積り3 時間アーカイブ
オーバーラップなしRTF 0.8〜2.4 倍2.5〜7 時間
50% オーバーラップRTF 1.6〜4.8 倍5〜14 時間

→ 現実的でない。 しかも本開発機は 12 スレッドと強めで、 利用者の PC はより遅い想定が必要。これは試算 (実測ではない) ですが、 桁を外していないはずです。

緩和できる要素

手効果
無音カット後の音声に対して実行入力長が実測で 3〜7 割に減る (素材次第)
VAD で発話区間だけ分離さらに短縮。既に Silero VAD の仕組みがある
16kHz モノラルで足りる TUSS では使えない (48kHz バンド分割前提のため、16kHz 入力は学習と不一致)。 軽量な代替モデルなら効く
FasTUSS (−81% 演算) 重みが非公開のため我々では使えない (自前学習は非現実的 / §4.3)
GPU を使うCUDA 不使用方針 (配布サイズ 1.93GB) の覆しが必要

4.3 自前で学習し直す案は非現実的

  • 学習データに WSJ0 (LDC の有償ライセンス)、MOISESDB (要手動取得)、 WHAMR! (要シミュレーション)、FSD50K / FMA / MUSDB-HQ / DnR / VCTK-DEMAND / LibriVox (URGENT 2024) を使用。
  • 学習は 150 エポック × 2.5k ステップ、バッチ 8。GPU クラスタ前提の規模。

→ 学習は選択肢に入りません。 使うなら公開重みをそのまま使う以外にない。

4.4 効果の不確実性 (第 3 の壁)

  • 4 本の論文はすべて SI-SNR / SNR のみで評価。 文字起こし精度の評価が無い。
  • 一方で我々が本当に知りたいのは「ゲーム実況の日本語 CER がどれだけ下がるか」。
  • 分離音は「人が聞いて綺麗」でも、認識器にとっては学習時の分布から外れた音になり得る。

→ 測らずに実装してはいけない部分です (§7)。

7. 先にやるべき計測 (実装前の 1〜2 日)

目的: 「ゲーム実況の日本語 CER が、分離前処理でどれだけ下がるか」を数字にする。

  1. 素材を 3 本選ぶ — BGM が大きい回 / 効果音が多い回 / 静かな雑談回。各 10 分。
  2. 正解を作る — 各素材 10 分を手で書き起こす (または既存テロップを手で直したものを正解とする)。
  3. 4 条件で認識する
    #条件
    ①現状のまま (ベースライン)
    ②Demucs の vocals を認識へ入力
    ③DeepFilterNet の強調音を認識へ入力
    ④(参考) TUSS medium の speech を認識へ入力 ※検証用にローカルで試すだけ。配布はしない
  4. 測る指標 — CER (文字誤り率) / 取りこぼし (未検出発話) / ハルシネーション件数 / 処理時間 (RTF)。
  5. 判定 — CER が 相対 10% 以上下がり、 処理時間が許容内 (例: 元動画の 0.3 倍以内) の条件があれば実装へ。 無ければ 実装しない (§8 の軽い手を先に試す)。

④ の TUSS を手元で試すこと自体は AGPL 上問題ありません (頒布しないため)。 「我々の技術の上限はどこか」を知る基準値として測る価値があります。

9. まとめ

  • PDF の技術は TUSS。プロンプトで「声・音楽・効果音」を指定して分ける単一モデルで、 ゲーム実況アーカイブの音と問題設定が一致しており、着眼点は正しいと考えます。
  • コードと学習済み重みは公開済みで、我々の配布物には torch / torchaudio が 既に入っているため、「技術的に動かせるか」という問いには 動かせる が答えです。
  • ただし AGPL-3.0 と 音声 1 秒あたり 43.1 GMAC (CPU 専用配布) の 2 点で、TUSS そのものを製品へ入れるのは現実的でない。
  • 目的 (文字起こし精度) は、MIT / Apache-2.0 の軽量な分離を「認識専用の前処理」として入れる 形で狙うのが現実的 (§5 案B / §6)。 出力動画の音は触らないため音質リスクは発生しません。
  • ただし効果は未検証です。論文は音質指標しか測っておらず、 分離が認識を悪化させる例も知られています。 §7 の A/B 計測を先に回し、CER が実際に下がった方式だけを実装する ことを提案します。
