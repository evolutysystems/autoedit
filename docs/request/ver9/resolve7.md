# ver9 resolve7 — Timeline 編集画面が重い原因の特定と対策 (ドラッグ中の描画 / 絵の取り直し)

報告: 2026-10-26 のチャット
> プレビュー、テロップ移動、テロップ範囲の修正など大体の動きが重い。
> **テロップの内容を編集するときは重くない。**

対象: `src/gui/timeline/timeline_view.py` / `preview_panel.py` / `src/timeline/builder.py`
調査日: 2026-10-26 (main `115e257` / v1.6.1 + ver9 resolve5・resolve6 実装後)
計測環境: 実プロジェクト `vod_2910070011` (要素 499 件 / 素材 1920x1080 / 画面 1600x700)
種別: **調査報告 + 修正記録**。§5 に実装した対策、§6 に残した対策

## 0. 先に結論

### 0.1 3 行で

1. **重いのは描画とデコードで、モデル側ではない。** 履歴のスナップショットもコマンド実行も
   波形の計算も **1.5ms 以下**で、原因から外れた (§2.3)。
2. **原因は 2 つ。** ① Timeline の再描画が **14〜27ms** かかり、ドラッグ中はマウスを
   動かすたびに走るのでマウスの 8〜16ms 間隔に追いつかない。
   **描画時間の半分以上が波形**だった (§2.1)。
   ② プレビューのフレーム取得が **32〜44ms** かかり、編集のたび・再生ヘッドを
   動かすたびに走る (§2.2)。
3. **「内容編集だけ軽い」のはドラッグを伴わないから。** 重い処理が確定時の 1 回で済む。
   逆に移動・トリムは掴んでいる間ずっと①が走り、離した瞬間に②が走る (§3)。

### 0.2 実装した対策と効果

| 対策 | 内容 | 効果 (実測) |
| --- | --- | --- |
| **A** | ドラッグ中は波形を描かない | 描画が **1.9〜3.2 倍速**。zoom 50 で 14.6→6.7ms (149fps 相当) |
| **D** | 編集後の絵の取り直しもまとめる (即時をやめる) | 連続操作で走るデコードの回数が減る |
| **E** | `update_debounce_ms` を 60 → 100 | スクラブ中のデコードが途切れず走る状態を解消 |

## 1. 計測の方法

実機の GUI では「どこが遅いか」を数字で切り分けられないため、
実プロジェクトを読み込んだうえで処理ごとに時間を測った。

| 対象 | 測り方 |
| --- | --- |
| 履歴・コマンド・波形の計算 | モデルを直接呼んで 20〜200 回の平均 |
| Timeline の再描画 | `QImage` へ `render()` し、ズーム別に 8〜12 回の平均 |
| フレームのデコード | `frame_source.create_frame_source()` で実素材から取得 |

`QT_QPA_PLATFORM=offscreen` で測っているため、実機の GPU 合成ぶんは含まれない。
ただし Qt の `QPainter` は CPU 描画なので、描画時間そのものは実機と近い。

## 2. 実測結果

### 2.1 Timeline の再描画 (ドラッグ中の重さの原因)

| ズーム | 波形あり | 波形なし | 波形のぶん |
| --- | --- | --- | --- |
| 5 px/秒 (全体表示) | **27.4 ms** (37fps) | 13.8 ms | +13.6 ms |
| 20 px/秒 | **20.1 ms** (50fps) | 13.9 ms | +11.2 ms |
| 50 px/秒 (編集でよく使う) | **14.6 ms** (69fps) | 8.0 ms | +6.4 ms |
| 200 px/秒 | **11.0 ms** (91fps) | 4.3 ms | +12.0 ms |

**描画時間の半分以上が波形**である。一方、波形の**計算**は 0.01〜0.03ms しかかからない
(§2.3)。遅いのは計算ではなく、**列ごとに `QLine` を立てて描く部分**だった。

ドラッグ中は `mouseMoveEvent` が `_drag_preview` を更新して `update()` を呼ぶため
(`timeline_view.py:864`)、**マウスを動かすたびに画面全体を描き直す**。
マウスは 8〜16ms 間隔でイベントを出すので、1 回 14〜27ms の描画では追いつかない。

### 2.2 プレビューのフレーム取得 (プレビューの重さの原因)

| 取り方 | 時間 | 走る場面 |
| --- | --- | --- |
| 同じ位置を繰り返し (キャッシュ) | 0.00 ms | 同じコマへ戻ったとき |
| 0.1 秒ずつ前進 (読み進め) | 6.6 ms | 再生中 |
| **5 秒シーク** | **32.5 ms** | **編集のたび・再生ヘッドの移動** |
| **後ろへ 2 秒戻る** | **43.6 ms** | 戻し操作・Undo の直後 |
| 別素材へ切り替え | 38.6 ms | クリップを跨ぐとき |

取得はワーカースレッドで走るので UI は固まらないが、CPU を食い、
**結果が届くまで絵が変わらない**ため「反応が遅い」と体感される。

#### なぜ毎回デコードするのか

`timeline.preview.proxy.mode` が **`"off"`** になっている。
これは **ver8 resolve8 §24-8 での意図的な判断**で、再生中にタイルの継ぎ目で
暗転する不具合を消すため v1.5.9 で全員へ適用したものである。

ただし当時**推奨された案b「停止中だけタイルを使う」は未実装**のままなので、
現在は停止中もプロキシの恩恵が無く、常にこの経路を通る。

### 2.3 原因から外れたもの (いずれも 1.5ms 以下)

| 処理 | 時間 |
| --- | --- |
| 履歴のスナップショット (`_snapshot` / Timeline 全体の複写) | 1.00 ms |
| `_restore` | 0.01 ms |
| `timeline.normalize()` | 0.11 ms |
| コマンド 1 回 — 内容の編集 (`EditSubtitle`) | 1.52 ms |
| コマンド 1 回 — 位置の変更 (`MoveOverlay`) | 1.31 ms |
| 波形の列計算 (`Peaks.columns` / 1200 列) | 0.01 ms |
| 同 (180 秒ぶんから 1200 列) | 0.03 ms |

**内容編集と位置変更のコマンドはほぼ同じ時間**である。
つまり体感の差はモデル側では説明できず、GUI 側 (§2.1 / §2.2) にある。

## 3. 「内容編集だけ軽い」理由

| 操作 | ドラッグ中 | 確定時 |
| --- | --- | --- |
| テロップの内容編集 | **なし** | コマンド 1.5ms + デコード 32〜44ms + 描画 |
| テロップの移動 (プレビュー) | シーンの再描画 | 同上 |
| テロップの移動・範囲修正 (Timeline) | **画面全体の描画 14〜27ms × マウス移動の回数** | 同上 |
| 再生ヘッドのスクラブ | 同上 + デコード | — |

内容編集は**ドラッグを伴わない**ので、重い処理が確定時の 1 回で済む。
移動・トリムは掴んでいる間ずっと描画が走り、離した瞬間にデコードが走る。

## 4. 対策の候補 (検討した全体像)

| # | 対策 | 効果 | 規模 | 判断 |
| --- | --- | --- | --- | --- |
| **A** | ドラッグ中は波形を描かない | 描画が 2〜3 倍速 | 小 | **実装した** |
| B | 波形を `QLine` の列から塗り (`QPainterPath`) へ変える / 列を間引く | 常時効く | 小〜中 | 見送り (§6) |
| C | ドラッグ中の再描画を変更範囲だけにする (`update(rect)`) | 全クリップの走査が消える | 中 | 見送り (§6) |
| **D** | 編集後のフレーム取得もデバウンスする | 連続操作の無駄なデコードが消える | 小 | **実装した** |
| **E** | `update_debounce_ms` を 60 → 100 | スクラブ中のデコード回数が減る | 設定値のみ | **実装した** |
| F | プロキシの案b (停止中だけタイルを使う) | 停止中が軽くなり出力とも一致 | 中〜大 | 見送り (§6) |

A・D・E はいずれも**既知の不具合 (再生中の暗転など) を再発させない**範囲に収まる。

## 5. 実装した対策

### 5.1 対策A — ドラッグ中は波形を描かない

```python
# src/gui/timeline/timeline_view.py  _paint_waveform の冒頭
if self._waveform_hide_while_dragging and self._drag != _DRAG_NONE:
    return
```

- `_drag` はクリップの移動・左右のトリム・再生ヘッドのスクラブで立つ。
  **掴んでいる操作すべてで省く**。
- 離せば `_drag` が `_DRAG_NONE` へ戻り、次の描画で元どおり出る。
  「波形が消えたまま」にならないことをテストで固定した (§7)。
- 設定 `timeline.waveform.hide_while_dragging` (既定 `true`) で元の挙動へ戻せる。

**効果 (実測)**

| ズーム | 通常 | ドラッグ中 | |
| --- | --- | --- | --- |
| 5 px/秒 | 27.4 ms (37fps) | **14.3 ms (70fps)** | 1.9 倍速 |
| 20 px/秒 | 20.1 ms (50fps) | **8.9 ms (112fps)** | 2.2 倍速 |
| 50 px/秒 | 14.6 ms (69fps) | **6.7 ms (149fps)** | 2.2 倍速 |
| 200 px/秒 | 11.0 ms (91fps) | **3.4 ms (293fps)** | 3.2 倍速 |

編集でよく使うズーム (20〜200 px/秒) では 3.4〜8.9ms になり、
**マウスのイベント間隔 (8〜16ms) に収まる**。

### 5.2 対策D — 編集後の絵の取り直しもまとめる

```python
# src/gui/timeline/preview_panel.py  _on_timeline_changed
self._update_time_label()     # 時刻表示だけは即時
self._schedule_refresh()      # 絵は update_debounce_ms ぶんまとめる
```

以前はここだけ `_refresh_all()` で**即時**だった。再生ヘッドの移動には
既にデバウンスがあったのに、編集には無かったため、続けて操作すると
1 回ごとにデコード (32〜44ms) が走っていた。

`_schedule_refresh` は「前回から `update_debounce_ms` 以上たっていれば即時、
そうでなければ残り時間だけ待って 1 回にまとめる」ため、
**単発の編集は今までどおり即時に反映される**。連続操作のときだけ間引かれる。

音声バッファとプロキシの無効化は従来どおり行う (ここを飛ばすと古い音・古い絵が残る)。

### 5.3 対策E — `update_debounce_ms` を 60 → 100

プロキシが off の環境ではフレームの取り直しに 32〜44ms かかる。
60ms 間隔では**デコードがほぼ途切れずに走り続ける**ため、100ms へ上げた。

変更箇所は 3 つ (既定値が 2 か所にあるため両方を揃える):

| ファイル | 内容 |
| --- | --- |
| `src/timeline/builder.py` | `preview.get("update_debounce_ms", 100)` |
| `src/settings/settings_window.py` | `DEFAULT_SETTINGS` の値 |
| `src/settings/setting.json` | 実際に使う値 |

### 5.4 変更したファイル

| ファイル | 内容 |
| --- | --- |
| `src/timeline/builder.py` | `waveform.hide_while_dragging` を追加 / `update_debounce_ms` の既定を 100 へ |
| `src/gui/timeline/timeline_view.py` | ドラッグ中は `_paint_waveform` を抜ける |
| `src/gui/timeline/preview_panel.py` | `_on_timeline_changed` をデバウンス経路へ |
| `src/settings/settings_window.py` / `setting.json` | 既定値 |
| `tests/test_timeline_drag_perf.py` | **新規** 10 件 |

テストは **1910 件すべて成功** (追加前 1900 件 → 10 件追加)。

## 6. 残した対策 (未実装)

| # | 対策 | なぜ今回やらなかったか |
| --- | --- | --- |
| **B** | 波形を塗りで描く / 列を間引く | A でドラッグ中は解決した。常時の描画 (14.6ms / 69fps) は操作に追いつく水準にある。見え方が変わる変更なので、必要になってから行う |
| **C** | ドラッグ中の部分再描画 (`update(rect)`) | A で 3.4〜8.9ms まで下がり、部分描画の必要性が薄れた。実装すると「どの範囲を汚したか」の管理が増え、描き残しの不具合を生みやすい |
| **F** | プロキシの案b (停止中だけタイルを使う) | §2.2 の根本的な解決で、**停止中のプレビューが軽くなり出力とも一致する**。ただし ver8 resolve8 §24 の暗転と同じ機構に触るため、設計から起こす必要がある |

**次に効くのは F** である。停止中のフレーム取得 (32〜44ms) がタイルの読み出しに置き換わり、
プレビューの反応が変わる。着手するなら resolve8 §24-7 の推奨案bをそのまま設計へ起こす。

### 7.1 手で確かめる

1. Timeline でテロップを掴んで動かす → **掴んだ瞬間に波形が消え、離すと戻る**こと
2. 同じ操作が以前よりなめらかに追従すること
3. クリップの左右端を掴んでトリムしても同じであること
4. 再生ヘッドをドラッグ (スクラブ) してもなめらかであること
5. 編集を 1 回だけ行ったとき、絵がすぐ (100ms 以内に) 反映されること
6. 続けて何度も編集したとき、絵の取り直しがまとめられること
7. 再生中の表示に暗転が出ていないこと (プロキシ off の挙動を変えていないことの確認)
