# ver9 resolve6 — V1 クリップの拡大率 (数値入力) と、拡大中のドラッグによる配置移動

## 2. 設計方針

> **V1 の `transform.scale` / `x` / `y` を `compositor` の「ソース → キャンバス段」で効かせる。
> 100% のときは、生成されるフィルタ文字列を 1 文字も変えない。**

`compositor` は「合成の計算を持つ唯一の場所」という規約を持つ (`compositor.py:8-14`)。
ここへ入れれば、書き出し (`renderer`)・プロキシ (`proxy_render`)・高精度プレビュー
(`preview_panel`) の 3 経路すべてに同じ計算が行き渡る。
**片方へ直接書いてはならない**というこの規約が、本件でそのまま効く。

## 3. 決めること

### 3.1 【最重要】V1 の 100% は「キャンバスへ収めた状態」

| | オーバーレイ (既存) | V1 (本件) |
| --- | --- | --- |
| `scale` の基準 | キャンバス**幅**に対する比率 | **キャンバスへ収めた状態 (fit) に対する倍率** |
| 100% の意味 | 画面の横幅いっぱい | **今の見た目のまま** |
| 根拠 | `compositor.py:253` `target_w = profile.width * scale` | 要望「デフォルトは 100%」 |

同じ `transform.scale` という欄を、トラックによって違う基準で読む。
**これは危険なので、次の 3 つで担保する。**

1. V1 とオーバーレイは `track.is_base` で構造的に分かれ、同じクリップが両方になることはない。
2. 読み書きする関数を**それぞれ 1 つに限る** (`base_zoom_filters` / `overlay_chain`)。
3. コメント・ツールチップ・設定キー名のすべてで「拡大率 (zoom)」と「大きさ (scale)」を
   **言葉から分ける**。UI のラベルも V1 は「拡大率」、オーバーレイは「大きさ」とする。

> 別案として V1 用に `transform.zoom` を新設する手もあるが採らない。
> 保存形式・プロキシ署名・コピー/貼り付け・Undo の経路がもう 1 本増えるのに対し、
> 得られるのは「名前が別」だけで、上の 3 点で足りる。

### 3.2 100% のときは 1 文字も変えない

`still_filters` には「素材の規格がキャンバスと一致すればフィルタを足さない」という
性質があり (`compositor.py:150` / `tests/test_compositor.py:147`)、
ここが崩れると**既存プロジェクトの出力が全部変わる**。

→ `abs(zoom - 1.0) <= _ZOOM_EPS` かつ位置指定なしのときは、**従来の分岐へそのまま落ちる**。
既存テストがこの性質を守る。新しいテストでも「100% では従来と同一文字列」を固定する (§7)。

### 3.3 拡大と縮小のフィルタ

キャンバスを `W×H`、素材をキャンバスへ収めた寸法を `fw×fh`、拡大率を `z` とする。

```
scale=<fw*z>:<fh*z>                     ← 収めた寸法の z 倍 (縦横比は維持)
  はみ出す軸 → crop=<cw>:<ch>:<ox>:<oy>  ← 切る (見せる場所を ox/oy が決める)
  足りない軸 → pad=W:H:<ox>:<oy>:black   ← 余白を足す (置く場所を ox/oy が決める)
```

**crop と pad は「どちらか」ではなく、軸ごとに要否が違う** (実装で判明 / §10.2)。
例えば 4:3 素材を 110% にすると、**高さは余って幅は足りない**。
`z > 1 なら crop、z < 1 なら pad` と分岐すると、この場合に
「入力が余白の内に収まらない」と FFmpeg が失敗する。
よって crop (はみ出す軸) と pad (足りない軸) を**両方**通し、
それぞれ必要なときだけ出す。

- `fw×fh` は `scale=W:H:force_original_aspect_ratio=decrease` と同じ計算を
  **数値で**求める (`fit = min(W/mw, H/mh)`)。素材寸法は `media.width/height` にある。
- **幅と高さ**は必ず偶数へ丸める (`compositor._even` / yuv420p の制約)。
  **座標は偶数へ丸めない。** 座標まで偶数にすると、プロキシ (本番の 1/2 寸法) で
  丸め先が食い違って本番との相似が崩れる (実装で判明 / §10.2)。
  座標が奇数のときのクロマの半画素ずれは視覚的に判別できない。
- `z < 1` の余白は**黒**とする (回答 #1)。ぼかし背景は縦動画の `crop` が持つ機能で、
  そこと二重に持つと「どちらの指定が効いているか」が分からなくなる (§3.6)。
- `setsar=1` / `fps` / `format=yuv420p` は従来の正規化と同じものを後段へ残す。

### 3.4 配置 (`x` / `y`) の意味と可動範囲

`transform.x/y` は「キャンバス中心を原点とする正規化座標 (-1.0〜1.0)」(`model.py:104`)。
V1 では**拡大した映像の中心をキャンバス中心からどれだけずらすか**として使う
(オーバーレイの「クリップ中心の位置」と同じ考え方なので、座標系を足さずに済む)。

可動範囲は**黒帯が出ない範囲に丸める**:

```
z > 1: |offset_px| <= (拡大後の寸法 - キャンバス) / 2      ← 端を越えると黒帯が出る
z < 1: |offset_px| <= (キャンバス - 縮小後の寸法) / 2      ← 余白の中だけ動かせる
z = 1: 動かせない (そもそも欄も出さない)
```

丸めは**モデル側 (コマンド)** で行う。画面側だけで丸めると、数値入力で拡大率を下げたときに
前の位置が範囲外のまま残る。拡大率を変えたときも位置を同じ式で丸め直す。

### 3.5 コマンドは新設する (既存の除外を外すのではなく)

| コマンド | ラベル | 役割 |
| --- | --- | --- |
| `ZoomBaseClip(clip_id, zoom)` | 「拡大率の変更」 | V1 クリップの `transform.scale` を変える。範囲は V1 用の設定で丸める。位置も §3.4 で丸め直す |
| `MoveBaseClip(clip_id, x, y)` | 「表示位置の変更」 | V1 クリップの `transform.x/y` を変える。§3.4 で丸める。`zoom == 1.0` のときは**何もしない** (履歴も汚さない) |

`ResizeOverlay` / `MoveOverlay` は**触らない**。基準 (§3.1)・可動範囲 (§3.4)・
許容する値の範囲が違うため、同じコマンドに相乗りさせると分岐だらけになる。
どちらも既存の「ドラッグ確定時に 1 回だけ積む」規約に合わせる。

### 3.6 縦動画の切り抜き (crop) とは併用しない

縦動画プロジェクトの `crop` は「ソースのどこを切り抜いて、縦キャンバスのどこへ置くか」を
既に持ち、`crop_chain` が正規化を兼ねている (`compositor.py:167`)。
拡大率と役割がまるごと重なるため、**crop 指定があるときは拡大率を適用せず、欄も出さない**。

→ `crop.load(timeline)` が有効な指定を返す場合、V1 の拡大率 UI は「縦動画の切り抜きで
位置と大きさを指定しています」と出して無効にする。既存プロジェクトの挙動は変わらない。

### 3.7 ドラッグできる条件

プレビューは**再生ヘッド位置**のフレームを映すが、V1 クリップはカットごとに複数ある。
取り違えを防ぐため、ドラッグは次の条件がすべて揃ったときだけ受ける:

1. 再生ヘッド位置にある V1 クリップが**選択中**であること
   (見えていないクリップを動かさない / 選んでいないクリップを動かさない)
2. そのクリップの拡大率が 100% でないこと (要望どおり)
3. 縦動画の切り抜き指定が無いこと (§3.6)

条件を満たすときだけカーソルを `OpenHandCursor` にし、満たさない間は従来どおり
`BaseFrameItem` を触れないままにする。**「掴めるかどうかが見た目で分かる」**ことを守る。

### 4.6 プロキシとの二重適用を避ける

プレビューのフレームには 2 系統ある (`preview_panel.py:673` の `from_proxy`)。

| フレームの出どころ | 拡大率の扱い |
| --- | --- |
| プロキシのタイル由来 | **何もしない**。`compositor` 経由で既に焼かれている |
| 素のフレーム (プロキシが無い間) | Qt 側で `setScale` / `setPos` により近似表示する |

これはオーバーレイの `_draft_visible` (`preview_items.py:165`) と同じ考え方で、
「出力と一致する絵が在るならそれを見せ、無い間は近似を見せる」という既存の構えに乗せる。

```json
  }
}
```

| キー | 意味 |
| --- | --- |
| `enabled` | false で拡大率の欄を出さない (切り戻し用) |
| `min` / `max` | 拡大率の範囲。**縮小を許すため `min` は 1.0 未満** (回答 #1)。
オーバーレイの `0.02〜4.0` とは意味が違う (§3.1) ため分けて持つ |
| `step_percent` | 数値入力の増減幅 |

縮小 (100% 未満) を許す。余白は黒で埋める (§3.3)。
`min` を 0.1 とするのは、それ以下では映像が点になり編集の役に立たないため。

### 4.8 Resolve 出力 (FCPXML)

`fcpxml_builder` は `adjust-transform` (scale / position) を書く仕組みを
透かし用に持っている (:520-537)。V1 クリップへも同じ要素を足し、拡大率を反映する。

換算 (FCPXML の座標系は素材寸法基準・キャンバス中心原点):

```
scale    = fit * z          ← fit = min(W/mw, H/mh)。素材寸法に対する倍率
position = (x * W/2, -y * H/2)   ← Y は FCPXML が下向き正
```

**ここは実機確認が必要な唯一の箇所**である (回答 #4 により実装する)。
DaVinci Resolve の読み込み結果を見ないと、倍率の基準 (素材寸法かキャンバスか) と
Y の符号は最終的に確定できない。そこで:

- 換算は **1 つの関数** (`fcpxml_builder` へ渡す前の変換) に閉じ、符号や基準を
  直すときに 1 か所で済むようにする。
- 100% かつ位置指定なしのクリップには **`adjust-transform` を書かない**。
  既存プロジェクトの FCPXML が 1 バイトも変わらないようにするため。
- 実機で食い違ったときに戻せるよう、設定 `export.resolve.write_base_transform`
  (既定 true) で出力を止められるようにする。

### 5.1 字幕とぼかしは一緒に拡大されない (重要)

拡大は「ソース → キャンバス段」で効く。字幕・コメントアイコン・ぼかし・透かしは
その後段でキャンバスへ載るため、**V1 を拡大しても字幕の大きさと位置は変わらない**。

これは意図した挙動とする。字幕は視聴者が読むためのもので、映像の拡大に合わせて
大きくなったり画面外へ出たりするべきではない。
ただし**ぼかし**は話が別で、ぼかす座標は素材の位置を指しているため、
拡大すると**ぼかす場所がずれる**。回答 #3 により今回は追従させない (§8.1)。

### 8.1 残課題 — ぼかしと拡大率の併用 (回答 #3 により今回は扱わない)

ぼかしの指定は**素材の座標**で持たれており、拡大率は考慮されない。
そのため拡大・縮小したクリップでは**ぼかす位置がずれる**。

今回は追従させない。併用したときは利用者が見て気づける種類のずれ
(ぼかしが人物から外れる) であり、ぼかしと拡大率を同じクリップで使う場面も
現状では想定しにくいためである。必要になった時点で、ぼかし座標へ
同じ変換を掛ける設計を別に行う。

## 9. やらないこと

| 項目 | 理由 |
| --- | --- |
| 回転・不透明度 | `Transform` に欄はあるが要望外。V1 で使う場面が思い当たらない |
| 縦横比を崩す拡大 | `transform.scale` がスカラー 1 つであることで**構造的に**保たれる。既存のオーバーレイと同じ担保 (`commands.py:1411`) |
| 時間変化するズーム (キーフレーム) | 「クリップに 1 つの拡大率」の範囲を超える。必要なら別要望として設計する |
| ドラッグでの拡大 (四隅ハンドル) | V1 はキャンバスを埋めるものでハンドルを掴む余地が画面外になる。数値入力とドラッグ移動で足りる |
| `transform` の意味を V1 とオーバーレイで統一する作り直し | 既存のオーバーレイの出力が変わる。得るものより危険が大きい (§3.1) |
