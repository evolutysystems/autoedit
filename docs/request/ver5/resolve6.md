### 0.2 実装状況 (2026-09-21)

**Phase 1〜5 をすべて実装した。**確認事項は §10 のとおり「すべて推奨どおり」で決定した。
全テスト (896 件 = 既存 867 + 新規 29) が通る。

実装で本書の案から変えたことは次の 2 点。

| 項目 | 本書の案 | 実装 | 理由 |
| --- | --- | --- | --- |
| 自動修復の範囲 | 控えの**無い**素材だけを穴埋めで復元する | **加えて、セクションの控えからそのまま引ける素材も素材単位の控えへ写す** | 写さないと、次に統合したときにその素材まで控えを失う。1 回開いて保存すれば、以後はプロジェクト単体で完結する |

### 0.3 一言でいうと

セクション追加の設計は**「1 セクション = 1 素材」**を前提にしている。
ところが**統合 (merge)** は 1 つのセクションに 2 本以上の素材をぶら下げる。
この食い違いが B1・B2 を生み、同じ「セクション = 区間」という粗い見方が B3 を生んでいる。

## 2. 現状分析

### 2.1 セクション追加が作るもの

「セクション追加...」を押すと、次の順で処理が進む。

| 段 | 実装 | やること |
| --- | --- | --- |
| ① 計画 | `timeline_builder.plan_section_add` (`:524`) | 既存セクションとの重なりを見て、**用意すべき区間**と**統合先**を決める |
| ② 準備 | `_SectionPrepareWorker` → `clip_writer.prepare_one_clip` (`:410`) | VOD から切り出し → 正規化 → 音量解析 → 編集点検出 → 文字起こし。出力は `<workdir>/clip<N>/normalized.mp4` |
| ③ 挿入 | `AddArchiveSection._insert_one` (`:655`) | 素材をメディアプールへ足し、V1・音声・字幕へクリップを並べ、**`source.archive.clips` へセクションの控えを 1 件足す** |
| ④ 統合 | `AddArchiveSection._merge_sections` (`:738`) | 重なった既存セクションと番号を揃え、**控えを 1 件へ畳む** |

控え (`source.archive.clips` の 1 件) は次の形である。

```jsonc
{"index": 4, "vod_start": 1411.0, "vod_end": 1591.0, "media_id": "m8",
 "media_role": "normalized", "timeline_start": …, "timeline_end": …, "score": …, "theme": …}
```

**`media_id` が 1 つしか無い。**これがすべての起点になっている。

### 2.2 B1・B2 の原因 — 統合が「素材の復元情報」ごと畳んでいる

`_merge_sections` (`:738`) は、畳む側の控えを**落とす**。

```python
for entry in meta:
    if entry.get("index") == target:
        entry["vod_start"] = span_start
        entry["vod_end"] = span_end
        kept.append(entry)
    elif entry.get("index") in merged:
        continue                 # 代表へ畳む      ← ★ ここで media_id ごと消える
    else:
        kept.append(entry)
meta[:] = kept
```

一方で、畳まれた側の**素材はメディアプールに残り、クリップも残る**
(クリップは `origin[ORIGIN_ARCHIVE_INDEX]` を代表番号へ書き換えるだけ)。
結果、**「Timeline が使っているのに、控えがどこにも無い素材」**ができる。

この素材が効かなくなる場所は 2 つある。

**(1) 音声サイドカーが保存されない**

`ArchiveTimelineDialog._media_to_copy` (`:150`) は控えを回って素材を集める。

```python
for entry in (archive_timeline.archive_section(timeline).get("clips") or []):
    media_id = str(entry.get("media_id", "") or "")
```

控えに無い素材はここに現れないため、`<プロジェクト>.media/` へサイドカーが作られない。

**(2) 開き直しのときに復元できない**

`project_resume.make_media_recover.recover_one` (`:57`) も控えを引く。

```python
entry = next((c for c in clips if c.get("media_id") == media.id), None)
if entry is None:
    return None                 # アーカイブのクリップ素材ではない (画像など)
```

控えに無い素材は `None` が返る。素材の実体は実行のたびに作り直される一時フォルダ
(`%TEMP%\archive_clips_<ランダム>\clip<N>\normalized.mp4`) にあり、既に消えている。
よって `media_recovery.recover` (`:42`) は最後の手段へ落ち、
`missing_media_dialog` (`:54`) の

> このプロジェクトが使っている動画素材が元の場所にありません。

が開く。**これが B1 の本体であり、「復元できる素材とできない素材が混ざる」B2 そのものである。**

### 2.3 B1 のもう 1 つの原因 — 使っていない素材も尋ねられる

`media_recovery.recover` (`:42`) は **`timeline.media_pool` を全件**回る。
どのクリップからも参照されていない素材でも、実体が無ければ差し替えを尋ねる。

セクション追加は素材をメディアプールへ足すが、**プールから外す経路が無い**。
追加したセクションのクリップを削除しても、統合で番号が変わっても、素材はプールに残る。
開き直すたびに一時フォルダは変わるため、**残骸のぶんだけダイアログが増える**。

### 2.4 B3 の原因 — 「使用中」が作成時の宣言区間を見ている

`plan_section_add` (`:524`) は、控えの `vod_start` / `vod_end` をそのまま「使用中の区間」として扱う。

```python
covered = [(float(e.get("vod_start", 0.0)), float(e.get("vod_end", 0.0))) for e in touched]
ranges = _subtract_covered(span_start, span_end, covered)
if not ranges:
    return None                      # 既存セクションに完全に含まれている
```

しかし `vod_start` / `vod_end` は**セクションを作ったときに宣言した範囲**であり、その後に

* **無音カット**で区間が刻まれても
* 利用者が Timeline 上で**クリップを削除・トリム**しても

更新されない。よって「もう Timeline に無い区間」も「使用中」のままになる。
`plan` が `None` になると、画面は

> 指定した区間は既にセクションに含まれているため、追加するものがありません。

を出す。**これが B3 である。**

### 2.6 なぜ素材のパスが毎回変わるのか (前提)

`project_resume` (`:209`) は開くたびに

```python
with tempfile.TemporaryDirectory(prefix="archive_clips_", ignore_cleanup_errors=True) as workdir:
```

で**新しい一時フォルダ**を掘り、そこへ VOD から切り直す。
セクション追加の素材もこの `workdir` に置かれる (`clip_workdir`)。
よって**保存された素材パスは、次にアプリを起動した時点で必ず存在しない**。
復元は「パスを探す」のではなく「VOD から作り直す」しかなく、そのために控えが要る。

依頼者のプロジェクトに `f327g2gm` / `g_e62q30` / `t8y90d44` / `3w1it4gp` の
4 世代のパスが混在しているのは、この仕組みのとおりである。

## 3. 方式選定

### 3.1 素材の復元情報をどこに持つか (Q1 / B1・B2)

| 案 | 内容 | 判定 |
| --- | --- | --- |
| A | `_merge_sections` で控えを畳まない (セクションを分けたまま持つ) | **不可**。統合は「1 セクションに見せる」ことが目的。控えを分けたままにすると、クリップバー・テーマ・使用可否・書き出しがすべて 2 件として振る舞う |
| B | 控えに `media_ids: [...]` を足す | 惜しい。復元には素材ごとの **VOD 区間**が要るため、ID だけでは足りない |
| **C (採用)** | **`source.archive.media` を新設し、素材 1 本ごとに「どの VOD 区間から作ったか」を持つ** | 採用。セクションの見せ方 (`clips`) と素材の作り方 (`media`) を分ける。統合は `clips` だけを畳み、`media` には触らない |

**C の要点**は「控えの役割を 2 つに分ける」ことである。

| 置き場 | 役割 | 統合で畳まれるか |
| --- | --- | --- |
| `source.archive.clips` | **セクションの見せ方** (区間・スコア・テーマ・使用可否の単位) | 畳まれる (今までどおり) |
| `source.archive.media` (新設) | **素材の作り直し方** (どの VOD 区間から切ったか) | **畳まれない** |

ver5 resolve4 で `store.media_key` を「素材の由来」で作ったのと同じ考え方である。
**「見せ方」と「作り方」を同じ 1 件に相乗りさせていたことが、今回の不具合の構造的な原因**だった。

### 3.2 既に壊れているプロジェクトをどう救うか (Q2 / B2)

新しい控えを足しても、**既に保存されてしまったプロジェクトには情報が無い**。
依頼者のプロジェクトがまさにそれで、m10 の VOD 区間はどこにも書かれていない。

| 案 | 判定 |
| --- | --- |
| 何もしない (今までどおり差し替えを尋ねる) | 不可。差し替え先の一時ファイルは既に消えており、利用者にできることが無い |
| 該当クリップを黙って無効化する | 不可。利用者が足したセクションが黙って消える |
| **穴埋めで復元する (採用)** | 採用。**セクションの宣言区間のうち、控えを持つ素材が埋めていない「穴」**へ、控えの無い素材を尺で突き合わせる |

**復元の手順** (§5.4):

1. セクションの宣言区間 `[S, E]` を取る
2. そのセクションのクリップのうち、**控えを持つ素材**が覆う VOD 区間を求める
3. `[S, E]` から 2 を差し引いた「穴」を求める
4. 控えの無い素材の**尺**と穴の長さを突き合わせ、**候補が 1 つに決まるときだけ**採用する
5. 決まらなければ採用しない (今までどおり尋ねる)。理由をログへ残す

**依頼者のデータで検証した結果:**

| 項目 | 値 |
| --- | --- |
| clip4 の宣言 | 1411–1591 |
| 控えを持つ m8 が覆う範囲 | 1411–1523 |
| 残る穴 | **1523–1591 (68 秒)** |
| 控えの無い m10 の尺 | **71.1 秒** |
| 判定 | 穴は 1 つ・尺がほぼ一致 → **m10 の `vod_start` = 1523 として復元できる** |

尺が 3 秒長いのは、`clip_writer.cut_region` が `-c copy` でキーフレームへ吸着するためで、
切り出しは常に要求より**少し前から・少し長く**なる。許容は
`max(切り出しの吸着幅, 長さの 10%)` を見込む (§5.4)。

### 3.3 使っていない素材の扱い (Q3 / B1 (b) / R3)

| 案 | 判定 |
| --- | --- |
| **復元時に尋ねない (採用・必須)** | どのクリップからも参照されていない素材は、無くても Timeline は成立する。**尋ねる意味が無い** |
| **保存時にプールから外す (採用)** | 残骸が溜まり続けるのを止める。**保存する JSON からだけ外し、開いている Timeline には触らない** (Undo 履歴を壊さない) |
| プール編集の UI を足す | 範囲外 |

2 つとも入れる。前者だけだと残骸は残り続け、後者だけだと既存プロジェクトが救われない。

> **注意**: 外してよいのは「どのクリップからも参照されていない素材」だけである。
> **無効 (enabled=False) なクリップが参照している素材は外さない** — 利用者が使用可否を
> 戻したときに復元できなくなるため。

### 3.4 「使用中」をどう判定するか (Q4 / B3)

**使用中 = セクションが宣言した区間**、をやめ、
**使用中 = Timeline に実際に載っているクリップが指す VOD 区間**、にする。

1 本のクリップが指す VOD 区間は、§3.1 の素材単位の控えがあれば正確に求まる。

```
VOD 区間 = 素材の vod_start + clip.source_in  〜  素材の vod_start + clip.source_out
```

**刻まれすぎへの手当て。**無音カットは区間を細かく割る。そのまま差し引くと、
依頼者の clip1 では **40 個**の穴ができてしまう。穴 1 つにつき
「切り出し→正規化→音量解析→編集点検出→文字起こし」が 1 回走るため、現実的ではない。

そこで**隙間が `used_gap_merge_sec` 以内なら 1 つの使用区間として繋ぐ**。実測:

| 隙間を繋ぐ幅 | 「未使用」と判定される穴の数 (全 4 セクション合計) |
| --- | --- |
| 0 秒 (繋がない) | 40 |
| 2 秒 | 29 |
| 5 秒 | 23 |
| **10 秒 (推奨)** | **16** |
| 20 秒 | 12 |
| 30 秒 | 11 |

無音カットが空ける穴はふつう数秒、利用者が消した塊は数十秒であるため、
**10 秒**が両者を分ける実用的な境目になる (§10 #3 で確認)。

さらに、刻まれた数が `max_ranges` (既定 20) を超える場合は、
**黙って 20 回の準備を始めず、理由を出して断る**。

### 3.5 セクションの内側へ入れる位置 (Q5 / R5)

§3.4 の修正で、**セクションの「内側」の穴**を追加できるようになる。
すると現在の挿入位置の決め方が足りなくなる。

`_insert_position` (`:716`) は**セクション単位**でしか位置を見ていない。

```python
for entry in anchors:
    if float(entry.get("vod_start", 0.0)) >= range_end - _SECTION_EPS:
        span = clip_range(timeline, entry.get("index"))
        ...
return timeline.duration_sec()
```

clip2 (宣言 2025–2205 / 実使用 2200–2206) の穴 2025–2200 を足す場合、
`range_end = 2200` に対して `vod_start >= 2200` のセクションは clip3 (3690) であり、
**clip3 の手前 = clip2 の残り 6 秒の"後ろ"**へ入ってしまう。VOD の時系列と逆になる。

**クリップ単位まで見るように変える** (§5.7)。
素材単位の控え (§3.1) があるので、V1 の各クリップの VOD 位置が分かる。
**「自分より後ろから始まる最初のクリップの手前」**へ入れれば、セクションの内側でも順序が保たれる。

## 4. 設計方針

1. **「見せ方」と「作り方」を分ける。**セクションの控え (`clips`) は統合で畳んでよい。
   素材の控え (`media`) は**何があっても畳まない**。
2. **復元の入口を 1 つにする。**`project_resume` も `_media_to_copy` も、同じ
   `archive_media_entry(timeline, media_id)` を引く。2 か所で別々に探さない。
3. **判定は Timeline の実態を見る。**「宣言したこと」ではなく「今そこにあるもの」で決める。
   これは ver5 resolve3 §4-5「画面の表示と出力を同じ関数で決める」と同じ思想である。
4. **黙って壊さない・黙って重くしない。**復元できない素材があれば理由をログへ残す。
   刻まれすぎる追加は実行前に断る。
5. **既存プロジェクトを開けなくしない。**新しい控えが無ければ従来どおり `clips` を見る。
   壊れているものは可能な範囲で自動修復し、駄目なら今までどおり尋ねる。
6. **設定値はハードコードしない** (`docs/claude.md`)。判定の粒度と上限は `setting.json` へ置く (§7)。

### 5.4 既に壊れているプロジェクトの自動修復 (R2 / §3.2)

```python
# 控えの無い素材を、セクションの「穴」と尺で突き合わせて復元する (ver5 resolve6 §3.2)
#
# 統合のときに畳まれた素材は復元情報を失っている (§2.2)。その素材が埋めていた
# VOD 区間は「セクションの宣言区間のうち、控えを持つ素材が埋めていない所」である。
# 穴が 1 つに決まり、尺が合うときだけ採用する。決まらなければ何もしない
# (黙って間違った区間を切り出すより、今までどおり尋ねた方が安全)。
# 戻り値: 復元できた media_id の一覧
def repair_archive_media(timeline, tolerance_sec=5.0, tolerance_ratio=0.1): ...
```

**手順** (セクションごと):

1. そのセクションのクリップが使う素材を集め、**控えのある組 / 無い組**に分ける
2. 控えのある素材が覆う VOD 区間を求める (`vod_start + source_in 〜 vod_start + source_out`)
3. 宣言区間 `[vod_start, vod_end]` から 2 を差し引いて**穴**を求める
4. 控えの無い素材それぞれについて、長さが
   `abs(穴の長さ − 素材の尺) <= max(tolerance_sec, 素材の尺 × tolerance_ratio)`
   を満たす穴を探す。**候補がちょうど 1 つのときだけ**採用して `put_archive_media` する
5. 採用できなければ INFO ログ。以降は従来どおり差し替えを尋ねる

**呼ぶ場所**: `project_resume` の `media_recovery.recover` を呼ぶ**直前**。
修復した結果はそのまま復元に使われ、確定後の上書き保存で控えが JSON へ残る
(= 次からは修復も要らなくなる)。

> **なぜ尺で突き合わせるのか。**`cut_region` は `-ss` + `-c copy` のため、
> 切り出しはキーフレームへ吸着して**要求より少し前から・少し長く**なる。
> 依頼者のデータでは穴 68 秒に対して素材 71.1 秒だった。比率と絶対値の
> 大きい方を許容にすると、短い素材でも長い素材でも同じ感覚で当たる。

### 5.6 「使用中」を実態ベースにする (R4 / B3)

```python
# セクションが Timeline で実際に使っている VOD 区間を返す (ver5 resolve6 §3.4)
#   gap_merge_sec: 隙間がこの秒数以内なら 1 つの区間として繋ぐ
#                  (無音カットの細かい穴で区間が刻まれるのを防ぐ)
#   include_disabled: 使用可否が「使わない」のクリップも数えるか (既定 True)
# 戻り値: [(開始, 終了), …] 昇順・重なりなし
def used_vod_ranges(timeline, clip_index, gap_merge_sec=10.0, include_disabled=True): ...
```

`plan_section_add` (`:524`) の変更点は 2 つだけ。

```python
    # ① 何を「使用中」とみなすか
    if occupied_by == OCCUPIED_USED:
        covered = [r for e in touched
                   for r in used_vod_ranges(timeline, e.get("index"), gap_merge_sec)]
    else:
        covered = [(float(e.get("vod_start", 0.0)), float(e.get("vod_end", 0.0)))
                   for e in touched]

    # ② 差し引く先を「統合後の span」から「利用者が指定した区間」へ
    ranges = _subtract_covered(start, end, covered)
```

**②は従来方式では結果が変わらない。**`covered` が touched の宣言区間そのものである限り、
`span − covered` と `[start, end] − covered` は一致する (span は touched の宣言区間を
完全に含むため)。実使用ベースでは、**利用者が指定していない区間まで勝手に用意しない**ために必要になる。

**刻まれすぎの防止**:

```python
    if len(ranges) > max_ranges:
        return {"too_many": len(ranges), "ranges": [], …}   # 画面が理由を出して断る
```

* 判定に使うのは**統合対象のセクションだけ** (`touched`)。指定区間に掛からないセクションは関係ない。
* `include_disabled` を既定 True にするのは、「使わない」にしただけのクリップを
  未使用とみなして二重に用意してしまうのを防ぐため。

## 6. 実装手順

**「まず開けるようにする (B1・B2)、次に追加できるようにする (B3)」**の順にする。

### #2 の詳細 — 自動修復が効かない場合

1 つのセクションに**控えの無い素材が 2 本以上**あり、穴も 2 つ以上ある場合、
どの素材がどの穴かを尺だけで決めるのは危険である (尺が近いと取り違える)。
その場合は修復せず、従来どおり差し替えを尋ねる。

依頼者のプロジェクトは「穴 1 つ・素材 1 本」のため確実に直る。
仮に直らない場合でも、Phase 2 を入れておけば**その後に追加したセクションは二度と壊れない**ため、
影響は既存の 1 セクションに留まる。

### #3 の詳細 — 粒度を変えるとどうなるか

`used_gap_merge_sec` を小さくすると「未使用」と判定される穴が増える。
穴 1 つにつき「切り出し→正規化→音量解析→編集点検出→**文字起こし**」が 1 回走る。
文字起こしは依頼者の環境で**実時間の数倍**かかる (`autoedit_20260918.log` では
355 秒の素材に 15 分) ため、穴の数がそのまま待ち時間に効く。

| 設定 | 依頼者の素材での穴の数 | 想定される印象 |
| --- | --- | --- |
| 0〜2 秒 | 29〜40 | 無音カットの跡まで「未使用」に見え、追加のたびに細切れになる |
| **10 秒 (推奨)** | **16** | 消した塊だけが「未使用」に出る |
| 30 秒 | 11 | 短めに消した部分が「使用中」のままになる |
