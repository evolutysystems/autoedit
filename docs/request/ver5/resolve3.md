## 2. 現状分析

### 2.1 マスクの形は「矩形系」しか無い

* 解析結果のサンプルは**矩形だけ**を持つ (`{"t","x","y","w","h","score"}` / `analyzer._analyze_span` `:145`)。
  輪郭の情報はどこにも無い。
* マスクの塗りは `mask_builder._fill` (`:271`) で、人物は `rounded` / `rect` / `ellipse` の 3 種、
  **領域は常に矩形** (`kind != "person"` → `draw.rectangle` / `:281`)。
* 領域は利用者が**自由曲線で囲んで**登録するが、追従で使うのは囲みの**外接矩形**だけ
  (`region_tracker._tracks_for_region` `:243` `polygon_bounds`)。描いた形は捨てられている。

依頼者の素材 (5 人が近くに並んで座る配信 / 1920x1080) での検出枠を下表に示す (先頭サンプルの値)。
隣り合う人物の枠が大きく重なっており、**矩形のままでは「身体だけ」にならない**。

| tracklet | 人物 (判定) | 映っている人 | 指定 | 枠 (x, y, w, h) |
| --- | --- | --- | --- | --- |
| t1 | p1 (主役) | 左の眼鏡の男性 | ぼかす (明示) | 0, 196, 811, 877 |
| t4 | p1 (主役) | その右のオレンジ髪の男性 (**別人** / §2.5 (a)) | ぼかす (明示) | 452, 221, 460, 844 |
| t3 | p3 | 中央の黒シャツの男性 | **ぼかさない** | 911, 439, 606, 640 |
| t5 | p4 | 後ろに立つストライプシャツの男性 | ぼかす (明示) | 1005, 45, 629, 988 |
| t2 | p2 | 右端の男性 | ぼかす (明示) | 1541, 462, 376, 615 |

### 2.2 「ぼかさない」は「描かない」だけで、ぼかす枠を削っていない

* `mask_builder.build_plan` (`:139`) は**ぼかす対象だけ**を集め、ぼかさない対象は単に飛ばす。
  マスクは「ぼかす枠の和集合」であり、**ぼかさない人物の上にぼかす枠が重なれば、その部分はぼける**。
* 依頼者のプロジェクトでは p3 (ぼかさない) と p4 (ぼかす) の枠が
  横 512px (x=1005〜1517) × 縦 594px (y=439〜1033) にわたって重なっている。
  v1.4.9 の出力 (`…_edited_3.mp4` の 2.0 秒) を確認したところ、**p3 の顔から胸までがぼけていた**。
  これが要望 Q2 の直接の原因である。
* 領域の「ぼかさない」は**現状まったく効かない**。領域は既定でぼかさない (トラックを描かない) ため、
  「ぼかさない」で囲んでも出力は何も変わらない。Q2 を入れると初めて意味を持つ
  (「この看板の範囲だけは残す」)。

### 2.3 「枠を削除できない」の原因 (不具合 2 件 + 機能不足 1 件)

**(a) 削除した領域の枠が画面に残る — 不具合**

`RemoveBlurRegion` (`commands.py:1508`) は指定 (`source["blur"]["regions"]`) から領域を消すが、
**解析結果に足した追従トラック (`kind="region"`) は残る**。指定画面は解析結果のトラックを全部描き
(`blur_spec_dialog._boxes_at` `:244`)、指定が見つからない領域を
`should_blur_region(None)` で判定する。この関数は `mode` が無いと `"blur"` を返すため
(`decisions.py:123`)、**消したはずの領域が赤い枠 (ぼかす) のまま表示され続ける**。

実データで確認した: 依頼者のプロジェクトは `regions: []` だが、解析結果には `r1_m1_0` (領域 r1 の追従) が残っている。
出力 (`mask_builder.build_plan` `:155`) は指定を引くため実際にはぼけないが、画面では消えていないように見える。
Timeline 編集画面のプレビューの目印 (`timeline_editor_dialog._update_blur_markers` `:518`) も同じ判定で赤く出す。

**(b) 領域の枠をクリックすると人物の指定として記録される — 不具合**

`BlurCanvas` は枠のクリックで ID を送り (`blur_canvas.py:191`)、画面側は種類を見ずに
`SetBlurDecision` を積む (`blur_spec_dialog._on_box_clicked` `:335`)。領域 `r1` を押すと
`identities = {"r1": "keep"}` のような**意味の無い人物指定**が増えるだけで、領域の指定は変わらない。

**(c) 検出された人物の枠を消す手段が無い — 機能不足**

人物の枠に対してできるのは「ぼかす / ぼかさない」の切り替えだけで、
誤検出 (ポスター・画面に映った人・上半身の重複枠) を**対象から外す**操作が無い。
Q2 で「ぼかさない枠がぼかす枠を削る」ようになると、誤検出を「ぼかさない」にしておく逃げ道も
**周りのぼかしを削ってしまう**ため使えなくなる。削除 (= ぼかしも保護もしない) が必要になる。

### 2.4 「新規追加できない」の原因 (不具合 2 件 + 機能不足 2 件)

**(a) 削除した後に追加すると、新しい領域が古い追従結果に化ける — 不具合**

領域 ID の採番 `next_region_id` (`decisions.py:233`) は**指定に残っている ID だけ**を見る。
r1 を消してから追加すると再び `r1` が振られる。追従を作る `build_region_tracks` は
「その ID のトラックが既にあれば作らない」(`region_tracker.py:199-203`) ため、**新しい囲みの追従は作られず**、
§2.3 (a) で残った**古い r1 のトラック (前に囲んだ位置)** が新しい領域として使われる。
画面には「追従できた区間がありません」と出るか、前の位置に枠が出る。

次の手順をスクリプトで再現した。

```text
追加 → r1 / 削除 → regions=[] (トラック r1_m1_0 は残る) / 再追加 → 採番 r1 → 追従はスキップされる
```

**(b) 領域の追従は「カメラの動き」しか追わない — 機能不足**

`region_tracker` は**フレーム全体**を縮小して基準フレームと位相相関を取る
(`_samples_for_span` `:298` / 基準は `reference = _shrink(to_gray(anchor_image))` `:258`)。
求まるのは画面全体の平行移動 (パン・手ぶれ) であり、**囲んだ物そのものの動きではない**。
建物には合うが、**検出されなかった人物や動く物を手で足しても追いかけない**。
依頼者は r1 を p4 の口元 (65x38px) に置いたが、位置を出せたのは 5.6 秒のうち 0〜2.4 秒の区間だけで、その間も枠は画面全体の動きに合わせて動くだけだった。

**(c) 人物の枠に触れる囲みは、必ず「人物への指定」になる — 機能不足**

`_on_path_drawn` (`:320`) は囲みの中に人物の枠 (中心か 50% 以上の重なり) があれば人物へ指定し、
無いときだけ領域を足す。**人物に重なる位置へ新しい枠を足す**ことができない
(例: 検出枠が肩までしか無い人物の足元、主役の手に持った書類)。「指定する」と「追加する」が
同じ操作に混ざっているのが原因である。

**(d) 追従できないと何も残らない — 機能不足**

追従が 0 件だと、指定には領域が残るが**トラックが無いので画面にも出力にも出ない**
(`build_plan` はトラックを起点に形を作る)。利用者からは「追加できなかった」と区別がつかない。

### 2.5 同時に見つかった不具合 (要望の実現に直結するもの)

**(a) 並んで座った 2 人が同じ人物にまとめられる**

依頼者の素材では、眼鏡の男性 (t1) とオレンジ髪の男性 (t4) が**同じ時刻に並んで映っている**のに、
両方とも p1 (主役) にまとめられていた。`tracker._appears_together` (`:303`) は
「全身の枠と上半身の枠が重なって出る」場合に備え、**小さい方の枠の 50% 以上が大きい枠に入っていれば
同一人物**とみなす (`_SAME_BOX_CONTAINMENT = 0.5` / `:19`)。t4 は t1 に 78% 入っているため、
別人なのに同一人物と判定された。**この 2 人を別々に「ぼかす / ぼかさない」にできない**ため、
Q2 (ぼかさない優先) を入れても期待どおりにならない。

**(b) 「同じ人物にする」が効いていない**

`MergeBlurIdentities` は指定に `merges` を書くが、`analyzer.analyze` (`:40`) は
`cluster(tracklets, cfg)` を**`merges` を渡さずに**呼んでいる。
`tracker.apply_merges` はどこからも使われず、画面の「次の解析から反映されます」は実現していない。

**(c) 解析をやり直すと、追加した領域の追従が消える**

`build_region_tracks` は指定画面で囲んだ直後にしか呼ばれない。素材や設定が変わって解析をやり直すと
(`analyzer.analyze` は解析結果を丸ごと作り直す)、**領域の指定は残るのにトラックが無くなり、黙ってぼけなくなる**。
依頼者のログでは、同じ素材でパイプラインを実行するたびに「素材か設定が変わったため、ぼかしの解析をやり直します」が出ている。

## 3. 方式選定

### 3.1 輪郭の取り方 (Q1)

身体の輪郭を取るには**セグメンテーション**が要る。依頼者の素材のように人物が重なって並ぶ場面では、
「人物の画素かどうか」だけを返す**意味セグメンテーション**では足りない。隣の人物と画素がつながり、
「ぼかす p4 の身体」と「ぼかさない p3 の身体」を分けられないからである。
**人物ごとに分かれた輪郭 (インスタンス)** が必要になる。

| 候補 | 種類 | ライセンス (配布元で確認) | 人物ごとに分かれるか | 既存の検出枠を使えるか | 評価 |
| --- | --- | --- | --- | --- | --- |
| **SAM 系 (枠を与えて輪郭を返す)**: MobileSAM / EfficientSAM / SAM 2.1 tiny | 枠プロンプト型 | Apache-2.0 | **分かれる** | **使える** (YOLOX の枠をそのまま渡す) | **推奨** |
| RTMDet-Ins tiny (OpenMMLab) | インスタンスセグメンテーション | Apache-2.0 | 分かれる | 使えない (自前で検出し直す。YOLOX の枠と突き合わせが要る) | 次点。ONNX 化に mmdeploy が必要で手順が重い |
| MediaPipe Selfie Segmentation / PP-HumanSeg | 意味セグメンテーション | Apache-2.0 | **分かれない** | — | 不採用 (重なる人物を分けられない) |
| Ultralytics YOLOv8-seg / YOLO11-seg | インスタンス | **AGPL-3.0** | 分かれる | — | **不採用** (有償配布のため / resolve2 §9-2 と同じ理由) |
| Robust Video Matting | マット | GPL-3.0 | 分かれない | — | 不採用 |

**SAM 系を推奨する理由**

1. **今の解析の流れを変えない。**YOLOX が出した枠と tracklet はそのまま使い、その枠を**プロンプト**として輪郭だけを足す。
   人物 ID・主役判定・指定の仕組みに手を入れずに済む。
2. **重なっても分かれる。**枠ごとに輪郭を返すため、p3 と p4 の身体を別々に得られる。
3. **重い部分は 1 フレーム 1 回。**SAM 系は「画像エンコーダ (重い) を 1 回 → 枠ごとのデコーダ (軽い)」の 2 段構成で、
   人数が増えても重い部分は増えない。

3 つの候補のどれにするかは、**同じ素材での実測**で決める (§6 Phase 0 / §10 #1)。
判断材料は「1 フレームあたりの時間 (CPU)」「重なった人物の分かれ方」「ONNX の用意のしやすさ」「重みのライセンス (コードと別に確認する)」。
エンコーダの公称の大きさは MobileSAM が最小、SAM 2.1 tiny が最大であり、
**CPU 実行が前提の本製品では MobileSAM か EfficientSAM (Ti) が第一候補**になる見込み (実測で確定する)。

#### 3.1.1 Phase 0 の実測と決定 (2026-09-17)

依頼者の素材 (1920x1080・5 人・5.6 秒 / 解析サンプル 28 枚) で、CPU 7 スレッド (アプリと同じ) で測った。

| 候補 | 1 枚あたり (5 人) | ファイル | 重なった 5 人の輪郭 | 評価 |
| --- | --- | --- | --- | --- |
| **MobileSAM** (公式の重みを `tools/export_silhouette.py` で ONNX 化) | エンコーダ約 510ms + 1 人約 50ms | 44.5MB | 5 人とも分かれる | **採用** |
| EfficientSAM (Ti) (公式配布の ONNX) | 約 2,170ms | 41.4MB | MobileSAM と同程度 | 2 倍遅い |
| MobileSAM の int8 量子化 | 速くならない | 15.8MB | 元の輪郭との IoU が平均 0.69 に落ちる | 不採用 |
| MobileSAM のデコーダを複数人まとめて 1 回 | 速くならない | — | 同じ | 不採用 |
| SAM 2.1 tiny | 測っていない | — | — | エンコーダが MobileSAM の約 7 倍の大きさで、2 倍以内に収まる見込みが無いため除外 |

ONNX 化した MobileSAM は、PyTorch 版との最大誤差がエンコーダ 3.3e-6 / デコーダ 1.5e-4 だった。
重み・コードとも Apache-2.0 (配布元の LICENSE で確認)。`licenses/MobileSAM/` へ表記を入れた。

### 3.2 輪郭をいつ作るか

| 案 | 内容 | 評価 |
| --- | --- | --- |
| A. 書き出し時に毎フレーム | マスク生成でフレームを取り出して推論する | **不採用。**60fps × 10 分 = 36,000 回。書き出しが桁違いに遅くなる |
| **B. 解析時に間引いて作り、解析結果へ保存 (推奨)** | 解析ループで取り出したフレームのうち **N 枚に 1 枚**で輪郭を作り、サンプルへ付ける | **採用。**フレームの取り出し・検出を解析と共有でき、追加の取り出しが無い。書き出しは今と同じ速さ |
| C. 指定画面で指定した人物だけ後から作る | ぼかす人物が決まってから、その人物のサンプルだけ推論する | 解析は速いが、指定のたびに待ち時間が出る。`blur_others` では結局ほぼ全員が対象になる |

B を採る。輪郭は**「ぼかす / ぼかさない」が決まる前に**全員ぶん作る。
既定方針 `blur_others` では主役以外の全員が対象であり、C の節約はほとんど効かないためである。
間引き (`silhouette.every_n_samples`) で時間を調整できるようにする。

### 3.3 輪郭をフレーム間でどう動かすか

輪郭は間引いた時刻にしか無い (既定 5fps の 2 枚に 1 枚 = 2.5fps)。出力は 30〜60fps のため、間を埋める必要がある。

* **輪郭は「枠に対する相対座標」で持つ。**枠の中を 0〜1 とした座標で保存し、
  各出力フレームでは**既存の枠の補間** (`mask_builder._rect_at`) に当てはめる。
  人物が移動・拡大しても、輪郭は枠と一緒に動く。
* **形の変化は前後 2 つの輪郭を線形に混ぜる。**輪郭を**一定の点数 (既定 64 点) に打ち直し**、
  始点を「一番上の点」に揃えておけば、点どうしを対応させて混ぜられる。
* **動きの遅れは膨張で吸収する。**腕を振るなど、枠より速い部分の動きは補間で取りこぼす。
  輪郭を塗った後に `silhouette.dilate_ratio` (キャンバス幅比) ぶん**膨張**させて余白を持たせる。
  既存の `margin_ratio` (矩形を広げる量 0.06) より小さい値を既定にする。

**四角へ落とす条件 (Q5: 取りこぼしを出さない)**

次のどれかに当たる時刻は、その人物だけ**従来の矩形 (`render.shape`)** で塗る。

| 条件 | 理由 |
| --- | --- |
| 前後どちらの輪郭からも `silhouette.max_gap_sec` (既定 1.0 秒) 以上離れている | 形が古すぎて当てにならない |
| 輪郭の面積が枠の `silhouette.min_fill_ratio` (既定 0.15) 未満 | 輪郭の取り損ね (枠の一部しか拾えていない) |
| 輪郭モデルが無い・推論に失敗した | 機能としては動かし続ける |

#### 3.3.1 輪郭の持ち越し (実装で追加)

依頼者の素材は手持ちカメラで、0.4 秒の間に画面全体が左右へ 100px 以上揺れる。間引いた輪郭と枠の補間だけでは、
輪郭が人物からずれて「ぼかさない」人物の顔がぼけた。そこで解析の中で、**輪郭を作らなかった枚にも輪郭を付ける**。

```text
輪郭を作った枚 (基準) と今の枚で、人物のまわり (前後の枠を合わせて 15% 広げた範囲) を 1/4 に縮めて位相相関を取る
  → PSR が 8 以上なら、基準の輪郭を平行移動ぶんずらして今の枠の相対座標へ直し、サンプルへ付ける
  → 8 未満なら付けない (前後の本物の輪郭か、矩形で塗る)
ずらした輪郭からさらにずらすと誤差が積もるため、基準は常に「本物の輪郭を作った枚」にする
```

平行移動だけを補うため、**頭だけを傾けるような姿勢の変化には追いつかない**。これは膨張 (`dilate_ratio`) で一部を吸収する。

#### 3.3.2 実素材での漏れの計測 (2026-09-17)

全 167 フレーム (30fps) で MobileSAM の輪郭を作って「正解」とし、書き出しと同じマスクと比べた。
指定は依頼者のプロジェクトと同じ (p3 = ぼかさない / 他の 4 人 = ぼかす)。`every_n_samples=4`。

| 設定 | ぼかす人物の漏れ | 守る人物がぼけた割合 | 背景がぼけた割合 |
| --- | --- | --- | --- |
| **輪郭 / `dilate_ratio` 0.01 / `keep_margin_ratio` 0 (既定)** | **5.9%** | **5.8%** | **16%** |
| 輪郭 / 0.02 / 0 | 4.8% | 7.2% | 24% |
| 輪郭 / 0.05 / 0 | 3.3% | 10.4% | 47% |
| 輪郭 / 0.01 / 0.01 | 7.2% | 3.7% | 16% |
| 角丸の四角 (従来) | 16.5% | 1.4% | 73% |

* 輪郭にすると、**ぼかす人物の漏れが四角の約 3 分の 1**になり、背景がぼける範囲も大きく減る。
  四角の漏れが大きいのは、守る人物の枠いっぱいでぼかしが削られ、その中にいる隣の人物が見えるため (§3.4 の定義どおり)。
* 代わりに、守る人物の輪郭の端がずれた時刻にぼけることがある (5.8%)。膨張を大きくすると漏れは減るが、守る人物がよりぼける。
* 既定値は §10 #4 (守る側の余白 0) のとおりにし、膨張は 0.01 とした。素材に合わせて `setting.json` で変えられる。
* **この既定は §3.3.3 で改めた** (依頼者の確認で、激しい動きでぼかしが外れたため)。

#### 3.3.3 激しい動きへの余白 (2026-09-17 / 依頼者の確認を受けて追加)

依頼者が試したところ、**ぼかす人物が激しく動くと、輪郭のぼかしが人物から外れた**。
「輪郭からおおまかに余白を取る」よう求められたため、ぼかす人物の余白を次のように決め直した。

```text
余白 (キャンバス px) = max(画面幅 x dilate_ratio, 人物の枠の短い辺 x margin_box_ratio) + 動いた量
動いた量 = 前後 motion_lookahead_sec の枠について、中心の移動 + 大きさの変化の半分 (前と後ろで大きい方)
上限 = 人物の枠の長い辺 x max_margin_box_ratio
```

* **人物の大きさに比例させる。**手前に大きく映る人物ほど、腕や頭の動きも画面上で大きいため。
* **動いた量を足す。**輪郭は間引いた時刻の形しか持たず、その間の激しい動きには追いつかないため。
* **激しく動いている時刻は輪郭をやめ、角丸の四角 (+ 余白) でぼかす。**動いた量が人物の枠の短い辺の
  `fast_motion_box_ratio` を超えたとき。
* **姿勢が変わったら輪郭を持ち越さない。**枠の幅・高さが基準から 2 割以上変わったら (かがむ・腕を広げる)、
  §3.3.1 の持ち越しをしない。実素材で、立っている人物がかがんだ時刻に頭がまるごとぼかしから外れていた原因。
* 守る人物には既定で余白を付けない。`render.keep_motion_margin` を true にすると、守る人物が動いた時刻だけ
  動いた量ぶん守る形を広げる。

§3.3.2 と同じ方法で測った結果 (解析は持ち越しの修正後):

| 設定 | ぼかす人物の漏れ | 守る人物がぼけた割合 | 背景がぼけた割合 |
| --- | --- | --- | --- |
| 修正前の既定 (§3.3.2) | 5.9% (最悪のフレーム 33%) | 5.8% | 16% |
| **余白 0.15 + 動き 0.3 秒 + 四角へ切り替え 0.15 (新しい既定)** | **1.7% (同 11%)** | 12.4% | 71% |
| 上に加えて `keep_motion_margin` = true | 6.8% (同 27%) | 2.5% | 67% |
| 角丸の四角 (従来) | 16.0% (同 24%) | 1.5% | 82% |

* ぼかす人物の漏れは修正前の約 3 分の 1 になった。残る最悪のフレーム (11%) は、評価用の「正解」を作るときに
  1 人に検出枠が 2 つ出て、片方を別の人物として数えたもの (実際に見えている顔ではない)。
* 代わりに、**守る人物が激しく動いた時刻は、その顔や肩がぼけやすい** (12.4%)。守る人物の余白を付けると
  守る人物はぼけにくくなるが、守る形が広がった分だけ、重なったぼかす人物が見える (漏れ 6.8%)。
  依頼者の要望 (ぼかしが外れないこと) を優先し、既定は付けない。

### 3.4 「ぼかさない」を優先する合成 (Q2)

マスクを 2 層で作り、最後に削る。

```text
ぼかす層   B = (ぼかす対象の形を塗る) → 膨張 → フェザー (ぼかし)
ぼかさない層 K = (ぼかさない対象の形を塗る)            … 膨張もフェザーもしない
最終マスク   M = B × (1 − K)
```

* **フェザーは B にだけ掛け、K で削った後には掛けない。**後から全体をぼかすと、
  削った境界からぼかしが数 px ぶん**ぼかさない人物へ染み出す**ため。Q2 は「ぼかさない優先」なので、境界は K 側を守る。
* K は**膨張させない**。ぼかさない人物の輪郭ちょうどで削る。余白を足すと、隣のぼかす人物の身体が見えてしまう
  (§10 #4 で余白を足すかを確認する / 既定 0)。
* 輪郭が使える場合は K も輪郭で削るため、**ぼかす人物の見えてしまう範囲は最小になる**。
  矩形同士の場合は、ぼかさない人物の枠いっぱいまで、ぼかす人物が見えてしまう。これは要望の定義どおりの動作である。

**「ぼかさない」に含めるもの (推奨 / §10 #2)**

| 対象 | K に入れるか |
| --- | --- |
| 明示的に「ぼかさない」を指定した人物 | **入れる** |
| 主役 (明示的に「ぼかす」にしていない限り、暗黙にぼかさない / resolve2 R3) | **入れる** |
| 「ぼかさない」で追加した領域・手動の枠 | **入れる** |
| `manual_only` で何も指定していない人物 (ぼかさないのは「対象外」だから) | **入れない** |
| 削除した枠 (§3.5) | **入れない** |

最後の 2 つを入れない理由: `manual_only` で建物をぼかしたとき、前を通った人物の形に**建物のぼかしが抜けてしまう**。
「対象外」は「守る対象」ではない。

### 3.5 枠の「削除」の意味 (Q3)

| 枠の種類 | 削除したときの扱い |
| --- | --- |
| 追加した領域・手動の枠 | **指定から消し、画面にも出さない** (§2.3 (a) の修正) |
| 検出された人物の枠 (tracklet) | **その tracklet を「ぼかさない / ぼかす」のどちらにも使わない** (除外)。人物 ID ごとではなく**枠 1 本ごと**に消す |

人物の枠を**枠 1 本ごと**に消すのは、誤検出の多くが「別人の枠が 1 本だけ紛れる」「全身と上半身の枠が重複する」形で出るためである。
人物ごと消したい場合は、一覧から人物を選んで「この人物をすべて削除」を使う (§5.5.3)。

**解析をやり直しても消した枠が戻らないようにする**

tracklet の ID (`t1`, `t2`, …) は解析のたびに振り直されるため、ID では覚えられない。
**「どの素材の、何秒に、どこにあった枠か」(アンカー)** で覚え、解析後に当て直す。

```text
除外の指定: {"media_id": "m1", "t": 2.0, "rect": [452, 221, 460, 844]}
当て込み  : 同じ素材の tracklet のうち、t から ±1 サンプル以内に IoU 0.5 以上の枠を持つもの
```

### 3.6 枠の「新規追加」と追従 (Q4)

「指定する」と「追加する」を**別の操作モード**に分ける (§2.4 (c))。追加には 2 種類を用意する。

| 追加の種類 | 追いかけるもの | 方式 | 向いているもの |
| --- | --- | --- | --- |
| **人物・物** (新規) | **囲んだ物そのもの** | 前の位置の周りを切り出して **YOLOX で検出し直し**、一番重なる枠へ乗り換える。検出できない時刻は切り出し範囲の位相相関で位置を補う | 検出されなかった人物、手に持った物 |
| **場所** (既存の領域) | **カメラの動き** | 既存の `region_tracker` (フレーム全体の位相相関) / `follow="fixed"` | 建物・看板・背景の窓 |

**人物・物の追従 (推奨方式)**

1. 囲んだ時刻 (アンカー) で、囲みの外接矩形を初期位置にする。YOLOX の枠 (しきい値を下げた `manual.detector_score`) に
   IoU 0.5 以上で重なるものがあれば、**その枠へ吸着**する (手描きの囲みは雑でよい)。
2. アンカーから**前と後ろの両方向**へ、解析と同じ間隔で進む。
3. 各時刻で、前の位置を `manual.search_ratio` 倍に広げた範囲を切り出し、**切り出した画像で YOLOX を走らせる**
   (切り出して拡大するため、小さな人物も検出しやすい)。前の位置と IoU が `manual.min_iou` 以上の枠へ乗り換える。
4. 検出できなければ、切り出し範囲どうしの位相相関で**平行移動だけ**補う (物・部分的な隠れ)。
   `region.match_psr` を下回る状態が `region.hold_sec` を超えたら、その方向の追従を打ち切る。
5. **その素材の区間 (セクション) の中だけ**を追う。他のセクションへは広げない
   (手で足した物は「その場面にある物」であり、他の場面で同じ見た目を探すと誤爆が多い)。

**追従できなくても何かを残す (§2.4 (d))**

追従の結果がアンカーの 1 点だけだった場合は、次の確認を出す。

```text
この枠は追いかけられませんでした。
[この位置に固定でぼかす (前後 N 秒)] [取り消す]
```

「固定」は既存の `follow="fixed"` と同じ扱いで、アンカーの前後 `manual.fixed_span_sec` (既定 2 秒) に置く。
利用者が範囲を広げたい場合は、別の時刻でもう一度追加する。

**追加した枠の形**

* 人物・物: 輪郭が有効なら輪郭 (§3.3)、無効なら**描いた囲みの形**を枠の中の相対座標で保存して塗る
  (`rounded` 等の矩形系より身体に近い)。
* 場所: **描いた囲みの形**をそのまま使う (§2.1 で捨てていた形を使う)。

## 4. 設計方針

1. **機能 OFF なら 1 行も通らない (Q6)。**追加する処理はすべて `blur.enabled` の内側に置き、
   OFF のときは import もしない (resolve2 §4-1 と同じ)。
2. **取りこぼしを出さない (Q5)。**輪郭・追従が当てにならない時刻は、ぼかす対象を**広く**塗る側へ倒す
   (矩形へ落とす / 固定で残す)。例外は Q2 の「ぼかさない優先」だけで、これは要望として明示された優先順位である。
3. **既存の人物 ID を動かさない。**枠の除外・分割・手動追加では、既存の人物 ID (`p1`, `p2`, …) を振り直さない。
   明示した指定 (`identities`) は人物 ID で持っているため、振り直すと指定が別人へ移ってしまう。
   分割でできる人物は別の名前空間 (`s1`, …)、手動の枠は領域と同じ `r1`, … を使う。
4. **指定はアンカーで覚える。**解析で振り直される ID (tracklet) を指定から直接参照しない (§3.5)。
5. **画面の表示と出力を同じ関数で決める。**指定画面・Timeline のプレビューの目印・マスク生成が、
   それぞれ別に「ぼかすか」を判定していたことが §2.3 (a) の原因になった。
   判定は `blur.plan` (新設 / §5.1) にまとめ、3 か所から同じ結果を引く。
6. **解析結果とトラックの整合は、足す側で保証する。**領域・手動の枠の追従は、
   「指定にあるのにトラックが無い」「トラックの形が指定と違う」ときに自動で作り直す (§5.7)。

### 5.3 輪郭の解析 (`silhouette.py` / `contour.py` / `analyzer.py`)

#### 5.3.1 入口

```python
# 画像 1 枚と枠の一覧から、枠ごとの輪郭を返す。
#   image : RGB ndarray (素材ピクセル)
#   boxes : [(x, y, w, h, score), …] detector.detect の戻り値
# 戻り値: [輪郭 or None, …] (boxes と同じ並び)。輪郭は枠内の相対座標 [(u, v), …] (0〜1)
def segment(image, boxes, cfg): ...

# 輪郭モデルが使えるか (無ければ理由を返す / 設定画面の状態表示に使う)
def availability(cfg): ...
```

#### 5.3.2 1 枚の処理

```text
1. エンコーダ: 画像を長辺 1024 へ縮小 → 埋め込み (1 枚 1 回)
2. デコーダ: 枠ごとに、枠をプロンプトとして渡す → 確率マップ (低解像度)
3. 2 値化 (silhouette.threshold) → 一番大きい連結成分だけ残す (枠の外へ伸びた部分は枠で切る)
4. 境界を追跡して多角形にする → contour.resample で等間隔 N 点・始点を最上点へ揃える
5. 枠内の相対座標へ直す → 面積が min_fill_ratio 未満なら None
```

* 境界の追跡は numpy だけで書く (Q8)。確率マップは 256x256 程度のため、単純な方法で十分に速い。
* エンコーダの入力解像度・前処理 (正規化の平均と分散) はモデルごとに違うため、
  `silhouette.format` (`"mobilesam"` / `"efficientsam"` / `"sam2"`) で切り替える
  (`detector_format` と同じ作り / resolve2 §3.7.3)。

#### 5.3.3 解析ループへの組み込み

`analyzer._analyze_span` (`:145`) の中で、既にある 1 枚ごとの処理へ足す。

```python
boxes = detector.detect(image, cfg)
embeddings = reid.embed(image, boxes, cfg) if boxes else []
contours = None
if silhouette_enabled and boxes and index % every_n == 0:     # 新規
    contours = silhouette.segment(image, boxes, cfg)
tracker.update(sec, boxes, embeddings, contours=contours)    # サンプルへ "sil" を付ける
```

* `Tracker.update` は枠と tracklet を対応付けた時点でサンプルを作るため、同じ並びの `contours` を受け取って付ける。
* 輪郭の推論に失敗しても解析は続ける (その枚だけ輪郭なし)。**失敗が続いたら 1 回だけ WARNING** を出す。

#### 5.3.4 進捗

解析の進捗表示は変えない (区間の秒数で進む)。輪郭が有効なときは、ボタンの表示を
「ぼかし解析中… 42% (輪郭あり)」にして、遅くなる理由が分かるようにする。

### 5.4 マスク生成の変更 (`plan.py` / `mask_builder.py`)

#### 5.4.1 判定を 1 か所へ (`plan.py`)

```python
# 1 本のトラックの役割を決める: "blur" (ぼかす) / "keep" (守る) / None (使わない)
#   §3.4 の表のとおり。除外・分割・孤立したトラック (指定に無い領域) もここで判断する。
def role_of(track, decisions, cfg, main_id): ...

# その時刻に塗る形の一覧 [(役割, 形の種類, キャンバス座標の多角形 or 矩形), …]
# 指定画面・プレビューの目印・マスク生成がすべてこれを使う (§4-5)。
def shapes_at(timeline, analysis, decisions, cfg, media_id, source_sec): ...
```

* **孤立したトラック (指定に無い領域・手動の枠) は `None`** を返す。§2.3 (a) の表示不具合はここで直る。
* 分割 (`splits`) は `role_of` の中で当て込み、人物 ID を置き換えてから判定する。

#### 5.4.2 1 フレームの絵 (`_iter_mask_frames` `:184` の置き換え)

```text
B = 0 の画像、K = 0 の画像 (どちらも mask_scale の大きさ)
for 役割, 形 in shapes_at(…):
    "blur" → B へ塗る (輪郭なら多角形、落としたら矩形系)
    "keep" → K へ塗る (同上。膨張させない)
B を膨張 (輪郭で塗ったものだけ silhouette.dilate_ratio) → フェザー (feather_ratio)
K に keep_margin_ratio があれば膨張
M = B × (1 − K/255)   … numpy で 1 回の掛け算
```

* **K に何も塗らないフレームでは、掛け算を飛ばす** (今と同じ速さ)。
* 膨張は、**頂点を外側へずらした多角形**を重ねて塗って行う (矩形系は枠を広げる)。当初の `ImageFilter.MaxFilter` は
  1 枚 20ms かかり、マスク生成の 85% を占めた (§0.2)。
* 輪郭で塗る人物と矩形で塗る人物は、1 枚の中で混在してよい。

#### 5.4.3 「ぼかす対象が無い」の判定

`decisions.needs_mask` (v1.4.9 で追加) はそのまま使う。ぼかす形が 1 つも無いフレームは今までどおり黒のまま使い回し、
全フレームで無ければマスクを作らない (R9 相当の挙動を維持)。

### 5.7 領域・手動の枠と追従結果の整合

**(1) ID を使い回さない**

`next_region_id` は `region_seq` (通し番号) から採番し、**削除しても番号を戻さない**。
Undo で `region_seq` が戻ることがあるため、あわせて**解析結果に残っているトラックの ID も避ける**
(`next_region_id(decisions, analysis)`)。§2.4 (a) はこれで起きなくなる。

**(2) 形の指紋でトラックを確かめる**

追従トラックに `shape_hash` (指定の `kind` / `path` / `media_id` / `anchor_sec` / `follow` から作る) を持たせる。
`build_region_tracks` は「ID が同じトラックがあるか」ではなく「**ID と `shape_hash` が一致するトラックがあるか**」で
作り直しを判断する。万一 ID が重なっても、古い位置のトラックが使われることは無い。

**(3) 解析をやり直したら追従も作り直す (§2.5 (c))**

`analyzer.analyze` の最後で、指定にある領域・手動の枠のうち**トラックが無いもの**の追従を作る
(`region_tracker.build_region_tracks` / `manual_tracker.build_manual_tracks`)。
解析はバックグラウンドのワーカーで走っているため、追加の待ち時間は解析の進捗に含めて見せる。

**(4) 追従できなかった枠を黙って捨てない (§2.4 (d))**

* 追加した直後: §3.6 の確認を出す。
* 解析のやり直しで追従が 0 件になった場合: 指定画面の一覧で「追加 1 (追従できていません)」と表示し、
  書き出し時は `renderer._confirm_blur_failure` (`:101`) と同じ確認を出す (「ぼかすと指定したのに素で出た」を防ぐ)。

### 5.8 人物のまとめ方の修正 (`tracker.py` / `analyzer.py`)

**(1) 並んだ 2 人を同一人物にしない (§2.5 (a))**

「全身と上半身の重複枠」は、**小さい枠がほぼ丸ごと大きい枠に入り、しかも横方向の中心がそろう**。
並んで座った 2 人は、入っている割合が高くても中心が横にずれる。判定に中心のずれを足す。

```python
# 同一人物の重複枠とみなす条件 (どちらも満たすとき)
contained  >= analysis.same_box_containment      # 既定 0.85 (現状 0.5)
center_gap <= analysis.same_box_center_ratio * 小さい枠の幅   # 既定 0.5 (実装で 0.25 から変更)
```

依頼者の素材の t1 / t4 は、入っている割合 0.78 / 中心のずれ 277px (小さい枠の幅 460px の 0.60 倍) で、
**どちらの条件でも別人になる**。既存のテスト `test_cluster_merges_duplicate_boxes_of_one_person` の重複枠は
左端がそろっていて中心のずれが 0.40 倍あるため、0.25 では別人になってしまう。**0.5 に決めた**。
修正後の解析で、依頼者の素材は 4 人から **5 人**になった。

**(2) 「同じ人物にする」を効かせる (§2.5 (b))**

`analyzer.analyze` は、指定の `merges` と `splits` を受け取って `cluster(tracklets, cfg, merges=…)` へ渡す。
呼び出し元 (`BlurAnalysisWorker`) は `decisions.load(timeline)` を渡す。

### #1 の詳細 — 輪郭の時間

§2.6 のとおり、現状でも依頼者の PC で**1 枚あたり約 0.55 秒**かかっている。
輪郭のエンコーダは検出器 (YOLOX-Tiny / 416 入力) より入力が大きく (長辺 1024)、
1 枚あたりの時間が**検出より長くなる可能性が高い**。`every_n_samples=2` でも解析時間が倍近くになりうるため、
「どこまで待てるか」を先に決めておく必要がある。倍を超える場合の選択肢は次のとおり。

| 選択肢 | 影響 |
| --- | --- |
| `every_n_samples` を 3〜5 に上げる | 形の更新が粗くなり、腕の動きなどで膨張 (`dilate_ratio`) を大きくする必要がある |
| 輪郭は**ぼかす人物だけ**、指定後に作る (§3.2 案 C) | 解析は速いまま。指定のたびに待ち時間が出る |
| エンコーダの入力を 1024 → 512 に下げる | 速いが、遠くの小さい人物の輪郭が崩れやすい。崩れたら四角へ落ちる |

### #8 の詳細 — 人物 ID がずれる問題

明示した指定は人物 ID (`p1`, `p2`, …) で持ち、ID は「映っている秒数の多い順」で振る。
§5.8 (1) の修正で 1 人だった p1 が 2 人に分かれると、それ以降の ID が 1 つずつずれ、
**「p3 をぼかさない」が別人を指す**ことがある。これは今回の修正に限らず、素材を差し替えて解析し直したときにも起きうる
(resolve2 からある制約)。根本の対策は、指定を ID ではなく**見た目 (ReID のベクトル)** で覚えて、解析後に当て直すことだが、
影響が大きいため本書の範囲外とし、当面は解析し直して人物数が変わったときに確認を促すに留める。
