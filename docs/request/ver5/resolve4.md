### 0.2 実装状況 (2026-09-20)

**Phase 0〜6 をすべて実装した。**確認事項は §10 のとおり「すべて推奨どおり」で決定した。

実装で本書の案から変えたことは次の 3 点。

| 項目 | 本書の案 | 実装 | 理由 |
| --- | --- | --- | --- |
| 由来キーに元動画の**パス**を混ぜるか | 混ぜる (パス + サイズ + 更新時刻) | **混ぜない** (サイズ + 更新時刻だけ) | パスを混ぜると、元動画を別フォルダへ移しただけで解析し直しになる。中身が同じなら同じ指紋でよい |

## 2. 現状分析

### 2.1 呼び名は「人物 N」固定で、画面の都合で振られている

表示名を作っているのは `plan.BlurPlan.labels` (`plan.py:135`) の 1 か所だけ。

```python
for index, identity in enumerate(self.identities, 1):
    name = f"人物 {index}"
    if identity["main"]:
        name += " (主役)"
    labels[identity["id"]] = name
```

* 人物 ID (`p1`, `p2`, … / 分けた人物は `s1`, `s2`, …) とは別に、**並び順で毎回振り直される通し番号**である。
* 名前を持つ場所は**どこにも無い**。`decisions.load` (`decisions.py:48`) が読む項目は
  `identities` / `merges` / `regions` / `excluded` / `splits` / `region_seq` だけ。

**依頼者の実データ** (`vod_2877176496`):

| 項目 | 値 |
| --- | --- |
| 人物 | **50 人** (上限に張り付いている) |
| tracklet | 2026 本 (サンプル 32,168 / うち輪郭あり 16,859) |
| 明示した指定 | **22 件**。内訳は「ぼかさない」21 人 + 「ぼかす」1 人 |
| 同じ人物にする | 2 組 (`p2`+`p7` / `p5`+`p1`) |
| 削除した枠 | 6 件 |

**50 人の中から 21 人を手で「ぼかさない」に選び分けている。**
見本画像 (64px) と「人物 14」「人物 32」「人物 48」という番号だけでこれを行っており、
一度決めた人物を後から探し直す手掛かりが無い。要望 R1 はここから来ていると読める。

### 2.2 人物上限で溢れた枠は、解析結果に残らない (ぼかし漏れ)

`tracker._to_identities` (`tracker.py:300`) は人物数が `max_identities` (既定 50) を超えると
**短い人物から切り捨てる**。切り捨てられた人物の tracklet には人物 ID が振られない
(`_assign` は残った人物の tracklet しか回らない / `tracker.py:392`)。
そして `analyzer.analyze` (`analyzer.py:106`) が

```python
analysis["tracks"] = [track.to_dict() for track in tracklets if track.identity]
```

としているため、**人物 ID の無い枠はキャッシュにすら書かれない**。

依頼者のログ (`src/gui/logs/autoedit_20260919.log`):

```
人物が 77 人を超えたため、短いものから捨てます (上限 50)
人物クラスタリング: tracklet 2064 本 → 人物 50 人 (主役 p1)
```

保存された枠は 2026 本。**27 人ぶん・枠 38 本が消えている。**
消えた枠は指定画面に出ないため、利用者は存在に気付けない。既定方針が
「主役以外はぼかす」でも、**この 27 人はぼかされずに出力される**。
残った人物の最小の合計秒数が 4.6 秒なので 1 人あたりは短いが、映り込みの取りこぼしであることに変わりはない。

要望 R2 の「解析して人物枠が出現すると思いますが、それを選択し、新規で人物と割り当てられる」は、
**本来出るべき枠が出ていない**この状態と地続きの可能性が高い。R4 として一緒に直す。

### 2.3 枠を人物へ付け替える手段は 2 つあるが、どちらも要望に届かない

| 既存の手段 | 実体 | 届かない理由 |
| --- | --- | --- |
| 「別の人物にする」(`blur_spec_dialog.py:252` / `_split_selection:696`) | `SplitBlurTrack` → `decisions.with_split` が `s1`, `s2`, … を採番 (`decisions.py:392`) | **要望の言葉と一致しない。**「別の人物」は「今とは違う誰か」とも読め、「新しい人物を作る」と伝わらない。作った人物には名前も見本画像も付かないため、一覧で見分けられない |
| 「選んだ 2 人を同じ人物にする」(`blur_spec_dialog.py:155` / `_merge_identities:914`) | `MergeBlurIdentities` → `decisions.merges` | **効くのは次に解析し直したとき**。`merges` を使うのは `tracker.cluster` (`tracker.py:277`) だけで、画面では何も変わらない。依頼者の素材は解析に約 2 時間かかる (§2.6) ため、事実上やり直せない |

一方で、**枠 1 本を別の人物 ID へ付け替える仕組みは既にあり、即時に効く**。
`plan._entry` (`plan.py:178`) が `splits` を当て込んでいる部分がそれで、`as` に書かれた ID をそのまま使う。

```python
for split in self._decisions.get("splits", []):
    if decisions_module.anchor_matches(split, track, self._tolerance):
        entry["identity"] = str(split["as"])
        break
```

**`as` に既存の人物 ID を書けば、そのまま「既存の人物へ割り当て」になる。**
判定・マスク生成はすべて `BlurPlan` 経由なので、解析し直さずに出力まで一貫する (§3.3)。

### 2.4 プレビューはどこも「本物のぼかし」を出していない

ぼかしを見せている画面は 3 つあり、**いずれも実際のぼかし処理をしていない**。

| 画面 | 実装 | 出しているもの | 画像 (オーバーレイ) |
| --- | --- | --- | --- |
| ぼかし指定画面のキャンバス | `blur_spec_dialog._update_overlay` (`:402`) → `blur_canvas.set_overlay` (`:129`) | 「仕上がり表示」ON のとき、最終マスクを**赤 55% で塗った半透明の絵**。マスク自体は `mask_builder.frame_mask` = 書き出しと同じ計算 | **出していない** (フレームと枠だけ) |
| Timeline 編集画面のプレビュー | `timeline_editor_dialog._update_blur_markers` (`:540`) → `preview_panel.set_blur_markers` (`:405`) | ぼかす形を**赤い枠と塗り**で重ねた目印。コメントにも「**実際のぼかし処理はしない**」と明記 (resolve2 §5.7 の判断) | 出している (`_rebuild_overlays:462` / 画像・動画・字幕) |
| 高精度プレビュー | `preview_panel._show_high_quality` (`:967`) | ffmpeg で**本番と同じ ASS 字幕 + コメントアイコン**を焼いた 1 枚絵 | **出していない** (字幕とアイコンだけ。画像・動画オーバーレイもぼかしも無い) |

「**画像とボカシも反映**」という言い方に当てはまる面が複数ある。
どれを指すかは §10 #1・#2 で確認する。本書は 3 つとも設計し、Phase で切り分ける (§6)。

なお resolve2 §5.7 が実ぼかしを見送った理由は「**1 枚ずつ取得しているので画像処理を足すとスクラブが重くなる**」だった。
当時は実測していない。今回実測した結果、**止まっている間なら十分間に合う**ことが分かった (§2.6 / §3.4)。

### 2.5 依頼者の使い方から読み取れること

* 50 人のうち 21 人を「ぼかさない」、1 人を「ぼかす」に指定している。
  既定方針は `blur_others` なので、**「ぼかさない」を選ぶ作業が主**になっている。
* 統合 `[p5, p1]` は主役 (`p1`) と `p5` を同じ人物とする指定だが、同時に `p5` には `blur` の指定が残っている。
  **再解析待ちの統合と、即時に効く指定とが混ざって、利用者から見て結果が読めない状態**になっている。
  R2-2 (即時に効く割り当て) は、この混乱そのものへの対応でもある。
* 削除した枠 6 件・領域 0 件。輪郭の採用率はログで **11%** (`autoedit_20260920.log`)。

### 2.6 処理時間の実測 (2026-09-20 / 依頼者の素材 / キャンバス 1920x1080・素材 960x540)

| 処理 | 実測 | 備考 |
| --- | --- | --- |
| `BlurPlan` の構築 | **20.6 ms** | 枠 2026 本・人物 50 人。輪郭のデコードを含む |
| `plan.shapes_at` 1 回 | 0.4 ms | 構築済みの plan を使う場合 |
| `mask_builder.frame_mask` 1 枚 | 20.4 ms | **中身はほぼ `BlurPlan` の構築**。毎回作り直している |
| マスク 1 枚 (plan を使い回した場合 / ぼかす 7 件) | **4.8 ms** | 480x270。`_MaskPainter.paint` のみ |
| フレーム 1 枚の取得 (`frame_source.frame_at`) | **52.6 ms** | 960x540。現状のスクラブの主なコスト |
| ぼかし合成: 960x540 全面ガウス (σ=12) + 合成 | 24.7 ms | PIL `GaussianBlur` |
| ぼかし合成: **ぼかす枠だけ切り出して**ガウス + 合成 (3 枠) | **10.4 ms** | 採用案 (§3.4) |
| ぼかし合成: 1920x1080 全面ガウス (σ=24) + 合成 | 67.2 ms | 参考 |
| 解析全体 (依頼者の素材 / 全 3 素材 1795 秒) | **約 1 時間 50 分** | ログの 01:47→03:36 |

**結論**: プレビューへ本物のぼかしを出す追加コストは、`BlurPlan` を使い回せば
**マスク 4.8 ms + 合成 10.4 ms ≒ 15 ms**。フレーム取得 52.6 ms に対して +29% で、
スクラブなら体感できるほどではない。一方、60fps の再生 (1 枚 16.7 ms) には収まらないため、
**再生中は今までどおり目印にする** (§3.4)。

### 2.8 開き直すと必ず解析し直しになる (R5 / 不具合)

**ご認識のとおりで、これは不具合である。**解析結果は既にプロジェクトの隣へ保存されており
(`<プロジェクト名>.blur.json` / `store.cache_path_for`)、再利用する仕組みもある
(`analyzer.analyze:64` の「既に同じ指紋の結果があれば解析しない」)。
**しかし指紋が毎回変わるため、その分岐に入らない。**

#### (a) 指紋が「毎回作り直される一時ファイル」でできている

`store.fingerprint` (`store.py:42`) は素材ごとに**パス・サイズ・更新時刻**を混ぜる。

```python
for path in sorted(str(p) for p in paths if p):
    parts.append(f"path={path}")
    stat = os.stat(path)
    parts.append(f"size={stat.st_size}")
    parts.append(f"mtime={int(stat.st_mtime)}")
```

ところが `media.path` が指しているのは、実行のたびに作り直される一時ファイルである。
依頼者の保存済みプロジェクトを読むと、次のようになっている。

| プロジェクト | `media.path` |
| --- | --- |
| `20260620_…source.timeline.json` | `%TEMP%\autoedit_i_a5erxv\loudness_normalized.mp4` |
| `vod_2877176496.archive.timeline.json` | `%TEMP%\archive_clips_f327g2gm\clip1\normalized.mp4` (他 2 本) |

`timeline.project.keep_media` は既定 `false` (依頼者の `setting.json` も `false`) のため、
素材はプロジェクトの隣に残らない。開き直すと `project_resume.make_media_recover` が
**新しい一時フォルダへ VOD から切り直す** (`archive_clips_<ランダム>`)。
パスも更新時刻も変わるので、**指紋は必ず変わる** → `store.load` が捨てる → 全解析。

しかも `store.fingerprint` のコメントには、

> `source.media_path` (正規化後の一時ファイル) は毎回変わるため使わない。
> `input_path` (元動画) を使うことで、開き直しても同じ指紋になり解析を省ける。

と**意図が明記されている**。実際には `analyzer.analyze:58` が

```python
media_paths = [_media_path(timeline, media_id) for media_id, _ranges in spans]
fingerprint = store.fingerprint(timeline, cfg, media_paths)
```

と**常に `media.path` を渡すため、`input_path` へ倒れる分岐 (`store.py:47`) に入らない**。
意図と実装が食い違っている。

**実証 (2026-09-20 / 依頼者の保存済みプロジェクト)**

| プロジェクト | 保存された指紋 | 今 `media.path` から作る指紋 | 今 `input_path` から作る指紋 |
| --- | --- | --- | --- |
| `20260620_…source` | `fe2f7a48…` | `7e835e5e…` **不一致** | `c55dcaa9…` |
| `vod_2877176496.archive` | `3bbbcd1f…` | `3bbbcd1f…` 一致 (※) | `e1a88d7b…` |

※ アーカイブ側が今たまたま一致するのは、**9/19 の再開で作られた一時フォルダがまだ消えずに残っている**ため。
その 9/19 のログには「ぼかし解析: キャッシュを再利用します」が出ておらず、
`01:47:38` → `03:36:58` の **約 1 時間 50 分の再解析**が走っている。
クリップ経路 (`20260620_…`) は一時フォルダが既に消えており、**不一致が現に起きている**。

#### (b) 保存しても解析結果が付いてこない

`timeline_editor_dialog.save_project` (`:611`) は音声サイドカー (`_export_audio_sidecars`) と
素材の複製 (`_copy_media_beside_project`) は面倒を見るが、**`*.blur.json` は一切動かさない**。

解析結果の置き場は画面を開いた時点の `store.cache_path_for(self._project_path, self._work_dir)` で決まる
(`timeline_editor_dialog.py:460`)。**プロジェクト未保存のまま解析すると結果は `work_dir` に置かれ、
その後「名前を付けて保存」してもプロジェクトの隣へは来ない。**`work_dir` は実行の終わりに消えるため、
次に開くと解析結果そのものが存在しない。

#### (c) 改名・削除が解析結果を知らない

`project_io.related_paths` (`:695`) / `rename_project` (`:714`) / `delete_project` (`:821`) が
面倒を見るのは `<プロジェクト>.autosave.json` と `<プロジェクト>.media/` だけである。

* **改名**すると `.blur.json` が古い名前のまま取り残され、`decisions["cache"]` の相対パスが外れる → 再解析。
* **削除**すると `.blur.json` (依頼者の素材で **6.9MB**) がゴミとして残る。
* プロジェクトライブラリの削除確認にも出ない (`related_paths` を引いているため、足せば自動で出る)。

#### まとめ

| # | 事象 | 影響 |
| --- | --- | --- |
| (a) | 指紋が一時ファイルのパス・更新時刻でできている | **開き直すたびに必ず全解析** (依頼者の素材で約 1 時間 50 分) |
| (b) | 保存が解析結果を隣へ持ってこない | 未保存のまま解析した場合、結果が消える |
| (c) | 改名・削除が解析結果を知らない | 改名で再解析。削除でゴミが残る |

## 3. 方式選定

### 3.1 人物の名前をどこに持つか (Q1)

| 案 | 内容 | 判定 |
| --- | --- | --- |
| A | 解析結果 (`*.blur.json`) の `identities[].name` に持つ | **不可**。キャッシュは指紋が変われば捨てられる (`store.load`)。名前が消える |
| B | `source["blur"].names` に **人物 ID → 名前**で持つ | 可。既存の `identities` (指定) と同じ持ち方で、Undo (`_snapshot` の deepcopy) と `project_io` にそのまま乗る |
| **C (採用)** | B に加え、**命名した時点の枠のアンカーを一緒に持つ** | 採用。解析し直して人物 ID がずれても名前が付いて回る |

**なぜ C が要るか。** resolve3 §10 #8 に記録があるとおり、人物 ID (`p1`, `p2`, …) は
「映っている秒数の多い順」で毎回振り直される。素材を差し替えたり、人物のまとめ方を直したりすると
**`p3` が別人を指す**。指定 (`blur` / `keep`) が別人へ移るのも困るが、
**名前が別人へ移るのは見て分かる形で壊れる**ため、放置できない。

名前 1 件の持ち方:

```json
{"id": "p3", "name": "スタッフA", "anchor": {"media_id": "m1", "t": 512.4, "rect": [820.0, 140.5, 210.0, 480.0]}}
```

アンカーは `decisions.track_anchor` が作るものと同じ形で、1 件あたり約 90 バイト。
名前 50 件でも 5KB 弱に収まる。`decisions.py` 冒頭の「1KB 程度」という方針からは外れるが、
**`excluded` / `splits` が既に同じ形のアンカーを持っている**ため、性質としては同じものを増やすだけである。

名前の当て込み順 (`BlurPlan` の初期化時に 1 回):

1. アンカーが当たる枠があれば、**その枠の (分割・割り当て適用後の) 人物 ID** へ名前を付ける
2. 当たらなければ `id` をそのまま使う
3. 1 人に複数の名前が当たったら**先に登録したものを採用**し、後のものは無視する (ログ DEBUG)

こうすると、解析し直して `p3` → `p7` に番号がずれても、その人が映っていた枠を通して名前が追いかける。
**アンカーに使う枠は「その人物の一番長い枠の真ん中のサンプル」**とする (`track_anchor` と同じ流儀)。

### 3.2 名前の編集操作 (Q2)

| 案 | 判定 |
| --- | --- |
| 一覧のダブルクリックで編集 | **不可**。ダブルクリックは resolve3 §5.5.2 で「ぼかす / ぼかさないの切り替え」に割り当て済み。奪うと既存の操作が壊れる |
| 専用のダイアログ (`QInputDialog`) を出す | 可。ただし 50 人に名前を付けるのにダイアログが 50 回開く |
| **一覧のインライン編集 (採用)** | 採用。`QListWidget.editItem()` で項目の上に直接入力する。開く引き金は **「名前を変更」ボタン / 右クリックメニュー / F2 キー**の 3 つ |

`QListWidget` は既定でダブルクリック編集が効いてしまうため、
**`setEditTriggers(QAbstractItemView.NoEditTriggers)` を明示**し、`editItem()` を呼んだときだけ開く。
これで既存のダブルクリック操作と衝突しない。

一覧の項目は現在 2 行 (`名前` / `秒数 / 指定`) だが、インライン編集は 1 行しか編集できない。
そこで**項目のテキストは名前だけにし、秒数と指定は右寄せの副表示 (カスタムデリゲート) へ移す**。
代案は「編集中だけ 1 行表示に落とす」だが、描画が一瞬変わるため**デリゲートを採用**する (§5.4.2)。

### 3.3 枠を人物へ割り当てる仕組み (Q3)

`plan._entry` (`plan.py:178`) が `splits[].as` の人物 ID をそのまま使うため、
**`as` に書く値を変えるだけで 3 つの操作がすべて同じ仕組みに乗る**。

| 操作 | `as` の値 | コマンド |
| --- | --- | --- |
| 新しい人物にする (既存の「別の人物にする」) | 新規採番 `s1`, `s2`, … | `SplitBlurTrack` (既存) |
| **既存の人物へ割り当てる (新規)** | 既存の人物 ID (`p7` / `s2`) | `AssignBlurTrack` (新規) |
| 元の人物へ戻す | — (項目を消す) | `UnsplitBlurTrack` (既存) |

この方式の効きどころ:

* **即時に効く。**`BlurPlan` は画面・目印・マスク生成すべての入口 (resolve3 §4-5) なので、
  割り当てた瞬間に一覧・枠の色・仕上がり表示・書き出しが揃って変わる。**再解析が要らない。**
* Undo に乗る。`source["blur"]` を書き換えるだけなので `commands._snapshot` がそのまま面倒を見る。
* 既存データと互換。v2 の `splits` はすべて `as = s*` であり、読み方を変えない。

`merges` (「選んだ 2 人を同じ人物にする」) は**残す**。人物まるごとの統合は
解析のクラスタリングへ戻す方が正しく、枠単位の割り当てとは目的が違うため。
ただし**一覧のボタンに「(次の解析から反映)」と明示**し、§2.5 の混乱を減らす。

### 3.4 プレビューへ本物のぼかしを出す方法 (Q4)

**やること**: 書き出しと同じマスク (`mask_builder` の `_MaskPainter`) を作り、
書き出しと同じ効果 (`blur.render.mode` / `strength` → `blur_sigma`) でフレームを加工する。

| 判断 | 採用 | 理由 (§2.6 の実測) |
| --- | --- | --- |
| マスクの作り方 | `frame_mask` ではなく、**`BlurPlan` と `_MaskPainter` を使い回す専用クラス**を新設 | `frame_mask` は毎回 `BlurPlan` を作り直しており、20.4 ms のうち 20.6 ms 相当がその構築。使い回せば 4.8 ms になる |
| ぼかす範囲 | **マスクが白い所の外接矩形だけを切り出して**ぼかす | 全面 24.7 ms → 枠だけ 10.4 ms。何も映っていないフレームは 0 ms (元のフレームをそのまま返す) |
| 切り出しの余白 | σ の 3 倍ぶん広げて切り出し、内側だけ貼り戻す | 切り口でガウスが折り返し、境界に筋が出るのを防ぐ |
| 解像度 | **フレームの解像度のまま**。σ は `フレーム幅 / キャンバス幅` で換算 | 縮小してからぼかしても 17.6 ms までしか下がらず (リサイズ代)、見た目が甘くなるだけ |
| 再生中 | **反映しない。**今までどおり赤い目印に戻す | 15 ms の追加は 60fps (1 枚 16.7 ms) に収まらない |
| PIL が無い環境 | 反映しない。赤い目印・赤い塗りへ落ちる | マスク生成自体が PIL に依存している (`mask_builder`) |

**種類 (ガウス / モザイク) も書き出しに合わせる。**モザイクは `blur_overlay.build_chains` と同じく
「一度粗く縮めて最近傍で戻す」で再現する。強さの見え方が書き出しと揃うことが、この機能の目的である。

### 3.5 プレビューへ「画像」を出す方法 (Q5)

「画像」が何を指すかは §10 #2 で確認するが、取り得る解釈は次の 3 つで、いずれも設計しておく。

| 解釈 | 現状 | 対応 |
| --- | --- | --- |
| (a) **ぼかし指定画面に、オーバーレイ (画像・動画・字幕) が出ていない** | 出ていない (§2.4) | 指定画面のキャンバスへ `preview_items` の部品を重ねる。**ぼかしの上に描く** (§5.7.2) |
| (b) **仕上がり表示が赤い塗りで、絵が見えない** | 赤 55% の塗り | R3 本体 (§3.4) でそのまま解消する。赤い塗りは「どこが削られたか」の確認用として選べる形で残す |
| (c) **高精度プレビューに、画像オーバーレイもぼかしも無い** | 無い (§2.4) | ffmpeg のチェーンへ `overlay` と `blur_overlay.build_chains` を足す (§5.9)。Phase 6 (任意) |

**(a) でオーバーレイをぼかしの上に描くのは、出力がそうなっているため。**
`blur_overlay` のコメントにあるとおり、ぼかしは**必ずフィルタチェーンの先頭**に入る (resolve2 R8)。
字幕・コメントアイコン・画像オーバーレイはぼかしの後に載るのでぼけない。
指定画面でも重ね順を `フレーム → ぼかし → オーバーレイ → 枠` にして、出力と同じ見え方にする。

オーバーレイは人物の枠を隠して指定の邪魔になることがあるため、
**表示の ON/OFF をチェックで切り替えられる**ようにする (既定 ON / `blur.spec.show_overlays`)。

### 3.6 解析結果を開き直しても使えるようにする (Q6 / R5)

#### 3.6.1 解析結果をどこへ置くか

| 案 | 内容 | 判定 |
| --- | --- | --- |
| A | 解析結果をプロジェクト JSON の `source` へ入れる (要望の字面どおり「1 ファイルに保存」) | **不可**。依頼者の素材で **6.9MB**。`commands._snapshot` が `source` を deepcopy するため、**編集操作のたびに 6.9MB をコピーして画面が固まる** (resolve2 §4-2 がこれを理由に別ファイルにした) |
| **B (採用)** | 今までどおり `<プロジェクト名>.blur.json` に置き、**照合の鍵 (指紋) を作り直す**。保存・改名・削除でも付いて回るようにする | 採用。要望の目的 (開き直しても解析し直さない) は満たしつつ、Undo の速さを壊さない |
| C | 指紋をやめ、開くたびに「解析し直しますか」と利用者に聞く | 不可。利用者に判断材料が無い。素材が変わっていれば枠がずれ、変わっていなければ 2 時間待つ |

**要望は「プロジェクトとして保存したときにぼかしの情報も保存されること」であり、
1 つのファイルに詰め込むことではない。**隣に置いたファイルが確実に付いて回れば要望は満たせる (§5.12.3)。

#### 3.6.2 指紋を「素材の由来」で作る

一時ファイルのパスと更新時刻を**一切使わない**。代わりに素材ごとの「由来キー」を作る。

| 経路 | 鍵にするもの |
| --- | --- |
| アーカイブ (`source.archive.clips` にその素材の項目がある) | 元 VOD のサイズ・更新時刻 + その clip の `vod_start` / `vod_end` + `media_role` |
| 通常のクリップ (`source.input_path` がある) | 元動画のサイズ・更新時刻 + `source.media_role` |
| 利用者のファイルをそのまま使っている素材 (OP/ED・画像) | `media.path` のサイズ・更新時刻 (**このファイルは消えない**ので従来どおりでよい) |
| どれにも当てはまらない | `media.path` のサイズ・更新時刻 (従来どおりのフォールバック) |

**パスそのものは混ぜない** (実装で本書の案から変えた / §0.2)。
中身が同じなら、元動画を別のフォルダへ移しても同じ指紋になる方がよい。

どの経路でも、加えて **`幅 x 高さ x round(尺, 2)`** を混ぜる。
復元に失敗して尺や解像度が変わった素材は**別物として解析し直す** (枠がずれたまま使わない / R5-3)。

**なぜ「元動画 + 切り出し範囲」で足りるか。**復元は `clip_writer.cut_region` が
`-ss <vod_start> -i <VOD> -t <長さ> -c copy` という**決まった引数**で切り直す。
同じ VOD・同じ範囲なら毎回同じ中身になり、解析結果の「素材の何秒に、どこに枠があったか」はそのまま通用する。
逆に VOD が差し替わる・切り出し範囲を変えると鍵が変わり、正しく解析し直される。

#### 3.6.3 素材ごとに照合する

解析結果へ素材ごとの鍵も残し、`media_id` 単位で突き合わせる。

```jsonc
"media": {
  "m1": {"key": "vod:…|clip:0.000-611.200|role:normalized", "width": 960, "height": 540, "duration": 611.2}
}
```

* **全部一致したときだけ**再利用する (今回の範囲)。
* 一致しなかった素材があれば、**どの素材の何が変わったかをログとボタンのツールチップに出す** (R5-3)。
  「なぜ 2 時間待たされるのか」が分かるだけで、原因の切り分けが利用者側でできる。
* 一部の素材だけ解析し直す差分解析は**本書の範囲外**とする (§10 #13)。

#### 3.6.4 指紋の作り方を変える = 既存のキャッシュは 1 回だけ無効になる

指紋の式が変われば、今あるキャッシュはすべて一致しなくなる。**移行のために 1 回だけ全解析が要る。**

R4 (人物上限で溢れた枠を残す / §5.5.4) も `SCHEMA_VERSION` を上げるため 1 回の解析し直しを伴う。
**この 2 つは同じリリースへまとめる。**そうすれば利用者が払う待ち時間は**合計 1 回**で済み、
その後は開き直しても解析が走らなくなる (§6 / §10 #6)。

## 4. 設計方針

1. **表示名を作る場所を増やさない。**名前の解決は `BlurPlan.labels()` の中だけで行い、
   画面・目印・マスク生成は今までどおり `labels()` を引く (resolve3 §4-5 の踏襲)。
2. **枠の人物への割り当ては、既存の `splits` の一般化で済ませる。**新しい判定経路を作らない。
3. **プレビューのぼかしは書き出しと同じ関数を通す。**`BlurPlan` → `_MaskPainter` → 同じ σ・同じ種類。
   表示専用の近似は作らない (作ると「画面では消えていたのに出力に残る」が再発する)。
4. **重い計算は使い回す。**`BlurPlan` は指定が変わったときだけ作り直し、スクラブのたびには作らない。
5. **落ちない。**マスク生成・ぼかし合成・見本画像の失敗はすべて握り潰し、元のフレームを出す (resolve2 §5.9)。
6. **設定値はハードコードしない** (`docs/claude.md`)。名前の上限・プレビューのぼかし ON/OFF・
   オーバーレイ表示は `setting.json` の `blur` セクションへ置く (§7)。
7. **既存のプロジェクトを壊さない。**`source["blur"]` は version 2 → 3 にするが、
   v2 をそのまま読め、v3 を古い版で開いても指定は生きる (未知のキーは無視されるだけ)。

### 5.2 データモデル

#### 5.2.1 `source["blur"]` (version 3)

追加するのは `names` の 1 項目だけ。`splits` は**書式を変えずに意味を広げる**。

```jsonc
{
  "version": 3,
  "identities": {"p2": "keep", "p5": "blur"},          // 既存 (指定)
  "merges": [["p2", "p7"]],                            // 既存 (次の解析から反映)
  "regions": [ /* 既存 */ ],
  "excluded": [ /* 既存 */ ],
  "splits": [
    {"media_id": "m1", "t": 512.4, "rect": [820.0, 140.5, 210.0, 480.0], "as": "s1"},  // 新しい人物 (既存)
    {"media_id": "m1", "t": 760.2, "rect": [300.0, 200.0, 180.0, 420.0], "as": "p7"}   // 既存の人物へ割り当て (追加)
  ],
  "region_seq": 4,
  "names": [                                            // ★ 追加
    {"id": "p3", "name": "スタッフA",
     "anchor": {"media_id": "m1", "t": 512.4, "rect": [820.0, 140.5, 210.0, 480.0]}}
  ]
}
```

* `names[].name`: 前後の空白を除き、改行を除いた文字列。空になったら項目ごと捨てる (= 名前なし)。
  長さの上限は `blur.spec.name_max_len` (既定 32 文字)。
* `names[].anchor`: 省略可。`decisions._anchor` で読み、壊れていれば `None` として `id` だけで当てる。
* 互換: `load()` は `version` を見ずに `names` を読む (無ければ空)。
  `store()` は `names` が空なら書かない (従来どおりプロジェクト JSON を無駄に太らせない)。

#### 5.2.2 解析結果 (`*.blur.json`) の変更

| 項目 | 変更 |
| --- | --- |
| `tracks[]` | **人物 ID の無い枠も保存する** (R4 / §5.5.4)。`identity` は空文字 |
| `identities[]` | 「新しい人物にする」で作った人物の見本画像を後から足せるようにする (`id` が `s*` の項目 / §5.5.3) |

`SCHEMA_VERSION` は **3 へ上げる**。人物 ID 無しの枠が増える = 指定画面の見え方が変わるため、
古いキャッシュをそのまま使うと「枠が出る人と出ない人」が混ざる。上げれば一度だけ解析し直される。

> **注意**: 依頼者の素材は解析に約 2 時間かかる (§2.6)。`SCHEMA_VERSION` を上げると
> **次に開いたときに必ず解析し直しになる**。R4 を Phase 3 に置き、名前と割り当て (Phase 1〜2) を
> 先に出せる順番にしてある (§6)。§10 #6 で確認する。

### 5.6 ぼかしのプレビュー (`src/blur/preview.py` / 新規)

#### 5.6.1 公開するもの

```python
# フレーム 1 枚へ、書き出しと同じマスク・同じ効果でぼかしを当てる (ver5 resolve4 §3.4)
#
# 書き出し (mask_builder + blur_overlay) と同じ判定・同じ σ を通すため、
# 画面で見えるぼかしと出力のぼかしが食い違わない (resolve3 §4-5 の踏襲)。
#
# 重い BlurPlan は指定が変わったときだけ作り直し、スクラブのたびには作らない (§2.6)。
class BlurPreview:

    # timeline / analysis / decisions / cfg は BlurPlan と同じもの
    def __init__(self, timeline, analysis, decisions, cfg): ...

    # 指定が変わったら呼ぶ (次の apply で BlurPlan を作り直す)
    def invalidate(self, decisions=None): ...

    # 素材解像度のフレームへぼかしを当てて返す。
    #   frame_rgb   : RGB のバイト列 (高さ x 幅 x 3)
    #   width/height: frame_rgb の大きさ (素材ピクセル)
    #   media_id / source_sec : どの素材の何秒か
    # 戻り値: ぼかし済みのバイト列。ぼかす対象が無い・失敗した場合は **入力をそのまま返す**
    def apply(self, frame_rgb, width, height, media_id, source_sec): ...

    # その時刻の最終マスク (指定画面の「ぼかす範囲 (赤)」表示用)。PIL Image or None
    def mask(self, media_id, source_sec): ...
```

#### 5.6.2 `apply` の手順

1. `BlurPlan` (使い回し) → `_MaskPainter.paint(media_id, source_sec)` でマスクを得る (480x270 / 4.8 ms)
2. マスクが真っ黒なら**入力をそのまま返す** (`Image.getbbox()` が `None`。大半のフレームがこれ)
3. **キャンバス座標のマスクを、素材解像度のフレームへ写す**
   * `geometry.source_to_canvas_transform(media, timeline.width, timeline.height)` で `(倍率, 横, 縦)` を得る
   * マスク上の素材の領域 = `(offset_x * s, offset_y * s, (canvas_w - offset_x) * s, (canvas_h - offset_y) * s)`
     (`s` = マスク幅 / キャンバス幅) を切り出し、`(width, height)` へ拡大する (BILINEAR)
   * レターボックスが無い素材 (倍率 1.0・オフセット 0) では、素直な拡大と一致する
4. マスクの外接矩形を `3σ` ぶん広げて切り出し、**切り出した部分にだけ**効果を当てる
   * `blur.render.mode == "gaussian"` → `ImageFilter.GaussianBlur(σ)`
   * `blur.render.mode == "pixelate"` → 一度 `1/block` へ最近傍で縮め、最近傍で戻す
     (`blur_overlay.build_chains` と同じ式。`block = max(int(σ), 2)`)
   * `σ = blur_sigma(canvas_width, cfg) * (width / canvas_width)`
     … **キャンバス基準の強さをフレームの解像度へ換算する**。これをしないと素材の解像度で強さが変わる
5. `Image.composite(ぼかし, 元, マスク)` で貼り戻し、バイト列にして返す

**失敗は握り潰す。**PIL が無い・例外が出た場合は入力をそのまま返し、WARNING を 1 回だけ出す。

#### 5.6.3 コスト (§2.6 の実測から)

| --- | --- |
| ぼかす対象が映っていない (大半のフレーム) | マスク 4.8 ms のみ (合成は走らない) |
| ぼかす対象が 3〜7 件 | 4.8 + 10.4 ≒ **15 ms** |

| 停止中 + `blur.preview_blur` が ON | **実際のぼかし**。目印 (赤枠) は出さない |
| 再生中 | 従来どおり**赤い目印**。ぼかしは当てない (§3.4) |
| `blur.preview_blur` が OFF | 従来どおり赤い目印 |
| 解析が終わっていない | 何も出さない (現状どおり) |

実装:

* `preview_panel` へ `set_blur_preview(preview_or_none)` を足す。`timeline_editor_dialog` が
  解析完了時 (`_on_blur_analysis_done:473`) と指定画面を閉じた後 (`_open_blur_spec:518`) に渡す。
* `preview_panel._on_frame_ready` (`:438`) で、**停止中かつ `_blur_preview` があるときだけ** `apply` を通す。
  `_on_frame_ready` は GUI スレッドで動くため、15 ms は 1 枚ぶんの遅れで済む。
* `timeline_editor_dialog._update_blur_markers` (`:540`) は
  **「再生中 or ぼかし反映 OFF」のときだけ**目印を出すように変える。
  人物の目印のラベルは、名前が付いていれば名前を出す (§5.4.3)。
* 再生の開始・停止 (`playing_changed`) で 1 枚出し直す (止めた瞬間にぼけた絵へ切り替わる)。

### 5.9 高精度プレビューへの反映 (Phase 6 / 任意)

`preview_panel._show_high_quality` (`:967`) の ffmpeg チェーンを拡張する。

1. **ぼかし**: `BlurPreview.mask()` の 1 枚を PNG (`preview_hq_mask.png`) へ書き出し、
   `blur_overlay.build_chains` と同じ形で**チェーンの先頭へ**足す。
   マスク動画 (`movie=…mkv`) の代わりに PNG を読むだけで、既存の関数へ
   「マスクのパス」として渡せる (`movie=` は PNG も読める)。
2. **画像・動画オーバーレイ**: その時刻に映っているオーバーレイを `-i` で足し、
   `scale` + `overlay=x:y` を**ぼかしの後・字幕の前**へ挟む。位置と大きさは
   `preview_items` が使っている正規化座標から画素へ直す。

**ぼかしは必ず先頭。**後ろへ足すと字幕・コメントアイコン・画像までぼける (resolve2 R8)。

この 2 つは「本番と同じ描画」という高精度プレビューの目的に沿うが、
要望が指しているか確定していない (§10 #1) ため、**独立した Phase** に置く。

### 5.12 解析結果を開き直しても使えるようにする (R5)

#### 5.12.1 素材の由来キー (`store.media_key`)

```python
# 素材の「由来」を表す文字列を返す (ver5 resolve4 §3.6.2)
#
# 一時ファイルのパスと更新時刻は**使わない**。中間ファイルは実行のたびに
# 別の一時フォルダへ作り直されるため、それを鍵にすると開き直すたびに
# 指紋が変わり、解析結果を必ず捨ててしまう (§2.8 (a))。
#
# 代わりに「どの元動画の、どの範囲から、どう作られた素材か」を鍵にする。
# 同じ元動画・同じ範囲なら、復元した中間ファイルの中身は毎回同じになる。
#   アーカイブ : VOD のサイズ・更新時刻 + vod_start / vod_end + media_role
#   クリップ   : 元動画のサイズ・更新時刻 + media_role
#   その他     : media.path のサイズ・更新時刻 (利用者のファイルは消えないため)
# いずれにも「幅 x 高さ x 尺」を混ぜる = 復元がずれていたら別物として解析し直す。
def media_key(timeline, media): ...
```

`fingerprint()` は `media_paths` を受け取る形をやめ、**`media_id` → `media_key` の並び**で作る。

```python
def fingerprint(timeline, cfg, media_ids=None):
    parts = [f"schema={SCHEMA_VERSION}"]
    for media_id in sorted(media_ids or []):
        parts.append(f"{media_id}={media_key(timeline, timeline.media_by_id(media_id))}")
    parts.append(f"canvas={timeline.width}x{timeline.height}")
    ...  # 以降 (sample_fps / detector / models / same_box / silhouette) は従来どおり
```

`analyzer.analyze` (`:58`) の呼び出しを `store.fingerprint(timeline, cfg, [m for m, _r in spans])` へ変える。
`mask_builder.prepare` など他の呼び出し元も同じ引数に揃える (書き出し時の照合も同じ鍵でなければ意味がない)。

> **`store.fingerprint` の古いコメント**「`input_path` を使うことで開き直しても同じ指紋になり解析を省ける」は、
> 本改修で**初めて実際にそうなる**。コメントもあわせて実装に合わせて直す。

#### 5.12.2 素材ごとの照合と、やり直す理由の提示

解析結果へ素材ごとの鍵を残す (§3.6.3)。

```python
# store.new_analysis へ追加
analysis["media"] = {media_id: {"key": …, "width": …, "height": …, "duration": …}}

# 指紋が合わなかったとき、どの素材の何が変わったかを人が読める文にする (R5-3)
# 例: "clip2 の素材が変わりました (元動画の更新時刻が違います)"
#     "clip1 の尺が変わりました (611.2 秒 → 598.4 秒)"
def describe_mismatch(analysis, timeline): ...
```

* `store.load` が指紋不一致で捨てるときに `describe_mismatch` を呼び、**INFO ログへ理由を残す**。
* `timeline_editor_dialog._on_blur_analysis_done` は、解析し直しになった場合に
  ボタンのツールチップへ同じ文を出す (resolve3 で入れた「(確認してください)」の仕組みに相乗りする)。

#### 5.12.3 保存・改名・削除で付いて回るようにする (R5-2)

**(1) 保存 — `timeline_editor_dialog.save_project`**

```python
# 音声サイドカー・素材の複製と同じ並びで、解析結果もプロジェクトの隣へ置く
if self._project_cfg["keep_blur_cache"]:
```

## 6. 実装手順

**「一番損をしている再解析 (R5) を先に止め、次に要望そのもの、プレビューは後から」**の順にする。

| Phase | 内容 | 要件 | 解析し直し |
| --- | --- | --- | --- |
| **0** | **解析結果の再利用**: `store.media_key` / `fingerprint` の作り直し・素材ごとの照合・理由の提示・保存/改名/削除への追従 | **R5 / R5-2 / R5-3** | **1 回だけ必要** (指紋の式が変わるため) |
| 1 | `decisions` v3 (`names` / `with_assign`) + `plan.labels` の名前解決 + コマンド 2 本 | R1 / R2-2 の土台 | 不要 |
| 2 | 指定画面: 人物一覧のデリゲートとインライン編集、「名前を変更」、「新しい人物にする」への改名、「人物へ割り当て」メニュー、名前の表示反映 | R1 / R1-2 / R1-3 / R2 / R2-2 / R2-3 | 不要 |
| 3 | 新しい人物の見本画像 (`store.put_identity_thumb`) / 人物上限で溢れた枠を残す | R4 | **1 回だけ必要** (`SCHEMA_VERSION` 3) |
| 4 | `blur/preview.py` + 指定画面の表示 3 択 | R3 | 不要 |
| 5 | Timeline 編集画面のプレビューへの反映 + 設定項目 | R3 | 不要 |
| 6 | 指定画面のオーバーレイ表示 / 高精度プレビューのぼかし・画像 (任意) | R3-2 | 不要 |

**Phase 0 を最優先にする理由**は費用対効果である。現状は開くたびに約 1 時間 50 分を失っており
(§2.8)、これは他のどの改善よりも大きい。Phase 0 は指定画面に触らないため、
Phase 1 以降と独立して先に出せる。

**Phase 0 と Phase 3 は同じリリースへまとめる。**どちらも解析し直しを 1 回伴うため、
別々に出すと利用者は 2 時間の待ちを 2 回払うことになる。まとめれば**1 回で済み、その後は 0 回**になる
(§3.6.4 / §10 #6)。

```jsonc
"blur": {
  // …既存…
  // プレビューで停止中に実際のぼかしを表示する (ver5 resolve4 §5.8)
  "preview_blur": true,

    "hit_ratio": 0.5,

    // 人物の名前の最大文字数 (ver5 resolve4 §5.3)
    "name_max_len": 32,
    // 指定画面を開いたときの表示 ("blur" 実際のぼかし / "mask" ぼかす範囲 (赤) / "none" 枠だけ)
    "preview_mode": "blur",
    // 指定画面に画像・動画・字幕のオーバーレイを重ねる (ver5 resolve4 §5.7.2)
    "show_overlays": true
  }
}
```

```jsonc
"timeline": {
  "project": {
    // …既存 (keep_media / keep_audio / autosave_suffix / media_dir_suffix …)…
    // プロジェクト保存時に、ぼかしの解析結果をプロジェクトの隣へ残す (ver5 resolve4 §5.12.3)
    // false にすると保存しても隣へ来ないため、開き直したときに解析し直しになる。
    "keep_blur_cache": true
  }
}
```

* `keep_blur_cache` は `keep_audio` と同じ並びで `builder.timeline_config` が型を整える。
* 解析結果はプロジェクト 1 件あたり数 MB (依頼者の素材で 6.9MB) になるため、
  ディスクを使いたくない利用者のために切れるようにしておく。既定は `true`。

* `config.py` の `_DEFAULTS` と `settings_window.DEFAULT_SETTINGS["blur"]` の両方へ同じ既定を入れる
  (既存の規約どおり。`_fill_blur_nested_defaults` が古い設定を補完する)。
* `preview_mode` は `("blur", "mask", "none")` 以外を既定へ落とす。
* **指紋 (`store.fingerprint`) には入れない。**表示だけの設定で、解析結果は変わらないため。

### #1・#2 の詳細 — なぜ確定できないか

request4 の第 3 項「プレビュー画面にて、画像とボカシも反映するようにしてください。」には、
**「画像が反映されていない画面」が実コードに複数ある** (§2.4)。

| --- | --- |
| 指定画面のキャンバスに画像 (オーバーレイ) が無く、ぼかしも赤い塗りだけ | 事実。第 1・2 項と同じ「ボカシ設定画面」の話として一続きに読める |
| Timeline 編集画面のプレビューが、ぼかしだけ目印のまま | 事実。画像オーバーレイは既に出ている |

### #6 の詳細 — 解析し直しは「あと 1 回だけ」にする

依頼者の素材 (3 素材 / 合計 1795 秒) の解析は **約 1 時間 50 分**かかっている
(`autoedit_20260919.log` 01:47:38 → 03:36:58)。

現状はこれを**開くたびに払っている** (§2.8)。Phase 0 (R5) を入れると、

| | 現状 | Phase 0 のみ | Phase 0 + Phase 3 を同時に |
| --- | --- | --- | --- |
| 移行のための解析し直し | — | 1 回 | **1 回** |
| 2 回目以降に開いたとき | **毎回 約 1 時間 50 分** | 0 | 0 |
| 人物上限で溢れた枠 (ぼかし漏れ) | 直らない | 直らない | 直る |

Phase 0 と Phase 3 を別々のリリースにすると、利用者は移行のための 2 時間を**2 回**払う。
**同じリリースへまとめれば 1 回で済む。**Phase 1〜2 (名前と割り当て) は解析結果に触らないため、
まとめても増えない。これが推奨の理由である。

なお R4 の代案として「`blur.analysis.max_identities` を 50 → 100 へ上げる」だけでも溢れは減るが、
**`max_identities` は指紋に入っていない**ため、上げても解析し直しは起きず、キャッシュがある間は何も変わらない。
効かせるには結局解析し直しが要るうえ、そのときは人物数が変わって
**人物 ID が総ずれ**する (resolve3 §10 #8)。R4 の方が筋が良い。

### #11 の詳細 — なぜ 1 つのファイルにまとめないか

要望の字面は「プロジェクトとして保存した際にボカシの情報も保存できないか」である。
**ぼかしの「指定」(誰をぼかす / ぼかさない・削除した枠・追加した枠) は、既にプロジェクト JSON の中に入っている**
(`source["blur"]` / `decisions.py`)。保存して開き直せば、この指定はそのまま残っている。

残りの「解析結果」(検出した枠の座標と輪郭) だけが別ファイルで、これが依頼者の素材で **6.9MB** ある。
`commands._snapshot` は Undo のために `timeline.source` を毎回 deepcopy するため、
ここへ 6.9MB を入れると**クリップを 1 つ動かすたびに 6.9MB のコピーが走り、編集画面が固まる**
(resolve2 §4-2 がこの理由で別ファイルにした)。

したがって「1 ファイルにする」のではなく、
**隣のファイルが保存・改名・削除・移動のすべてで確実に付いて回るようにする** (§5.12.3) ことで、
利用者から見た要望 —「保存して開き直したらぼかし判定をやり直さない」— を満たす。
