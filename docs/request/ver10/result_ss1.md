## 0. 先に結論

### 0.1 4 行で

1. **分離は文字起こしを明確に悪化させる (正解データのある 2 素材で再現)。**
   **S1 で CER 0.334 → 0.502 (相対 +50.1%)**、**S3 で 0.066 → 0.092 (相対 +40.1%)** (§5.1 / §11.2)。
   S1 では取りこぼしが **5.6% → 22.0%**、認識できた文字数が **2,274 → 1,821 字 (2 割減)** に落ちた。
   htdemucs の `vocals` が配信者の声そのものを削っている (§5.2)。
   「無音カットは駄目でも文字起こし専用の前処理として残る」という最後の可能性は**消えた**。
2. **音声分離そのものは正しく動く。** htdemucs の `vocals` は時間軸を 1 サンプルも狂わせず
   取り出せており (長さ厳密・位置ずれ 0 / §3)、21 分素材でも RTF 0.75 で安定している (§6)。
3. **無音カットの改善は、ほぼ「閾値を正しく選ぶこと」で説明できる。**
   閾値を揃えて比べると、分離の寄与は F1 素材で **+0.1〜+0.9 ポイント**しかない (§4.5-2)。
   当初 S5 で見えた「残存率 78.4% → 32.7%」という劇的な改善は、
   **現行の閾値推定が -37dB という異常値を返していたこと**が原因だった (§4.5-3)。
   元音声を -23dB で切れば分離音とほぼ同じ性能になる。
   **ただし「閾値を直せば良くなる」も正解データでは成立しなかった** —
   S1 は最良が「カットしない」、**S3 は現行の -21dB がそのまま最良**で、
   どちらも伸びしろが無い (§9.3-2 / §11.3)。残る問題は S5 の異常値だけである (§11.5-1)。
4. **分離が与えるものは「閾値への頑健さ」だけ。** 元音声は閾値を外すと崩壊する (-40dB で 34.7%) が、
   分離音は全域で 90〜92.5% に収まる (§4.5-4)。
   ただし代償は **RTF 0.75 = 3 時間 VOD で +2.3 時間**であり、§3.6 の基準 (0.3) を満たさない。

### 0.3 いちばん大事な発見 — 直すべきは閾値推定

**分離を入れるより先に、`analyze_min_speech_db` を直すほうが効く。**

| 素材 | 現行の自動閾値 | 代理指標で最良の閾値 | 現行の調和平均 → 最良 |
| --- | --- | --- | --- |
| S5 (F1) | **-37dB** | **-23dB** | **45.3% → 91.6%** |
| S3 (F1) | -21dB | -30dB | 91.4% → 92.1% |
| S1 (IRL) | -17dB | -14dB | 0.0% → 4.1% |

S5 では**閾値の選び方だけで 46 ポイント**動く。これは**コスト 0** で、
分離 (RTF 0.75) が稼ぐ +0.9 ポイントとは比較にならない。
ver9 resolve4 §8「分離より先に試せる軽い手」の指摘がそのまま当たった。

> **この見立ては 2026-11-12 に大きく後退した。**
> 正解データを作った 2 素材のどちらにも**閾値推定の改善余地が無かった**。
>
> | 素材 | 現行の自動閾値 | 正解データでの最良 | 伸びしろ |
> | --- | --- | --- | --- |
> | S1 (IRL / 無音率 0%) | -17dB | **「カットしない」** (-20dB 以下 / M1 0.8340) | **無し** (§9.3-2) |
> | S3 (F1 視聴 / 無音率 66%) | **-21dB** | **-21dB = 現行** (M1 0.7654) | **無し** (§11.3) |
>
> さらに**代理指標は S3 の最良閾値を 9dB 外していた** (-30dB と判定 / §11.4)。
> 上の表の「代理指標で最良の閾値」と「46 ポイント」も同じ性質の数字なので、そのまま信じられない。
>
> 残る根拠は **S5 が -37dB という異常値を返すこと**だけである。これは全素材の底上げではなく
> **「閾値推定が壊れるケースの修復」**として扱うべきだった (§8.1 / §11.5-1)。
>
> **その原因は 2026-11-12 に判明した (§12)。**
> S5 は低域が強い素材で、**-28dB 前後の定常ノイズが「発話候補区間」に 27% 混入**しており、
> 10 パーセンタイルが完全にノイズ領域に落ちていた。
> **`max` (ピーク音量) で非発話区間を外せば直る** — S5 は -37dB → -20dB、
> **S1 / S3 の閾値は 1dB も動かない** (§12.3)。
> つまり「閾値推定を直す」の正体は**全素材の底上げではなく、この 1 つのバグの修復**だった。

### 2.0 S1 の正体 — **IRL 配信だった** (2026-11-09 / 利用者の指摘で判明)

**S1 は配信者 3 人による IRL 配信** (展示会会場を歩きながらブースを回る回) である。
選定時は「音が常時鳴っている回」= ゲーム音が大きい回と読んでいたが、
鳴り続けていたのは**会場のざわめき (人混み・BGM・他ブースの音)** だった。
認識結果の内容 (ブース紹介・エルガト・Stream Deck・「あと 3 日あるので遊びに来てください」) で裏が取れている。

これは実験の解釈を変える。

| | 当初の想定 (ゲーム配信) | S1 の実態 (IRL 配信) |
| --- | --- | --- |
| 常時鳴っている音 | ゲームの BGM・SE | 会場のざわめき・**周囲の人の声** |
| 分離で落としたいもの | 音楽・効果音 | 環境ノイズ・**他人の声** |
| htdemucs (音楽分離) の向き | **合う** (BGM を落とす前提の設計) | **合わない。** `vocals` は周囲の人の声も拾う |
| 配信者が喋っている割合 | 低い (ゲーム中は黙る) | **高い** (実測 64〜71%) |
| 無音カットの伸びしろ | 大きい | **小さい** (最大でも 3 割弱) |

**ここが効いている**: 分離した `vocals` が元音声より平均 4dB しか低くなかった (§4.2) のは、
**周囲の人の声も「声」として残るため**である。
`docs/quality/resolve1.md` §12.3-1 の「ゲーム内ボイスは声なので分離しても残る」と同じ限界が、
IRL では「周囲の人の声」として現れている。

→ **S1 はこの実験の仮説を試す素材として向いていない。**
　 「悪化しないことの確認」には使えるが、**効果の確認には BGM・SE が主役のゲーム配信が必要**
　 (ver9 resolve4 §5.1 が htdemucs を第 1 候補にした理由がそれである)。
　 §8 の次アクションに「ゲーム配信の素材を 1 本選ぶ」を追加した。

### 4.3 `silencedetect` が分離音を扱えない (原因)

S1 で閾値を振った結果 (最小無音 0.6 秒は固定):

| 閾値 | C0 残存率 | C0 区間数 | C1 残存率 | C1 区間数 |
| --- | --- | --- | --- | --- |
| -17 dB | 99.9% | 2 | 99.1% | 8 |
| -20 dB | 100.0% | 1 | **100.0%** | 1 |
| -25 dB | 100.0% | 1 | **100.0%** | 1 |
| -30 dB | 100.0% | 1 | **100.0%** | 1 |
| -35 dB | 100.0% | 1 | **100.0%** | 1 |
| -40 dB | 100.0% | 1 | **100.0%** | 1 |

**閾値をどれだけ下げても無音は 1 件も出ない。**
`silencedetect` は「0.6 秒のあいだ 1 度も閾値を超えないこと」を求めるため、
分離音に常に乗っている残渣のピークで連続性が切れる。
**平均レベルは下がっているのに「ずっと静か」とは認識されない。**

> 閾値 -20dB で「100%」なのに -17dB で「99.1%」になるのは矛盾ではない。
> 閾値が高い (= -17dB) ほど「静か」と見なす範囲が広いためで、判定は単調である。

| -25 dB 以下 | 100.0% | 1 | 0.0% |

削減がフレーム割合 (52%) ほど伸びないのは、**静かな区間が短く散らばっている**ためである

### 4.5 閾値を揃えて比べ直した — **分離の寄与はほとんど無かった** (2026-11-09)

§4.1〜§4.4 は「自動で決まった閾値」同士の比較だった。
**閾値を揃えて並べ直すと結論が変わる。** そのために正解データ無しで使える代理指標を作った。

#### 4.5-1. 代理指標 (と、最初に間違えた指標)

| | 定義 |
| --- | --- |
| 発話時間 | C0 の認識結果の**語の時刻** (`word_spans`) を重ね合わせたもの |
| **発話の残存** | 残す区間 ∩ 発話 ÷ 発話 (高いほど取りこぼしが少ない) |
| **非発話の削除** | (非発話 − 残す区間) ÷ 非発話 (高いほど不要な音を削れている) |
| 調和平均 | 上 2 つの F1。閾値の良さを 1 つの数にする |

**最初は認識の「区間」をそのまま発話時間として使い、誤った結論を出した。**
認識の区間は VAD の都合で実発話よりはるかに長くなる (実測: 10 文字の一言に 14〜25 秒)。
そのため発話時間が 3 倍近く過大になり、「分離は発話も同じ割合で削っている」と読めてしまった。

| 素材 | 区間ベース (誤) | **語ベース (正)** |
| --- | --- | --- |
| S1 | 70.3% | **67.2%** |
| S3 | 87.2% | **32.9%** |
| S5 | 92.4% | **32.3%** |

→ 以降の数字はすべて語ベースである (`tools/splitsound/sweep.py`)。

#### 4.5-2. 閾値スイープの結果 (各条件の最良点)

| 素材 | 背景 | C0 (元音声) の最良 | C1 (htdemucs) の最良 | C3 (+ゲート) の最良 | 分離の寄与 |
| --- | --- | --- | --- | --- | --- |
| **S3** (F1) | エンジン音 (断続) | **92.1%** (-30dB) | 92.2% (-30dB) | 92.2% (-30dB) | **+0.1 pt** |
| **S5** (F1) | エンジン音 (強・常時) | **91.6%** (-23dB) | 92.5% (-40dB) | 92.5% (-40dB) | **+0.9 pt** |
| **S1** (IRL) | 人混み・人の声 | **4.1%** (-14dB) | 21.7% (-14dB) | **34.4%** (-14dB) | +17.6 / **+30.3 pt** |

(数字は調和平均。全データは `output/_splitsound/sweep.md`)

#### 4.5-3. §4.1 の「S5 で 78.4% → 32.7%」の正体は**閾値の異常値**だった

| S5 / C0 (元音声) | 閾値 | 残存率 | 発話の残存 | 非発話の削除 | 調和平均 |
| --- | --- | --- | --- | --- | --- |
| 自動で選ばれた値 | **-37dB** | 0.784 | 95.5% | 29.7% | **45.3%** |
| 良い点 | **-23dB** | 0.329 | 89.3% | 94.0% | **91.6%** |
| 分離音 (C1) の最良 | -40dB | 0.363 | 93.8% | 91.2% | **92.5%** |

**元音声を -23dB で切れば、分離した音とほぼ同じ性能 (91.6% 対 92.5%) になる。**
§4.1 で見えた劇的な改善は、分離の効果ではなく
**`analyze_min_speech_db` が -37dB という異常値を返していたこと**が原因だった。

原因: エンジン音があるため、発話候補区間 (緩い基準 -30dB で検出) に
ノイズだけの静かな区間が多数混ざり、その下側 10% 分位点が -37dB まで落ちる。
分離すると候補区間が実際の声だけになり -20dB になる。
**分離は閾値推定の壊れ方を間接的に治していただけ**である。

#### 4.5-4. 分離の本当の価値は「閾値への頑健さ」

| 閾値 | S5 / C0 の調和平均 | S5 / C1 の調和平均 |
| --- | --- | --- |
| -20dB | 91.4% | 91.4% |
| -23dB | **91.6%** | 91.6% |
| -26dB | 88.5% | 91.9% |
| -30dB | 74.7% | 92.3% |
| -34dB | 55.7% | 92.4% |
| -37dB | 45.3% | 92.3% |
| -40dB | 34.7% | **92.5%** |

**C0 は閾値を外すと崩壊する (-40dB で 34.7%)。C1 は全域で 90〜92.5% に収まる。**
ピーク性能の差は +0.9 pt しかないが、「閾値を外しても壊れない」という性質は
利用者が閾値を触る製品では価値がある。ただしその代償は **RTF 0.75** である。

#### 4.5-5. IRL (S1) はどの条件でも使えない

発話が 67.2% を占め、残る 33% は**発話と同じ音量の人混み**である。

| 条件 | 最良の非発話の削除 | 発話の残存 |
| --- | --- | --- |
| C0 | **2.1%** | 99.5% |
| C1 | 12.2% | 97.2% |
| C3 (+ゲート) | **21.1%** | 94.5% |

分離 + ゲートで非発話の削除が 2.1% → 21.1% (10 倍) に上がるが、
**絶対値として使える水準ではない**。IRL では「配信者が話している個所だけ」は
現状のどの手でも成立しない。

> **C3 (ゲート) は F1 素材では C1 と完全に同じ数字**になった。
> ゲートが効くのは IRL のように「分離しても残渣が多い」素材だけである。

#### 同じ区間で 2 人が話しているとき

**行を分けて 2 行書く** (時刻が重なってよい)。
無音カット側 (M1 / M2) は区間を重ね合わせて「残したい声がある時間」とし、
CER は本文を開始時刻の順に繋ぐ。
片方が主でもう片方が後ろのガヤなら主の 1 行だけ、両方聞き取れれば 2 行、
片方だけ聞き取れなければその行を `[?]` にする (`tools/splitsound/truth_schema.md`)。

> 認識エンジンは 1 本の音声から 1 本の文字列しか出さないため、2 人分を正解に書くと
> 片方は取りこぼしとして CER に乗る。これは**現状の限界を正しく映した数字**であり、
> 全条件が同じ正解を使うので C0 と C1 の差は正しく出る。

#### 人が聞き取れない区間の扱い

推測で書くと**正しく認識できていた方が誤りに数えられる**ため、`[?]` を入れて採点から外す。
`[?]` の行では**正解と生成テロップの両方**をその区間ごと外す (片側だけ外すと不当に悪く出る)。
区分 (残す/切る) は残るので M1 / M2 / M5 には使われる。
`metrics.csv` に `unclear_rows` / `unclear_sec` / **`cer_scored_ratio`** (採点できた割合) を出し、
CER の絶対値はこの割合と一緒に読む。IRL のようにざわめきが大きい素材では
聞き取れない区間が増えるため、**この列が条件間で揃っていることを確認してから CER を比べる**
(正解は全条件で同じなので、揃わないことは原理上ないが、記録として残す)。

## 7. 判明した技術的事実 (設計へ反映済み)

### 7.1 同じファイルの同じ時刻が、読み方で 13 サンプルずれる

手元の m4a (AAC) は 325 秒付近にタイムスタンプの不連続を持っており、

- `-ss` を `-i` の後に置く読み方 (タイムスタンプ基準)
- 先頭から流し読みしてサンプルを数える読み方 (サンプル数基準)

で**同じ時刻の内容が 13 サンプルずれた** (正規化相互相関 0.9999 / 誤差ではない)。
`silencedetect` が返す時刻は前者、分離を作るのに自然なのは後者なので、
混ぜると**不連続より後ろの編集点が全部ずれる**。

- 実験側の対処: 共通入力を **PCM WAV へ 1 回だけ確定**させ、全条件がそれだけを見る。
- 本体側への含み: `voice_isolation` は「入力と同じ時間軸を持つ音声」を作る責務を負い、
  §4.2-4 の 3 検査 (長さ・無音でない・位置ずれ) を**本体にも実装する**。
  これは分離を足して初めて踏む問題である (設計書 §4.2-2a)。

### 7.2 `silencedetect` は「平均が下がった音」では無音を見つけない

§4.3 のとおり。**分離の効果を無音カットへ渡すには、間にゲートが必要**である
(設計書 §12.4-4 / 代案は「100ms RMS 基準の検出器を分離音専用に持つ」)。

### 7.3 DeepFilterNet は pip で入らない

```text
$ python -m pip install --dry-run deepfilternet
  Cargo, the Rust package manager, is not installed or is not on PATH.
  → 依存の deepfilterlib は Python 3.12 / Windows 向け wheel が無く、
    ソースビルドに Rust ツールチェーンを要求する
  → --only-binary :all: でも全バージョン (0.1.2〜0.5.6) が解決不能
```

対処: 公式配布の単体実行ファイル **`deep-filter`** を外部プロセスとして呼ぶ実装にした
(`--df-bin` / 環境変数 `SPLITSOUND_DF_BIN`)。実行ファイルが置かれ次第 C2 を測れる。

> **副産物**: DF3 を exe か ONNX で動かせるなら、**torch を同梱しなくて済む**。
> 設計書 §5.8 の「配布 +361MB」は htdemucs を採る場合の話で、
> DF3 だけなら数 MB〜十数 MB で収まる。

### 7.4 demucs の導入は既存環境を壊さない

`pip install demucs` が追加したのは `demucs einops julius lameenc sphn` の 5 つだけで、
**torch 2.11.0+cpu は再インストールされていない** (事前に `--dry-run` で確認)。
htdemucs の重み (約 80MB) は初回実行時に HuggingFace から自動取得される。

## 9. 閾値は「最終動画に出るテロップ」を変えるか — S1 で実測 (2026-11-12)

### 9.1 なぜ測る必要があったか

§5 の CER は「**認識エンジンの素の精度**」であり、**閾値に依存しない**。
現行の既定フロー (`timeline.enabled=true` / `silence_cut.mode=edit_points`) では、
認識は**素材そのまま**に対して行うためである。

```text
src/modules/subtitle_generator.py (recognize_for_timeline)
    認識 = text_source.extract(context.current_video_path())   ← 素材そのまま
    → speaker_filter.apply()           配信者以外の声を落とす (F15)
    → テロップの単位を決める           (keep_segments を見てカット境界で切る)
    → map_items_to_timeline()          ← ★ ここで閾値が効く
         ・一部がカットへかかる → かかった分だけ短くなる
         ・全体がカットへ落ちる → 載せない (カットした無音への幻聴字幕もここで落ちる)
```

つまり**閾値は「どのテロップが最終動画に出るか」を決めている**が、
`evaluate.py` の CER は認識結果を全部つないで比べているため、この影響を測っていなかった。

> **認識が閾値非依存であることは、この実験を安くする。**
> ASR を再実行せず、既にある認識結果を閾値ごとに絞り直すだけで測れる
> (S1 の認識は 1 回 14 分。12 閾値 × 2 条件 = 24 回分を回避した)。
> 落ちる / 残るの判定は推測で再実装せず、**実機と同じ `TimeMap.split_interval` を import して**使っている
> (`tools/splitsound/sweep_truth.py`)。

### 9.3 分かったこと 3 点

**1. ゲーム音テロップ (M4) は閾値で落とせない。**
閾値を -17dB から -5dB まで 12dB 分厳しくしても、
**M4 は 10 件 → 8 件にしか減らない**。
その代償は CER 0.3344 → 0.4075 (**+21.9% 悪化**)、
取りこぼし 5.6% → **19.6%** (3.5 倍)、テロップ 29 件の消失である。
理由は明らかで、**S1 は環境音と配信者の声が同じ区間に重なっている** (無音率 0%) ため、
音量の閾値では両者を分けられない。

**2. S1 では「カットしない」が M1 最良。**
-20dB 以下では残す区間が **1 個** (= 丸ごと残す) になり、そのとき M1 = 0.8340 で最良になる。
現行の -17dB (2 区間 / M1 0.8332) はすでにほぼその位置にある。
**無音カットが機能する余地が構造的に無い**ことが、正解データで裏付けられた。

**3. 分離音 (C1) はどの閾値でも C0 を下回る。**
C1 の全 12 閾値で CER は 0.5021〜0.5636、取りこぼしは 22.0%〜37.9% で、
**C0 の最悪値よりも悪い**。閾値をどう選んでも分離の不利は埋まらない
(§8.0 の no-go 判定の追認)。

### 9.4 M4 対策は閾値ではなく `speaker_filter` の仕事である

この調査で分かったことだが、実機には**すでに対策が入っている**。

```text
src/modules/subtitle_generator.py:
  # ゲーム内のボイス (無線通信・カットシーンの台詞) は人の声そのものなので、
  # VAD でも音源分離でも配信者の声と分かれない (§12.3-1)。
  # 配信者が「VOD 全体で最も長く喋る 1 人」であることを使って絞り込む。
  timeline_items, _stats = speaker_filter.apply(...)   # F15 / docs/quality/resolve1.md §12.5
```

**「音源分離でも配信者の声と分かれない」という認識がすでにコードに書かれており、
今回の実測 (§5.2 / §9.3) はそれを数字で裏付けた形になる。**

なお、ハーネスの認識結果は**素の結果**で `speaker_filter` を通していないため
(`run_conditions.py`: 設定差で CER が動くのを避けるため整形を掛けていない)、
**実機の M4 はここで出た 10 件より小さい**。
この表は「閾値による変化の向きと大きさ」を読むためのものである。

### 9.5 §0.3 (閾値推定の改善) への条件付け

§0.3 は「分離を入れるより先に閾値推定を直すほうが効く」としたが、
**S1 (IRL / 無音率 0%) に限っては閾値も効かない** (最良が「カットしない」なので、
直しても得るものが無い)。

閾値推定の改善が 46 ポイント動くと示しているのは **S5 (F1 視聴 / 無音率 66%)** であり、
これは代理指標の数字で、**S5 には正解データが無い**。
つまり「閾値推定を直せば良くなる」は**無音が存在する素材に限った話**であり、
検証するには S3 / S5 の正解データが必要になる (§8.1 #2)。

## 10. S3 の正解データ作成の準備 (2026-11-12)

§9.5 の結論 (閾値推定の改善は無音がある素材でしか検証できない) を受けて、
S3 (F1 視聴 / 6 分) の正解データ作成に着手した。その準備で分かったことを残す。

### 10.1 S3 は S1 と**正反対**の素材だった (実測)

`analysis_source.wav` の 100ms ごとの RMS を測った結果:

| | 非発話区間の中央値 | -50dB 未満 (ほぼ無音) の割合 |
| --- | --- | --- |
| S1 (IRL / 展示会) | **-17.4dB** | **0.0%** = 本当に鳴り続けている |
| S3 (F1 視聴) | **-58.9dB** | **84.5%** = ほぼ無音 |

**§2.2 の「S3 はエンジン音と実況が常に背景に乗る」という判定は、実測と食い違っていた。**
実際には配信者が喋っていない時間はほぼ無音である。
音が鳴っている空き区間は 22 件あるが、鳴っている時間の合計は 28 秒で、
**1 秒を超えるものは 4 件だけ**だった。

→ S3 は「非音声の背景を分離で落とす」本命素材ではなく、
**「無音を正しく切れるか」を測る素材**である。分離の出番はここにも無い。

### 10.2 作業ページの作り方を 3 点直した

**1. 認識区間ではなく「語の時刻」で行を切る (`--by-words`)**

付けないと時刻が過大になり、M1 / M2 が意味を失う。

| | S3 で覆う時間 (尺 360s) |
| --- | --- |
| 認識区間そのまま | **314.0s (87.2%)** ← 喋っていない時間まで `host` になる |
| `--by-words` | **147.5s (41.0%)** (語の union の真値 118.6s + 息継ぎ) |

S1 は発話が密 (69.6%) なので区間のままでも害が小さかったが、
S3 では**区間ベースが実発話の 2.5 倍**になるため、このままでは使えなかった。

これには `run_conditions.py` が**語の本文**を保存する必要があり、S3 の C0 を回し直した
(4 分)。既存の数字は完全に再現した (items 65 件 / 閾値 -21dB / 本文 818 字がすべて一致)。

**2. faster-whisper の語時刻の癖へ対処した**

各認識区間の最初の語は**区間の開始時刻へ強制的に合わせられる**ため、
実発話より早い断片ができる (「マ」が 10.18 / 次の語「ジ」が 16.76 = 6 秒の空白)。
この断片の時刻を残すと喋っていない時間を `host` として記録してしまうので、
**1〜2 文字の断片は時刻を捨てて本文だけ本体の行へ寄せる**ようにした。
結果、65 区間 → **71 行**で、本文は 804 字すべて保存される。

**3. 空き区間の音量を実測して出す**

空き区間 (灰色の行) に `音あり 9.0s` / `実測ほぼ無音` の印を付け、
「音がある空きだけ」で絞り込めるようにした。
S3 では 33 件のうち**音ありが 22 件**、うち 1 秒超は 4 件なので、確認はそこだけで足りる。

### 10.3 S3 では `game_everywhere` を宣言する (方針変更)

## 12. S5 の閾値推定が壊れる原因 (§8.1 #1 の調査 / 2026-11-12)

### 12.1 結論

**低域の定常ノイズが「発話候補区間」に混入し、分位点を引き下げていた。**
`analyze_min_speech_db` の設計そのものではなく、**発話候補区間の作り方**に原因がある。
`max`(ピーク音量) を見て非発話区間を外せば直り、**S1 / S3 の閾値は 1dB も動かない**。

### 12.2 原因

`src/modules/volume_analyzer.py` の `analyze_min_speech_db` はこう動く。

```text
① base_noise_db (既定 -30dB) で無音検出 → その補集合を「発話候補区間」にする
② 0.8 秒以下の区間を捨てる / 長い順に 100 区間まで標本化
③ 各区間の代表音量 (mean) を測る
④ その 10 パーセンタイル (metric="percentile" / percentile=10) を閾値にする
```

S5 (「低域が強い / 別 VOD」) では **63〜97 秒付近に -28dB 前後の低域ノイズが継続して鳴っている**。
これが ① の -30dB を**わずかに超える**ため、無音と判定されず発話候補に入る。

発話候補 70 区間を `max` で分けると、**二峰にきれいに分かれた**。

| | 区間数 | 合計 | mean の範囲 | **max の範囲** |
| --- | --- | --- | --- | --- |
| **非発話 (低域ノイズ)** | **19 区間** | **53.6s** | -38.2 〜 -31.8 dB | **-28.8 〜 -23.7 dB** |
| 発話 | 51 区間 | 116.6s | -19.8 〜 -10.9 dB | **-4.9 〜 -1.1 dB** |

**`max` に 19dB の空白がある** (-23.7 と -4.9 の間)。
人の発話はピークが立つが、定常ノイズは立たないためである。

候補の **27% (19/70) がノイズ**なので、**10 パーセンタイルを採ると完全にノイズ領域に落ちる**。

| | S5 の mean dB の分位点 |
| --- | --- |
| 0% | -38.2 dB |
| **10% (現行の設定)** | **-37.2 dB ← これが閾値になっていた** |
| 25% | -32.2 dB |
| 50% | -18.1 dB |

`metric="percentile"` / `percentile=10` は「少数の外れ値」への対策としては正しく働くが、
**27% の汚染には足りなかった**。

### 12.3 対策案の比較

いずれも「発話候補区間の mean dB の 10% 分位点を閾値にする」ことは変えず、
**どの区間を候補に含めるか**だけを変えた実測である。

| 方式 | S1 | S3 | **S5** |
| --- | --- | --- | --- |
| **現行 (全区間)** | -17 dB | -21 dB | **-37 dB (異常)** |
| **`max >= -20dB` の区間だけ使う** | **-17 dB** | **-21 dB** | **-19 dB** |
| `max >= -25dB` の区間だけ使う | -17 dB | -21 dB | -20 dB |
| `max >= -15dB` 〜 `-10dB` | -17 dB | -21 dB | -19 dB |
| percentile を 30 に上げる | -17 dB | **-20 dB** | -20 dB |
| percentile を 50 に上げる | -17 dB | **-18 dB** | -18 dB |

- **`max` で絞る案は S5 だけを直し、S1 / S3 を 1dB も動かさない。**
  `max` の空白が 19dB あるため、-25dB 〜 -10dB のどこで切っても結果は同じになる。
- **percentile を上げる案は S3 を悪化させる** (-21dB = 正解データでの最良 → -20dB)。
  S3 の正解データで確かめた最良は -21dB なので (§11.3)、これは採れない。

### 12.4 対策の効果 (S5 / 代理指標)

| 閾値 | 残存率 | 発話の残存 | 非発話の削除 | 調和平均 |
| --- | --- | --- | --- | --- |
| **-37dB (現行)** | **0.784** | 95.5% | **29.7%** | **45.3%** |
| **-20dB (`max` で絞った場合)** | **0.327** | 88.9% | **94.1%** | **91.4%** |
| -23dB (代理指標での最良) | 0.329 | 89.3% | 94.0% | 91.6% |

**調和平均 45.3% → 91.4% (+46 ポイント)。**

> **代理指標の絶対値は信用しない** (S3 で最良閾値を 9dB 外した / §11.4)。
> ただし**残存率は代理指標に依存しない事実**である。
> S5 の語ベースの発話は **32.3%** しかないのに、現行の -37dB は **78.4% を残している**
> (2.4 倍残しすぎ)。-20dB なら 32.7% で発話率とほぼ一致する。
> 「現行が壊れている」ことはこの 1 点で十分に言える。

### 12.5 実装 — **済** (ver11 resolve1 / 2026-11-12)

設計と実装の記録は  へ移した。
実測: S5 は **-37dB → -19dB** (70 区間のうち 19 区間を除外)、
**S1 (-17dB) ・ S3 (-21dB) は 1dB も動かない**。
新規テスト 8 件 / 既存を含む全 2,327 件 OK。

以下は起案時の案であり、そのまま実装された。

`src/` は未変更のままである。実装は `docs/CLAUDE.md` の決め (実装前に設計) に従い、
**別 resolve として起票してから**行う。

| | 案 |
| --- | --- |
| 設定 | `volume_analysis.min_region_peak_db` を追加 (既定 **-20**)。`null` / 未設定で従来動作 |
| 変更箇所 | `analyze_min_speech_db` の ③ — `values.append(value)` の前に `max_db < min_region_peak_db` の区間を外す |
| 既存への影響 | S1 / S3 では 1 区間も外れず**閾値が変わらない** (§12.3 の実測)。`per_sec` 経路 (`_region_levels_from_scan`) も `max_db` を返すので同じ処理で足りる |
| 外し過ぎの防止 | 全区間が外れた場合は**従来どおり全区間で計算する** (フォールバック)。静かな素材で候補が消えるのを防ぐ |
| 検証 | S5 の正解データを作って M1 / M2 で確かめるのが本筋 (§8.1 #3)。代理指標の絶対値は使えない |

> **なぜ `max` が効くのか** (設計の根拠): 人の声は子音・母音の立ち上がりでピークが立ち、
> `mean` と `max` の差が大きい (S5 の発話区間で 15dB 前後)。
> 一方、低域の定常ノイズは差が小さい (同 9.6dB)。
> `base_noise_db` は **mean ではなく瞬間値**で無音を判定するため、
> 「ピークが立たないが常に鳴っている音」を無音と判定できない。
> そこを `max` の下限で塞ぐ、という筋である。

## 13. 再現手順

```bash
# 素材の下見
python tools/splitsound/prepare.py --survey --min-duration 300

# 共通入力 (切り出し → 正規化 → PCM WAV)
python tools/splitsound/prepare.py --cut --only S1

# 分離 (C1) と ゲート (C3)
python tools/splitsound/separate.py --materials S1 --conditions c1_htdemucs
python tools/splitsound/separate.py --materials S1 --conditions c3_gate

# 閾値 → 無音検出 → 文字起こし
python tools/splitsound/run_conditions.py --materials S1 \
    --conditions c0_baseline,c1_htdemucs
#   --no-asr を付けると文字起こしを飛ばす (c3_gate は --no-asr で回した)

# 閾値スイープ (正解データ無しで選択性を測る / §4.5)
python tools/splitsound/sweep.py --materials S1,S3,S5

# 正解データを作る (人手 / 作業ページを生成 → ブラウザで作業 → ファイルで保存)
python tools/splitsound/make_label_page.py --materials S1
#   無音が多い素材は --by-words が必須 (§10.2)
python tools/splitsound/make_label_page.py --materials S3 --by-words --game-everywhere
#   output/_splitsound/<素材>/label.html をブラウザで開いて作業し、
#   「ファイルで保存」→ docs/request/ver10/ss1_truth/<素材>.jsonl として置く

# 指標 (§5 の確定値はこれで出した)
python tools/splitsound/evaluate.py --materials S1

# 閾値 × 最終テロップ (§9 / ASR の再実行は不要)
#   閾値が先頭に - を持つため --thresholds=... の形で渡す
python tools/splitsound/sweep_truth.py --materials S1 \
    --conditions c0_baseline,c1_htdemucs \
    "--thresholds=-5,-8,-11,-14,-17,-20,-23,-26,-30,-34,-37,-40"
```
