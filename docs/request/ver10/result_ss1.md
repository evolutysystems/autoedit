## 0. 先に結論

### 0.1 4 行で

1. **分離は文字起こしを明確に悪化させる。** S1 の正解データで測ると
   **CER 0.334 → 0.502 (相対 +50.1% の悪化)**、取りこぼしは **5.6% → 22.0%** になった (§5.1)。
   htdemucs の `vocals` が配信者の声そのものを削っており、
   認識できた文字数が **2,274 → 1,821 字 (2 割減)** に落ちている (§5.2)。
   「無音カットは駄目でも文字起こし専用の前処理として残る」という最後の可能性は**消えた**。
2. **音声分離そのものは正しく動く。** htdemucs の `vocals` は時間軸を 1 サンプルも狂わせず
   取り出せており (長さ厳密・位置ずれ 0 / §3)、21 分素材でも RTF 0.75 で安定している (§6)。
3. **無音カットの改善は、ほぼ「閾値を正しく選ぶこと」で説明できる。**
   閾値を揃えて比べると、分離の寄与は F1 素材で **+0.1〜+0.9 ポイント**しかない (§4.5-2)。
   当初 S5 で見えた「残存率 78.4% → 32.7%」という劇的な改善は、
   **現行の閾値推定が -37dB という異常値を返していたこと**が原因だった (§4.5-3)。
   元音声を -23dB で切れば分離音とほぼ同じ性能になる。
4. **分離が与えるものは「閾値への頑健さ」だけ。** 元音声は閾値を外すと崩壊する (-40dB で 34.7%) が、
   分離音は全域で 90〜92.5% に収まる (§4.5-4)。
   ただし代償は **RTF 0.75 = 3 時間 VOD で +2.3 時間**であり、§3.6 の基準 (0.3) を満たさない。

### 2.0 S1 の正体 — **IRL 配信だった** (2026-11-09 / 利用者の指摘で判明)

**S1 は配信者 3 人による IRL 配信** (展示会会場を歩きながらブースを回る回) である。
選定時は「音が常時鳴っている回」= ゲーム音が大きい回と読んでいたが、
鳴り続けていたのは**会場のざわめき (人混み・BGM・他ブースの音)** だった。
認識結果の内容 (ブース紹介・エルガト・Stream Deck・「あと 3 日あるので遊びに来てください」) で裏が取れている。

これは実験の解釈を変える。

| | 当初の想定 (ゲーム配信) | S1 の実態 (IRL 配信) |
| --- | --- | --- |
| 常時鳴っている音 | ゲームの BGM・SE | 会場のざわめき・**周囲の人の声** |
| 分離で落としたいもの | 音楽・効果音 | 環境ノイズ・**他人の声** |
| htdemucs (音楽分離) の向き | **合う** (BGM を落とす前提の設計) | **合わない。** `vocals` は周囲の人の声も拾う |
| 配信者が喋っている割合 | 低い (ゲーム中は黙る) | **高い** (実測 64〜71%) |
| 無音カットの伸びしろ | 大きい | **小さい** (最大でも 3 割弱) |

**ここが効いている**: 分離した `vocals` が元音声より平均 4dB しか低くなかった (§4.2) のは、
**周囲の人の声も「声」として残るため**である。
`docs/quality/resolve1.md` §12.3-1 の「ゲーム内ボイスは声なので分離しても残る」と同じ限界が、
IRL では「周囲の人の声」として現れている。

→ **S1 はこの実験の仮説を試す素材として向いていない。**
　 「悪化しないことの確認」には使えるが、**効果の確認には BGM・SE が主役のゲーム配信が必要**
　 (ver9 resolve4 §5.1 が htdemucs を第 1 候補にした理由がそれである)。
　 §8 の次アクションに「ゲーム配信の素材を 1 本選ぶ」を追加した。

### 4.3 `silencedetect` が分離音を扱えない (原因)

S1 で閾値を振った結果 (最小無音 0.6 秒は固定):

| 閾値 | C0 残存率 | C0 区間数 | C1 残存率 | C1 区間数 |
| --- | --- | --- | --- | --- |
| -17 dB | 99.9% | 2 | 99.1% | 8 |
| -20 dB | 100.0% | 1 | **100.0%** | 1 |
| -25 dB | 100.0% | 1 | **100.0%** | 1 |
| -30 dB | 100.0% | 1 | **100.0%** | 1 |
| -35 dB | 100.0% | 1 | **100.0%** | 1 |
| -40 dB | 100.0% | 1 | **100.0%** | 1 |

**閾値をどれだけ下げても無音は 1 件も出ない。**
`silencedetect` は「0.6 秒のあいだ 1 度も閾値を超えないこと」を求めるため、
分離音に常に乗っている残渣のピークで連続性が切れる。
**平均レベルは下がっているのに「ずっと静か」とは認識されない。**

> 閾値 -20dB で「100%」なのに -17dB で「99.1%」になるのは矛盾ではない。
> 閾値が高い (= -17dB) ほど「静か」と見なす範囲が広いためで、判定は単調である。

### 4.5 閾値を揃えて比べ直した — **分離の寄与はほとんど無かった** (2026-11-09)

§4.1〜§4.4 は「自動で決まった閾値」同士の比較だった。
**閾値を揃えて並べ直すと結論が変わる。** そのために正解データ無しで使える代理指標を作った。

#### 4.5-1. 代理指標 (と、最初に間違えた指標)

| | 定義 |
| --- | --- |
| 発話時間 | C0 の認識結果の**語の時刻** (`word_spans`) を重ね合わせたもの |
| **発話の残存** | 残す区間 ∩ 発話 ÷ 発話 (高いほど取りこぼしが少ない) |
| **非発話の削除** | (非発話 − 残す区間) ÷ 非発話 (高いほど不要な音を削れている) |
| 調和平均 | 上 2 つの F1。閾値の良さを 1 つの数にする |

**最初は認識の「区間」をそのまま発話時間として使い、誤った結論を出した。**
認識の区間は VAD の都合で実発話よりはるかに長くなる (実測: 10 文字の一言に 14〜25 秒)。
そのため発話時間が 3 倍近く過大になり、「分離は発話も同じ割合で削っている」と読めてしまった。

| 素材 | 区間ベース (誤) | **語ベース (正)** |
| --- | --- | --- |
| S1 | 70.3% | **67.2%** |
| S3 | 87.2% | **32.9%** |
| S5 | 92.4% | **32.3%** |

→ 以降の数字はすべて語ベースである (`tools/splitsound/sweep.py`)。

#### 4.5-2. 閾値スイープの結果 (各条件の最良点)

| 素材 | 背景 | C0 (元音声) の最良 | C1 (htdemucs) の最良 | C3 (+ゲート) の最良 | 分離の寄与 |
| --- | --- | --- | --- | --- | --- |
| **S3** (F1) | エンジン音 (断続) | **92.1%** (-30dB) | 92.2% (-30dB) | 92.2% (-30dB) | **+0.1 pt** |
| **S5** (F1) | エンジン音 (強・常時) | **91.6%** (-23dB) | 92.5% (-40dB) | 92.5% (-40dB) | **+0.9 pt** |
| **S1** (IRL) | 人混み・人の声 | **4.1%** (-14dB) | 21.7% (-14dB) | **34.4%** (-14dB) | +17.6 / **+30.3 pt** |

(数字は調和平均。全データは `output/_splitsound/sweep.md`)

#### 4.5-3. §4.1 の「S5 で 78.4% → 32.7%」の正体は**閾値の異常値**だった

| S5 / C0 (元音声) | 閾値 | 残存率 | 発話の残存 | 非発話の削除 | 調和平均 |
| --- | --- | --- | --- | --- | --- |
| 自動で選ばれた値 | **-37dB** | 0.784 | 95.5% | 29.7% | **45.3%** |
| 良い点 | **-23dB** | 0.329 | 89.3% | 94.0% | **91.6%** |
| 分離音 (C1) の最良 | -40dB | 0.363 | 93.8% | 91.2% | **92.5%** |

**元音声を -23dB で切れば、分離した音とほぼ同じ性能 (91.6% 対 92.5%) になる。**
§4.1 で見えた劇的な改善は、分離の効果ではなく
**`analyze_min_speech_db` が -37dB という異常値を返していたこと**が原因だった。

原因: エンジン音があるため、発話候補区間 (緩い基準 -30dB で検出) に
ノイズだけの静かな区間が多数混ざり、その下側 10% 分位点が -37dB まで落ちる。
分離すると候補区間が実際の声だけになり -20dB になる。
**分離は閾値推定の壊れ方を間接的に治していただけ**である。

#### 4.5-4. 分離の本当の価値は「閾値への頑健さ」

| 閾値 | S5 / C0 の調和平均 | S5 / C1 の調和平均 |
| --- | --- | --- |
| -20dB | 91.4% | 91.4% |
| -23dB | **91.6%** | 91.6% |
| -26dB | 88.5% | 91.9% |
| -30dB | 74.7% | 92.3% |
| -34dB | 55.7% | 92.4% |
| -37dB | 45.3% | 92.3% |
| -40dB | 34.7% | **92.5%** |

**C0 は閾値を外すと崩壊する (-40dB で 34.7%)。C1 は全域で 90〜92.5% に収まる。**
ピーク性能の差は +0.9 pt しかないが、「閾値を外しても壊れない」という性質は
利用者が閾値を触る製品では価値がある。ただしその代償は **RTF 0.75** である。

#### 4.5-5. IRL (S1) はどの条件でも使えない

発話が 67.2% を占め、残る 33% は**発話と同じ音量の人混み**である。

| 条件 | 最良の非発話の削除 | 発話の残存 |
| --- | --- | --- |
| C0 | **2.1%** | 99.5% |
| C1 | 12.2% | 97.2% |
| C3 (+ゲート) | **21.1%** | 94.5% |

分離 + ゲートで非発話の削除が 2.1% → 21.1% (10 倍) に上がるが、
**絶対値として使える水準ではない**。IRL では「配信者が話している個所だけ」は
現状のどの手でも成立しない。

> **C3 (ゲート) は F1 素材では C1 と完全に同じ数字**になった。
> ゲートが効くのは IRL のように「分離しても残渣が多い」素材だけである。

区分 (残す/切る) は残るので M1 / M2 / M5 には使われる。
`metrics.csv` に `unclear_rows` / `unclear_sec` / **`cer_scored_ratio`** (採点できた割合) を出し、

聞き取れない区間が増えるため、**この列が条件間で揃っていることを確認してから CER を比べる**
(正解は全条件で同じなので、揃わないことは原理上ないが、記録として残す)。

## 7. 判明した技術的事実 (設計へ反映済み)

### 7.1 同じファイルの同じ時刻が、読み方で 13 サンプルずれる

手元の m4a (AAC) は 325 秒付近にタイムスタンプの不連続を持っており、

- `-ss` を `-i` の後に置く読み方 (タイムスタンプ基準)
- 先頭から流し読みしてサンプルを数える読み方 (サンプル数基準)

で**同じ時刻の内容が 13 サンプルずれた** (正規化相互相関 0.9999 / 誤差ではない)。
`silencedetect` が返す時刻は前者、分離を作るのに自然なのは後者なので、
混ぜると**不連続より後ろの編集点が全部ずれる**。

- 実験側の対処: 共通入力を **PCM WAV へ 1 回だけ確定**させ、全条件がそれだけを見る。
- 本体側への含み: `voice_isolation` は「入力と同じ時間軸を持つ音声」を作る責務を負い、
  §4.2-4 の 3 検査 (長さ・無音でない・位置ずれ) を**本体にも実装する**。
  これは分離を足して初めて踏む問題である (設計書 §4.2-2a)。

### 7.2 `silencedetect` は「平均が下がった音」では無音を見つけない

§4.3 のとおり。**分離の効果を無音カットへ渡すには、間にゲートが必要**である
(設計書 §12.4-4 / 代案は「100ms RMS 基準の検出器を分離音専用に持つ」)。

### 7.3 DeepFilterNet は pip で入らない

```text
$ python -m pip install --dry-run deepfilternet
  Cargo, the Rust package manager, is not installed or is not on PATH.
  → 依存の deepfilterlib は Python 3.12 / Windows 向け wheel が無く、
    ソースビルドに Rust ツールチェーンを要求する
  → --only-binary :all: でも全バージョン (0.1.2〜0.5.6) が解決不能
```

対処: 公式配布の単体実行ファイル **`deep-filter`** を外部プロセスとして呼ぶ実装にした
(`--df-bin` / 環境変数 `SPLITSOUND_DF_BIN`)。実行ファイルが置かれ次第 C2 を測れる。

> **副産物**: DF3 を exe か ONNX で動かせるなら、**torch を同梱しなくて済む**。
> 設計書 §5.8 の「配布 +361MB」は htdemucs を採る場合の話で、
> DF3 だけなら数 MB〜十数 MB で収まる。

### 7.4 demucs の導入は既存環境を壊さない

`pip install demucs` が追加したのは `demucs einops julius lameenc sphn` の 5 つだけで、
**torch 2.11.0+cpu は再インストールされていない** (事前に `--dry-run` で確認)。
htdemucs の重み (約 80MB) は初回実行時に HuggingFace から自動取得される。

## 8. 判定と次にやるべきこと

### 8.0 判定: no-go (2026-11-12 確定)

**設計書 §5 の本体組み込みは行わない。** 根拠は §0.2 / §5.1。

| | 理由 |
| --- | --- |
| **無音カット** | M1 -0.002 / M2 ±0% / M5 **+16.3 pt 悪化**。基準 3 つすべて未達 |
| **文字起こし** | CER **+50.1% の悪化**。「文字起こし専用の前処理」としても**成立しない** |
| **処理時間** | 分離 RTF 0.762 (基準 0.3) に加え、**認識自体が +52.8% 遅くなる**。全体で **2.07 倍** |
| **残すもの** | `tools/splitsound/` は実験ハーネスとして保持。`src/` は 1 行も変更していない |

> **この実験の価値は「やらない判断を数字で固めたこと」である。**

> **torch / torchaudio を配布物へ戻す判断 (§5.8 / 831MB → さらに増加) も不要になった。**

## 9. 再現手順

```bash
# 素材の下見

python tools/splitsound/sweep.py --materials S1,S3,S5
```
