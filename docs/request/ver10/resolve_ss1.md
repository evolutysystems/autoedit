## 1. 現状の仕組み (調査結果)

### 1.1 音がどこを通るか

1 本編集 (Timeline 経路 / `silence_cut.mode="edit_points"`) の実際の順序は
`src/pipeline/pipeline_runner.py` の `_run_timeline` のとおり。

```text
入力動画
  │
  ├─⓪ 音声解析・正規化            loudness_normalizer.run          (runner:408)
  │     loudnorm 2 パスで -14 LUFS / -1 dBTP へ。映像は -c:v copy。
  │     出力 = loudness_normalized.mp4 → context.set_current_video_path()
  │     ※ 以降の全工程はこの「正規化後の動画」を見る
  │
  ├─ 音量解析・カット閾値の確認     _apply_volume_analysis           (runner:415 / 505)
  │     volume_analyzer.analyze_min_speech_db(context.current_video_path())  (runner:522)
  │     → 発話候補区間の代表 dB の下側 10% 分位点 → GUI ダイアログ
  │     → 確定値を settings["volume_analysis"]["last_cut_db"] へ保存
  │
  ├─① 無音検出 (実カットしない)     silence_cutter.detect_edit_points (runner:419)
  │     input_path = context.current_video_path()                    (silence_cutter:515)
  │     detect_silence(input_path, last_cut_db, cut_min_silence_sec)
  │       = ffmpeg -af silencedetect=noise=<dB>:d=<秒>
  │     → build_keep_segments(無音区間, 総尺) = **残す区間 keep_segments**
  │
  ├─② 音声認識                     subtitle_generator.recognize_for_timeline (runner:424)
  │     text_source.extract(context.current_video_path(), "ja")      (subtitle_generator:2653)
  │       = faster-whisper large-v3 / int8 / CPU / Silero VAD 有効
  │     ※ 認識は**素材そのまま** (カット前) に対して行い、
  │       結果を keep_segments で詰めた軸へ写す (map_items_to_timeline)
  │     speaker_filter.apply(items, context.current_video_path(), …) (subtitle_generator:2672)
```

### 1.2 分離音の「使い先」は 3 か所ある

| # | 使い先 | 今の入力 | 分離音を流すと何が変わるか |
| --- | --- | --- | --- |
| A | 音量解析 (`analyze_min_speech_db`) | 正規化後の動画 | 発話候補区間の代表 dB が**配信者の声だけ**から決まる。ゲーム音でかさ上げされた閾値がずれなくなる |
| B | **無音検出 (`detect_silence`)** | 正規化後の動画 | **要望の本命。** ゲーム音だけで有音判定されていた区間が無音に落ち、「配信者が話している個所だけ」が残る |
| C | 文字起こし (`text_source.extract`) | 正規化後の動画 | ver9 resolve4 §0.2 の仮説。BGM/SE の SNR が上がる一方、分離の副作用で悪化する恐れもある |
| (D) | 話者照合 (`speaker_filter.apply`) | 正規化後の動画 | 既定 off。分離音なら成立する可能性があるが**本実験の対象外** (§10 Q5) |

**A と B は閾値 (dB) を共有している**点が重要で、ここが実験と実装の最大の注意点になる (§3.5-4 / §5.5)。
分離すると音の絶対レベルが変わるため、A を分離音で測り直さずに B だけ分離音へ向けると、
**閾値の意味が壊れてカットが全く効かない / 全部切れる**という壊れ方をする。

### 1.3 「今どれだけ外しているか」は既に実測がある

docs/quality/resolve1.md §12.3 に、Twitch VOD 1 本 (`vod_2887226037.mp4` / 1,747 秒 /
空戦ゲーム・無線通信が常時流れる) の実測が残っている。

| 項目 | 値 |
| --- | --- |
| 生成テロップ | 111 件 |
| うち内容から**ゲーム内音声**と判別できたもの | **24 件** |
| うち**配信者**と判別できたもの | 14 件 |
| 残り | 73 件 (混在などで判別困難) |
| 音量による切り分けの限界 | -34dB でゲームの 92% を除けるが、**配信者も 36% 失う** (§12.3-3) |
| ステレオ定位 / 帯域による切り分け | **使えない** (重なりが大きい / ほぼ同一) |

この「24 件」が本実験のいちばん分かりやすい比較対象になる (§3.4 M4)。
同じ資料の §12.3-1 には「**音源分離も効かない** (ゲーム内ボイスは声そのものだから)」
という表がある。本実験はその記述の射程を確かめるものでもある:
**分離が効くのは BGM・SE に埋もれた配信者の声**であって、
**ゲーム内の「人の声」は分離後も vocals 側に残る**と予想している (§3.4 M4 の反証条件)。

## 2. 実験が答えるべき問い

| # | 問い | 仮説 | 反証されたと見なす条件 |
| --- | --- | --- | --- |
| Q1 | 無音カットは「配信者が話している個所だけ」に近づくか | 近づく。ゲーム音だけの区間が無音側へ落ちるため | 残す区間の F1 (§3.4 M1) がベースライン +0.05 未満 |
| Q2 | 文字起こしの精度は上がるか | **不確実。** SNR は上がるが分離の副作用で悪化し得る (ver9 resolve4 §0.2) | CER (M3) の相対改善が 10% 未満 |
| Q3 | ゲーム内ボイス由来のテロップ (A9) は減るか | **あまり減らない。** 声は vocals 側に残る | 24 件相当がほぼそのまま残る → 「分離では解けない」と結論して記録する |
| Q4 | どれだけ遅くなるか | htdemucs は重い (CPU で RTF 0.3〜1 / ver9 resolve4 §5.1)。DF3 は軽い | — (測って表にする) |
| Q5 | 2 モデルのどちらを使うか / 併用するか | 精度は htdemucs、速度は DF3。併用 (DF3 → htdemucs) は未知 | — (§3.1 の C4 で測る) |

Q3 は「ゲーム内の人の声を落とせるか」。分離は前者に効き後者には効かない、が事前の読み。
両方を 1 つの「文字起こし精度」にまとめると、どちらが動いたのか分からなくなる。

## 3. 実験の設計

### 3.1 条件 (5 条件)

| # | 条件 | 解析用音声の作り方 | 目的 |
| --- | --- | --- | --- |
| **C0** | ベースライン (現状) | 正規化後の音声そのまま | 比較の基準。既存パイプラインと同一結果になることを確認する |
| **C1** | htdemucs | Demucs `htdemucs` の **vocals** stem | 要望の第 1 候補 |
| **C2** | DF3 | DeepFilterNet DF3 の強調音 | 要望の第 2 候補 |
| **C3** | htdemucs + ゲート | C1 の vocals に、分離前後のレベル差でゲートを掛ける | 分離の残渣で有音判定が残る場合の押さえ (結果を見て実施) |
| **C4** | DF3 → htdemucs | DF3 で雑音を落としてから htdemucs | 併用の効果 (Q5)。C1/C2 が両方「効く」ときだけ実施 |

- 各条件で、無音カットの閾値の決め方を 2 通り測る (§3.5-4):
  **T1 = 分離音で `analyze_min_speech_db` を測り直す (推奨)** / **T2 = C0 の確定 dB を流用**。
- C3/C4 は任意。**C0・C1・C2 の 3 条件 × T1/T2 が必須の最小セット**。

### 3.2 素材

| # | 素材 | 長さ | 選ぶ理由 |
| --- | --- | --- | --- |
| S1 | BGM が大きい回 | 10 分 | 分離がいちばん効くはずの条件 |
| S2 | **ゲーム内ボイスが多い回** | 10 分 | Q3 の検証。`docs/quality/resolve1.md` §12 と同系統の素材 (空戦ゲーム等) が望ましい |
| S3 | 静かな雑談回 | 10 分 | **悪化しないこと**の確認 (分離は無駄で済むか、声を削るか) |
| S4 | 全長 1 本 (S1〜S3 のいずれかの元 VOD) | 1.5〜3 時間 | 処理時間 (M7) の実測とチャンク分割の検証。精度の指標は取らない |

- 10 分は**元 VOD から時刻を指定して切り出す** (`ffmpeg -ss … -t 600`)。切り出し後のファイルを
  正規化 (`loudness_normalizer.normalize_file`) し、**その出力を全条件の共通入力**にする。
  = C0 と C1〜C4 の違いが「分離だけ」に限定される。
- 素材の実ファイルと切り出し時刻は `tools/splitsound/materials.json` に記録し、再実行できるようにする。

#### 3.2-1. 実際に選んだ素材 (2026-11-09 / `prepare.py --survey` の実測)

手元にあるのは `output/*.archive.media/m*_audio.m4a` = アーカイブ切り抜きが素材復旧用に
残した **`media_role="normalized"` の音声** (正規化済み・無音カット前)。
映像は残っていないが、本実験が測る指標はすべて音声だけで決まるため成立する
(レンダリングは行わないので映像は不要)。

| ID | 素材 | 尺 | LUFS | **無音率** | 低-中 dB | 役割 |
| --- | --- | --- | --- | --- | --- | --- |
| **S1** | `vod_2877176496` m1 の 300〜900 秒 | 600s | -14.3 | **0.000** | -12.6 | 音が常時鳴っている回 |
| **S2** | `vod_2881981221` m7 の 200〜800 秒 | 600s | -14.8 | 0.014 | -9.1 | 別 VOD・低域が強い (別ゲーム) |
| **S3** | `vod_2866841954` m2 の 0〜360 秒 | 360s | -14.1 | **0.665** | -13.9 | 静かな回 (素材が 361.8s しか無いため 6 分窓) |
| **S4** | `vod_2877176496` m1 全長 | 1,261s | -14.3 | 0.000 | — | 処理時間の計測用 (W=300s で 5 窓) |

> **無音率は「現行のカット閾値 (-20dB / 0.6s) で無音と判定された割合」**である。
> S1 は **0.000** = いまの無音カットはこの素材から**何も削れていない**。
> 「配信者が話している個所だけカット」(R5-1) との差がそのまま伸びしろになる。
> 一方 S3 は 0.665 で正常に効いており、**素材によって現状の効き方が極端に違う**ことも分かった。

> **訂正 (2026-11-09 / 利用者の指摘)**: **S1 (= S4) は配信者 3 人の IRL 配信**
> (展示会会場) だった。鳴り続けているのはゲーム音ではなく**会場のざわめきと周囲の人の声**である。
> 分離 (`vocals`) は周囲の人の声も残すため、**この素材では仮説を試せない**
> (`result_ss1.md` §2.0)。本書 §3.2 が求めている「BGM が大きい回」に相当する
> **ゲーム配信の素材が別に必要**である。S1 は「悪化しないことの確認」に使う。
>
> あわせて**ラベルの決め方**も確定した (`tools/splitsound/truth_schema.md`):
> 複数人の配信では**共演者の声も `host`** (= 残したい声)、会話相手 (出展者・スタッフ) も `host`。
> 区別したいときだけ `sub` を使い、評価では `host` と同じ扱いにする。
> `other` は**残したくない人の声** (場内アナウンス・通行人・他ブース) に限る。
> これに伴い **M2 は「残したい声が無い区間の残存率」**と読む (ゲーム配信なら従来どおり)。
- **S4 は 1.5〜3 時間ではなく 21 分**である。手元に全長 VOD が無いため (§10.2 Q9)。

### 3.3 正解データ (人手が必要なのはここだけ)

**1 ファイルにまとめる** (`docs/request/ver10/ss1_truth/<素材ID>.jsonl`)。1 行 1 発話:

```json
{"start": 12.34, "end": 15.80, "speaker": "host", "text": "いやーもうF14でしょこれは"}
{"start": 21.05, "end": 24.60, "speaker": "game", "text": "ジョーカー隊、着艦せよ"}
{"start": 40.10, "end": 41.20, "speaker": "other", "text": ""}
```

| フィールド | 意味 |
| --- | --- |
| `start` / `end` | 発話の実時間 (秒 / 素材の先頭基準)。**聞こえ始め〜聞こえ終わり**を取る |
| `speaker` | `host` = 配信者 / `game` = ゲーム内音声 (ボイス・BGM・SE を問わず) / `other` = 同席者・来客音など |
| `text` | **`host` のみ必須**。CER の正解。`game` / `other` は空でよい |

- ラベル付けの単位は「息継ぎで切れるまで」。0.3 秒未満の間は切らない。
- 作業量の目安: 10 分 × 3 本。`host` の書き起こしが主な工数。
  **既存のテロップ出力を叩き台にして人手で直す**のが早い (ver9 resolve4 §7-2 と同じ方針)。
- `game` は時刻だけでよいので、**S2 は時刻ラベルを厚く、S1/S3 は書き起こしを厚く**取ると効率が良い。

### 3.4 測る指標

評価は **10ms グリッド**へ落として集合演算で行う (区間の端の扱いで揺れないようにするため)。

```text
H = speaker=="host" の区間を 10ms フレーム集合へ展開したもの (配信者が話しているフレーム)
G = speaker=="game" のフレーム集合
K = その条件で得られた keep_segments のフレーム集合 (= 残す区間)
N = 素材全体のフレーム集合
```

| # | 指標 | 式 / 定義 | 良い向き |
| --- | --- | --- | --- |
| **M1** | 残す区間の F1 | P = \|K∩H\| / \|K\| , R = \|K∩H\| / \|H\| , F1 = 2PR/(P+R) | 大 |
| **M2** | ゲーム音のみ区間の残存率 | \|K ∩ (G−H)\| / \|G−H\| | **小** (要望「配信者が話している個所だけ」の直接指標) |
| M2' | 尺削減率 | 1 − \|K\| / \|N\| | 参考 (大きすぎれば声を落としている) |
| **M3** | CER (文字誤り率) | `host` の正解文を時間順に連結した文字列と、生成テロップ (全件) を時間順に連結した文字列のレーベンシュタイン距離 ÷ 正解文字数 | 小 |
| **M4** | **ゲーム由来テロップ件数** | 生成テロップのうち、その表示区間の重なりが `G−H` に 50% 以上あるものの件数と比率 | 小 (A9 / §1.3 の「24 件」に対応) |
| M5 | 取りこぼし率 | `host` の発話のうち、重なるテロップが 1 件も無いものの比率 | 小 |
| M6 | ハルシネーション件数 | 生成テロップのうち、`H ∪ G ∪ other` のいずれとも重ならない (= 完全な無音区間に出た) 件数 | 小 |
| **M7** | 処理時間 | 工程別の秒数と RTF (= 処理秒 ÷ 音声秒)。**分離・音量解析・無音検出・文字起こし**の 4 つを分けて出す。合計は C0 との差分 (秒 / 倍率) で示す | 小 |

- **M3 の算出順序**: 正解・生成の双方へ同じ正規化を掛ける
  (空白除去 / 句読点と記号除去 / 全角英数→半角 / カタカナはそのまま)。
  本体の `strip_fillers` / `apply_replacements` は**掛けない** (設定差で数字が動くため)。
- M1/M2 は **閾値 T1 / T2 の両方**で出す。M3〜M6 は T1 のみでよい (文字起こしは閾値に依存しない)。
- M7 は専用の計測実行で取る (指標計算と同時に測ると I/O が混ざる)。§7 の書式でログへ出す。

### 3.5 手順

1. **素材の用意** — S1〜S4 を切り出し、`loudness_normalizer.normalize_file` で正規化する。
   `materials.json` へ元 VOD・時刻・正規化後パス・SHA-256 を記録する。
2. **正解データの作成** — §3.3 の JSONL を 3 本。先に C0 を 1 回回してテロップを出し、
   それを叩き台に直す。
3. **分離** — C1〜C4 の解析用音声を作る (§4.2)。
   **作った直後に長さを検査**し、サンプル数が入力と一致しない条件はそこで止める (§4.2-4)。
4. **閾値の決定** — 各条件で
   T1 = `volume_analyzer.analyze_min_speech_db(解析用音声, settings)` の `min_db` /
   T2 = C0 で決まった `min_db` を使う。**両方を記録する** (分離でレベルがどれだけ動いたかが分かる)。
5. **無音検出** — `silence_cutter.detect_silence(解析用音声, 閾値, cut_min_silence_sec)` →
   `build_keep_segments(…, 総尺)`。`cut_min_silence_sec` は既定 0.6 のまま動かさない。
6. **文字起こし** — `subtitle_generator.resolve_text_source(settings, eff_cfg)` で得たエンジンへ
   解析用音声を渡す。**モデル・設定は C0 と完全に同じ**にする
   (large-v3 / int8 / CPU / beam 8 / VAD 有効 / `condition_on_previous_text=False`)。
7. **指標計算** — §3.4 を計算し、条件 × 素材の表と生データ (JSON) を出す。
8. **処理時間** — S4 (全長) で C0 / C1 / C2 を 1 回ずつ通し、M7 を取る。
9. **記録** — `docs/request/ver10/result_ss1.md` に表と考察を書く。
   数字は**素材ごとに出す** (平均だけにしない。1 本でも悪化していれば設定で逃げ道が必要になる)。

### 3.6 判定基準 (go / no-go)

**3 本すべてで下を満たした条件があれば、§5 の本体組み込みへ進む。**

| 観点 | 基準 |
| --- | --- |
| 無音カット | **M1 が C0 比 +0.05 以上**、かつ **M2 が C0 比で相対 30% 以上減**、かつ **M5 (取りこぼし) が悪化しない (+2 ポイント以内)** |
| 文字起こし | **M3 が C0 比で相対 10% 以上改善** (ver9 resolve4 §7-5 の基準を引き継ぐ)。悪化なら「無音カット専用に使う」判断もあり得る (§5.7 で A/B を別フラグにする理由) |
| 処理時間 | **分離工程の RTF が 0.3 以下** (3 時間 VOD で +54 分以内)。超える場合は「既定 off の任意機能」としてのみ可 |
| 安全性 | どの素材でも**無音カットが崩壊しない** (M2' が 95% 超 = ほぼ全部カット、または 5% 未満 = ほぼ無カット にならない) |

- **文字起こしだけ改善 / 無音カットだけ改善**も十分な成果である。
  その場合は使い先を片方に絞る (§5.7 の `use_for_silence` / `use_for_asr` を別に持つ理由)。
- どれも満たさない場合は **実装しない**。`result_ss1.md` に数字を残し、
  docs/quality/resolve1.md §12.3-1 の「音源分離も効かない」の裏付けとして閉じる。
  その場合は ver9 resolve4 §8 の軽い手 (hotwords / replacements の充実) へ戻る。

### 4.2 分離の仕様 (`separate.py`)

#### 4.2-1. 入出力

| | 内容 |
| --- | --- |
| 入力 | 正規化後の素材を **PCM WAV へ確定させたもの** (`analysis_source.wav` / 48kHz ステレオ)。理由は §4.2-2a |
| 中間 | モデルに合う形へ変換 (htdemucs = 44.1kHz ステレオ / DF3 = 48kHz モノラル) |
| 出力 | **48kHz モノラル 16bit PCM WAV** (`voice.wav`)。`silencedetect` も faster-whisper も WAV を直接読める |
| 長さ | **入力と同一** (サンプル単位)。先頭を切る・末尾を詰める処理を一切入れない |

**48kHz へ揃える理由**: `ffmpeg.audio_sample_rate` の既定が 48000 で、
既存の `extract_audio_segments` / `speaker_filter.extract_wave` と足並みが揃う。
16kHz へ落とすのは faster-whisper 側に任せる (内部でリサンプルされる)。

#### 4.2-2. 時間軸の保全 (最重要)

分離音の時刻は、そのまま **`keep_segments` = 実際の映像のカット点**になる。
**1 サンプルのずれが映像のずれになる**ため、次を守る。

- `atrim` / `apad` / `asetpts` を使わない。モデルへ渡す前の変換は**リサンプルとチャンネル変換だけ**。
- モデルの出力が入力より短い/長い場合 (フレーム長で割り切れない端数) は、
  **末尾を 0 埋め / 切り捨てして入力長へ合わせる**。この補正量をログへ出し、
  **1 フレーム (= 10ms) を超えたら異常として止める**。
- 出力後に `ffprobe` で `duration` と総サンプル数を取り、入力との差を検査する (§4.2-4)。

#### 4.2-2a. 時間軸は 2 種類ある (2026-11-09 の実測で判明 / 設計の追補)

実装して検査を回したところ、**同じファイルの同じ時刻が、読み方で 13 サンプルずれた**。

```text
素材: output/_splitsound/S3/normalized.m4a (AAC / 360.0s)

  ① -ss を -i の後に置いて読む (先頭からデコードして捨てる = タイムスタンプ基準)
  ② 先頭から流し読みして N サンプル目を数える (= サンプル数基準)

  → 325 秒より前: ①と②は一致 (lag 0)
  → 325 秒より後: **13 サンプルずれる** (正規化相互相関 0.9999 で、誤差ではなく本物)
```

原因は素材の AAC に**タイムスタンプの不連続**があるためで、
①は不連続を時刻として数え、②は詰めて数えるため、そこから先が食い違う。

**なぜ重大か**: 分離は②(流し読み)で作るのが自然だが、
`silencedetect` が返す時刻は①(タイムスタンプ基準)である。
2 つを混ぜると、**不連続より後ろの編集点が全部ずれる**。

| | 対処 |
| --- | --- |
| 実験 (第1段) | 共通入力を **PCM WAV へ 1 回だけ確定させ**、全条件がその WAV だけを見る。WAV には編集リストも欠落も無いため、①と②が一致する (実測で lag 0 を確認済み) |
| 本体 (第2段) | 分離音を作るときの入力と、`silencedetect` を掛ける対象を**同じ 1 本に揃える**。`voice_isolation` は「入力の時間軸をそのまま持つ WAV」を作る責務を負う。§4.2-4 の位置ずれ検査を**本体側にも実装する** (§5.6 の「長さ検査 NG なら分離音を破棄」に位置ずれも含める) |

> この食い違いは分離を入れなければ表に出ない (今は 1 本の動画を全工程が共有しているため)。
> **分離を足すことで初めて踏む問題**なので、設計の前提として明記しておく。

#### 4.2-3. 長尺のチャンク分割

3 時間の音声を一度にモデルへ渡すとメモリが足りない。次の方式で分ける。

```text
窓長   W = 300 秒 (設定可)
のりしろ O = 5 秒 (設定可)

チャンク i: [i*W - O, (i+1)*W + O) を分離し、
            **中央の [i*W, (i+1)*W) だけを採用**して連結する (のりしろは捨てる)
```

- クロスフェードは**しない**。捨てるだけなら連結点でサンプル数が狂わないため、§4.2-2 を守れる。
- のりしろを取るのは、窓の端でモデルの受容野が足りずに声が削れるのを避けるため。
- 連結は Python 側で numpy 配列を繋いで `soundfile` で 1 本書く
  (ffmpeg の concat を挟むと再エンコードの端数が入る)。
- 先頭チャンクの前・末尾チャンクの後にのりしろは無い (素材の外は読まない)。

#### 4.2-4. 作った直後の自己検査 (これが通らない条件は測らない)

| 検査 | 合格条件 |
| --- | --- |
| 長さ | 総サンプル数の差が **0** (補正後)。補正前の差が 10ms 超なら異常終了 |
| 無音でない | 全長の RMS が -60dBFS より大きい (モデルが黙って無音を返す事故を検出する) |
| 位置ずれ | 入力と出力の相互相関のピークが **0 サンプル** (±1 以内)。ずれていたらモデルの遅延が乗っている |

位置ずれ検査は全長では重いので、先頭・中央・末尾から 30 秒ずつ抜いて行う。

#### 4.2-5. htdemucs の呼び方 (C1)

| 項目 | 値 |
| --- | --- |
| パッケージ | `demucs` (MIT / `facebookresearch/demucs`) |
| モデル | `htdemucs` (既定の 4 stem)。使うのは **`vocals`** |
| 入力 | 44.1kHz ステレオ (モデルの学習条件) |
| 呼び方 | **Python API** (`demucs.pretrained.get_model` + `demucs.apply.apply_model`) を使う。CLI (`python -m demucs`) はファイル入出力とフォルダ構成が固定で、チャンク分割と長さ検査を自分で持てないため |
| スレッド | `torch.set_num_threads()` を CPU 数で明示する (既定任せにしない / 計測が安定しない) |
| stem の落とし先 | `vocals` をモノラル化 (L/R 平均) してから 48kHz へリサンプル |
| 重み | 初回実行時に自動取得 (約 80MB)。取得先とサイズを `README.md` へ記録する |

#### 4.2-6. DeepFilterNet (DF3) の呼び方 (C2)

| 項目 | 値 |
| --- | --- |
| パッケージ | `deepfilternet` (MIT または Apache-2.0 のデュアル / `Rikorose/DeepFilterNet`) |
| モデル | **DF3** |
| 入力 | **48kHz モノラル** (モデルの前提。リサンプル不要で済む) |
| 呼び方 | **単体実行ファイル `deep-filter` を外部プロセスとして呼ぶ** (下記の理由により Python API は使えない) |
| 性質 | 雑音抑圧。**音楽の除去は得意でない** (ver9 resolve4 §5.1)。BGM が主因の素材では C1 に負ける見込み |
| 重み | 約 2MB |

**Python パッケージが入らない (2026-11-09 の実測)**

```text
$ python -m pip install --dry-run deepfilternet
  Cargo, the Rust package manager, is not installed or is not on PATH.
  This package requires Rust and Cargo to compile extensions.
  → deepfilterlib (依存) は Python 3.12 / Windows 向けの wheel が無く、
    ソースからのビルドに Rust ツールチェーンを要求する
  → --only-binary :all: でも全バージョン (0.1.2〜0.5.6) が解決不能
```

| 選択肢 | 評価 |
| --- | --- |
| Rust (rustup) を開発機へ入れてビルドする | 可能だが開発機に 1GB 級のツールチェーンが増える。**利用者の確認が必要** (§10.2 Q8) |
| **公式 prebuilt の `deep-filter` 実行ファイルを呼ぶ** | **採用。** ffmpeg と同じ「外部 exe を呼ぶ」形で、既存の作法に馴染む。`--df-bin` / 環境変数 `SPLITSOUND_DF_BIN` で場所を渡す |
| ONNX へ変換して onnxruntime で動かす | 配布済みの onnxruntime を使えるので**第2段では有力**。ただし変換の手間が実験の前に増える |

> **第2段への含み**: DF3 を exe / ONNX で動かせるなら、**torch を同梱せずに済む**。
> §5.8 の「+361MB」は htdemucs を採る場合の話で、DF3 だけなら数 MB〜十数 MB で収まる。
> C2 が §3.6 を満たした場合、配布の判断は大きく楽になる。

#### 4.2-7. C3 (ゲート) / C4 (併用)

- **C3**: C1 の vocals に対し、「**元音声と vocals のレベル差**が小さい区間 = 元から声しか無い区間」
  という見方で、差が設定値を超える区間を減衰させる。
  C1 の M2 (ゲーム音のみ残存率) が十分下がらなかったときだけ実施する。
- **C4**: DF3 → htdemucs の順。どちらも 48kHz/44.1kHz の変換が 1 回増えるため、
  §4.2-2 の長さ検査を**各段で**行う。

## 5. 第2段の実装設計 — パイプラインへの組み込み (§3.6 を満たした場合のみ)

### 5.1 新モジュール `src/modules/voice_isolation.py`

既存の単機能モジュール (`loudness_normalizer` / `volume_analyzer`) と同じ作りにする。

| 関数 | 役目 |
| --- | --- |
| `isolation_config(settings)` | `voice_isolation` セクションを既定で補完して返す (`loudness_config` と同じ作法) |
| `available(cfg)` | エンジンが import できるか。**凍結配布で torch が無ければ False** (`speaker_filter._import_torch` と同じ考え方) |
| `isolate_file(input_path, output_path, settings, on_progress=None)` | 分離 1 本。§4.2 の仕様そのまま (チャンク分割・長さ検査を含む)。失敗したら **None を返す** (例外を投げない) |
| `run(context)` | 工程としての入口。`context.current_video_path()` から分離音を作り、`context.set_analysis_audio_path()` へ載せる。失敗・無効・未導入なら**何もしないで返る** |

### 5.2 `PipelineContext` への追加

```python
# 解析専用の音声パス (ver10 resolve_ss1 §5.2)
# 話者の声だけを取り出した音声を「解析にだけ」使うために持つ。
# 出力動画の音声には使わない (要望 R3) ため、レンダリング経路は参照しない。
# 未設定 (None) のとき analysis_audio_path() は current_video_path() を返すので、
# 分離を使わない実行は従来とまったく同じ経路になる。
self._analysis_audio_path = None

# 解析 (音量解析・無音検出・文字起こし) に使う音声のパスを返す
def analysis_audio_path(self):
    return self._analysis_audio_path or self._current_video_path

# 分離音のパスを保持する (voice_isolation が生成直後に呼ぶ)
def set_analysis_audio_path(self, path):
    self._analysis_audio_path = path
```

- `cleanup()` で `None` へ戻す (`_asr_audio_path` と同じ寿命管理)。
- **`set_current_video_path` は呼ばない。** これを呼ぶと出力動画の音が分離音になり R3 に反する。

### 5.3 差し替える箇所 (`current_video_path()` → `analysis_audio_path()`)

| # | ファイル:行 | 関数 | 差し替える | 理由 |
| --- | --- | --- | --- | --- |

| 2 | `silence_cutter.py:515` | `detect_edit_points` | **する** | 残す区間を分離音で決める (§1.2 B / 本命) |

| 4 | `subtitle_generator.py:2653` | `recognize_for_timeline` | **する** | 文字起こしの入力 (§1.2 C) |

| 6 | `subtitle_generator.py:1969` | `_prepare_asr_audio` | **しない** | プレビュー再生用の音声。利用者が聞くものなので元音声を使う |

**3 と 5 が設計の核心**で、「解析は分離音・出力は元音声」をコードの形で守る部分である。

### 5.4 工程と進捗

```text
⓪  音声解析・正規化        (既存)
⓪' 音声分離               ← 新規。voice_isolation.run(context)
    音量解析・カット閾値    (既存 / 入力が分離音になる)
①  無音検出               (既存 / 入力が分離音になる)
②  音声認識               (既存 / 入力が分離音になる)
③  Timeline 構築 → ④ レンダリング (既存 / 元音声のまま)
```

- `total_steps` を **4 → 5** (Timeline 経路) / **5 → 6** (従来フロー) へ増やす
  (`pipeline_runner._prepare_context` のコメントも更新する)。
  **分離が無効なときは増やさない** (進捗バーが途中で止まって見えるのを避ける)。
- 分離中の進捗はチャンクの進み (`i / チャンク数`) を `progress_subcallback("音声分離")` へ流す。
  ffmpeg ではなく Python の計算なので `run_ffmpeg_progress` は使えない。

### 5.5 dB 閾値の扱い (ここだけは慎重に)

分離すると音の絶対レベルが下がる (ゲーム音ぶんが消える)。
`volume_analysis.last_cut_db` は **setting.json に保存され、次回以降も使われる値**なので、
分離音で測った値をそのまま同じキーへ書くと、**分離を off にした次の実行で閾値がおかしくなる**。

| 方針 | 内容 |
| --- | --- |
| 保存先を分ける | 分離が有効なときは **`volume_analysis.last_cut_db_isolated`** を読み書きし、`last_cut_db` は触らない |
| ダイアログ | 閾値確認ダイアログには「音声分離後の音声で測った値」である旨を出す (`volume_analysis_callback` の `info` にフラグを 1 つ足す) |
| 実験で選ぶ | T1 (測り直す) を既定にするか T2 (流用) にするかは **§3.5-4 の結果で決める**。現時点では推測しない |
| 逃げ道 | `voice_isolation.gain_match`: 分離音を元音声と同じ Integrated LUFS へ合わせてから測る案。実験で T1 が不安定なときの手段として設計に残す |

### 5.6 失敗時の方針

| 事象 | 挙動 |
| --- | --- |
| `voice_isolation.enabled=false` | 工程をスキップ。従来と完全に同一 |
| エンジン未導入 (凍結配布で torch 無し) | 警告ログ 1 行で素通り (`speaker_filter` と同じ) |
| 分離中の例外 | 警告ログ + 分離音を破棄して素通り。**パイプラインは止めない** (`loudness_normalizer` と同じ「品質改善の工程は失敗で止めない」方針) |
| 長さ検査 NG (§4.2-4) | **分離音を破棄**して素通り。ずれた音で編集点を作るほうが危険 |
| `max_rtf` 超過 (時間切れ) | 分離を打ち切って素通り。打ち切り時点までの中間物は捨てる |
| `PipelineCancelled` / `DiskSpaceError` | **貫通させる** (resolve3 R9-6 の決まり) |

### 5.7 `setting.json` 定義 (案)

`DEFAULT_SETTINGS` へ新しいセクションを 1 つ足す。**既定はすべて現行動作と同一**。

```python
# 音声分離 (ver10 resolve_ss1) — 話者の声だけを取り出した音声を「解析専用」に使う。
# 出力動画の音声には使わない (要望 R3)。UI には出さず setting.json で管理する。
"voice_isolation": {
    "enabled": False,          # 既定 False = 現行動作。実験で効果が出た条件だけ True を検討する
    "engine": "htdemucs",      # "htdemucs" | "df3" | "df3+htdemucs"
    "use_for_silence": True,   # 無音カット (音量解析 + 無音検出) に使う
    "use_for_asr": True,       # 文字起こしに使う
    "sample_rate": 48000,      # 解析用音声のサンプリング周波数
    "chunk_sec": 300,          # チャンク長 (§4.2-3)
    "overlap_sec": 5,          # のりしろ (捨てる)
    "threads": 0,              # torch のスレッド数 (0 = CPU 数)
    "max_rtf": 0.5,            # これを超えたら打ち切って素通りする (時間切れ判定)
    "gain_match": False,       # 分離音を元音声と同じ Integrated LUFS へ合わせる (§5.5)
    "length_tolerance_ms": 10, # 長さ検査の許容 (§4.2-4)
    "keep_debug_wav": False,   # 分離音を中間フォルダへ残す (調査用)
},
```

- `use_for_silence` / `use_for_asr` を**別に持つ**のは、§3.6 のとおり
  「無音カットだけ効く / 文字起こしだけ効く」があり得るため。
- `volume_analysis` へ `last_cut_db_isolated` を 1 キー追加する (§5.5)。
- 既存キーの意味は変えない。`_merge_with_defaults` のセクション単位マージに乗るので、
  古い `setting.json` でも欠落キーは既定で埋まる。

### 5.8 配布への影響 (第2段の判断材料)

| 項目 | 現状 (v1.8.3) | 分離を入れると |
| --- | --- | --- |
| 配布サイズ | 831MB (`src/dist/Stretheus`) | **+361MB 前後** (torch/torchaudio の再同梱 / `main_window.spec` の excludes を戻す) + 重み (htdemucs 約 80MB / DF3 約 2MB) |
| GitHub Releases の上限 | 1 ファイル 2GiB (`docs/HowToRelease.md`) | 収まる見込みだが**実測が必要** |
| ライセンス | — | Demucs = MIT / DeepFilterNet = MIT または Apache-2.0。`tools/collect_licenses.py` の manifest へ追記が必要 |
| セキュリティ | sec2 S6 で「使っていない重量依存を配らない」と決めた | 分離を**使う**なら前提が変わる。ただし `transformers` は引き続き不要 |
| CPU 時間 | — | §3.6 の RTF 基準内であること。既定 off なら影響は無い |

> サイズと効果の兼ね合いで決める論点なので、§3.6 を通ってから改めて判断する (§10 Q6)。

## 6. エラー処理方針

- 本実験のスクリプトは `src/exceptions.py` の例外体系をそのまま使う
  (`InputError` / `FFmpegError` / `DiskSpaceError`)。独自の例外は作らない。
- **条件 1 つの失敗で実験全体を落とさない。** 失敗した (素材 × 条件) は
  `result.json` に `"error"` を書いて次へ進み、最後に失敗一覧を出す。
- 分離の**長さ検査 NG は必ず「失敗」として扱う** (警告で通さない)。
  ずれた音で測った数字は判断を誤らせるため。
- 第2段 (§5.6) は「品質改善の工程は失敗で止めない」既存方針を守る。
  ただし `PipelineCancelled` / `DiskSpaceError` は貫通させる。

## 7. ログ出力方針

- 既存の `utils.logger.get_logger(__name__)` と `utils.stage_timer` を使う。新しい仕組みは作らない。
- 分離の工程名は **「音声分離」**。`stage_timer.timed("音声分離")` で囲む。
  `stage_timer.report` の `main` 一覧に当てはまらない名前は末尾に並ぶ仕様なので、改修は不要。
- 分離 1 本につき 1 行を INFO で残す:

```text
音声分離: engine=htdemucs / 入力 600.0s / チャンク 2 本 (W=300s,O=5s) /
          所要 214.3s (RTF 0.36) / 長さ差 0 サンプル / 出力 RMS -31.2 dBFS
```

- 閾値は分離の前後を並べて出す (§5.5 の事故を見つけるため):

```text
カット閾値: 元音声 -28 dB / 分離音 -41 dB (T1 で測定) → 採用 -41 dB
```

- 実験ハーネスは上記ログを `logs/` へ残したまま、指標は CSV/JSON へ別途書く。

| `tools/splitsound/evaluate.py` | §3.4 の M1〜M7 を計算し `metrics.csv` と表を出す |
| `tools/splitsound/truth_schema.md` / `README.md` / `materials.json` | 正解データの形式 / 手順 / 素材定義 |

**`src/` は 1 行も変更していない。** 既存関数を import して使うだけ (§4.3)。

依存は `pip install demucs` で `demucs einops julius lameenc sphn` の 5 つが増えただけで、
**torch は再インストールされていない** (事前に `--dry-run` で確認)。

### 12.2 検査が本物のバグを捕まえた (§4.2-2a)

最初の実装は窓ごとに `-ss` で読み出していたため、AAC のタイムスタンプ不連続を踏んで
**窓 2 以降が 13 サンプルずれた**。§4.2-4 の位置ずれ検査がこれを検出し (正規化相互相関
0.9996 / 偶然ではない水準)、原因を追って「共通入力を PCM WAV へ確定させる」方式へ直した。
直した後は長さ・RMS・位置ずれの 3 検査すべてが合格している。

> **設計への含み**: この検査は**本体 (第2段) にも必ず入れる**。
> 分離を足すと時間軸が 2 本になり、ずれても画面には出ず「カット位置が微妙にずれた動画」
> として出てしまう。検査で弾ければ、ずれた分離音は使われず現行動作へ落ちる (§5.6)。

### 12.3 ここまでの実測値 (精度の指標は正解データ待ち)

| 項目 | 実測 |
| --- | --- |
| htdemucs の処理速度 (12 スレッド / CPU) | **RTF 0.71〜0.76** (6 分の音声に 4.3〜4.6 分) |
| ver9 resolve4 の見積り | RTF 0.3〜1 → **範囲内だが遅い側** |
| §3.6 の基準 (RTF 0.3 以下) | **満たしていない。** このままなら「既定 off の任意機能」どまり |
| 3 時間 VOD へ外挿すると | 分離だけで **2.1〜2.3 時間** の追加 |
| S3 (静かな回) の無音カット | C0: 残す区間 55 件 / 残存率 34.2% → C1: 53 件 / 34.1% = **ほぼ変化なし (悪化もなし)** |
| S3 の閾値 | C0 も C1 も -21dB (分離してもレベルの代表値が動かなかった) |

  分離しても落ちるものが無い。狙いは S1 / S2 (無音率 0.000 の素材) の側にある。
- 速度が §3.6 の基準に届いていないため、**C2 (DF3) の速度が重要**になった。
  DF3 は「極めて軽い」設計 (ver9 resolve4 §5.1) で、実行ファイルを置けば測れる (§10.2 Q8)。

### 12.4 S1 の結果と、**設計の前提が 1 つ崩れたこと** (2026-11-09)

#### 12.4-1. 分離は成功している。しかし無音カットは変わらなかった

| | C0 (現状) | C1 (htdemucs) |
| --- | --- | --- |
| 分離の検査 | — | **合格** (長さ厳密 / ずれ 0 / RTF 0.761) |
| 検出された無音 | 1 件 | 3 件 |
| 残す区間 | 2 件 / **99.88%** | 4 件 / **99.65%** |
| 自動で決まった閾値 (T1) | -17 dB | -18 dB |

**分離しても、残す区間はほぼ 100% のまま**だった。

#### 12.4-2. 原因: 情報は取れているが `silencedetect` が使えない

100ms フレームの RMS を数えると、分離の効果は**はっきり出ている**。

| 100ms フレームが閾値以下である割合 | 元音声 | 分離音 (vocals) |
| --- | --- | --- |
| -20 dB 以下 | 14.7% | **52.1%** |
| -25 dB 以下 | 1.0% | 16.4% |
| -30 dB 以下 | 0.0% | 1.8% |
| フレームレベルの中央値 | -16.0 dB | **-20.3 dB** |

ところが `silencedetect` に掛けると、**閾値を -40dB まで下げても無音は 1 件も出ない**。

```text
threshold |  C0 keep%  C0 segs |  C1 keep%  C1 segs
      -17 |      99.9        2 |      99.1        8
      -20 |     100.0        1 |     100.0        1
      -25 |     100.0        1 |     100.0        1
      -30 |     100.0        1 |     100.0        1
      -40 |     100.0        1 |     100.0        1
```

理由は `silencedetect` の判定方法である。
**「指定した長さ (0.6 秒) のあいだ 1 度も閾値を超えないこと」**を求めるため、
分離音に常に乗っている**残渣のピークで連続性が切れる**。
平均レベルは下がっているのに、「ずっと静か」な区間としては認識されない。

#### 12.4-3. ゲートを足すと動く (ただし削減は 1 割強)

「静かなフレームを本当の無音 (ゼロ) にする」ゲートを挟むと、`silencedetect` は従来どおり拾う。
ゲートはヒステリシス (開 `open_db` / 閉 `open_db - 6dB`)・ホールド 250ms・
立ち上がり 40ms の前開きを持つ (`separate.apply_gate`)。

| ゲート開放閾値 | 残す区間 | 区間数 | 削減 |
| --- | --- | --- | --- |
| -18 dB | 87.3% | 64 | **12.7%** |
| -20 dB | 95.7% | 26 | 4.3% |
| -22 dB | 98.8% | 9 | 1.2% |
| -25 dB 以下 | 100.0% | 1 | 0.0% |

削減がフレーム割合 (52%) ほど伸びないのは、**静かな区間が短く散らばっている**ためである
(ホールド 250ms と `silencedetect` の最小無音 0.6 秒で、短い隙間は残る)。

> **この 12.7% が「正しい 12.7%」か (ゲーム音だけを削り、配信者の声を削っていないか) は
> 正解データが無いと判定できない。** それが §3.4 の M1 / M2 であり、
> **段 3 (ラベル付け) がいま一番の律速**である。

#### 12.4-4. 設計の訂正: §5.3 の「入力を差し替えるだけ」では足りない

本書 §5.3 は「`current_video_path()` を `analysis_audio_path()` に差し替える」だけで
無音カットが分離音を見るようになる、という設計だった。
**実測の結果、これは無音カットについては不十分**である。

| | 当初の設計 | 実測後 |
| --- | --- | --- |
| 音量解析 (A) | 入力の差し替えで足りる | 同じ (ただし閾値の意味が変わる / §5.5) |
| **無音検出 (B)** | 入力の差し替えで足りる | **足りない。** ゲート (または RMS フレーム基準の検出器) が必要 |
| 文字起こし (C) | 入力の差し替えで足りる | 同じ (未測定) |

第2段へ進む場合、`voice_isolation` は「声を取り出す」だけでなく
**「静かな区間を本当の無音にして返す」**ところまでを責務に含める必要がある
(= 上のゲートをモジュール内に持ち、`gate_open_db` / `gate_hold_ms` などを設定にする)。
そうすれば既存の `silencedetect` 経路は 1 行も変えずに済み、§5.3 の差し替えだけで成立する。

**代案**: `silencedetect` の代わりに「100ms RMS が閾値以下」で無音を決める検出器を
分離音専用に持つ。情報量としてはこちらの方が素直 (52% を直接使える) だが、
既存の無音検出と二系統になるため、ゲート案の方が影響範囲が小さい。
どちらを採るかは M1 / M2 の数字を見てから決める (§10.2 Q10)。

## 13. まとめ

- 要望の「分けた音声を使って既存パイプラインを行う」は、現行コードでは
  **音量解析 → 無音検出 → 文字起こし**の 3 か所へ同じ音を流すことを意味する (§1.2)。
  このうち**無音検出が要望 R5-1「配信者が話している個所だけカット」の本体**で、
  ver9 resolve4 が見ていなかった新しい論点である。
- 「完成した動画は元の音声」(R3) は、分離音を `current_video_path` に**しない**ことで守る。
  そのために `PipelineContext` へ解析専用のパスを 1 本足す設計にした (§5.2)。
  レンダリング経路には触らないため、音質のリスクはゼロである。
- 効果は**まだ誰も測っていない**。論文は音質指標しか見ておらず、
  `docs/quality/resolve1.md` §12.3-1 には「音源分離も効かない」という逆向きの記述もある。
  そこで第1段は **`src/` を触らない実験ハーネス** (§4) で数字を作り、
  §3.6 の基準を満たした条件だけを本体へ入れる (§5)。
- 処理時間 (R5-2) は分離を独立した工程として `stage_timer` で測り、
  **工程別の秒数と RTF、C0 との差分**で出す (§3.4 M7 / §7)。
