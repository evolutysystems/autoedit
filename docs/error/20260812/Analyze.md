対象現象: `docs/error/20260812/error.md`（VOD `https://www.twitch.tv/videos/2833484601`）

* 発話のタイミングとテロップのタイミングがずれる

* ズレによりテロップが重なっている箇所があり、クリックすると選択したテロップが別の場所へ飛ぶ

## 1. 結論（先に要点）

報告された 4 点は **独立した 3 つの原因** に分解できる。うち 2 つは再現による確定、
1 つは「時間軸生成側に累積誤差が無い」ことを実測で確認したうえでの絞り込みである。

| # | 症状 | 原因 | 確度 |
|---|---|---|---|
| A | テロップが**クリップ境界で重なる** | 各クリップの**最後のテロップに +2.0 秒のホールドが付き**、クリップ終端を越えて次クリップの先頭テロップ（そのクリップの 0 秒地点から始まる）と重なる | **確定**（clip1 で 2.596 秒はみ出しを実測） |
| B | 重なったテロップを**クリックすると別の場所へ飛ぶ** | 移動距離ゼロのクリックでも `MoveClip` が発行され、`_clamp_position()` が「重なりの解消」として隣接テロップの外側へ強制的に寄せる | **確定**（実行して +2.116 秒の移動を再現） |
| C | 発話とテロップが**ずれる／クリップ毎にリセット** | **時間軸の生成側（音声抽出・Timeline 配置）に累積誤差は無い**ことを実測で確認（クリップ全体で +21ms・非累積）。原因は**「残す区間だけを連結した継ぎ接ぎ音声」に対する音声認識が返す時刻そのもの**で、クリップの後方ほど遅れる。認識をクリップ単位で独立に行うため誤差もクリップ内で閉じる＝「クリップ毎にリセット」 | **確定**（対照実験で前半 +0.64s → 後半 +1.05s の系統的な遅れを実測） |
| — | 映像と音声はズレない | V1（映像）と A1（音声）は同一クリップから導出されるため原理的にズレない。報告と整合する | 整合 |

重要な点として、**A と B はテロップ時刻の誤差がゼロでも発生する**。
つまり C を改善しても A・B は残るため、それぞれ別に対処が必要である。

## 2. 前提となる処理経路

`setting.json` は `archive.clip_pipeline.timeline_review = true` のため、
アーカイブ用切り抜きは **Timeline 経路**（実カットしない経路）で動く。

```
VOD
 └ _cut_region()            区間 [start,end] をストリームコピーで切り出し   → raw.mp4
    └ normalize_file()      ラウドネス正規化（映像は -c:v copy）           → normalized.mp4
       ├ detect_edit_points()          無音検出のみ（実カットしない）      → keep_segments
       └ recognize_for_timeline()      keep_segments の音声だけを連結して認識
          ├ extract_audio_segments()   区間音声を連結                      → asr_audio.m4a
          ├ WhisperTextSource.extract()  faster-whisper 1.2.1 / large-v3
          └ adjust_display_timing()    表示タイミング整形                  → items
 └ build_archive_timeline()  クリップを TOP 順に 1 本の Timeline へ並べる
 └ ArchiveTimelineDialog     編集
 └ split_by_clip() → renderer.render()  クリップ単位へ戻して書き出し
```

ここで **3 つの時間軸** が登場し、これらが一致していることが正しさの条件になる。

| 軸 | 実体 | 生成箇所 |
|---|---|---|
| ① Timeline 軸（映像） | `keep_segments` の尺を順に積んだ位置 | `timeline_builder.py:89-105`（`cursor += duration`） |
| ② 認識音声の軸 | `asr_audio.m4a` 内の実時間 | `silence_cutter.extract_audio_segments()` |
| ③ 字幕の軸 | `items[].start/end` | Whisper の戻り値 → `adjust_display_timing()` |

## 3. 症状 C（テロップのタイミングずれ）の解析

### 3-1. 実測: 軸①と軸②は一致している（累積誤差は無い）

`docs/error/20260811/resolve.md` で修正した「実カット後ファイルに対して認識すると
区間ごとの CFR 量子化と AAC プライミングが累積する」問題が**再発していないか**を、
今回の VOD の clip1（945.0〜1125.0）を実際に再現して確認した。

再現スクリプト: `_cut_region` → `normalize_file` → `detect_edit_points`
→ `extract_audio_segments` を本番と同じコード・同じ設定（`last_cut_db=-23`）で実行。

| 項目 | 実測値 | 本番ログ（08:33:38〜08:33:57） |
|---|---|---|
| raw.mp4 尺 | 181.07s | — |
| normalized.mp4 尺 | 181.10s | 総尺 181.1s |
| 残す区間 | 38 件 / 合計 **54.384s** | 38 件 / 54.4s |
| `asr_audio.m4a` の**実尺** | **54.405s** | — |
| 理想値との差 | **+0.021s** | — |

**+0.021s = 1024 サンプル（AAC 1 フレーム）ちょうど**で、区間数に比例しない定数である
（`docs/error/20260811/resolve.md` §10-1 で「許容」とした既知の誤差そのもの）。

補足として、同じ形（38 区間相当・20 区間）の合成素材でビープ位置を測定したところ、
連結後のビープ位置は理想位置から最大 36ms しかずれず、**区間数に応じた累積は観測されなかった**。

> **したがって「音声を切り貼りする過程で字幕が後ろへずれていく」という 20260811 と同じ機構ではない。**

### 3-2. 実測: Timeline への配置（軸①・オフセット）も正しい

`build_archive_timeline()` は

* V1 クリップを `duration = end - start` で隙間なく積む（`timeline_builder.py:89-105`）
* 字幕へは同じ `cursor` の値（`clip_start`）を一律で足す（同 `:107-109`, `:150-176`）

ため、**クリップ先頭のオフセットは定義上ずれない**。本番ログもこれを裏づける。

```
アーカイブ Timeline 構築: 10 クリップ / V1 409 本 / S1 472 件 / 全長 770.6s
```

* V1 409 本 = 各クリップの残す区間数の合計（38+40+50+44+48+48+35+32+37+37）と一致
* S1 472 件 = 各クリップの字幕件数の合計（36+49+55+57+50+41+59+34+54+37）と一致
* 全長 770.6s に対し、**各クリップの尺の合計は 767.56s**（54.38+80.19+98.13+76.80+72.32
  +81.45+66.49+71.49+101.37+64.94）

差の **+3.04s は映像ではなく字幕のはみ出し**である。
`Timeline.duration_sec()`（`model.py:629-636`）は字幕トラックも計算に含めるため、
最後のクリップの末尾テロップが映像の終端を 3.04 秒超えていることを意味する（→ §4 の症状 A）。

### 3-3. 残る誤差は「認識が返す時刻」そのもの

軸①②とオフセットが正しい以上、発話とテロップの相対ズレは **③（Whisper の戻り値）** に帰着する。
再現した clip1 の認識結果（36 セグメント）には、次の明確な破綻が含まれていた。

```
 34    52.92    54.58   ヒットして…
 35    54.58    54.98   ○○○○      ← 音声ファイルの実尺 54.405s の「外側」
```

**最後のセグメントは音声が存在しない位置に置かれている。**
末尾で 0.6 秒以上、時刻が後ろへ張り出していることになる。

この経路が構造的に不利な理由は次のとおり。

* 認識対象の `asr_audio.m4a` は **38 個の断片を継ぎ接ぎした音声**（1 区間あたり平均 1.43 秒、
  最短 0.014 秒）で、区間の間には本来あった無音が一切無い。
* Whisper の単語タイムスタンプは 30 秒窓のメルスペクトログラム上の DTW で求められるため、
  こうした不連続な montage では前後の窓へ滑りやすい。
* `whisper_vad_filter=true` により Silero VAD がさらに非発話（ゲーム音・歓声など）を除去してから
  認識し、時刻を復元する二段構えになっている（faster-whisper 1.2.1 の
  `restore_speech_timestamps()` 自体は単語時刻も正しく写す実装であることをソースで確認済み）。

そして **認識はクリップごとに独立して 1 回ずつ**行われる（`_prepare_clips()` のループ）。
したがってこの誤差は**クリップ内で完結し、次のクリップでは 0 に戻る**。
これが報告の「上記のタイミングは、クリップ毎にリセットされている」と完全に一致する。

### 3-3-1. 対照実験: 「素材そのままの認識」と突き合わせる

認識時刻が本当に遅れているのかを確かめるため、**同じ clip1 の `normalized.mp4`（無音カット前・181.1s）を
そのまま認識**し、得られた素材時刻を `TimeMap.from_segments(keep_segments)` で
「詰めた軸」へ写して、連結音声（54.4s）の認識結果と同じテキストどうしで比較した。

素材そのままの認識は、発話の間に本来の無音が残っている自然な音声に対する認識であり、
継ぎ接ぎ音声よりも時刻が信頼できる**参照側**として使える。

| 連結音声側の開始 | 素材そのまま → 詰めた軸 | 差 | テキスト |
|---|---|---|---|
| 26.60 | 26.06 | **+0.54** | 諦めるなよ諦めるなよ |
| 31.24 | 30.90 | **+0.34** | いやあでも |
| 34.74 | 33.90 | **+0.84** | 何や分からんな |
| 35.48 | 34.64 | **+0.84** | でもほとんどの人は |
| 37.68 | 36.84 | **+0.84** | なんか知ってる人は |
| 42.30 | 41.30 | **+1.00** | 最速で130ぐらいなんじゃないかな |
| 50.66 | 49.57 | **+1.09** | このゲーム |
| 52.92 | 51.78 | **+1.14** | ヒットして見えないといけないから |
| 54.58 | 53.42 | **+1.16** | わからん |

（テキスト一致率 0.6 以上で対応が取れた 9 件。認識 49 件 対 36 件で文の切れ方が異なるため
すべては対応しないが、対応した全件が同じ傾向を示した。）

* **差は全件が正（＝連結音声側が遅い）**
* **前半平均 +0.64s → 後半平均 +1.05s** と、クリップの後方ほど広がる
* 26.6s 時点で既に +0.54s、末尾では +1.16s

> **結論: 「残す区間だけを連結した音声」に対する認識は、クリップの後方へ行くほど時刻が遅れる。**
> 遅れは 1 クリップの中で 0 →約 1 秒まで広がり、認識がクリップ単位で独立しているため
> 次のクリップの先頭で 0 に戻る。**報告の「ズレはクリップ毎にリセットされている」と完全に一致する。**

なお対照側も Whisper の出力であり厳密な真値ではないが、
(1) 差の符号が全件そろっていること、(2) 時間に対して単調に広がること、
(3) §3-3 のとおり連結音声側の最終セグメントが音声ファイルの外側に置かれていること、
の 3 点が同じ方向を指しており、連結音声側の時刻が信頼できないと判断してよい。

これは 20260811 の修正（実カットをやめて区間音声で認識する）が持ち込んだ**副作用**である。
軸のズレ（当時 20 区間で約 0.6 秒）は解消できたが、
**認識対象そのものが継ぎ接ぎ音声になったことで、認識時刻の精度が落ちている。**

### 3-4. 表示整形がズレを増幅する側面

`adjust_display_timing()`（`subtitle_generator.py:817-846`）は

* 次の発話まで 2.0 秒以内なら **次の発話開始まで表示を伸ばす**（R3）
* 次が無い／2.0 秒超なら **発話末 +2.0 秒**まで表示する（R2）

という規則で、テロップを隙間なく連結する。
連結音声では発話間の無音が取り除かれているため実質すべて R3 が適用され、
**1 件でも開始時刻が遅れると、その手前のテロップの表示終了も一緒に後ろへ延びる**。
結果としてズレが「点」ではなく「帯」として体感される。

## 4. 症状 A（テロップの重なり）の解析 — 確定

### 4-1. 発生機構

`adjust_display_timing()` の R2 により、**各クリップの最後のテロップは必ず「発話末 +2.0 秒」まで表示される。**
クリップの最後の発話はクリップ終端の直前にあるため、この 2 秒はほぼ丸ごと**クリップの外**に出る。

clip1 の実測（本番と同じ設定で整形した結果）:

| 項目 | 値 |
|---|---|
| クリップ尺（V1 の合計） | 54.384s |
| 最後のテロップの表示区間 | **54.580 〜 56.980s** |
| クリップ終端からのはみ出し | **+2.596s** |
| 終端を超えるテロップ | 2 件 |

`build_archive_timeline()` はクリップを隙間なく連結するため、
**54.384s 以降は clip2 の領域**である。そして clip2 の最初のテロップは
clip2 の 0 秒地点（= 54.384s）から始まる（Whisper の 1 件目は 0.00 開始だった）。

```
時間 →
 clip1 の映像 |==============================|  (…54.384)
 clip2 の映像                                |==============================
 clip1 の字幕                            [====== 54.580–56.980 ======]
 clip2 の字幕                                [=== 54.384–… ===]
                                              ↑ ここで重なる
```

**クリップ境界 9 か所すべてで必ず発生する。** 報告の「重なっている個所があり」と一致する。

### 4-2. なぜクリップ用では起きなかったか

クリップ用（`src/timeline/builder.py`）は素材 1 本ぶんの Timeline であり、
末尾テロップの 2 秒はエンディングの手前か Timeline の終端に落ちるだけで、
後続のテロップと衝突しない。**クリップを連結するアーカイブ用に固有の問題**である。

### 4-3. 書き出しへの波及

`split_by_clip()`（`timeline_builder.py:243-249`）は字幕を **開始時刻だけ**で振り分ける。

```python
if offset - 1e-6 <= subtitle.timeline_start < end - 1e-6:
```

clip1 の最後のテロップは開始が 54.580s（= clip1 の終端 54.384s より後）なので、
**clip2 のグループへ入り、clip2 の冒頭に焼き込まれる**（`_render_clips()` は
グループごとに `renderer.render()` するだけのため素通しになる）。
すなわちこの不具合は**編集画面だけでなく最終出力にも出る**。

## 5. 症状 B（クリックするとテロップが飛ぶ）の解析 — 確定

### 5-1. 経路

`src/gui/timeline/timeline_view.py`

* `mousePressEvent`（`:591-635`）は、クリップを掴んだ時点で無条件に
  `self._drag = _DRAG_MOVE` と `_drag_preview = {"id", "start", "duration"}` を設定する。
  **ドラッグ開始のしきい値（何 px 動いたら移動とみなすか）が無い。**
* `mouseReleaseEvent`（`:673-695`）は、マウスが 1px も動いていなくても
  `self._controller.move_clip(clip_id, preview["start"])` を実行する。
  `preview["start"]` は押した時点の位置＝**移動距離 0** である。

### 5-2. `MoveClip` は「移動距離 0」でも重なりを解消してしまう

`src/timeline/commands.py`

```python
# MoveClip.apply (:316-325)
target = _clamp_position(track, clip, self._new_start, self._min_clip_sec)
if abs(target - clip.timeline_start) <= _EPS:
    return False
clip.timeline_start = target
```

```python
# _clamp_position (:145-163) — 同一トラック内で他クリップと重ならない位置へ丸める
for other in others:
    if end <= other.timeline_start + _EPS or desired >= other.timeline_end - _EPS:
        continue
    to_left  = other.timeline_start - clip.duration
    to_right = other.timeline_end
    desired = to_left if (abs(desired - to_left) <= abs(desired - to_right) and to_left >= 0) else to_right
```

`_clamp_position()` は「これから置こうとする位置」が正しい前提で書かれているため、
**すでに重なっている状態で同じ位置を指定されると、重なりを解消する方向へ強制的に動かす。**
`abs(target - clip.timeline_start) <= _EPS` の早期 return は clamp の**後**にあるため機能しない。

### 5-3. 再現結果

§4 の状況（clip1 末尾テロップと clip2 先頭テロップの重なり）を模したモデルに対し、
**位置を変えずに** `MoveClip` を実行した。

```
クリック前: s1=53.000  s2=54.384      （s1 は 53.000–56.500、s2 は 54.384–55.584）
クリック後: s1=53.000  s2=56.500      （changed=True）
→ s2 が +2.116s 移動した
```

**クリックしただけでテロップが 2 秒以上先へ飛ぶ**ことを再現できた。報告と一致する。

### 5-4. 付随する問題

* この移動は履歴に積まれるため Undo で戻せるが、**ユーザーに何の通知も出ない**。
* 重なっている 2 件のうち `clip_at_pos()`（`:552-567`）は `reversed(track.clips)` で
  最初に当たったもの（＝後から描かれた＝見た目で手前のもの）を返すため、選択自体は妥当。
  飛ぶのは選択後の `MoveClip` が原因。
* V1（映像）は隙間なく並び重なりが無いため、この症状は**字幕トラックでのみ**顕在化する。

## 7. 対策案（実装は未着手・設計は別途）

| # | 対象 | 案 | 効く症状 |
|---|---|---|---|
| 1 | `archive/timeline_builder.py::_append_subtitles` | 字幕をそのクリップの範囲 `[clip_start, clip_end]` でクランプする。終端を超える分は短縮し、完全に外へ出るものは載せない | A（根本） |
| 2 | `archive/clip_writer.py::_prepare_edit_points` | 整形時に「クリップ終端」を渡し、最後のテロップのホールドを終端で打ち切る（`display_max_hold_sec` の意味を変えずに済む） | A |
| 3 | `gui/timeline/timeline_view.py` | ドラッグ開始のしきい値（数 px）を設け、動いていないクリックでは `MoveClip` を発行しない | B（根本） |
| 4 | `timeline/commands.py::MoveClip` | clamp の前に「要求位置＝現在位置」なら何もしない判定を入れる（3 の保険） | B |
| 5 | `archive/timeline_builder.py::split_by_clip` | 字幕の振り分けを「開始時刻」ではなく「範囲の交差＋グループ終端でのクランプ」にする | A（書き出し側） |
| 6 | `modules/subtitle_generator.py` / `archive/clip_writer.py` | 認識時刻の精度改善（症状 C の根本）。候補は **(a) 素材そのまま（無音カット前）を認識し `TimeMap.to_timeline()` で詰めた軸へ写す**、(b) 区間ごとに認識して区間内の相対時刻として扱い、区間の開始位置を足す、(c) `whisper_vad_filter` の要否を実測で見直す | C |

対策 1〜5 は局所的で既存挙動への影響が小さい。
対策 6 は §3-3-1 の対照実験でそのまま (a) の実測を兼ねており、**(a) が最も筋が良い**。
ただし次のトレードオフがあるため、単独で設計・計測してから判断すべきである。

* **認識時間**: clip1 で認識対象が 54.4s → 181.1s と約 3.3 倍。今回の実行（clip あたり約 2.5 分）
  から見て、10 クリップで **20〜30 分の増加**が見込まれる。
* **ハルシネーション**: 無音を含む素材をそのまま認識すると、`docs/error/20260626` で対策した
  無音区間への幻聴字幕が再燃しうる（`whisper_vad_filter` が効くため悪化しない可能性もある。要計測）。
* **カット区間へ落ちた字幕の扱い**: `TimeMap.to_timeline()` はカット済み区間内の時刻に対して
  `None` を返す。捨てるのか直近の境界へ寄せるのか、`split_interval()` で分割配置するのかを決める必要がある
  （クリップ用 `builder._append_subtitles` は逆方向の写像しか使っていないため前例が無い）。
* (b) は認識回数が区間数（clip1 なら 38 回）に増え、1〜2 秒の断片単体では文脈が失われて
  認識精度自体が落ちるため、現実的ではない。

## 8. 再現・検証の手順

本解析で用いた検証は次の 3 つ。いずれも本番と同じコード・同じ `setting.json` を使用した。

1. **軸の一致確認**（§3-1）
   `_cut_region(VOD, 945.0, 1125.0)` → `normalize_file` → `detect_edit_points`
   → `extract_audio_segments` を実行し、`asr_audio.m4a` の実尺と `sum(end-start)` を比較する。
2. **はみ出し確認**（§3-3, §4-1）
   1 の音声を `WhisperTextSource.extract()` にかけ、`adjust_display_timing(items, 2.0, 0.5)`
   の結果とクリップ尺 54.384s を比較する。
3. **クリック移動の再現**（§5-3）
   重なった 2 件の `SubtitleClip` を持つ `Timeline` を作り、
   `commands.MoveClip(id, 現在の timeline_start).apply(timeline)` を実行する。
4. **対照実験**（§3-3-1）
   1 の `normalized.mp4` をそのまま `WhisperTextSource.extract()` にかけ、
   得られた時刻を `TimeMap.from_segments(keep_segments).to_timeline()` で詰めた軸へ写し、
   2 の結果とテキスト一致で突き合わせて差を取る。

手動確認としては、Timeline 編集画面でクリップ境界（採点グラフのマーカでジャンプできる）へ移動し、
前クリップの最後のテロップが次クリップの冒頭に残っていること、
それをクリックすると位置が変わることを確認できる。
