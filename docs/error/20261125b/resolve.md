# セクション追加が「区間が途切れています」で失敗する 原因と修正設計書

現象の報告: `docs/error/20261125b/error.md`

本書は `docs/CLAUDE.md`「実装前に設計を行うこと」に従う **設計書** である。

---

## 1. 結論

**区間取得のキャッシュフォルダが「セクション番号」だけで決まっており、
取得する区間が変わっても同じフォルダを使い回す。**

```python
# src/archive/vod_range.py:231
cache_root = os.path.join(workdir, f"vod_range_{tag or 'x'}")
```

`tag` はセクション番号 (`job["index"]`) である。番号が同じなら、
**3350 秒ぶんを取ったフォルダへ 4230 秒ぶんを落としにいく**。

さらに取得前の片づけ (`twitch_source._clear_broken_leftovers`) は
**番号付きセグメントをわざと残す**。これは `docs/error/20261118` §9 R5 の決定で、
「再試行が前回の続きから進む」ようにするためである。意図どおりに残ったセグメントが、
今回は**別の区間のもの**だったため、取得結果に混ざった。

```python
# twitch_source.py:650 のコメント
# **番号付きセグメント本体は残す** = download_with_retries() が既存分を飛ばすので、
# 再試行が前回の続きから進む (区間ぶんの落とし直しを避ける)。
```

この前提は「**再試行は同じ区間に対して行われる**」である。区間が変わるときには成り立たない。

## 2. 証拠

### 2.1 セグメント数が区間の広さに依らない

| 時刻 | 要求 | 取得できたセグメント |
|---|---|---|
| 11:34:12 | 4227→6306 秒 (2079 秒) | 212 件 |
| 11:35:20 | 4227→6243 秒 (2016 秒) | 212 件 |
| 11:36:19 | 4227→4323 秒 (96 秒) | 212 件 |
| 11:37:09 | 4227→4263 秒 (36 秒) | 212 件 |

36 秒ぶんの取得で 212 件になるのは、**フォルダにあるものを全部数えている**からである
(`twitch_source.list_segments` はフォルダ内の番号付きファイルを全部返す)。

### 2.2 番号が実際の時刻と一致する

`00334`〜`00336` は 11:04 に取得した 3347→3363 秒 (`3347 / 10 = 334.7`)、
`00422` 以降が 11:34 以降の 4227 秒〜 (`4227 / 10 = 422.7`) である。

### 2.3 `verify_continuous` は正しく働いている

欠番で止めているのは**正しい**。止めなかった場合、

```python
# vod_range.py:250
origin = segment_origin(starts, indexes[0])
```

`indexes[0]` が残骸の 334 になり、**素材の原点が 3340 秒として記録される**。
実際の中身は 4227 秒からなので、**890 秒ずれたセクションが黙って挿入される**。
検証が無ければ気付けない壊れ方であり、この検査は残す。

## 3. 影響範囲

| 経路 | 影響 |
|---|---|
| セクション追加 (元 VOD が手元に無く、区間を取り直す場合) | **本件**。同じセクション番号で 2 回目以降に別の区間を指定すると必ず失敗する |
| セクション追加 (元 VOD が手元にある場合) | 影響なし (`_source_for` が取得を行わない) |
| VOD 全体の取得 (`download_vod`) | 影響なし (フォルダが別) |
| AI 編集 | 影響なし (素材は元 VOD から切り出す) |

**同じ番号が 2 回使われる**のは珍しくない。追加が失敗した・Undo した・
プロジェクトを開き直した場合、`next_section_index` は同じ番号を返す。

## 4. 修正方針

### R1. 区間が変わったらキャッシュを捨てる（本丸）

キャッシュフォルダに**そのフォルダで取得した区間**を控え、次の取得で区間が違えば
フォルダごと捨ててから落とす。

| 条件 | ふるまい |
|---|---|
| 控えが無い (初回・前のセッションの残り) | 捨ててから落とす |
| 控えの区間が**今回と同じ** | **残す** = 20261118 §9 R5 の「再試行は前回の続きから」を保つ |
| 控えの区間が今回と違う | 捨ててから落とす |

控えは `vod_range_<tag>/requested_window.txt` に `開始-終了` の 1 行で書く。
判定は `vod_range.fetch_range` が行う。ここは `window_start` / `window_end` を
決めている場所であり、取得の入口でもある。

* `twitch_source` 側は触らない。残骸の片づけ方 (`_clear_broken_leftovers`) は
  20261118 の決定どおりのままにする。**「同じ区間なら残す」という前提が
  成り立つ状態を作る側**を直す。
* 捨てるのは**取得を始める前**だけ。失敗後のキャッシュの扱い
  (`keep_cache_on_error`) は変えない。

### R2. 取れたセグメントが要求とかけ離れていたら止める（安全網）

R1 を入れてもフォルダが汚れる経路が残るかもしれない (手で置いた・別プロセスなど)。
`fetch_range` は要求した区間から**必要なセグメント数の上限**を見積もれるので、
極端に多ければ止める。

```
想定 = (window_end - window_start) / セグメント長 + 余裕
```

セグメント長はプレイリストから分かる。ただし本件は `verify_continuous` が既に
捕まえているため、**R2 は実装しない** (§7 P1 へ送る)。検査を二重にするより、
一度きちんと止まるほうがよい。

### R3. 採らなかった案

| 案 | 却下理由 |
|---|---|
| フォルダ名に区間を含める (`vod_range_13_4227_6306`) | 混ざらなくなるが、**区間ごとにフォルダが増える**。今回のように 2000 秒ぶんを 3 回試すと数 GB が一時領域へ積み上がる (実行時の空きは 9.4 GB だった) |
| `_clear_broken_leftovers` で番号付きセグメントも常に消す | 20261118 §9 R5 の「再試行が前回の続きから進む」を壊す。回線が細いときに同じ区間を落とし直すことになる |
| `list_segments` の代わりに `playlist_downloaded.m3u8` の並びを使う | より正確だが、`download_vod_range` の戻り値の意味が変わり、`.ts` 形式 (取得分プレイリストが無い) の経路を別扱いにする必要がある。本件の原因はフォルダの使い回しであり、そこを直すのが筋 |
| セクション番号ではなく通し番号を `tag` にする | 取得のたびに新しいフォルダになり、**再試行で前回の続きから進めなくなる** |
| `verify_continuous` を緩める | 原点が 890 秒ずれた素材が黙って入る (§2.3)。**絶対に緩めない** |
