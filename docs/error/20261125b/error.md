## 決定的な手がかり

**要求した区間の広さが 30 秒でも 2070 秒でも、取得できたセグメント数が必ず 212 件で同じ**である。

```
11:34:12  区間取得: 4227→6306 秒 → 区間取得完了: … (212 セグメント)
11:37:09  区間取得: 4227→4263 秒 → 区間取得完了: … (212 セグメント)   ← 36 秒なのに 212 件
```

取得先フォルダの中身を見ると、**別の区間のセグメントが混ざっていた**。

```
C:\…\archive_clips_prex6coe\vod_range_13\2938439428\chunked\
    00334.mp4  00335.mp4  00336.mp4     ← 11:04 に取得した 3347→3363 秒ぶん (残骸)
    00422.mp4  00423.mp4  …             ← 11:34 以降に取得した 4227 秒〜ぶん
```

* `3347 / 10 = 334.7` → セグメント 334〜336
* `4227 / 10 = 422.7` → セグメント 422〜

つまり「336 の次が 422」は**前回の取得の残骸と今回の取得が同じフォルダに同居している**ことを
指している。

## 直前に何があったか

```
11:04:02  区間取得: 2938439428 3347→3363 秒 (要求 3350.4→3360.0)
11:04:06  区間取得完了: …\vod_range_13\2938439428\chunked (3 セグメント)
11:04:47  セクション追加: clip13 を挿入 (成功)
```

この成功した取得が `vod_range_13` に 00334〜00336 を残した。その後 `vod_range_13` が
**同じ番号で**使い回され、4227 秒ぶんの取得と混ざった。

## 再現の形

1. セクション追加で区間 A を取得する (成功・失敗どちらでもよい)
2. **同じセクション番号**でもう一度セクション追加を行い、区間 A と離れた区間 B を指定する
3. `verify_continuous` が A と B のセグメント番号の飛びを検出して必ず失敗する

いったんこの状態になると、**以後その番号での追加は何を指定しても失敗し続ける**
(今回の 4 連続失敗)。アプリを再起動すると作業フォルダが変わるため直る。

原因と修正設計は `docs/error/20261125b/resolve.md`。
