# AiEditor resolve2 — 採点を AI に行わせる設計 (ドーパミン採点)

要望: `docs/AiEditor/request2.md` / 前提: `docs/AiEditor/resolve1.md` (特に §5 / §6 / §7)

本書は `docs/CLAUDE.md`「実装前に設計を行うこと」に従う **設計書** である。実装はレビュー後。

---

## 0. 先に結論

1. **機械測定 (`features.extract_cells`) は残す。** これは採点のためだけの部品ではなく、
   無音カットの閾値・ラウドネス・書き出しが使う `audio_scan` の供給元である (§1.1)。
2. **候補を作る役を AI へ移す。** 現在「音量の線形和で上位 N 窓を選ぶ」ところを、
   **全長を区切って映像(静止画)とコメントを AI に見せて山を列挙させる**方式に替える
   (新工程 `ai/scene_scanner.py`)。これが要望 A の実体である。
3. **採点の軸を YouTube 指標へ張り替える。** 単一の「面白さ」ではなく、
   CTR / 視聴維持率 / 満足度に対応する 7 軸 + 離脱リスクで測り、重みは設定に置く (§5)。
   AI に順位そのものを作らせない (`resolve1.md` §7.3 の決まりを踏襲)。
4. **`curve` と `clips` の形は変えない。** 採点グラフ・セクション追加・`clip_writer` が
   この形に依存している。AI のスコアは既存の窓へ焼き直して返す (§6)。
5. **映像を送る。** `resolve1.md` §5.5 の「映像は送らない」を本工程について反転する。
   同意文面の版を 1 → 2 へ上げ、取り直す (§10)。
6. **文字起こしは S1 では使わない。** 要望どおり S1 のコンテキストは「動画 + コメント」だけ。
   全長の Whisper は CPU で 1 時間級になり現実的でない (§8)。文字起こしは従来どおり
   候補が決まってから候補区間だけに行う。

## 1. 現状 — 採点は何をしているか

### 1.1 既存採点の正体

`archive/pipeline.analyze` の中身は 3 段である。

| 段 | 実装 | 中身 |
|---|---|---|
| 特徴抽出 | `archive/features.extract_cells` | 全長 1 パスで 1 秒ごとの dB と無音区間を測り、`slide_sec` ごとのセルへ畳む。戻り値の `audio_scan` は**書き出し側が使い回す** |
| コメント集計 | `archive/comment_source.aggregate_into_cells` | セルごとに `w_count` / `laugh_word_count` / `laugh_emote_count` / `comment_count` |
| 採点 | `archive/scoring.score_window` | `emotion` = 正規化音量の平均 + 大声セル加点 + 無音セル減点、`comment` = ｗ・草・エモートの数 + 急増ボーナス。`total` は両者の重み付き和 |

つまり**「音が大きくて、ｗが多いところ」を探しているだけ**である。
笑いの起点・期待と解決・表情・画面の変化は一切見ていない。

### 1.2 今の AI はどこに居るか

`resolve1.md` §7 の 3 段構えのうち、

* 第 1 段階 (候補抽出) = **既存採点のまま**。`ai.candidates.top_n` = 30 で本数だけ増やす
* 第 2 段階 (`ai/scene_finder.py`) = AI が 8 軸で**再評価**
* 第 3 段階 = 設定の重みで順位付け (`base_score_weight` = 0.2 で既存点も混ぜる)

**第 1 段階で落ちたものは AI に見えない。** 静かに面白い場面、画面だけで笑える場面、
コメントが薄い配信は候補にならない。これが要望 A/C の核心である。

`resolve1.md` §7.4 に「`ai.sweep`」(全長を文字起こしして拾い直す / 既定 `false`) が
設計されているが、実装は入っておらず、文字起こし前提のためコストが跳ねる。
**本書はこれを作り直し、文字起こしの代わりに映像とコメントを使う。**

### 1.3 設計で吸収しなければならない事実

| # | 事実 | 根拠 | 設計への影響 |
|---|---|---|---|
| Z1 | **Claude に動画は送れない。** 静止画だけ | `ai/vision.py` の冒頭、`resolve1-API.md` の `images` | 「動画を見せる」= フレームを抜いて送る。抜き方と枚数の設計が要る (§7) |
| Z2 | 1 リクエストの画像は **16 枚まで** | `resolve1-API.md` `limits.maxImagesPerRequest = 16` | チャンクの長さは「16 枚で足りる範囲」で決まる。**クライアントは今この値を読んでいない** (§7.3 で対処) |
| Z3 | 1 プロジェクトの呼び出しは **40 回**、入力は **300,000 トークン**まで | `ai.cost` / `limits.maxCallsPerProject` | スイープの呼び出し回数に上限を設け、超えたら粗くする (§8.2) |

| Z8 | 映像を送ることは現在の同意の範囲外 | `resolve1.md` §5.5 / `ai/consent.py` `CURRENT_VERSION = 1` | 同意の版を上げる (§10) |

## 2. 方針の比較

| 案 | 内容 | 判断 |
|---|---|---|
| A | 既存採点を捨て、AI の出力だけで `curve` / `clips` を作る | **却下**。`audio_scan` が作れず無音カット・ラウドネスが動かない。AI が落ちた日に機能ごと止まる。採点グラフの連続した折れ線も作れない |
| B | 今のまま (既存採点で候補を作り、AI が再評価) | **要望を満たさない**。§1.2 のとおり第 1 段階で落ちたものは見えない |
| C | **機械測定は残し、候補の生成を AI のスイープへ替える。AI のスコアを既存の窓へ焼き直す** | **採用**。要望 A〜D を満たし、Z6 の契約を保ち、AI が落ちても機械採点へ縮退できる |
| D | 全長を 1 回の呼び出しで評価させる | **却下**。Z2 (16 枚) と Z3 (300k トークン) に収まらない。6524 秒を 30 秒間隔で撮るだけで 218 枚 |
| E | 動画を直接送る | **不可**。Z1 |

### 2.1 なぜ機械測定を「残す」で、「併用」なのか

AI の判断は再現しない。同じ VOD を 2 回かけて順位が入れ替わると、
利用者から見て「壊れた」になる。機械測定は毎回同じ値を返すため、

* **床** — AI が見落としても、音量とコメントが極端な区間は候補に残る
* **較正** — AI のスコアが全体的に高すぎる/低すぎるときの基準になる
* **縮退** — AI が使えない日は機械採点だけで従来どおり動く

を担わせる。`resolve1.md` §7.3 の `base_score_weight` と同じ考え方を、
候補生成の段まで広げる。

## 3. 採用案の全体像

```
S0 機械測定            features.extract_cells → 1 秒 dB / 無音 / セル     [AI 無し・必須]
   + コメント集計      comment_source.aggregate_into_cells
   + 機械採点          scoring.score_window → machine_curve              [床・縮退用]
        │
S1 スイープ (新)       全長を chunk_sec ごとに区切る
   ★AI               各チャンク = フレーム 16 枚 + セルの数値 + コメント要約
                      → 「山」の列挙 (start / end / peak / 7 軸 / title_line)
        │
S2 候補の確定          S1 の山 + 機械採点の上位を統合 (重複は既存規則で畳む)
                      → candidates (ai.candidates.top_n 件)
        │
S3 精査 (既存)         候補区間だけ文字起こし → scene_finder が 8 軸で再評価
   ★AI               ※ S1 の軸と S2 の軸は別物。S3 は「文字が読めた上での評価」
        │
S4 焼き直し            AI スコア → 既存の窓へ写す → curve / clips を返す  [AI 無し]
        │
        └→ 以降は現行どおり (構成 → 編集指示 → 素材 → Timeline)
```

* S0・S4 は決定論。**AI が落ちたら S1 と S3 を飛ばして従来の結果が出る。**
* S1 が新規。S2 は `scoring.select_top_events` の統合規則を使い回す。
* S3 は既存 (`ai/scene_finder.py`) をそのまま使う。**軸は増やさない** (S1 と役割が違う)。

## 4. S1 スイープの設計

### 4.1 チャンクの切り方

```
chunk_sec     = ai.scan.chunk_sec        既定 480 (8 分)
frame_interval= ai.scan.frame_interval_sec 既定 30
→ 1 チャンクのフレーム = 480 / 30 = 16 枚 = Z2 の上限ちょうど
```

* 6524 秒の VOD → `ceil(6524 / 480)` = **14 チャンク = 14 回の呼び出し**。
* チャンクは**重ねない**。境目に跨る山は S2 の統合で 1 つに畳まれる
  (`scoring._merge_time_sections` と同じ規則)。
* 呼び出し回数の上限 `ai.scan.max_calls` (既定 16) を超える長さの VOD は、
  `chunk_sec` を自動で伸ばす (= フレーム間隔も伸びる)。**打ち切らない**。

### 4.2 1 回の呼び出しで送るもの

| 種別 | 内容 | 量 |
|---|---|---|
| 画像 | チャンク内の等間隔フレーム。長辺 `ai.scan.frame_edge_px` (既定 512) | 16 枚 |
| 数値 | セルごとの `{t, mean_db, max_db, silence_ratio, comments, laughs}` (チャンク内のみ) | 480/45 ≒ 11 行 |
| コメント | チャンク内のコメント本文。`ai.budget.max_comments_per_cell` で間引き。**投稿者名は送らない** | 数十行 |
| 位置 | チャンクの `start` / `end` と、フレーム 1 枚ごとの秒 | — |

**送らないもの**: 音声そのもの、文字起こし、投稿者名、ファイルパス。

フレームは「何秒の絵か」を必ず添える。添えないとモデルが時刻を推測し、
2026-11-25 のテロップずれと同じ事故 (AI に秒を推測させる) を繰り返す。

### 4.3 前置き (プロンプトの骨)

`ai/prompts.py` へ `SCENE_SCAN` として置く。出力先では変えない (`resolve1.md` §6.4 のキャッシュ方針)。

```
あなたは YouTube で伸びる切り抜きを選ぶ編集者である。
渡された区間の静止画 (秒つき)・音量の数値・視聴者コメントだけを根拠に、
「指が止まり、最後まで見られ、人に見せたくなる」山を列挙する。

山とは次の形を持つひとまとまりである。
  起こり → 山 → 落ち
期待が作られ、それが外れるか満たされるところを探す。
音が大きいだけ・コメントが多いだけの区間は山ではない。

守ること:
・時刻は渡された区間の中だけで答える。新しい時刻を作らない。
・根拠は渡されたものだけに置く。画面に無いものを推測して書かない。
・山が無い区間には何も返さない (空の配列を返す)。無理に埋めない。
・1 つの山は {min_sec}〜{max_sec} 秒に収める。
・title_line は視聴者が内容を想像できる {max_chars} 文字以内の 1 行。煽り過多にしない。
・出力は {language} で書く。
```

「山が無ければ空で返す」を明記するのが要点である。
全チャンクから均等に拾わせると、退屈な区間からも候補が出て精度が落ちる。

### 4.4 応答スキーマ (構造化出力)

```json
{
  "moments": [
    {
      "start": 4588.0,
      "end": 4702.0,
      "peak": 4596.5,
      "beats": { "setup": 4588.0, "hit": 4596.5, "settle": 4620.0 },
      "scores": {
        "hook": 86, "payoff": 78, "emotion_delta": 81, "surprise": 74,
        "clarity": 69, "shareability": 72, "drop_risk": 22
      },
      "title_line": "フロントウイング無しで走ってた",
      "why": "自信のある発言の直後に画面の破損に気付き、コメントが一斉に反応している",
      "evidence": { "frames": [4590, 4620], "comments": 12 }
    }
  ]
}
```

* `beats` が**後段の自然な編集のための情報**である (§15)。
* `evidence` は「どのフレーム・何件のコメントを根拠にしたか」。
  レビュー PDF (`ai/review_report.py`) に出し、人が後から検算できるようにする。
* 範囲外・欠落は `plan_validator` と同じ流儀で**丸めて残す** (落とさない)。

## 5. ドーパミン / YouTube 指標

### 5.1 軸の定義

| 軸 | 0..100 の意味 | YouTube で効く場所 |
|---|---|---|
| `hook` | 冒頭 3 秒で指が止まるか (画面の変化・表情・音の立ち上がり) | **CTR / 離脱の初速** |
| `payoff` | 期待 → 解決がこの区間の中で閉じるか。ドーパミンの本体は「予測と報酬の差」であり、**解決が区間外にあるものは価値が落ちる** | 平均視聴率 |
| `emotion_delta` | 感情の振れ幅 (静 → 動、無反応 → 絶叫)。絶対的な音量ではなく**変化量** | 視聴維持率の山 |
| `surprise` | 予測外か | 再生時間 / 共有 |
| `clarity` | 初見で何が起きたか分かるか (前提の説明が要らないか) | 離脱率 |
| `shareability` | 人に見せたい・もう一度見たいか | いいね / 共有 / 再視聴 |
| `drop_risk` | 離脱しやすさ (説明が長い・無反応が続く・同じ絵が続く)。**負の重み** | 平均視聴率 |

`title_line` は数値ではないが CTR の材料として必ず書かせる。
これがうまく書けない山は、そもそもサムネ・タイトルにできない = 伸びない。

### 5.2 既存 8 軸との関係

S3 (`scene_finder`) の 8 軸は**文字起こしを読んだ上での評価**であり、残す。
S1 の 7 軸は**映像とコメントだけで見た評価**である。両者を混ぜない。

| | S1 (scan) | S3 (eval) |
|---|---|---|
| 入力 | フレーム + 数値 + コメント | 文字起こし + 数値 + コメント |
| 目的 | **候補を見つける** (再現率) | **候補を選ぶ** (適合率) |
| 軸 | 本節の 7 軸 | `resolve1.md` §7.2 の 8 軸 |

### 5.3 重み (設定)

```
ai.scan.weights = {
  "hook": 0.25, "payoff": 0.25, "emotion_delta": 0.20, "surprise": 0.10,
  "clarity": 0.10, "shareability": 0.10, "drop_risk": -0.20
}
scan_score = Σ scores[k] * weights[k]   → 0..100 へ丸める
```

* 重みは `ai.scene_eval.weights` と同じ作りにし、用途 (`long` / `shorts`) で 2 組持つ。
  ショートは `hook` と `emotion_delta` を上げ、`clarity` を下げる。
* **コメントが薄い配信への対処 (Z5)**: `comments_per_min` が
  `ai.scan.sparse_comment_threshold` (既定 0.5 件/分) を下回るとき、
  AI へ「コメントは参考程度」と伝え、§6.1 の混合比 `ai_weight` を上げる。
  設定で書き換えられるようにし、ハードコードしない。

## 6. `curve` / `clips` への焼き直し (Z6 の契約)

### 6.1 窓スコアの混合

既存の窓 (180 秒 / 45 秒スライド) をそのまま使い、各窓に AI のスコアを乗せる。

```
ai_window   = 窓に重なる moment の scan_score の最大値 (重なりが無ければ 0)
total       = ai_weight * ai_window + (1 - ai_weight) * machine_total
ai_weight   = ai.scan.ai_weight   既定 0.3 (§14.2 で決定)
```

* `emotion` / `comment` の 2 項目は**機械の値をそのまま残す**。
  採点グラフの内訳表示とセクション追加の `best_window_for_range` が使っている。
* 窓に `ai_score` と `moment_index` を**足す** (消さない)。レビュー PDF と
  採点グラフの色分けに使える。
* `ai_weight = 0` にすれば完全に従来互換。**既定は 0.3** (根拠は §14.2 の全長スイープの実測)。

### 6.2 差し込み口

`archive/pipeline.analyze` に引数を 1 つ足す。

```python
def analyze(input_path, settings, progress_cb=None, comments=None, markers=None,
            scan=None):
    ...
    curve = [scoring.score_window(...) for w in windows]
    curve = [w for w in curve if w]
    # ★ AI スイープ (渡されたときだけ)。失敗しても機械採点のまま続ける
    moments = scan(input_path, settings, cells, comments, duration) if scan else []
    if moments:
        curve = ai_scoring.blend(curve, moments, settings)
    clips = scoring.select_top_events(curve, cfg["top_n"], ...)
    return {"duration": ..., "curve": curve, "clips": clips,
            "audio_scan": audio_scan, "moments": moments}
```

* `scan=None` のとき**今と完全に同じ**挙動 (経路 B = 従来の切り抜きは変わらない)。
* `scan` を渡すのは `ai_runner.run_ai` だけ (経路 D)。
* `moments` を戻り値へ足し、`context_builder` が `AnalysisBundle.moments` として持つ。
  これが S3 と構成 (§15) へ流れる。
* `pipeline.py` は `ai/` を import しない (`resolve1.md` §4 の依存の向き)。
  **関数を渡す形**にして向きを守る。

## 7. フレーム抽出の設計

### 7.1 1 回のデコードで済ませる (必須)

現在の `vision._extract_with_ffmpeg` は **1 枚ごとに ffmpeg を起動して seek する**。
12 枚なら問題ないが、218 枚では起動と seek だけで時間が溶ける。
`vision.frames_every()` を新設し、**1 パスで全部抜く**。

```
ffmpeg -skip_frame nokey -i <vod>
       -vf "select='not(mod(n\,{k}))',scale='min({edge},iw)':-2"
       -vsync 0 -q:v 5 <workdir>/scan_%05d.jpg
```

* `-skip_frame nokey` でキーフレームだけデコードする。Twitch VOD のキーフレームは
  約 2 秒間隔なので、30 秒間隔なら十分な粒度が得られ、デコード量が 1/60 になる。
* 抜いた絵は**送信用に読んだら消す** (`resolve1.md` §12.5 の決まりを踏襲)。
* **実測 (P1 / 2026-11-25)**: VOD `2938816056` (6.9 GiB / 6524 秒 / 2560x1440@60fps) で
  **219 枚を 106.6 秒**。1 枚 25 KB・合計 5.3 MB。全長 1 パスの音声解析 (16.5 秒) の
  約 6 倍だが、候補の文字起こし (16 分) に比べれば小さい。

### 7.2 時刻の対応付け

ファイル名の連番から秒を逆算してはいけない (キーフレームの位置は等間隔ではない)。
`showinfo` が 1 枚につき 1 行出す `pts_time` を読み、出力順にファイルへ対応させる。
`archive/cut_origin.py` が同じ問題 (要求位置と実際のパケット位置のずれ) を
既に解いており、その考え方を使う。

**実装上の落とし穴 (P1 で踏んだ)**: `ffmpeg_runner.execute_capture` は
**stderr の末尾しか返さない** (エラー表示用)。これを使うと行が足りず、
先頭のファイルに末尾の時刻が付く = **全部の時刻が間違う**。
`subprocess` で自分で回して全文を読むこと (`archive/cut_origin.py` と同じ作法)。
行とファイルの数が合わないときは、**間違った時刻を付けるくらいなら抽出ごと捨てる**。

### 7.3 枚数の上限をクライアントが守る

`resolve1-API.md` の `limits.maxImagesPerRequest` (16) を、現在クライアントは読んでいない。
`remote.server_config()` の応答に既に入っているので、

* `ai/config.py` へ `images_per_request` を持ち、サーバー値があればそちらを優先する
* `scene_scanner` は送る前に必ず切り詰める (超えたら 400 になる)

## 8. コストと時間

### 8.1 見積り (VOD 6524 秒 = 1 時間 49 分)

| 項目 | 量 | 根拠 |
|---|---|---|
| フレーム枚数 | 218 枚 (30 秒間隔) | 6524 / 30 |
| 1 枚のトークン | 約 197 | 512×288 の画像。Claude の画像は概ね (幅×高さ)/750 |
| 画像の入力 | 約 43,000 トークン | 218 × 197 |
| 文字の入力 | 約 15,000 トークン | セルの数値 11 行 + コメント数十行 × 14 チャンク |
| **S1 合計** | **約 58,000 トークン / 14 回** | `ai.cost.max_input_tokens_per_project` 300,000 の約 1/5 |
| 既存 S3 + 構成 | 約 30,000 トークン / 8 回 | 2026-11-25 の実測 (`scene_eval` 8,905 + `plan` 3,998 + 3,561 ほか) |

呼び出し回数は 14 + 8 = **22 回**。`max_calls_per_project` 40 に収まる。
40 を 3 出力先で割ると余裕は薄いので、`ai.scan.max_calls` で頭を押さえる (§4.1)。

### 8.2 予算を超えたときの振る舞い

**止めない。粗くする。**

1. `chunk_sec` を倍にする (フレーム間隔も倍)
2. それでも超えるなら `frame_edge_px` を下げる (512 → 384 で 1 枚 111 トークン)
3. それでも超えるなら S1 を飛ばし、機械採点だけで続ける (= 現状の挙動)

段数と順序は設定ではなくコードで固定する。利用者が「なぜ結果が変わったか」を
追えるよう、どの段で粗くしたかを**ログと レビュー PDF に残す**。

### 8.3 時間

S1 はフレーム抽出 (1 パス) + 14 回の呼び出しである。呼び出しは Z4 によりジョブへ落ちる前提で、
14 回 × 20〜70 秒 = **5〜15 分**を見込む。並列化は設計しない
(サーバーのポイント計測とレート制限を跨ぐため。§16 Q3 で確認する)。

現状の経路 D は 30 分かかっており、その内 16 分が候補の文字起こしである。
S1 を足すと伸びるが、**S1 の結果で候補が絞れれば文字起こしの対象も減る**ため、
全体では相殺される見込み。これも要実測。

### 14.2 全長スイープの実測と `ai_weight` の決定 (2026-11-25 / VOD 2938816056)

サーバーへ `sceneScan` を入れたうえで、**1 本を頭から終わりまで**流した
(`tools/ai_scan_probe.py`、14 区間 / 静止画 219 枚)。

#### 実測値

| 項目 | 実測 |
|---|---|
| 区間 | 14 (480 秒ごと。最後だけ 284 秒) |
| 画像 | 219 枚 (13 区間 x 16 枚 + 11 枚) |
| 入力 | 合計 59,843 トークン (1 区間 3,117〜4,734) |
| キャッシュ読み | 合計 24,402 (全 14 区間で `cache_read=1743` = **前置きは毎回キャッシュに乗った**) |

| 時間 | フレーム抽出 119 秒 + AI 97 秒 = **約 3.6 分** |

見積り (§8.1) は 14 回 / 約 43,000 入力トークンだった。入力が 1.4 倍になったのは
音量の数値とコメントが乗るためで、桁は合っている。

#### 見つけた山

**全長 6,524 秒に対して山は 2 件 / 合計 216 秒 (3.3%)** だった。

| 区間 | 点 | 題 | 内訳 |
|---|---|---|---|
| 6150.0-6240.0 | 45.65 | 最終ラップから表彰台でシャンパンまで | `hook=55 payoff=60 emotion_delta=62 surprise=25 clarity=55 shareability=45 drop_risk=40` |
| 4375.0-4480.0 | 34.50 | ダメージを抱えて走り続け、セッション中断 | `hook=35 payoff=65 emotion_delta=45 surprise=50 clarity=45 shareability=40 drop_risk=65` |

* 4375-4480 は **P2 の抜き取り (4370-4480) とほぼ同じ**。再現している
* 6150-6240 は新規。機械の最高点 (6345-6524 / 64.0) と**同じ終盤を指している**
* 0〜480 秒は 14 区間を通して 0 件。機械が 3 位・4 位に置いていた
  `45-225` (60.8) と `0-180` (60.0) を**AI は山と見なかった**。
  これはエンジン音で音量が飽和していただけで、要望どおりの判断である

#### 混合の効果 (機械の窓 142 件 / AI の山に重なる窓 12 件 = 8.5%)

| `ai_weight` | 上位の並び | 判断 |
|---|---|---|
| 0.0 | 1 位 6345-6524 / 3 位 `45-225` / 4 位 `0-180` | **誤検出が 3・4 位に残る**。現状 |
| 0.2 | 誤検出はまだ 3・4 位。AI の山は 7 位・10 位 | 足りない |
| **0.3** | **1 位が AI の表彰台 (6210-6390)。`45-225` は 6 位、`0-180` は 9 位へ落ちる** | **採用** |
| 0.5 | 上位 10 のうち 8 枠が山 2 件の近傍の重複窓。機械の窓は 9 位に 1 つだけ | 偏りすぎ |
| 0.7 | 上位 10 が全て山 2 件の近傍 | 偏りすぎ |
| 1.0 | 山に重なる窓が**全て同点**になり解像度を失う | 不可 |

**既定は `ai_weight = 0.3` とする。** 理由は 3 つである。

1. **狙った誤検出だけが落ちる。** エンジン音の飽和窓 (`0-180` / `45-225`) は
   AI の点が 0 なので 0.7 倍され、AI が認めた窓は 0.3 ぶん積まれる。
   この 1 点が要望の出発点だった
2. **素材が枯れない。** 山は全長の 3.3% しか無い。重ならない窓は
   **一律 (1-w) 倍**なので**互いの順位は保たれ**、長尺の穴埋めに使える。
   0.5 以上にすると上位が 2 件の近傍の重複窓で埋まり、セクションの多様性が死ぬ
3. **AI の点は機械より低く出る。** 実測の上限は 45.65 で、機械の 64.0 より小さい。
   0.3 では AI の寄与は最大 13.7 点だが、誤検出が失う 18 点のほうが大きいため
   順位は入れ替わる。重みを上げても上限が上がるわけではない

> **1 本での判断である。** レース配信・コメント 94 件という条件に寄っている。
> 0.5 以上へ上げるなら、雑談配信と高コメント配信で 2 本目・3 本目を測ってからにする。

## 15. 後段「自然な編集」への引き渡し

要望 E (自然な編集) は別件だが、**採点の段階で渡すべきものがある**。

| 渡すもの | 後段での使い道 |
|---|---|
| `beats.setup / hit / settle` | カットの始点・終点をここへ合わせる。山の手前で切らない・落ちる前に切らない |
| `peak` | ショートのフックの位置。既存の `RankedScene.peak` と同じ用途 |
| `title_line` | 構成のタイトル案・イントロカードの文言 |
| `drop_risk` の高い区間 | 詰める (無音カットを強める) 候補 |

`AnalysisBundle.moments` として `planner` まで届けておけば、
②③④ を直すときに「どこが山か」を AI に推測させずに済む。
**2026-11-25 のテロップずれは「AI に秒を推測させた」ことが原因**であり、
同じ轍を踏まないために、秒は必ず測った値を渡す。

### 16.1 サーバー側の宿題 (StretheusAPI)

**`sceneScan` の役がサーバーの許可リストに無い。** 2026-11-25 時点の
`GET /api/ai/config` は `sceneEval / plan / review / profile / classify` だけを返し、
`sceneScan` で送ると 400 `validation_failed` になる (実測: 全区間が落ちた)。

クライアントは**実行時にサーバーの `roles` を見て、無ければ `sceneEval` として送る**。
モデルと effort はクライアント側の `ai.models.scene_scan` / `ai.effort.scene_scan`
から引くため、送るモデルは変わらない (`AiRequest.model_key` を分けている)。
サーバーが役を足せば**設定を変えずに自動で切り替わる**。

サーバーへ依頼する内容:

| 項目 | 値 |
|---|---|
| 役 | `sceneScan` |
| モデル | `claude-sonnet-5-5` |
| effort | `medium` |
| `maxOutputTokens` | 16000 (山が多い区間で `moments` が伸びる) |
| 画像 | 1 リクエスト 16 枚まで (既存の `maxImagesPerRequest` のまま) |

役を分ける意味は、**計測と課金を S1 と S3 で分けて読めるようにする**ことである。
`sceneEval` に相乗りしたままだと、どちらがいくら使ったのかが分からない。
