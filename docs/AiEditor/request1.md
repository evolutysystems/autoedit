# Stretheus AI Clip Studio 基本構想・開発方針

## 1. プロジェクト概要

### 1.1 目的

既存のWindows向け動画編集ソフトウェア「Stretheus」に、AIによる動画制作機能「AI Clip Studio」を新機能として追加する。

本機能の目的は、Twitchの配信アーカイブから面白いシーンを自動的に発見し、AIが動画の企画・構成・編集方針を決定したうえで、Stretheusの既存編集エンジンを利用して動画を完成させることである。

最終的には、ユーザーが細かい編集作業を行わなくても、YouTube長尺動画・YouTube Shorts・TikTok向けの動画を自動生成できる状態を目指す。

### 1.2 基本方針

- 既存のStretheusの機能・編集エンジンを最大限再利用する。
- 既存機能と重複する処理を新規開発しない。
- AIには、従来のプログラムでは判断が難しいクリエイティブな作業を担当させる。
- AIの判断結果は構造化データとして出力する。
- 実際の動画編集・レンダリングは既存のStretheus編集エンジンで実行する。
- 将来的に複数のAIプロバイダー・モデルを利用できる構造にする。
- 人間による確認・修正が可能な設計にする。

---

## 2. システム全体の役割分担

AI Clip Studioは、既存機能と新規AI機能を組み合わせて構成する。

| 領域 | 担当 | 方針 |
|---|---|---|
| VOD取り込み | 既存Stretheus | 既存機能を利用 |
| 音声分離 | 既存Stretheus | 既存機能を利用 |
| 文字起こし | 既存Stretheus | 既存機能を利用 |
| 基礎的なシーン抽出 | 既存Stretheus | 既存機能を利用 |
| 面白シーンの発見・評価 | AI | 新規開発 |
| 動画企画・構成 | AI | 新規開発 |
| 編集指示の生成 | AI | 新規開発 |
| 動画編集 | 既存Stretheus | 既存編集エンジンを利用 |
| 動画レビュー | AI | 新規開発 |
| 編集内容の改善 | AI | 新規開発 |
| 投稿・分析 | AI＋外部API | 将来的に追加 |

重要なのは、AIにすべての処理を任せるのではなく、既存機能が得意とする処理とAIが得意とする判断を明確に分離することである。

## 3. AI Clip Studioの処理フロー

### 3.1 全体フロー

1. VOD・配信データの取得
2. 既存機能による音声・映像解析
3. AIによる面白シーンの発見・評価
4. AIによる動画企画・構成
5. AIによる編集指示の生成
6. 既存編集エンジンによる自動編集
7. AIによる品質レビュー
8. AIによる修正・再編集
9. ユーザーによる最終確認
10. 動画の出力

YouTube長尺動画・YouTube Shorts・TikTokについては、それぞれ独立した動画構成を生成する。

単純に同じ動画を異なるアスペクト比に変換するだけではなく、プラットフォームごとに最適な構成を考えることを基本とする。

## 4. AIによる面白シーン抽出

### 4.1 目的

既存のシーン抽出機能を利用しながら、AIによって従来のルールベース処理では発見できなかった面白いシーンも抽出できるようにする。

単純な音量変化やコメント数だけでは判断できない、会話の流れ・発言の意外性・状況の面白さなどを評価対象とする。

### 4.2 処理方式

面白シーン抽出は、以下の3段階で実施する。

#### 第1段階：既存機能による候補抽出

既存の解析機能を利用し、面白い可能性があるシーンを広く抽出する。

抽出に利用する情報の例：

- 音量の急激な変化
- 発話量・会話密度
- コメント数の急増
- 特定キーワードの検出
- 音声イベント
- 映像・シーンの変化
- 既存機能によるイベント検出結果

この段階では、面白さを確定させる必要はない。

面白い可能性があるシーンを取りこぼさずに候補化することを優先する。

#### 第2段階：AIによる面白さの評価

抽出された候補をAIが分析し、複数の評価軸から面白さを判断する。

評価項目：

| 評価項目 | 内容 |
|---|---|
| 面白さ | 純粋に笑える・楽しめるシーンか |
| 意外性 | 予想外の発言や展開があるか |
| 文脈依存度 | 前後の会話を理解する必要があるか |
| 初見理解度 | 配信を見ていない人にも伝わるか |
| 盛り上がり | 感情的な盛り上がりがあるか |
| ショート適性 | 短い動画として成立するか |
| 長尺適性 | 長尺動画の一部として価値があるか |
| 独立性 | 単独の動画として成立するか |

AIは、音声・文字起こし・コメント・映像情報など、利用可能な解析データを組み合わせて評価する。

また、既存機能で候補化されなかったシーンについても、AIが追加発見できる仕組みを検討する。

#### 第3段階：候補の統合・ランキング化

AIの評価結果をもとに候補を統合し、編集に利用するシーンをランキング化する。

出力する情報：

- シーン開始時刻
- シーン終了時刻
- 面白さスコア
- 意外性スコア
- 初見理解度スコア
- Shorts適性スコア
- 長尺動画適性スコア
- シーンの概要
- 面白いと判断した理由
- 必要な前後の文脈
- 推奨する利用方法

同じ出来事を複数の候補として抽出した場合は、重複を統合する。

### 4.3 重要事項

AIに単純に「面白いシーンを探してください」と指示するだけではなく、面白さを複数の評価軸に分解して判断させる。

これにより、評価の再現性を高め、将来的な評価モデルの改善にも利用できるデータを蓄積する。

## 5. AIによる動画企画・構成

### 5.1 目的

抽出した面白シーンを単純に時系列で並べるのではなく、AIが動画の企画・ストーリー・構成を考える。

同じ配信素材であっても、投稿先によって最適な構成は異なる。

そのため、YouTube長尺動画とShorts・TikTokは、それぞれ独立した構成案を生成する。

### 5.2 YouTube長尺動画

長尺動画では、視聴者が状況を理解し、動画を最後まで楽しめる構成を重視する。

基本構成の例：

1. オープニング：興味を引くシーン
2. 導入：状況や背景の説明
3. 展開：面白いシーンを組み合わせる
4. 盛り上がり：最も面白い場面
5. 締め：余韻やオチ

AIの判断項目：

- 採用するシーン
- シーンの順番
- シーン間のつながり
- 導入に使用するシーン
- 盛り上がりの配置
- カットする箇所
- 必要な前後の会話
- 動画全体の尺
- テロップ・効果音・BGMの演出方針

### 5.3 YouTube Shorts・TikTok

短尺動画では、冒頭から視聴者の興味を引き、短時間で面白さを伝えることを重視する。

基本構成の例：

1. 冒頭1〜2秒：強いフック
2. 状況説明：必要最小限の説明
3. 展開：テンポよく見せる
4. オチ：面白さのピーク

AIの判断項目：

- 冒頭に使用するシーン
- フックとなる発言・映像
- 不要な間の削除
- 状況説明に必要な会話
- オチまでの展開
- 最適な動画尺
- 縦型映像へのクロップ方針
- テロップ・効果音の演出方針

### 5.4 重要事項

長尺動画と短尺動画で同じ編集結果を使い回さない。

各プラットフォームの視聴習慣や動画特性に合わせて、AIが別々の企画・構成を生成する。

## 6. AIによる編集指示生成

### 6.1 基本方針

AIに直接FFmpegのコマンドや編集処理を書かせない。

AIは編集計画を構造化データとして出力し、Stretheus側がその内容を解釈して編集を実行する。

この中間データを、AIと既存編集エンジンを接続する共通インターフェースとして扱う。

### 6.2 編集指示データの例

```json
{
  "project": {
    "target": "youtube_shorts",
    "duration": 45
  },
  "scenes": [
    {
      "source_start": 1250.5,
      "source_end": 1278.2,
      "role": "hook",
      "reason": "意外な発言で興味を引く"
    },
    {
      "source_start": 845.0,
      "source_end": 870.5,
      "role": "context",
      "reason": "状況を理解するための説明"
    }
  ],
  "editing": {
    "subtitle": true,
    "vertical_crop": true,
    "sound_effects": true
  }
}
```

※上記は概念例であり、実際のスキーマは既存Stretheusの編集機能・プロジェクト構造に合わせて定義する。

### 6.3 将来的に定義する項目

- 動画の投稿先
- 動画全体の尺
- 使用する素材
- シーンの開始・終了時刻
- シーンの順番
- シーンの役割
- カット位置
- トランジション
- テロップの内容・位置・アニメーション
- BGM・効果音
- 音量調整
- クロップ位置・拡大率
- 映像エフェクト
- 演出意図
- 編集理由

### 6.4 設計上の重要事項

編集指示データは、AIモデルやプロバイダーに依存しない形式にする。

これにより、将来的にClaude・OpenAI・Geminiなどを切り替えても、既存編集エンジンを変更せずに利用できる構造を目指す。

## 7. 既存編集エンジンとの連携

### 7.1 基本方針

動画の実際の編集・レンダリングは、既存のStretheus編集エンジンを利用する。

AIは編集内容を決定し、既存編集エンジンはその指示に従って処理を実行する。

AI側に編集処理そのものを再実装させない。

### 7.2 役割分担

| 処理 | 担当 |
|---|---|
| シーン選定 | AI |
| 動画構成 | AI |
| カット位置の決定 | AI |
| テロップ・演出方針 | AI |
| 編集指示の生成 | AI |
| 編集指示の検証 | Stretheus |
| タイムラインへの反映 | 既存編集エンジン |
| エフェクト処理 | 既存編集エンジン |
| レンダリング | 既存編集エンジン |

編集指示の検証では、素材の存在・時間範囲・編集可能なパラメータ・処理の整合性などを確認する。

## 8. AIによる品質レビュー

### 8.1 目的

自動編集した動画を別のAI視点で評価し、問題点を発見する。

単一のAIに編集とレビューを兼任させるのではなく、レビュー専用の役割を設けることを推奨する。

### 8.2 レビュー担当

| 担当 | 評価内容 |
|---|---|
| 映像ディレクター | 映像の見せ方・テンポ・演出 |
| エンタメ評論家 | 面白さ・笑い・盛り上がり |
| 視聴者視点レビュアー | 初見でも理解できるか |
| プラットフォーム担当 | YouTube・Shorts・TikTokへの適性 |
| 品質管理担当 | 音声・映像・字幕・技術的な問題 |

### 8.3 レビュー結果

レビュー結果は、以下のような構造化データとして出力する。

- 問題がある時間
- 問題の内容
- 問題の重要度
- 問題を判断した理由
- 修正案
- 修正によって期待される効果
- 修正の優先順位

### 8.4 自動修正

レビュー結果をもとにAIが編集指示を修正し、再編集を実行する。

その後、再度レビューを行う。

ただし、無制限に修正を繰り返すことは避け、レビュー回数や処理コストに上限を設ける。

最終的にはユーザーが確認・承認できるようにする。

## 9. 新規開発の優先順位

既存機能を最大限利用することを前提に、以下の順序で開発する。

| 順序 | 開発項目 | 内容 |
|---|---|---|
| 1 | 既存機能との接続 | AIが既存の解析結果・素材情報を取得できる仕組み |
| 2 | AI面白シーン抽出 | 面白さの発見・評価・ランキング |
| 3 | AI動画構成 | 長尺・Shorts・TikTok別の企画・構成 |
| 4 | AI編集指示生成 | 共通形式による編集計画の生成 |
| 5 | 既存編集エンジンとの連携 | 編集指示を既存エンジンで実行 |
| 6 | AI品質レビュー | 動画の面白さ・構成・技術品質の評価 |
| 7 | AI自動修正 | レビュー結果に基づく編集計画の改善 |
| 8 | 投稿・分析 | プラットフォーム連携と投稿結果の分析 |

### 9.1 最初の完成目標（MVP）

最初の完成目標は、以下の一連の処理が動作する状態とする。

1. 既存Stretheus機能から解析データを取得する。
2. AIが面白いシーンを発見・評価する。
3. AIが動画の企画・構成を生成する。
4. AIが編集指示データを生成する。
5. Stretheusの既存編集エンジンで自動編集する。
6. 編集結果をユーザーが確認できる。

まずはここまでを実装し、その後にAIレビュー・自動修正・投稿・分析を追加する。

## 10. 設計上の共通原則

### 10.1 既存機能の再利用

既存機能で実現できる処理を重複して開発しない。

AI Clip Studioは既存機能を呼び出し、その結果を利用する独立した機能モジュールとして設計する。

### 10.2 AIとプログラムの責任範囲

AIに適した処理：
- 面白さの判断
- 文脈の理解
- 動画の企画
- シーンの選定
- 構成の決定
- 演出の提案
- 編集結果の評価
- 改善案の生成

プログラムに適した処理：
- ファイル操作
- 時間計算
- 素材の読み込み
- 編集指示の検証
- タイムライン操作
- レンダリング
- ジョブ管理
- エラー処理

AIの判断結果をそのまま無条件で実行するのではなく、必ずStretheus側で検証してから処理する。

### 10.3 AIプロバイダーの独立性

特定のAIプロバイダーに依存しない設計にする。

モデルの変更・追加が容易になるよう、AIへの入力・出力形式を統一する。

### 10.4 将来的な拡張性

将来的には以下の機能を追加できる構造にする。

- ユーザーごとの編集嗜好の学習
- チャンネルごとの動画スタイルの記憶
- 過去の動画の評価結果を利用した改善
- 投稿後の視聴維持率・反応を利用した分析
- ユーザーごとのAI編集プロファイル
- AIモデルの切り替え
- 複数の動画企画の自動生成

---

## 11. 最終的な目標

Stretheusを単なる動画編集ソフトウェアではなく、配信者の動画制作を包括的に支援するAI動画制作プラットフォームへと進化させる。

ユーザーが配信アーカイブを指定するだけで、AIが面白いシーンを発見し、動画の企画・構成を考え、既存の編集エンジンを利用して動画を完成させる。

最終的には、ユーザーが行う作業を最小限に抑え、確認・承認するだけでYouTube長尺動画・Shorts・TikTok向けの動画を制作できる状態を目指す。

## 12. 人間の編集ログ解析・AI編集学習機能

### 12.1 目的

本機能の最も重要な目的は、人間が行った編集作業を解析し、その編集傾向・判断基準・編集スタイルをAIに学習させることである。

AIが単に一般的な編集ノウハウに基づいて動画を編集するのではなく、実際に人間が行った編集を参考にし、その人間の編集スタイルに近い動画を制作できるようにする。

さらに、AIが編集した動画に対して人間が修正を行った場合、その修正内容とAIの編集結果との差分を解析する。

この差分を学習データとして蓄積し、次回以降のAI編集に反映する。

最終的には、ユーザーが修正する回数を継続的に減らし、人間の編集作業に近い品質・判断基準を再現できる状態を目指す。

### 12.2 基本的な学習サイクル

以下のサイクルを継続的に実施する。

1. 人間が編集したプロジェクトを取得する。
2. 編集ログ・タイムライン・素材情報を解析する。
3. 人間の編集傾向・判断基準・演出方法を抽出する。
4. 抽出した情報をユーザーごとの編集プロファイルに蓄積する。
5. AIが編集プロファイルを参考に動画を自動編集する。
6. 人間がAIの編集結果を確認・修正する。
7. AI編集前後の差分を解析する。
8. 修正理由・編集傾向を学習データとして蓄積する。
9. 次回のAI編集に反映する。

このサイクルを繰り返すことで、AIの編集品質を段階的に改善する。

### 12.3 人間の編集ログ解析

人間が作成した既存プロジェクトや編集操作の履歴を解析し、編集スタイルを抽出する。

解析対象：

| 分類 | 解析内容 |
|---|---|
| カット | カット位置・カット頻度・不要な間の削除 |
| テンポ | シーンごとの尺・会話の間・展開速度 |
| テロップ | 表示タイミング・文字数・位置・装飾 |
| テロップアニメーション | 使用するアニメーション・表示時間・頻度 |
| エフェクト | 使用する映像エフェクト・適用条件 |
| 音声 | 音量調整・効果音・BGMの使用傾向 |
| シーン構成 | シーンの順番・組み合わせ・展開方法 |
| 強調表現 | 重要な発言や面白い場面の強調方法 |
| 演出 | ズーム・画面揺れ・トランジションなど |
| 動画全体 | 導入・展開・オチ・締めの構成 |

単純に使用したエフェクトや編集操作を記録するだけではなく、どのような状況でその編集を行ったのかも解析対象とする。

例えば、以下のような判断を抽出する。

- 面白い発言の直前に不要な間を削除する。
- オチの直前に少し間を残す。
- 驚きの発言にズームと効果音を追加する。
- 重要な発言だけテロップを大きくする。
- 会話のテンポが悪い箇所を短くする。
- 初見では理解しにくい場面に補足テロップを入れる。

これらの編集パターンを、編集操作とその前後の映像・音声・会話の文脈を組み合わせて分析する。

### 12.4 AI編集と人間編集の差分解析

AIが編集したプロジェクトを人間が修正した場合、修正前後の編集データを比較する。

比較対象：

| 分類 | 差分の例 |
|---|---|
| カット | AIが残した部分を人間が削除した |
| 尺 | AIのカット範囲を短縮・延長した |
| テロップ | AIの文章を変更した |
| テロップ位置 | 表示位置やサイズを変更した |
| 演出 | エフェクトを追加・削除した |
| 音声 | 効果音やBGMを追加・変更した |
| 構成 | シーンの順番を変更した |
| 強調 | AIが強調しなかった場面を人間が強調した |
| 削除 | AIが採用したシーンを人間が不採用にした |
| 追加 | AIが採用しなかったシーンを人間が追加した |

差分解析では、単に編集操作の変更を記録するだけでなく、変更が発生した理由を推定する。

例えば、AIが10秒のシーンを採用し、人間が冒頭3秒を削除した場合、以下のように記録する。

- AIの判断：10秒間のシーンを採用
- 人間の修正：冒頭3秒を削除
- 差分：シーン開始位置を3秒後ろに変更
- 学習上の仮説：この種類のシーンでは導入部分を短くした方がよい可能性がある

ただし、編集操作だけで人間の意図を完全に判断することはできない。

必要に応じてAIが修正理由を推定し、ユーザーが確認・訂正できる仕組みを設ける。

### 12.5 編集プロファイル

解析・学習した情報は、ユーザーごとの編集プロファイルとして管理する。

編集プロファイルには以下の情報を保存する。

- 基本的な編集スタイル
- カットの傾向
- 動画のテンポ
- テロップのデザイン・表示傾向
- エフェクトの使用傾向
- 効果音・BGMの使用傾向
- シーン構成の傾向
- 好まれる演出
- 避けるべき編集
- AI編集に対する修正傾向
- 過去の編集から抽出した成功パターン

編集プロファイルは固定値ではなく、編集ログや差分データの蓄積に応じて更新する。

また、動画の種類や投稿先によって編集スタイルが異なる可能性があるため、必要に応じて複数の編集プロファイルを管理できる構造にする。

例：

- YouTube長尺動画向け
- YouTube Shorts向け
- TikTok向け
- ゲーム実況向け
- 雑談配信向け

### 12.6 学習データの管理

編集ログと差分データは、将来的なAIの改善に利用できる形式で蓄積する。

保存する情報：

- 元の素材情報
- 元の解析結果
- AIが生成した編集指示
- AI編集後のプロジェクト情報
- 人間による修正後のプロジェクト情報
- AIと人間の編集差分
- 修正が発生した時間・箇所
- 修正内容の分類
- 修正理由（取得できる場合）
- 最終的な編集結果
- ユーザーによる評価（取得できる場合）

学習データには、単なる編集操作だけでなく、編集対象となった映像・音声・会話の文脈を関連付ける。

これにより、AIが「どのような状況で、どのような編集を行うべきか」を学習できるようにする。

### 12.7 学習・改善方式

最初から独自モデルの追加学習を必須とする必要はない。

以下の段階的な方式を採用する。

#### Phase 1：編集プロファイルの生成

人間の編集ログを解析し、編集スタイルを構造化データとして保存する。

AIは編集時にこのプロファイルを参照する。

#### Phase 2：差分データの蓄積

AI編集と人間による修正の差分を自動的に記録する。

修正傾向を分類し、AI編集プロファイルを改善する。

#### Phase 3：編集判断の最適化

過去の編集ログや差分データを参照し、似た状況における編集判断を改善する。

必要に応じて、編集パターンの検索・類似事例の参照・プロンプトの改善などを行う。

#### Phase 4：独自モデルの学習

十分な学習データが蓄積された段階で、編集判断やシーン評価に特化したモデルの追加学習を検討する。

追加学習の対象は、データ量・品質・効果を検証したうえで決定する。

### 12.8 学習に関する重要事項

- ユーザーごとの編集データを適切に分離する。
- 別ユーザーの編集ログを無断で学習に利用しない。
- 編集ログから抽出した情報と、実際の編集データを区別して管理する。
- AIの推定した編集意図を確定した事実として扱わない。
- 一時的な修正と、継続的な編集スタイルの違いを区別する。
- 学習結果をいつでも確認・調整できる構造にする。
- 編集プロファイルの更新履歴を管理する。
- 学習データの品質を評価し、不適切な修正を無条件に学習しない。

### 12.9 最終目標

AIが人間の編集を模倣するだけでなく、人間がどのような判断で編集を行っているのかを理解し、その判断基準を再現できるようにする。

AIが編集し、人間が修正し、その差分をAIが学習する。

このサイクルを継続することで、ユーザーがStretheusを使用するほど、そのユーザーの編集スタイルに近づいていくAI編集環境を実現する。
